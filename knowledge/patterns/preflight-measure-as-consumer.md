# 문제
"도구가 설치돼 있는가"를 대화 셸에서 `X --version`으로 확인하고 있다고 판정하면 **거짓 양성**이 난다. 에이전트 실행 환경의 셸에는 도구가 함수·별칭·래퍼로 주입돼 있을 수 있고, 스크립트 컨텍스트와 대화 컨텍스트의 구현이 다를 수 있다.

실제 사고 두 건:
- 리더가 프리플라이트로 "ripgrep 14.1.1 있음"을 기록했으나, 그것은 에이전트 하네스가 대화 셸에 주입한 함수였고 **실제 바이너리는 머신에 없었다**. 코드가 `spawn('rg')`를 호출하는 순간 ENOENT로 실패했고, 구현 도중에야 발각돼 의존성을 번들 바이너리로 갈아엎어야 했다.
- 게이트 스크립트가 쓰는 `grep`은 BSD grep인데, 대화 셸에는 ugrep이 주입돼 있었다. 대화에서 검증한 정규식이 스크립트에서는 다르게 동작했다.

# 해법
**검증 방식을 소비 주체에 맞춘다.**

| 누가 쓸 것인가 | 어떻게 확인할 것인가 |
|---|---|
| 애플리케이션 코드(`child_process.spawn`) | `node -e "console.log(require('child_process').spawnSync('rg',['--version']).status)"` |
| 셸 스크립트(gate.sh 등) | 그 스크립트를 실제로 실행해 확인 |
| 컨테이너 안 프로세스 | 컨테이너 안에서 실행 |

그리고 **프리플라이트 결과에 측정 방식을 함께 기록**한다("rg 14.1.1 — 대화 셸 `--version` 기준"과 "rg 부재 — Node spawn ENOENT 확인"은 완전히 다른 정보다).

# 더 나은 회피
시스템 도구에 의존해야 한다면 **번들 바이너리 패키지**(예: `@vscode/ripgrep`의 `rgPath`)를 우선 검토한다. 설치 환경 편차가 사라지고 프리플라이트 자체가 불필요해진다 — 의존성을 없애는 것이 확인하는 것보다 낫다.

# 일반화
"있다고 들었다"와 "내가 쓸 방식으로 써봤다"는 다르다. 이는 방어선 실측(일부러 깨뜨려 확인)과 같은 원리다 — **관측 방식이 실사용과 다르면 관측은 증거가 아니다.**
