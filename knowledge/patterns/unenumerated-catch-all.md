# 문제

`else` · `default:` · `return 기본값` 처럼 **"나머지 전부"를 받는 분기**는 코드에서 가장 조용한 자리다. 명시된 분기는 이름이 있어 리뷰에서 읽히지만, catch-all 은 **무엇이 거기로 오는지 아무도 세지 않은 채** "그 외에는 이렇게" 한 줄로 통과한다.

실제 사고: 한 프로젝트의 키 라우팅 함수에서 **결함이 세 번** 났고, 셋 다 같은 한 줄로 떨어졌다.

```swift
return .interpretForComposition        // "나머지 전부"
```

| 증상 | 실제 원인 |
|---|---|
| 비라틴 자판에서 탈출 키가 엉뚱한 표기로 나감 | 그 분기 |
| 편집기 화음 키가 전부 사라짐 | 그 분기 |
| **방향키·delete·Enter 가 아무 일도 안 함** | 그 분기 |

세 번째는 **사용자가 직접 눌러 보고 신고**했다. 그 시점에 관련 테스트는 전부 초록이었다 — 테스트가 검사하는 항목이 그 분기의 *일부*였기 때문이다.

**세 개의 개별 실수가 아니라, 한 번도 열거되지 않은 기본 분기 하나다.**

# 해법

**catch-all 을 만들 때 최소 한 번은 그 안의 목록을 만든다.**

```
1. 이 분기로 오는 입력의 집합을 실제로 열거한다 (타입의 전 case, 플랫폼이 정의한 전 키, 스펙의 전 상태)
2. 각 항목에 대해 "이 처리가 맞는가"를 한 줄씩 답한다
3. 틀린 항목이 하나라도 나오면 그것을 명시 분기로 승격한다
4. 그 목록을 테스트로 고정한다 — 라우팅 표 단언 (아래)
```

목록을 코드 옆에 두지 말고 **테스트로 고정**한다. 그래야 항목이 늘어날 때 갱신이 강제된다.

```swift
// 이 표에 없는 키가 추가되면 실패한다 — "나머지"가 조용히 자라는 것을 막는다
#expect(Set(NamedKey.allCases) == expectedRoutingTable.keys)
```

# 왜 테스트가 못 잡나

catch-all 결함은 **"통과하는 테스트가 존재하는 상태"** 로 산다. 테스트는 열거된 것만 검사하고, 문제는 열거되지 **않은** 것에 있기 때문이다. 그래서 커버리지 숫자도 올라간다 — 그 줄은 실행되니까.

> **분기가 옳은지는 그 분기에 무엇이 오는지 알 때만 판정할 수 있다.**

# 이웃 함정: 넓이가 다른 축을 대신하지 못한다

같은 프로젝트에서 개발자가 화음 결함을 고치며 **26칸을 전수 확인**했다. 그런데 26칸이 **전부 같은 축**(자모 한 벌)이었다. 촘촘히 채운 것이지 넓힌 것이 아니었고, **방향키라는 다른 축은 0칸**이었다 — 그게 다음 결함이 됐다.

전수 확인을 주장하기 전에 묻는다: **내가 채운 것이 축 하나인가, 공간인가.**

# 적용 대상

키/이벤트 라우팅 · 메시지 타입 디스패치 · 상태 기계의 전이 default · HTTP 상태 매핑 · 파일 확장자 핸들러 · 에러 → 사용자 문구 매핑 · 권한 판정의 "그 외에는 거부/허용" — **집합을 나누는 모든 자리**.

# 일반화

Swift `switch` 의 전수성 검사, Rust `match` 의 exhaustiveness 처럼 **컴파일러가 열거를 강제하는 언어 기능이 있으면 그것을 쓴다.** `default:` 를 적는 순간 그 강제를 스스로 끈 것이다. 언어가 강제하지 못하는 자리(문자열 키, 외부 입력, 플랫폼 상수)에서는 위의 라우팅 표 테스트가 그 역할을 대신한다.
