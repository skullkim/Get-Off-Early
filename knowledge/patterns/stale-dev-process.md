# 문제
라이브 실측(실서버에 요청을 쏴서 확인)은 목·단위 테스트가 못 잡는 층을 잡아주지만, **떠 있는 서버가 지금 코드라는 보장이 없다**. `tsx`·`node`로 직접 띄운 프로세스는 watch가 아니므로, 몇 시간 전에 기동했다면 그 시점의 코드를 계속 서빙한다.

실제 사고: 이미 구현·머지된 엔드포인트에 404가 나왔다. QA는 "미구현"으로 리포트했고, 프론트 시니어는 그 통지를 받아 이미 보낸 "작업 가능" 안내를 취소했으며, 팀 하나가 잘못 차단됐다. 진범은 몇 시간 전에 띄운 구버전 dev 서버가 포트를 점유하고 있었던 것이다 — **세 사람이 모두 낡은 프로세스를 실측**했다.

# 해법
**라이브 실측 전에 프로세스 신선도를 배제한다.**

```
1. 기동 시각 확인: ps -o pid,lstart -p $(lsof -ti tcp:<PORT>)
   — 마지막 코드 변경보다 오래됐으면 신뢰하지 않는다
2. 또는 그냥 재기동하고 실측한다 (가장 확실·저렴)
3. watch 모드로 띄웠는지 확인 (tsx watch / nodemon / vite dev는 자동 갱신)
```

**404·미구현·회귀로 판정하기 전에 이것부터 배제한다.** 판정 비용보다 재기동 비용이 훨씬 싸다.

# 통지 규율 (2차 피해 차단)
낡은 실측이 만든 오판은 전파되면서 증폭된다. 그래서:
- **통지에 검증 시각을 병기**한다("20:22 실측 기준").
- **타 영역의 '가동/미구현' 주장은 중계 전 1회 실측**하거나, 못 하면 "○○ 통지 기준"임을 명시한다.
- 수신자는 "가장 최근에 받은 메시지"가 아니라 **"가장 최근에 실측된 사실"**을 따른다. 상충하면 직접 실행해 확인한다.

# 일반화
증거의 유효기간을 인식하는 문제다. 관측은 관측 시점의 상태이지 현재 상태가 아니며, 이 간극은 다인 병렬 작업에서 통지 지연과 겹쳐 커진다. 관련: [[real-browser-e2e]] · [[preflight-measure-as-consumer]]
