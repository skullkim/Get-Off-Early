# Product Design — 요구사항을 화면 설계로

확정된 요구사항을 개발자가 모호함 없이 구현할 수 있는 디자인 명세로 변환하는 절차. PD가 사용한다.

## 왜 이렇게 하는가
디자인이 "행복 경로 화면"만 정의하면, 개발자가 빈 상태·에러 상태·로딩을 임의로 만들고 그것이 QA 버그가 된다. 또 디자인 요소가 요구사항에 근거하지 않으면 스코프 크리프가 발생한다. 그래서 **모든 화면의 모든 상태를 정의**하고 **모든 디자인 요소를 REQ-ID에 매핑**한다.

## 절차

### 1. 요구사항 흡수
`_workspace/01_requirements.md`를 읽고, 화면/상호작용이 필요한 REQ를 추린다. 각 REQ가 어떤 화면·플로우로 충족되는지 머릿속에 매핑한다.

### 1.5 도메인 디자인 레퍼런스 참고 (권장)
프로젝트 도메인의 검증된 UI 패턴/플로우/컴포넌트를 레퍼런스에서 확인해, IA·플로우·컴포넌트·상태 선택을 *모델 추측이 아니라 실제 관례*에 근거시킨다.
- **참고처: wwit.design (What Was IT)** — 모바일 UI 패턴·플로우(로그인/온보딩/검색/결제/설정 등)·컴포넌트(인풋/탭/바텀시트/팝업/차트)·국내 앱 케이스를 산업/패턴/컴포넌트로 분류. `WebFetch`로 접근(예: `https://wwit.design/`).
- **텍스트 vs 시각 두 경로**:
  - *분류·체크리스트*는 `WebFetch`로(도메인이 보통 쓰는 화면·플로우·컴포넌트를 빠뜨리지 않게). WebFetch는 텍스트만 본다.
  - *실제 디자인을 눈으로 보려면* WebFetch 대신 **§8의 헤드리스 Chrome `--screenshot`으로 레퍼런스 페이지를 캡처해 Read**한다 — 그러면 갤러리 화면/패턴을 이미지로 직접 볼 수 있다(텍스트 한계 우회). 관심 카테고리/케이스 URL로 이동해 캡처.
  - 시각 디테일·토큰은 결국 §5 토큰·§8 프로토타입으로 본 프로젝트에 맞게 확정한다(레퍼런스 복붙 아님).
- 레퍼런스에서 가져온 패턴도 **반드시 REQ-ID에 매핑**한다 — 요구에 없는 패턴을 레퍼런스 봤다고 끌어오면 스코프 크리프다.

### 2. 정보구조(IA)와 화면 목록
- 필요한 화면을 나열하고 계층/네비게이션을 정의한다
- 각 화면이 어떤 REQ를 충족하는지 표시한다

### 3. 사용자 플로우
핵심 유스케이스별로 화면 간 이동을 단계로 그린다 (진입 → 행동 → 결과 → 다음). 분기(성공/실패)를 포함한다.

### 4. 화면별 컴포넌트 + 모든 상태
각 화면에 대해:
- 구성 컴포넌트 인벤토리
- **모든 상태**를 명시: 빈 상태(데이터 없음), 로딩, 에러/실패, 성공/정상, 권한 없음, 부분 로딩
- 각 상태에서 사용자가 보는 것과 할 수 있는 행동

### 5. 디자인 토큰
구체적 값으로 정의 ("예쁘게"가 아니라 구현 가능하게):
- 색상(역할별: primary/danger/surface/text, hex 값)
- 타이포그래피(크기/행간/굵기)
- 간격 스케일, 라운딩, 그림자
- 반응형 브레이크포인트와 각 구간의 레이아웃 변화
- 접근성: 대비비, 포커스 표시, 키보드 탐색, 대체 텍스트 규칙

### 6. 데이터 요구를 백엔드에 전달
각 화면이 필요로 하는 데이터(필드, 목록 페이지네이션/정렬/필터)를 정리해, 백엔드 API 설계에 반영되도록 한다.

### 7. 와이어프레임 (필수)
각 핵심 화면을 ASCII/박스 다이어그램 와이어프레임으로 그린다 — 영역 배치(헤더/컨트롤/콘텐츠/사이드/푸터)와 컴포넌트 위치·계층을 한눈에 보이게. 02 문서에 화면별로 포함한다(가끔이 아니라 항상).

### 8. HTML/CSS 프로토타입 + 자가 검증 (필수 — 디자인을 눈으로 확정)
텍스트 명세만으로는 "디자인대로 나왔는지" 아무도 못 본다. 그래서 PD가 **정적 HTML/CSS 프로토타입을 직접 만들어 렌더·검증**하고, 그 스크린샷을 **시각 기준물(visual source of truth)** 로 남긴다 — 프론트는 이걸 보고 구현하고, QA·리더는 실제 앱을 이 스크린샷과 대조한다.

1. **프로토타입 작성**: `_workspace/prototype/`에 정적 HTML/CSS. §5 디자인 토큰을 CSS 변수로 정의하고, 핵심 화면 + **주요 상태(빈/로딩/에러/성공, 게임류면 진행/승/패 등)** 를 더미 데이터로 표현. 빌드/JS 불필요(순수 HTML/CSS).
2. **헤드리스 렌더 + 스크린샷(모바일+데스크톱)** — Chrome 내장 `--screenshot` 사용:
   ```bash
   CHROME="/Applications/Google Chrome.app/Contents/MacOS/Google Chrome"
   "$CHROME" --headless=new --disable-gpu --hide-scrollbars --force-device-scale-factor=2 \
     --window-size=390,844 --screenshot=_workspace/prototype/shots/<화면>-mobile.png \
     "file://$PWD/_workspace/prototype/<화면>.html"
   # 데스크톱: --window-size=1280,800
   ```
3. **스크린샷을 Read로 직접 보고** 명세·토큰(색/간격/타이포)·레이아웃·반응형·모든 상태가 맞는지 **자가 검증**. 어긋나면 프로토타입(또는 명세)을 고치고 다시 렌더 — 보기 좋을 때까지 반복.
4. 산출물: `_workspace/prototype/`(HTML/CSS) + `prototype/shots/`(검증 스크린샷) + 02 문서에 경로·스크린샷 참조. **이 스크린샷이 디자인 충실도 검증의 시각 기준이 된다.**

## 출력 형식

`_workspace/02_design.md`:

```markdown
# 디자인 명세: {프로젝트명}

## 1. 정보구조 / 화면 목록
| 화면 | 경로(예상) | 충족 REQ | 설명 |
|------|-----------|---------|------|
| 대시보드 | / | REQ-001, REQ-004 | ... |

## 2. 사용자 플로우
### 플로우: {유스케이스명} (REQ-00X)
1. {진입} → 2. {행동} → 3. {결과}
   - 분기(실패): ...

## 3. 화면 상세
### 화면: {이름} (REQ-00X)
- 컴포넌트: {목록}
- 상태:
  - 빈 상태: {표시 내용}
  - 로딩: {표시}
  - 에러: {표시 + 복구 행동}
  - 성공/정상: {표시}
  - 권한 없음: {표시}
- 데이터 요구: {필요 필드/목록 특성}

## 4. 디자인 토큰
- 색상: primary #..., danger #..., surface #..., text #...
- 타이포: 본문 16px/1.5, 제목 ...
- 간격: 4/8/12/16/24/32
- 브레이크포인트: mobile <768, tablet 768~1024, desktop >1024
- 접근성: 대비 4.5:1 이상, 포커스 링 명시, 모든 입력에 라벨

## 5. REQ 커버리지 체크
| REQ-ID | 디자인 반영 위치 |
|--------|----------------|
| REQ-001 | 대시보드 화면, ... |
(화면 관련 모든 REQ가 한 곳 이상에 매핑되어야 함)

## 6. 와이어프레임 (화면별)
### {화면명}
{ASCII 박스 다이어그램 — 영역/컴포넌트 배치}

## 7. 프로토타입 (시각 기준)
- 위치: `_workspace/prototype/` (정적 HTML/CSS, 토큰=CSS 변수)
- 검증 스크린샷: `_workspace/prototype/shots/*.png` (화면×{모바일,데스크톱}, PD 자가 검증 완료)
- 프론트는 이 스크린샷을 시각 타깃으로 구현, QA·리더는 실제 앱을 이것과 대조
```

## 품질 게이트
- 모든 화면 관련 REQ가 디자인에 반영되었는가? (역방향 확인)
- 각 화면의 빈/로딩/에러 상태가 정의되었는가?
- 토큰이 구현 가능한 구체값인가?
- **각 핵심 화면에 와이어프레임이 있는가?**
- **HTML/CSS 프로토타입을 렌더·스크린샷으로 자가 검증했고(모바일+데스크톱), 명세·토큰과 일치하는가?** (시각 기준물 `prototype/shots/` 존재)

## 재실행 시
기존 `02_design.md`가 있으면 읽고, 변경된 요구사항이나 프론트엔드/QA 피드백에 해당하는 부분만 갱신한다.
