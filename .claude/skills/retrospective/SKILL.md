# Retrospective — 하네스 자가 발전 회고

매 프로젝트마다 대화와 산출물에서 배운 것을 하네스(에이전트·스킬·오케스트레이터)와 메모리에 반영해, 다음 빌드가 더 나아지게 하는 절차. `build-project`의 마지막 필수 단계이자, 언제든 수동 호출 가능하다.

## 절대 원칙: 회고는 리더(메인 세션)가 수행한다
회고의 가장 큰 정보원은 **이번 대화 자체**다. 대화 맥락을 가진 건 메인 세션뿐이고, 새로 스폰한 서브에이전트는 차갑게 시작해 대화를 모른다. 따라서 **회고를 위해 서브에이전트를 스폰하지 않는다.** 리더가 직접 이 절차를 따른다. (기계적 편집을 서브에이전트에 맡기더라도, 신호 분석과 판단은 리더가 한다.)

## 왜 이렇게 하는가
하네스는 고정물이 아니라 진화하는 시스템이다. 한 번 잘 만들었다고 끝이 아니라, 실제로 돌려보면 빈틈이 드러난다 — 같은 버그가 반복되거나, 사용자가 같은 정정을 되풀이하거나, QA 라운드가 길어진다. 이 신호를 그때그때 하네스에 반영하지 않으면 같은 실수가 매 프로젝트 재발한다. 회고는 그 피드백 루프를 **자동·구조화**한다.

## 입력: 어디서 신호를 캐는가

### 1. 이번 대화 (가장 중요)
다음을 훑는다:
- 사용자가 **정정**한 것 ("그게 아니라…", "다시 해줘", "왜 X를 안 했어?")
- 사용자가 **반복 요청**한 것 (한 번에 안 돼서 두 번 이상 말한 것)
- 사용자가 **추가 설명**해야 했던 것 (에이전트/스킬이 당연히 알았어야 할 맥락)
- 사용자가 **답답해하거나 수동으로 우회**한 지점 (하네스를 안 쓰고 직접 한 것)
- 사용자가 명시적으로 칭찬/확인한 접근 (확정된 좋은 패턴 — 보존 대상)

### 2. `_workspace/` 산출물
- `05_qa_report_round{N}.md`: **같은/유사 버그가 라운드마다 반복** → 해당 영역 스킬의 빈틈 (예: 경계면 버그 반복 → qa-verification 또는 architecture 스킬 보강)
- `04_coverage_matrix.md`: **놓친 REQ가 뒤늦게 발견** → define-requirements 또는 tdd-implementation 빈틈
- **QA 라운드 수**: 비정상적으로 많으면 → 프로세스/게이트/위임 빈틈
- 아키텍처/디자인 문서: 반복적으로 빠지는 항목 (예: 매번 에러 상태 누락) → 해당 스킬에 체크 항목 추가

### 3. git diff (저장소인 경우)
실제로 무엇이 만들어졌는지, 테스트가 실제로 도는지 등 산출물의 실재를 확인한다.

## 신호 → 타겟 매핑

각 신호를 일반화한 뒤 적절한 타겟에 연결한다:

| 신호 유형 | 수정 타겟 | 예시 |
|----------|----------|------|
| 결과물 품질 부족 | 해당 에이전트의 **스킬** | "분석이 피상적" → 스킬에 깊이 기준 추가 |
| 역할 공백/과부하 | **에이전트 정의** (.md) | "보안 검토 필요" → 에이전트 추가 / 역할 보강 |
| 단계 순서 문제 | **오케스트레이터** | "검증을 먼저" → Phase 순서 변경 |
| 팀 구성 부적합 | 오케스트레이터 + 에이전트 | "이 둘 합쳐도 됨" / "한 명 더 필요" |
| 트리거 누락/오발동 | **스킬 description** | "이 표현으로 안 됨" → description 확장 |
| 사용자 취향·반복 피드백 (프로젝트 무관) | **글로벌 메모리** | "항상 X 스택 선호", "에러 처리 꼼꼼히" |

## 일반화 원칙 (오버피팅 금지)
이번 프로젝트 한 건에만 맞는 좁은 규칙이 아니라 **원리 수준**으로 반영한다.
- 나쁨: "할 일 앱에서는 마감일 필드를 꼭 넣어라"
- 좋음: "요구사항에 날짜/기한 개념이 있으면 시간대·경계값(자정, 과거 날짜) 엣지 케이스를 수용 기준에 포함하라"

## 절차

1. **수집** — 위 3개 입력에서 신호를 모은다. 각 신호를 한 줄로 적고 근거(대화 인용/파일:라인)를 붙인다
2. **퇴행 점검** — `.claude/retro/log.md`를 읽어, 과거에 내린 결정을 되돌리려는 건 아닌지 확인한다 (있으면 이유를 명시)
3. **일반화 + 매핑** — 각 신호를 일반화하고 타겟(스킬/에이전트/오케스트레이터/description/메모리)에 연결한다
4. **회고 리포트 작성** — 아래 형식으로 제안할 변경을 구체적 편집안(파일 + 무엇을 어떻게 + 근거)으로 정리한다
5. **사용자 승인** — 리포트를 보여주고 승인받는다. 변경은 조용히 적용하지 않는다 (의도치 않은 드리프트 방지)
6. **적용** — 승인된 변경을 정밀 편집(Edit)으로 반영한다. 대규모 구조 변경(에이전트 추가/삭제, 아키텍처 변경)은 `harness` 스킬의 운영/유지보수 워크플로우를 따른다
7. **기록** — CLAUDE.md 변경 이력 테이블에 한 줄 추가 + `.claude/retro/log.md`에 회고 항목 append
8. **메모리 저장** — 프로젝트 무관 사용자 학습은 글로벌 메모리에 저장 (아래)

## 회고 리포트 형식

```markdown
# 회고 — {프로젝트명} ({날짜})

## 잘된 점 (보존)
- {확정된 좋은 패턴 — 건드리지 말 것}

## 발견된 신호
| # | 신호 | 근거 | 일반화 | 타겟 |
|---|------|------|--------|------|
| 1 | QA가 camelCase/snake_case 불일치를 2라운드 반복 발견 | round1,2 리포트 | "계약에 필드명 규칙 명시 강제" | architecture-and-delegation 스킬 |
| 2 | 사용자가 "에러 상태 빠졌다" 2회 정정 | 대화 | "모든 화면 상태 정의 게이트 강화" | product-design 스킬 |

## 제안 변경 (승인 필요)
### 변경 1 — {파일}
- 무엇: {추가/수정할 내용}
- 근거: 신호 #1
- 일반화 확인: {이번 건에만 맞지 않는지}

## 메모리 저장 제안
- {user/feedback 메모리로 저장할 항목}
```

## 글로벌 메모리 저장 규칙
프로젝트 파일이 아니라 **사용자/작업 방식**에 관한 학습만 저장한다:
- `feedback` 타입: 내가 일하는 방식에 대한 반복 지침 (정정·확정된 접근). 본문에 **왜** + **적용 방법** 포함
- `user` 타입: 사용자의 역할·전문성·선호 (예: 선호 스택, 꼼꼼함의 기준)
- 저장 후 `MEMORY.md` 인덱스에 한 줄 포인터 추가
- 이미 있는 메모리면 새로 만들지 말고 갱신한다
- 하네스 파일/스킬에 이미 반영한 절차적 개선은 메모리에 중복 저장하지 않는다

## 무엇을 회고하지 않는가
- 일회성·이 대화에서만 의미 있는 잡음 (다음 프로젝트에 도움 안 되면 버린다)
- 이미 하네스/메모리가 담고 있는 것 (중복)
- 코드베이스가 기록하는 것 (구현 세부)

## 재실행 시
회고는 매번 누적된다. 이전 `.claude/retro/log.md`를 먼저 읽어, 같은 신호가 반복되는지(이미 반영했는데 또 나오면 반영이 부족했다는 뜻) 본다.
