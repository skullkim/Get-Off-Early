# QA Verification — 요구사항 충족 + 통합 정합성 검증

QA가 구현을 검증하는 절차. 핵심은 "존재 확인"이 아니라 **"연결 확인(교차 비교)"**이다. 컴포넌트가 각각 올바르게 동작해도 연결 지점에서 계약이 어긋나면 런타임에 깨진다 — 이것이 가장 흔한 버그다.

또한 **목(MSW)·컨트롤러 슬라이스(MockMvc)·계약 읽기·curl이 전부 그린이어도 실제 통합은 깨질 수 있다.** 이들은 브라우저의 실제 HTTP 의미(CORS·프리플라이트·헤더/쿠키 전파·리다이렉트·mixed content)를 우회한다. 그래서 검증을 코드 대조에서 끝내지 않고 **실제 브라우저↔실제 백엔드 라이브 E2E 스모크**로 닫는다(아래 전용 섹션).

## 검증 우선순위
1. **통합 정합성** (가장 높음) — 경계면 불일치
2. **기능 스펙 준수** — 각 REQ의 수용 기준
3. **상태/엣지 케이스** — 빈/로딩/에러/권한없음
4. **코드 품질** — 미사용 코드, 명명

## 0단계: 계약 표면 전수 대조 + TDD 게이트 확인 (먼저)
**"전체 그린"은 존재하는 테스트의 그린일 뿐 계약 표면 전체를 증명하지 않는다.** 매 라운드 시작 시 **계약 문서의 엔드포인트/기능 목록 ↔ 실제 라우트 등록·구현을 전수 대조**한다(실제: 라우트 파일·등록·전체 그린이 다 있는데 엔드포인트 하나가 TODO 주석뿐이었고 테스트가 0건이라 아무도 실패하지 않았다 — inject 실측으로 404를 확인해 잡았다). 누락이 보이면 그 자리에서 실측(요청을 실제로 쏴서 응답 확인)하고 개발로 반려한다.


QA로 넘어온 작업이 게이트를 실제로 통과했는지 확인한다 (개발자 주장만 믿지 않는다):
- `_workspace/04_coverage_matrix.md`의 REQ 목록과 `01_requirements.md`의 REQ 목록을 대조 → **미커버 REQ가 있으면 개발로 반려**
- 테스트 실행 명령을 **직접 실행**해 전체 통과를 확인 → **실패가 있으면 개발로 반려**

게이트 미충족이면 기능 검증으로 넘어가지 않는다.

## 핵심 방법: "양쪽 동시 읽기"
경계면 버그는 한쪽만 봐선 못 잡는다. 반드시 생산자와 소비자를 **같이 열어** 비교한다.

### 1. API 응답 ↔ 프론트 데이터 계층 교차 검증
1. 백엔드 각 엔드포인트의 **실제 응답 직렬화부**에서 응답 shape을 추출
2. 프론트의 대응 데이터 훅/서비스가 기대하는 타입을 추출
3. shape과 타입이 일치하는지 비교 — 특히:
   - 래핑 여부: API가 `{ items: [...] }` 반환인데 프론트가 배열 기대?
   - 필드명: API `thumbnailUrl`(camel) vs 프론트 `thumbnail_url`(snake)?
   - 즉시 응답(202) vs 최종 결과: 프론트가 즉시 응답에서 비동기 결과 필드를 접근하지 않는가?
4. 모든 API 엔드포인트에 대응하는 프론트 호출이 있는가? (있는데 안 불리는 엔드포인트 = 호출 누락 의심)

### 2. 파일/라우트 경로 ↔ 링크 교차 검증
1. 실제 페이지/라우트 경로를 추출 (그룹 경로·동적 세그먼트 주의)
2. 코드 내 모든 링크/네비게이션 값을 수집
3. 각 링크가 실제 존재하는 경로를 가리키는지 확인 (경로 접두사 누락이 흔함)

### 3. 상태 전이 완전성
1. 정의된 상태/전이 맵을 추출
2. 코드의 모든 상태 업데이트를 검색
3. 맵에 없는 전이(무단 전이)와, 맵에 있지만 코드에 없는 전이(죽은 전이 — 중간 상태에서 못 빠져나옴)를 찾는다

## 기능 스펙 검증 (REQ별)
각 in-scope REQ에 대해:
1. 수용 기준(Given-When-Then)을 하나씩 확인 — 대응 테스트가 그 기준을 실제로 검증하는지, 그리고 동작이 기준과 일치하는지
2. 빌드/타입 통과 ≠ 정상 동작임을 기억한다. 제네릭 캐스팅·any로 우회된 타입 안전성을 의심하고 실제 응답/동작을 확인한다
3. 엣지/에러 케이스 AC가 실제로 처리되는지 확인 (행복 경로만 보지 않는다)
4. **통과용 테스트 판별**: 대응 테스트가 실제로 그 AC를 검증하는지 본다 — 단언(assert)이 없거나, 구현을 그대로 미러링하거나, 하드코딩 기대값으로 형식만 갖춘 테스트는 "커버"로 인정하지 않고 반려한다
5. **스펙 초과(커버리지의 역방향)**: 구현된 주요 기능·엔드포인트·화면 중 어느 REQ에도 속하지 않는 것을 나열한다 — 버그는 아니지만 범위 크리프·유지보수 부채 신호이므로 리더 보고 대상

## 라이브 E2E 스모크 (필수 — 목 그린 ≠ 실제 통합)
경계면 코드 대조("양쪽 동시 읽기")는 JSON 계약 불일치는 잡지만 **HTTP/인프라 레이어 버그는 못 잡는다**(CORS/Origin/프리플라이트, 인증 헤더·쿠키 전파, 리다이렉트, 상태코드, mixed content). 이 층은 **실제 서버를 실제 브라우저로** 한 번은 쳐야 드러난다.
- **완료 선언(또는 최종 라운드 PASS) 전, 핵심 플로우를 실제 환경에서 1회 E2E 스모크**한다: 실제 백엔드 기동 + 실제 프론트(또는 프리뷰/터널) + 실제 브라우저로 핵심 경로(예: 가입→로그인→핵심 CRUD)를 끝까지 수행한다.
- 헤드리스 브라우저(CDP/Playwright 등)로 자동화하거나 최소 실제 브라우저 수동 1회. **curl은 브라우저가 아니다** — Origin/프리플라이트/쿠키를 브라우저처럼 보내지 않아 CORS 같은 버그를 통과시킨다(실제 사례: curl 201인데 브라우저 403).
- 점검 항목: CORS(Origin 허용·OPTIONS 프리플라이트), 인증 토큰/쿠키 전파, 401 인터셉터·리다이렉트, 응답 상태코드(2xx/4xx) 실제 처리, 콘솔/네트워크 에러 0.
- dev 경로(프록시/터널)가 운영과 다르면 그 경로 자체의 변형(프록시가 Origin/Host를 어떻게 바꾸나)도 함께 본다.
- **실측 전에 서버 프로세스가 최신 코드인지 확인한다** — 장수 dev 프로세스는 "지금 코드"가 아니다(실제: watch 없이 몇 시간 떠 있던 서버가 구버전을 서빙해, 이미 구현된 엔드포인트에 404가 나왔고 QA·시니어가 모두 그 낡은 프로세스를 실측했다). 기동 시각을 확인하거나(`ps -o lstart`) 재기동 후 실측하라. 404·미구현 판정 전에 이것부터 배제한다.

### 기본 조작 상시 목록 (결함 목록과 무관하게 매 라운드)
라이브 라운드는 **"이번에 고친 것"을 밟는 쪽으로 굽는다.** 그래서 아무도 안 고친 기본 기능은 한 번도 안 눌린다.

**매 라이브 라운드에 결함 목록과 무관하게 다음을 넣는다** (앱 종류에 맞게 조정):
```
방향키 4방향 · Enter · Tab · Backspace/Delete · Home/End/PageUp/PageDown
스크롤 · 클릭 · 복사/붙여넣기 · 창 크기 변경
```
**근거(code-navigator-mac)**: 라이브 검증 6회·게이트 31종·테스트 1,407건이 도는 동안 **방향키와 Enter가 죽어 있었고, 둘 다 사용자가 찾았다.** 우리가 잰 것은 그날 고친 화음 26칸이었고, 그것은 전부 같은 축이었다.

> **고친 것만 재면 고친 자리만 보인다.**

**⚠ 그리고 결함을 고친 뒤에는 "그 수정이 만들 수 있는 반대 방향"을 같은 라운드에 잰다** — 중복 입력, 안 지워짐, 과다 차단. 고친 방향만 재면 고치면서 만든 결함을 놓친다.

### 시각/디자인 충실도 점검 (기능 그린 ≠ 디자인대로 나옴)
자동 테스트(마크업/aria/동작)와 위 E2E(네트워크/상태)는 **"디자인대로 보이는지"를 검증하지 않는다.** 기능 AC·상태 존재만 보고 시각 렌더는 아무도 안 보면, 컴포넌트 CSS가 통째로 없어도(=미스타일 UI) 모든 게이트를 통과해 사용자에게 나간다(실제 발생: 지뢰찾기, 토큰만 정의하고 컴포넌트 스타일 미작성). **완료 전, `02_design.md` + PD 프로토타입 스크린샷(`_workspace/prototype/shots/`, 있으면 1차 시각 기준)을 펴놓고 실제 앱 렌더를 화면별로 대조한다(디자인 충실도):**
- **스크린샷을 찍어 눈으로 02와 대조** — 핵심 화면 각각을 **모바일 + 데스크톱 뷰포트**로(헤드리스 CDP `Page.captureScreenshot` + `Emulation.setDeviceMetricsOverride`). 화면별로 02가 정의한 **레이아웃·컴포넌트 구성·디자인 토큰(색/간격/타이포)·모든 상태·시각 규칙**(예: 완료 취소선, 마감초과 강조, 배지 색)이 실제로 그대로 렌더됐는지 확인.
- **사용된 className이 전부 대응 CSS 규칙을 갖는지**(미정의 클래스 = 미스타일 신호). 미스타일/빈 화면/깨진·잘린 레이아웃·기본 브라우저 폼이면 디자인 미충실로 반려.
- **반응형**: 02의 브레이크포인트·모바일 규칙(잘림/오버플로우/스크롤·터치 타깃 크기)이 실제 동작하는지.
- (고충실도가 필요하면 product-designer를 재호출해 02 대비 구현 렌더를 리뷰시킬 수 있다 — 디자인 의도는 PD가 가장 잘 안다.)

## 방어선 실측 (최종 라운드 PASS 전 필수 — 그린 스위트 ≠ 방어선)
테스트가 전부 그린이어도 그 테스트들이 실제로 계약·불변식을 지키는지는 별개다 — **방어선이 있다고 믿는 것과 있는 것은 다르다.** 최종 PASS 선언 전, 핵심 지점 1~2곳을 일부러 깨뜨려 방어선이 실재하는지 실측한다:
- 대상: 가장 위험한 경계면(API 응답 shape 1곳)과 핵심 불변식(INV 1곳) 우선
- 방법: 일시적으로 깨뜨린다(예: 응답 필드명 변경, 불변식 검사 제거) → 대응 테스트가 **실제로 실패(빨간불)하는지** 확인 → 즉시 원복 + 원복 후 그린 재확인
- 판정: 깨뜨렸는데 아무 테스트도 실패하지 않으면 그 지점은 **무방비**다 — "커버됨"이 거짓이므로 해당 REQ를 개발로 반려한다(테스트 보강 요구)
- 원복 후 그린 재확인까지가 실측이다 — 깨뜨린 채 두면 실측이 오염이 된다
### 판정 명령은 도구로 승격한다 (즉석 명령은 근거가 아니다)
**같은 확인을 세 번 하면 스크립트로 만들고 자기 검사를 붙인다.** 그 전까지는 판정 근거로 쓰지 않는다.

**근거(code-navigator-mac)**: 검사가 눈먼 것이 **아홉 번**. 그런데 분포가 갈렸다:
```
자기 검사(--self-test)를 붙인 검사기      0회
대화 셸에서 즉석으로 친 grep/pgrep/find    9회
```
**같은 사람이 같은 날 쓴 것들이다.** 차이는 실력이 아니라 **그 명령이 스스로를 검사하는가**였다.

**실패 유형 셋 — ③이 가장 위험하다:**
```
① 도구가 그 옵션을 지원 안 함    pgrep -c 부재 · find -newermt 상대시각 · --include 글로브
② 패턴이 대상을 안 덮음          번들 경로가 바뀜 · 제네릭 선언 · 이름 충돌
③ 실패가 조용함                 2>/dev/null · grep -c 로 에러 세기 · filter 0건 매칭
```
①②는 **이상한 결과**를 내지만 ③은 **정상적인 결과**를 낸다.

**→ `2>/dev/null`을 판정 명령에서 쓰지 않는다.** "결과 없음"과 "명령 실패"가 구별 불가능해진다. 소음을 지우려는 목적이 분명할 때만 쓰고, 그때도 그 출력을 판정 근거로 삼지 않는다.

**→ 그리고 3회 반복된 규칙은 규칙이 아니라 도구로 만든다.** 같은 빌드에서 낡은 번들로 판정한 것이 네 번이었는데, `bundle.sh`가 `HEAD`·`clean`을 매니페스트로 적게 한 뒤 0회가 됐다. **사람이 기억해야 하는 규칙은 세 번 잊혔고, 스크립트가 답하는 사실은 0번 잊혔다.**

- **검사 스크립트 자체도 실측 대상이다** — 게이트의 시크릿 스캔·드리프트 검사처럼 "무언가를 잡아내는 검사"는 조용히 실패해도 아무도 모른다(실제: gate.sh 시크릿 스캔이 3중 결함으로 침묵 통과 — 브레이스 glob이 확장되지 않아 대상이 0건, `-i` 부재로 camelCase 미검출, 빈 허용목록이 결과 전체를 삼킴). **리크 픽스처를 넣어 검출(비0 종료)과 클린 통과(0 종료) 양방향을 확인**하라. 검사가 도는 것과 검사가 잡는 것은 다르다

## 사람 손이 필요한 측정 (자동화가 안 되는 칸)

권한 대화상자·입력 소스·생체 인증처럼 **합성으로 만들 수 없는 상태**가 있다. 그럴 때만 사용자에게 부탁하되, **부탁은 한 번뿐이라고 가정하고 설계한다.**

- **인자 0개·한 줄.** 긴 명령은 터미널에서 접히며 잘린다(실제: 경로가 두 조각으로 갈라져 두 명령이 됐고, 스크립트는 엉뚱한 경로로 "측정 불가"를 냈다). **길이가 곧 실패 확률이다.** 기본값은 스크립트가 정하고(예: 최신 번들), 무엇을 골랐는지 출력한다.
- **자기 검사를 먼저 돌린다.** 자동 측정은 이상하면 다시 돌리면 되지만 **사람의 1분은 한 번뿐**이다. 고장난 측정기로 그 1분이 낭비되면 두 번 부탁하게 된다.
- **사람이 하는 일을 최소로.** 픽스처·앱 기동·파일 열기·저장·판정은 전부 자동. 사람은 **합성으로 못 만드는 그 한 가지만** 한다.
- **잘못된 상태로 잰 것은 "통과"가 아니라 "다시 해 주세요"** 로 집계한다. 예: 자판 전환을 잊었으면 라틴 바이트가 들어오는데, 그것을 통과로 세면 결함이 남은 채 인증된다.
- **결과 해석표를 미리 만든다.** "안 된다"로만 오면 원인을 못 가른다. 관측이 여러 원인을 뜻할 수 있으면 **각각 무엇으로 갈리는지**를 스크립트가 출력하게 한다.
- **요구사항의 방어선을 검증 도구가 깨지 않는다.** 예: "앱은 사용자 입력 소스를 바꾸지 않는다"가 요구면, 그 전환을 강제하는 API를 검증 도구도 쓰지 않는다 — 중간에 죽으면 사용자 상태가 바뀐 채 남고, **규칙을 지키는지 재려고 규칙을 깨는 것**이 된다.

**그래도 못 재면 `미검증(측정 불가 — 필요 조건 미충족)`으로 적는다.** 통과로 적지 않는다. 그리고 **그 칸이 이번 빌드가 만든 위험이면** 그 사실을 인증 문서에 함께 적는다.

## 점진적(incremental) 검증
전체 완성 후 1회가 아니라, **각 모듈 완성 직후 즉시** 검증한다. 백엔드 API가 완성되면 그 즉시 해당 API + 대응 프론트 훅을 교차 검증한다. 버그를 일찍 잡아야 후속 모듈로 전파되지 않는다.

## 버그 리포트 형식
발견 즉시 책임 개발자에게 SendMessage로 보낸다. 경계면 이슈는 **양쪽 개발자 모두**에게.

```
[버그] {한 줄 요약}
- 위반 REQ: REQ-00X (AC-Y)
- 위치: {파일:라인} (경계면이면 양쪽 모두)
- 재현: {단계 또는 입력}
- 기대: {수용 기준상 결과}
- 실제: {관찰된 결과}
- 수정 방향: {구체적 제안}
- 심각도: blocker | major | minor
```

재현되지 않으면 버그로 단정하지 않는다 — 재현 단계를 반드시 적는다.

## 출력 형식
`_workspace/05_qa_report_round{N}.md`:

```markdown
# QA 리포트 — Round {N}

## TDD 게이트
- 커버리지: {100% | 미커버 REQ 나열}
- 테스트 실행: {전체 M / 통과 / 실패}

## REQ별 검증
| REQ-ID | 결과 | 근거/비고 |
|--------|------|----------|
| REQ-001 | PASS | test_login_* 통과 + 동작 확인 |
| REQ-002 | FAIL | 경계면 불일치 (아래 버그 #1) |

## 통합 정합성
- API↔프론트: {발견 사항}
- 라우팅: {발견 사항}
- 상태전이: {발견 사항}

## 버그 목록
### 버그 #1 (→ {담당 개발자})
{위 버그 리포트 형식}

## 종합
- 전체 PASS 여부: {예/아니오}
- blocker {n}, major {n}, minor {n}
```

## 재검증과 종료 조건
- 개발자가 수정 완료를 통지하면 해당 항목을 **재검증**한다 (회귀 확인 포함)
- 모든 REQ가 PASS이고 blocker/major 버그가 없고 **방어선 실측(위 섹션)까지 수행**했으면 "검증 통과"를 리더에게 보고
- 같은 버그가 2라운드 연속 미해결이거나 진전이 없으면 리더에게 **에스컬레이션**한다 (무한 루프 방지)
