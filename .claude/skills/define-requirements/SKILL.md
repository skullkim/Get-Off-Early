# Define Requirements — 검증 가능한 요구사항 명세 작성

모호한 요구를 팀 전체의 단일 기준이 되는 요구사항 명세로 변환하는 절차. PM이 사용한다. 이 명세의 REQ-ID는 디자인·테스트·QA가 끝까지 추적하는 단일 진실 공급원(single source of truth)이다.

## 왜 이렇게 하는가
요구사항이 검증 불가능하면 TDD의 테스트도, QA의 검증도 기준이 없다. "빠르게", "잘", "사용하기 쉽게"는 통과/실패를 판정할 수 없다. 모든 요구사항을 **참/거짓으로 판정 가능한 수용 기준**으로 분해해야, 개발자가 그 기준을 테스트로 옮기고 QA가 그 기준으로 검증할 수 있다.

## 절차

### 1. 목표와 맥락 파악
사용자에게 묻는다 (한 번에 2~4개로 묶어서):
- 이걸 왜 만드는가? 해결하려는 문제는?
- 주 사용자는 누구이고, 핵심 유스케이스는?
- 반드시 있어야 하는 것 vs 있으면 좋은 것은?
- 명시적 제약(마감, 기술 제약, 규정, 기존 시스템 연동)은?

추측으로 빈칸을 메우지 않는다. 단, 합리적 기본값이 있으면 "X로 가정하겠다"고 명시하고 진행해 사용자 피로를 줄인다.

### 2. 요구사항을 REQ-ID로 분해
큰 요구를 독립적으로 검증 가능한 단위로 쪼갠다. 각 단위에 `REQ-001`부터 순차 ID를 부여한다. ID는 영구적이다 — 한 번 부여하면 재사용·재번호하지 않는다.

### 3. 각 REQ에 수용 기준 작성
수용 기준은 **Given-When-Then** 형태를 기본으로 한다:
- Given (전제 상태) / When (행동) / Then (관찰 가능한 결과)

예:
- 나쁨: "로그인이 동작한다"
- 좋음: "Given 가입된 사용자가, When 올바른 이메일/비밀번호로 로그인하면, Then 200과 세션 토큰을 받고 대시보드로 이동한다"
- 좋음(엣지): "Given 가입된 사용자가, When 틀린 비밀번호로 로그인하면, Then 401과 '이메일 또는 비밀번호가 올바르지 않습니다' 메시지를 받는다 (어느 쪽이 틀렸는지 노출하지 않는다)"

### 4. 엣지 케이스를 명시적으로 포함
각 기능에 대해 행복 경로가 아닌 경우를 별도 REQ 또는 수용 기준으로 추가한다:
- 빈 상태(데이터 없음), 로딩, 에러/실패, 권한 없음, 동시성/중복, 입력 검증 실패, 경계값

누락된 엣지 케이스는 거의 항상 나중에 QA 버그가 된다.

### 5. 범위와 비기능 요구사항 확정
- in-scope / out-of-scope를 명시 (스코프 크리프 방지)
- 비기능: 성능(측정값), 보안, 접근성, 브라우저/디바이스 지원

### 6. 엄밀화 산출물 — 도메인 시맨틱 (비자명·상태/동시성 도메인은 필수)
기능 REQ 목록만으로는 하류에 모호함이 샌다 — 그 공백을 시니어가 ADR로, QA가 사후에 메우면 엄밀성이 떨어진다. PM 단계에서 **비즈니스 의미**를 확정한다(시각=PD/02, 기술 계약=시니어/03과 *경쟁하는 두 번째 소스를 만들지 말 것* — 여기서 정하는 건 비즈니스 의미뿐, 물리 스키마/타입/엔드포인트가 아니다). 사용자와 더 길게 대화해도 좋다.
- **도메인 용어집 + 개념 모델**: 핵심 명사·상태·이벤트의 단일 정의 + 엔티티/관계 스케치. 역할 간 용어 해석 드리프트를 차단(예: "hold/sub-order/settlement"가 무엇인지 한 곳에서 정의).
- **비즈니스 불변식(INV-ID)**: *항상 참이어야 하는* 규칙을 기능 AC와 별개로 번호화(예: 오버셀 0, 이중결제 0, 수수료=floor(gross×rate)). 이것이 동시성/속성 테스트의 대상이 된다.
- **상태 전이표**: 상태를 갖는 엔티티마다 허용/금지 전이 + 트리거 이벤트 + 가드. 불법 전이·멱등은 *비즈니스 결정*이므로 PM이 확정(시니어 ADR이 추측하지 않게).
- **수용 시나리오(SC-ID, Given/When/Then + 구체값)**: 핵심 REQ별로 예시 기반 시나리오를 **행복 + 불행/동시 경로**까지. AC→테스트/E2E 간극을 메우고, 누락 엣지(예: "결제 대기 중 같은 항목 재주문")를 요구사항 단계에서 드러낸다.
- **스케일링**: 단순 CRUD엔 용어집+시나리오만으로 충분. 상태기계·동시성·금전·권한이 얽힌 도메인일수록 불변식·상태표를 반드시 채운다. 과대명세 금지 — 자명한 건 생략.

## 출력 형식

`_workspace/01_requirements.md`에 아래 구조로 작성한다:

```markdown
# 요구사항 명세: {프로젝트명}

## 1. 개요
- 목표: {왜 만드는가}
- 주 사용자: {누구}
- 핵심 유스케이스: {무엇을 할 수 있어야 하는가}

## 2. 범위
- In-scope: {포함}
- Out-of-scope: {제외 — 명시적으로}

## 3. 도메인 용어집 + 개념 모델   ← 엄밀 산출물 (ubiquitous language)
- 용어: {핵심 명사·상태·이벤트의 단일 정의 — 역할 간 해석 드리프트 차단}
- 엔티티/관계: {주요 엔티티 + 관계 (텍스트 ERD) + 각 엔티티 핵심 속성(비즈니스 의미)}
> 비즈니스 의미만. 물리 스키마·타입·엔드포인트는 시니어(03) 몫. PD/시니어가 이 용어를 그대로 소비.

## 4. 기능 요구사항

### REQ-001: {제목}
- 영역: backend | frontend | both
- 우선순위: must | should | could
- 설명: {한 줄}
- 수용 기준:
  - [ ] AC-1: Given ... When ... Then ...
  - [ ] AC-2: Given ... (에러/엣지) ... Then ...
- 완료의 정의: {무엇이 충족되면 끝}

### REQ-002: ...

## 5. 비즈니스 불변식 (항상 참 — INV-ID)   ← 엄밀 산출물
- INV-1: {언제나 성립해야 하는 규칙. 예: 오버셀 0 — 동시 구매 합계가 총재고를 못 넘김}
- INV-2: {예: 이중결제 0 / 수수료 = floor(gross × rate)}
> 기능 AC와 별개. 이것이 동시성/속성 테스트(NF-동시성)의 대상.

## 6. 상태 전이표 (stateful 엔티티 — 해당 시)   ← 엄밀 산출물
- {엔티티}: 상태 = {…}. 허용 전이: {state --event[guard]--> state}. 금지 전이/불법 전이 시 동작(예: 409). 멱등 규칙.

## 7. 비기능 요구사항
### REQ-NF-001: 성능 — {측정 가능한 기준}
### REQ-NF-002: 보안 — {기준}
### REQ-NF-003: 접근성 — {기준}
### REQ-NF-005: 동시성/정합 — {INV과 연결, 동시 요청 시나리오로 검증}

## 8. 수용 시나리오 (Given/When/Then, 구체값)   ← 엄밀 산출물
- SC-1 (REQ-0NN): Given {구체 상태/값} When {행위} Then {기대 결과}.   ← 행복 경로
- SC-2 (REQ-0NN, 불행/동시): Given {경합/엣지} When {…} Then {…}.   ← E2E·동시성 테스트 명세로 직결
> 누락 엣지(빈/에러/권한없음/동시/재시도)를 시나리오로 강제해 요구사항 단계에서 드러낸다.

## 9. 미해결 질문 / 가정
- {사용자 확인이 필요한 항목, 또는 진행을 위해 둔 가정}
```
> 단순 도메인이면 §5/§6은 생략 가능(과대명세 금지). 상태기계·동시성·금전·권한 도메인은 §3·§5·§6·§8을 반드시 채운다.

## 품질 게이트
명세를 넘기기 전 자문한다:
- 모든 REQ의 수용 기준이 참/거짓으로 판정 가능한가? (모호하면 테스트도 QA도 불가능)
- 행복 경로뿐 아니라 에러/빈/권한/**동시/재시도** 케이스가 시나리오(§8)에 있는가?
- out-of-scope가 명시되어 범위가 닫혀 있는가?
- (엄밀 모드) REQ·시나리오에 쓰인 용어가 §3 용어집에 정의돼 있는가? 상태 엔티티의 전이가 §6에 명시됐는가? "항상 참" 규칙이 §5 불변식에 번호화됐는가?
- 엄밀 산출물이 PD(시각)·시니어(기술 계약)와 *중복·경쟁*하지 않고 비즈니스 의미에 머무는가?

## 재실행 시
기존 `01_requirements.md`가 있으면 읽고, 추가/변경/삭제만 반영한다. 기존 REQ-ID는 보존하고, 삭제는 `[DEPRECATED]`로 표시한다 (이미 작성된 테스트/QA 추적이 깨지지 않도록).
