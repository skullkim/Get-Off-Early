# 트리거 평가 — define-requirements

> 이 스킬이 **발동해야 할 때 발동하고, 발동하면 안 될 때 안 하는지**를 재는 표본 질의.
> 설명(description)을 고쳤으면 이 표를 돌려 확인한다. 돌리는 법: 각 질의를 새 세션에 그대로 주고,
> 어떤 스킬이 호출되는지 본다. 기대와 다르면 **설명의 "언제" 절을 고친다**(무엇이 아니라 언제가 트리거다).

| 구분 | 질의 | 기대 |
|------|------|------|
| 발동 | "뭘 만들지부터 정하자" | define-requirements |
| 발동 | "이 기능 수용 기준 좀 써줘" | define-requirements |
| 비발동 | "이 API 응답이 왜 틀렸는지 봐줘" | 스킬 없음 — 디버깅 |
| 경계 | "어떤 화면이 필요한지 정리해줘" | product-design — 화면 목록은 디자인이다. 요구사항은 *무엇을 왜* |
| 경계 | "이 요구사항이 충족됐는지 확인해줘" | qa-verification — 설명에 "검증"이 둘 다 있다. 기준을 **쓰는** 것이 여기, **대조**가 QA |

## 왜 경계 사례가 핵심인가

실측(2026-10-31): 이 하네스의 스킬 설명 여덟 개 중 **'요구사항' 이 여섯 개**에, '구현' 이 네 개에 들어 있다. "무엇"은 심하게 겹치고 "언제"는 얇다 — 공식 문서가 "엉뚱한 스킬 발동 → 설명을 '무엇' 이 아니라 '언제' 쓰는지로 구분해 명확화" 라고 처방한 모양 그대로다. 그래서 위 표의 **경계** 행이 발동/비발동 행보다 중요하다.
