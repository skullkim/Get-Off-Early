# 테스트 시나리오 — 정상 흐름과 에러 흐름

> `build-project` 스킬의 참조 파일. 본문에서 떼어 둔 이유는 이 내용이 **특정 국면에서만** 필요하기 때문이다 — 스킬이 트리거될 때마다 컨텍스트에 올리지 않는다.

## 테스트 시나리오

### 정상 흐름
1. 사용자가 "할 일 관리 웹앱 만들어줘" 요청
2. P1: 리더가 PM 역할로 요구사항 명세 작성 (REQ-001~00N), 사용자 확인
3. P2: PD가 화면·상태·토큰 디자인 (02_design.md)
4. P3: 팀 구성, 시니어들이 스택(예: 사용자 확인 후) + API 계약 합의
5. P4: 개발자들이 TDD로 구현, 시니어가 주니어에 위임, 점진적 QA, 게이트 충족
6. P5: QA Round 1에서 버그 2건 → 개발 수정 → Round 2 전체 PASS
7. P6: 팀 정리, 최종 보고
8. P7: 회고 실행 — QA가 경계면 버그를 반복 발견했다면 architecture/qa 스킬 보강을 제안 → 승인 → 적용 + 로그 기록
9. 예상 결과: 동작하는 코드 + 100% 요구사항 커버 테스트 통과 + QA 통과 리포트 + 발전된 하네스

### 에러 흐름
1. P5 Round 1: 경계면 버그(API가 `{items:[]}` 반환, 프론트가 배열 기대)
2. QA가 backend-senior와 frontend-senior **양쪽**에 통지
3. 두 시니어가 계약을 재합의(배열 반환으로 통일), 양쪽 수정 + 회귀 테스트 추가
4. Round 2 재검증 → PASS
5. (만약 Round 2,3에서도 같은 버그 미해결이면) 리더가 사용자에게 에스컬레이션
