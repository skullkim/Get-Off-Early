# Build Project — 가상 개발팀 오케스트레이터

요구사항 → 디자인 → TDD 개발 → QA 검증 루프를 조율해 프로젝트를 완성하는 통합 스킬.

## 실행 모드: 하이브리드

| Phase | 단계 | 모드 | 이유 |
|-------|------|------|------|
| 1 | 요구사항 정의 | **리더 직접** (인터랙티브) | 팀원은 사용자와 직접 대화 불가. 리더가 PM 역할로 AskUserQuestion 사용 |
| 2 | 디자인 | **서브 에이전트** | 집중된 단일 산출물, 팀 통신 불필요 |
| 3~6 | 아키텍처+TDD 개발+QA 루프 | **에이전트 팀** (5인) | 시니어↔주니어 위임, 개발↔QA 피드백 루프가 핵심 |

## 에이전트 구성

| 단계 | 에이전트 | 타입 | 역할 | 스킬 | 출력 |
|------|---------|------|------|------|------|
| P1 | pm | (리더가 역할 수행) | 요구사항 정의 | define-requirements | 01_requirements.md |
| P2 | product-designer | 커스텀 | 디자인 | product-design | 02_design.md |
| P3~6 | backend-senior | 커스텀 | 백엔드 설계+핵심 구현 | architecture-and-delegation, tdd-implementation | 03_backend_architecture.md + 코드 |
| P3~6 | backend-junior | 커스텀 | 백엔드 위임 구현 | tdd-implementation | 코드 |
| P3~6 | frontend-senior | 커스텀 | 프론트 설계+핵심 구현 | architecture-and-delegation, tdd-implementation | 03_frontend_architecture.md + 코드 |
| P3~6 | frontend-junior | 커스텀 | 프론트 위임 구현 | tdd-implementation | 코드 |
| P3~6 | qa | 커스텀(general-purpose 기반) | 검증 | qa-verification | 05_qa_report_round{N}.md |

스폰 호출에 **모델을 명시하지 않는다.** 각 에이전트 정의에는 `model: inherit` 만 적어 상속을 명시한다(비워 두면 "의도적 상속"과 "깜빡함"이 구별되지 않는다). 모델 교체가 하네스 파일 수정이 아니라 세션 설정 변경으로 끝나게 한다(모델은 부품, 공정이 자산 — 특정 모델명을 에이전트 frontmatter나 스킬에 하드코딩하지 않는다).

## 워크플로우

### Phase 0: 컨텍스트 확인
1. `_workspace/` 존재 여부 확인
2. 분기:
   - **미존재** → 초기 실행. Phase 1로
   - **존재 + 부분 수정 요청**(예: "QA 다시", "REQ-003만 고쳐", "디자인 보완") → 부분 재실행. 해당 단계 에이전트만 재호출하고, 이전 산출물을 프롬프트에 포함해 읽고 반영하게 함
   - **존재 + 새 프로젝트 입력** → 새 실행. 기존 `_workspace/`를 `_workspace_{YYYYMMDD_HHMMSS}/`로 이동 후 Phase 1
3. 부분 재실행 매핑:
   - 요구사항 변경 → Phase 1부터 (변경된 REQ가 하류로 전파)
   - 디자인만 → Phase 2 (PD) → 영향받는 프론트 재작업 → QA
   - 버그/기능 추가 → Phase 3~6 팀 (해당 개발자 + QA)
4. **중단된 빌드 이어받기**("계속해" + `_workspace/` 존재 + `BUILD_COMPLETE.md` 부재): 빌드는 **미완**이다 — 커버리지 매트릭스/QA 리포트가 "다 됐다"(라이브 E2E PASS·디자인 충실도 일치 포함)고 적혀 있어도 그건 *리더 인증 대기 중인 팀 주장*이지 완료가 아니다. 상태 문서(RESUME·매트릭스·QA 리포트)는 각기 다른 시점을 가리킬 수 있으니(실제 발생: 세 문서가 3개 시점) 가장 최신 문서를 진실로 믿지 말고, **직접 실행으로 재조정**(백 `./gradlew test`, 프론트 `pnpm test`)한 뒤 Phase 6 리더 독립 검증을 거쳐야만 완료를 선언한다. `BUILD_COMPLETE.md` 존재가 유일한 "완료" 신호다.

### Phase 1: 요구사항 정의 (리더 직접 · 인터랙티브)
1. `_workspace/` 생성 (또는 새 실행 시 기존 것 이동 후 재생성)
2. 리더가 PM 역할로 `define-requirements` 스킬을 따라 사용자와 대화한다 — `AskUserQuestion`으로 목표·사용자·범위·제약·엣지케이스를 끌어낸다 (한 번에 2~4개씩)
3. **기술 스택은 여기서 고정하지 않는다.** 비즈니스 제약만 확정하고, 스택은 Phase 3에서 시니어가 요구사항 기반으로 결정 → 사용자 확인
4. 산출물: `_workspace/01_requirements.md` (REQ-ID + 수용 기준 + 범위). **비자명·상태/동시성/금전/권한 도메인이면 엄밀 산출물도 포함**(define-requirements §6): 도메인 용어집+개념모델, 비즈니스 불변식(INV), 상태 전이표, 수용 시나리오(Given/When/Then 구체값). 이게 시니어 ADR 추측·QA 사후보강·늦은 경계 질문을 앞단에서 막는다. 엄밀화를 위해 사용자와 더 길게 대화해도 좋다(비즈니스 의미만 — 시각/기술계약과 중복 금지).
5. 사용자에게 요구사항 명세를 확인받은 뒤 다음 단계로 (요구사항이 닫혀야 하류가 안정적)

### Phase 2: 디자인 (서브 에이전트)
1. `product-designer`를 Agent 도구로 호출
   - 입력: `_workspace/01_requirements.md`
   - 지시: `product-design` 스킬을 따라 `_workspace/02_design.md` 생성. 모든 화면의 모든 상태 정의 + REQ 매핑 + **화면별 와이어프레임 + HTML/CSS 프로토타입 제작 후 헤드리스 스크린샷으로 자가 검증**(`_workspace/prototype/` + `shots/`). 이 스크린샷이 시각 기준물.
2. 결과(`02_design.md` + `prototype/shots/`)를 Read로 확인. 화면 관련 REQ 커버 + **프로토타입 스크린샷이 명세/토큰대로 보이는지** 점검(미스타일/깨짐이면 PD 재호출). 이후 프론트는 이 스크린샷을 시각 타깃으로 구현, QA·리더는 실제 앱을 이것과 대조
3. (API/순수 백엔드 프로젝트라 UI가 없으면 이 Phase를 데이터 계약·에러 형식 설계로 축소하거나 건너뛴다 — 요구사항에 화면이 없으면 PD 생략 가능)

### Phase 3: 팀 구성 + 아키텍처 (에이전트 팀)
0. **런타임 의존 프리플라이트**: 스택이 필요로 하는 런타임 의존을 팀 빌드 전에 확인·기동한다 — Docker 데몬 up(Testcontainers/dev DB용), 필요한 포트 비어있음(예: dev DB가 5432 점유 시 5433 등 다른 포트), 언어/툴 버전(java/node/pnpm/gradlew). 개발자가 TDD 중 블로커로 만나기 전에 리더가 선제 해소(실제 발생: Docker DOWN을 게임엔진 통합 단계에서야 발견).
   - **소비 주체와 같은 방식으로 실측한다** — 대화 셸의 `X --version`은 증거가 아니다. 에이전트 셸에는 도구가 주입돼 있을 수 있고(실제: `rg`가 Claude Code 주입 함수였고 실제 바이너리는 부재 → Node `spawn` ENOENT로 뒤늦게 발각, `grep`도 대화 셸은 ugrep·스크립트는 BSD grep), 스크립트 컨텍스트와 대화 컨텍스트의 도구가 다르다. 코드가 `spawn('rg')`로 쓸 바이너리는 **`node -e "spawnSync('rg')"`로**, 스크립트가 쓸 도구는 **스크립트를 실행해** 확인한다. 프리플라이트 결과는 RESUME에 적되 **누가 어떤 방식으로 쟀는지**를 함께 남긴다.
1. **빌드 팀 스폰 (리더가 named 에이전트로 스폰·생존을 단독 관리)**. 멤버 풀: backend-senior, backend-junior, frontend-senior, frontend-junior, qa (agent_type 동일명, 모델은 각 정의의 `model: inherit` 로 세션 상속). 스폰은 `Agent`(named spawn), 통신은 `SendMessage`(지연 도구 — `ToolSearch` 선행), 작업 목록은 `_workspace/00_tasks.md` 파일이다. **도구 이름을 추측하지 말고 `harness-runtime.md` 의 표를 따르고, 런타임이 바뀌었으면 그 파일의 재측정 절차를 먼저 돌린다.** **스폰은 단계적으로 — 주니어는 선(先)스폰하지 않는다**:
   - **먼저 두 시니어**(+ 첫 모듈 게이트레디 시 QA)를 스폰한다.
   - **주니어 just-in-time 스폰**: 시니어가 기반(백=도메인/서비스·계약, 프론트=base types/queryKeys/공유컴포넌트/라우트)을 세워 **기반준비된·독립적인 위임 작업 배치가 실재할 때만** 리더가 주니어를 스폰한다. 그런 배치가 없거나 시니어가 빠르게 끝낼 분량이면 **주니어를 스폰하지 않는다**(유휴 콜드스폰·충돌 churn 방지 — 실제로 주니어 작업이 시니어 기반에 100% 의존해 산출 0/marginal이 된 빌드 있음). 주니어 폐지가 아니라 *타이밍* 문제: 독립 화면/슬라이스 배치가 있으면 스폰해 병렬화한다. 배치가 파일 독립적이고 계약 기계화가 채택된 빌드면 `isolation: "worktree"`(격리 스폰)로 워크트리 격리 병렬을 쓸 수 있다 — 판단 기준·merge 규율은 architecture-and-delegation §5 "병렬화 판단 기준"을 따른다(merge 후 시니어가 풀게이트 재실행).
   - **소유권 브로커링(필수)**: 주니어 스폰 즉시 리더가 *어느 task/파일이 주니어 소유인지* 시니어에게 명시 통지한다. 시니어는 **주니어 스폰/생존을 가정하지 않는다**(리더가 관리) — "주니어 없으니 내가 직접"으로 같은 작업을 동시 구현하면 파일 충돌(실제 3회 발생). 가정 대신 리더에 확인.
   - **에이전트 교체 시 주소 브로드캐스트(필수)**: 팀원이 죽어 재스폰하면(이름이 바뀐다) 리더가 **관련자 전원에게 새 주소를 즉시 통지**한다. 통지 전에 발신된 메시지는 죽은 주소로 가서 **유실**되고, 그걸 모르는 발신자는 응답을 기다리며 stall한다(실제: 시니어의 위임 스펙이 죽은 주니어 주소로 가 유실 → 신규 주니어가 무한 대기). **죽은 주소 실패 알림이 관측되면 리더가 발신자를 즉시 교정**하라 — 알림은 "누군가 낡은 주소로 보내고 있다"는 신호다.
   - **지시 교차 시 우선순위 명시**: 리더 지시와 팀원 지시가 엇갈릴 수 있다(작성 시각 ≠ 도착 시각). 소유권을 재배정할 때는 수신자에게 **"다른 메시지와 충돌하면 이 지시가 우선"**을 명시하고, 이미 착수했으면 즉시 멈추고 보고하라고 지시한다(실제: 재배정 전 발송된 반려가 나중에 도착해 중복 구현 발생).
   각 prompt에 `_workspace/01·01b_requirements.md`·`02·02b_design.md` 경로 + 자기 스킬 지시 포함. **통신 규율**: 마일스톤·블로커·완료 위주, ack-only/예의성 반복 메시지("접수","idle 유지",인사) 자제 — 루틴 조율은 피어끼리, 리더엔 진척/막힘만(오케스트레이터 churn 감소). **통지에는 검증 시각을 병기하고, 타 영역의 "가동/완료" 주장은 중계 전에 1회 실측하거나 "○○ 통지 기준"임을 명시**한다 — 검증 시점과 도착 시점이 벌어지면 낡은 정보가 최신 사실을 덮는다(실제: QA의 "미구현" 통지가 구현 완료 후 도착해 프론트가 언블록 통지를 도로 취소, 작업이 잘못 차단됨). **학습 저널 규율**: 각 팀원은 블로커를 해소했을 때·결정을 뒤집었을 때·같은 실수가 2회 이상 반복될 때·계약이 변경될 때 `_workspace/06_journal.md`에 1~3줄 append 한다. **형식: `- [역할] (REQ-ID · 파일경로) 무엇 / 왜`** — 대상 식별자를 괄호에 넣는다. 자유 텍스트만 적으면 재개할 때 "이 항목이 이미 끝났는지"를 사람이 읽어 판단해야 하고, 실제로 상태 문서 세 개가 서로 다른 시점을 가리킨 적이 있다. 식별자가 있으면 작업 목록·커밋과 기계적으로 대조된다(공식 문서의 워크플로 저널이 결과를 내용 해시로 키잉해 "멈춘 지점부터 재개"를 성립시키는 것과 같은 이유). 메시지가 아니라 파일 append라 통신 churn 없음 — 서브에이전트의 경험은 세션이 닫히면 사라지므로 그 순간에 기록해야 남고, 회고(retrospective)가 이 저널을 정식 입력으로 마이닝한다.
2. 두 시니어가 `architecture-and-delegation` 스킬로 스택·구조·**API 계약**을 결정하고 합의
   - 백엔드 시니어가 API 계약 초안 → 프론트 시니어와 SendMessage 합의
   - 스택 결정 후 리더가 사용자에게 간단히 확인 (런타임 결정 원칙)
3. 산출물: `03_backend_architecture.md`, `03_frontend_architecture.md` (스택·계약·작업 분해표)

### Phase 4: TDD 개발 + 점진적 QA (에이전트 팀)
**실행 방식:** 팀원 자체 조율 + 시니어 위임

1. 시니어가 작업을 **작업 목록 파일(`_workspace/00_tasks.md`)**에 등록 (소유자·REQ-ID·완료 기준 명시 — `TaskCreate` 도구는 이 런타임에 없다). 복잡/핵심은 직접, 격리 작업은 주니어에게 할당 + `SendMessage`로 스펙 전달
2. 모든 개발자가 `tdd-implementation` 스킬로 구현 — **실패 테스트 먼저 → 구현 → 통과**. 각 테스트를 REQ-ID에 매핑
3. `_workspace/04_coverage_matrix.md`를 공동 갱신 (REQ ↔ 테스트 ↔ 통과 상태)
4. **점진적 QA**: 모듈(특히 백엔드 API)이 완성될 때마다 QA가 즉시 해당 부분 + 대응 프론트를 교차 검증. 경계면 버그를 일찍 잡는다
5. 시니어는 주니어 결과를 리뷰하고 미흡하면 반려. **소유권 규율**: 누구도 *다른 에이전트가 owner인 task/파일을 동시 구현하지 않는다*. 동시 작업 가능성이 보이면(파일이 막 쓰이는 중 등) 무편집으로 리더에 상태 보고 후 소유권을 받고 진행(실제: 주니어가 동시 쓰기 감지해 무편집 대기 = 옳은 행동).
6. **TDD 게이트**: (a) 모든 in-scope REQ가 테스트로 커버 + (b) 전체 테스트 통과 — 둘 다 충족해야 Phase 5 정식 QA로
7. **빌드 직렬화 주의**: 팀원이 같은 워크스페이스에서 풀빌드/테스트를 **동시에** 돌리면 빌드 락·데몬·포트 충돌로 **가짜 실패**가 난다(실제 발생 이력). 게이트 판정 풀빌드는 **시니어가 단독 1회** 실행하고 그 결과를 QA·리더가 게이트 근거로 쓴다. 개발자는 스코프 테스트만, 풀빌드는 시간 안 겹치게. (상세: `architecture-and-delegation`의 "빌드/테스트 실행 프로토콜")

### Phase 5: QA 검증 + 수정 루프 (에이전트 팀)
**생성-검증 루프. 통과할 때까지 반복하되 안전장치 포함.**

라운드 N (N=1,2,3,…):
1. QA가 `qa-verification` 스킬로 전체 검증 → `05_qa_report_round{N}.md`
   - TDD 게이트 재확인(미충족이면 개발 반려) → 통합 정합성 교차 검증 → REQ별 충족 검증
2. 버그 발견 시 QA가 책임 개발자에게 SendMessage (경계면은 양쪽 모두). 형식: 파일:라인 + REQ-ID + 재현 + 수정 방향
3. 개발자가 **버그 재현 테스트 추가 → 수정 → 전체 테스트 통과**(tdd-implementation) 후 QA에 재검증 요청
4. QA가 해당 항목 재검증(회귀 포함)
5. **종료 조건:** 모든 REQ PASS + blocker/major 버그 0 → 루프 종료, "검증 통과"
6. **안전장치(무한 루프 방지):** 같은 버그가 2라운드 연속 미해결이거나, 라운드가 진전 없이 반복되면 리더에게 에스컬레이션 → 리더가 사용자에게 현황 리포트와 함께 결정을 요청 (사용자는 "계속"/"범위 조정"/"수용" 선택 가능). 사용자가 "시간이 걸려도 끝까지"를 원하면 진전이 있는 한 계속 반복

### Phase 6: 마무리
> **완료 인증 단일 소스**: 빌드 '완료'는 **리더가 아래 독립 검증을 마치고 `BUILD_COMPLETE.md`를 쓴 시점에만** 성립한다. 커버리지 매트릭스·QA 리포트에 적힌 완료 문구는 — 특히 **라이브 E2E·디자인 충실도는 리더 인증 단계**라 — 팀이 자가 실행해 "PASS"로 적었어도 *인증이 아니라 리더 인증 대기 중인 주장*이다. 팀이 자가 E2E/시각 검증을 돌렸으면 매트릭스에 "팀 자가검증(리더 인증 대기)"로만 표기하고, 게이트 종결로 적지 않는다. `BUILD_COMPLETE.md` 부재 = 미완.
>
> **"존재 = 완료"로 판정하지 않는다.** 파일이 있고 테스트가 그린이어도 그것은 *존재하는 테스트의* 그린일 뿐 계약 표면 전체를 증명하지 않는다(실제: 라우트 파일·등록·전체 그린이 다 있는데 엔드포인트 하나가 TODO 주석으로 비어 있었고, 그 엔드포인트는 테스트가 0건이라 실패할 것도 없었다 — 리더가 done으로 오판, 시니어 리뷰와 QA 실측이 독립 발견). 완료 판정은 **계약 §3의 엔드포인트/기능 목록 ↔ 실제 구현·라우트 등록 전수 대조**로 한다. 상태 문서(tasks/매트릭스/QA) 간 모순은 이 오판의 선행 신호이니, 어긋나면 문서를 믿지 말고 실행·대조로 재판정한다.
1. **리더 독립 검증**: 완료 선언 전 리더가 직접 **풀게이트를 재실행**해(에이전트 주장이 아니라) 그린을 확인한다 — **`_workspace/gate.sh`가 있으면 그것을 실행한다**(게이트 판정과 리더 인증이 같은 실행물을 공유해야 "무엇이 게이트인가"가 드리프트하지 않는다 — architecture-and-delegation의 게이트 스크립트화). 스크립트가 없으면 직접 — 백엔드 `./gradlew clean test`, **프론트는 `tsc -b`(0 error) + `vite build`(성공) + `vitest`(전 통과) + `eslint`(0 error) 넷 다**(테스트만 보지 말 것 — 실제로 팀이 "tsc 0/build OK" 보고했으나 최종 편집 후 tsc 2에러로 드리프트, 테스트만 봤으면 놓쳤을 갭을 풀게이트 재실행이 포착). **브라우저 프론트가 있으면 여기서 멈추지 말고, 실제 앱을 구동해(실제 백엔드 + 실제 브라우저, 헤드리스 CDP 가능) 핵심 플로우를 1회 E2E 스모크**한다 — 목 스위트·curl만으로는 CORS/인프라 버그를 놓친다(`qa-verification`의 "라이브 E2E 스모크"). curl 그린은 브라우저 그린이 아니다. **이때 스크린샷(모바일+데스크톱)을 찍어 시각/반응형도 눈으로 확인**한다 — 테스트가 다 그린이어도 컴포넌트 CSS 미작성으로 미스타일일 수 있다(실제 발생).
2. **행위 검토 (산출물이 아니라 *무엇을 했는지* 를 본다)**: 1번까지는 **결과물**을 검증한다. 팀원이 **규율 안에서 일했는지**는 아무도 사후에 보지 않았고, 이 하네스의 사고 목록이 정확히 그 종류였다 — 주니어 작업을 시니어가 동시 구현해 파일 충돌 3회, 리더의 미검증 지시가 결함 원인 3건, 팀이 리더 전용 E2E를 자가 PASS로 기록. 결과물만 보면 전부 그럴듯했다.
   - 입력은 **행위 기록**이다: `git log --stat`(누가 어떤 파일을 고쳤나) · `_workspace/00_tasks.md`(소유자 열) · `_workspace/06_journal.md`(막힘·뒤집힌 결정).
   - 아래 셋을 찾아 `_workspace/07_conduct_review.md` 에 표로 적는다. **0건이면 0건이라고 적는다** — 안 적으면 검토를 했는지 안 했는지 구별되지 않는다.
     - 소유자 아닌 사람이 고친 파일 → 작업 목록의 소유자 열 ↔ `git log --stat` 의 파일 대조
     - 게이트 없이 완료로 적힌 작업 → 상태가 `done` 인데 커버리지 매트릭스에 테스트 매핑이 없는 행
     - 리더 전용 판정을 팀원이 적은 자리 → 매트릭스·QA 리포트에서 라이브 E2E·디자인 충실도를 PASS 로 적은 줄
   - 발견은 **Phase 7 회고의 정식 입력**이다. 사람을 탓하는 문서가 아니라 *규율이 도구로 막혀 있지 않은 자리*를 찾는 문서다 — 막을 수 있으면 `tools` 나 게이트로 내린다.

3. **팀 정리 (BUILD_COMPLETE 작성 직후 자동 수행 — 사용자 지시를 기다리지 않는다)**: 빌드가 끝났는데 팀이 살아 있으면 그건 미완이 아니라 **리더가 정리를 안 한 것**이다. 사용자가 "종료시켜라"라고 말해야 하는 상황이 오면 이미 절차를 빠뜨린 것이다(실제 발생 — 리더가 자연어 "작업 종료하라"만 일부에게 보내고 공식 종료 프로토콜·일회성 역할은 누락).
   - **대상 = 이 빌드에서 스폰한 전원**. 중간에 죽은 것으로 보이는 에이전트, 일회성 역할(product-designer 등 초반에 끝난 팀원), 교체로 생긴 구·신 이름 **전부 포함**한다. `ListAgents`로 실제 목록을 확인해 빠짐없이 처리한다 — 기억에 의존하면 초반 팀원을 흘린다.
   - **공식 종료 프로토콜을 쓴다**: `SendMessage`로 `{"type":"shutdown_request","reason":"..."}`. 자연어 "종료하라"는 통지일 뿐 종료가 아니다.
   - **응답 없음 ≠ 종료됨**: 한도 소진·인증 만료 상태의 에이전트는 `shutdown_request`를 처리하지 못해 실패 알림만 돌려주고 **프로세스는 계속 산다**. 이 빌드에서 실제로 7개 전원이 그랬다.
   - **잔여 프로세스를 실측하고, 남아 있으면 직접 종료한다**:
     ```bash
     pgrep -fl -- '--agent-id .*@session-<빌드세션ID>'   # 대상 확인 (다른 세션 것이 섞이지 않았는지 눈으로)
     pkill  -f  -- '--agent-id .*@session-<빌드세션ID>'   # 종료
     pgrep -fl -- '--agent-id .*@session-<빌드세션ID>' | wc -l   # 0 확인
     ```
     세션 ID로 범위를 좁혀 **다른 빌드·다른 사용자 세션을 죽이지 않는다**(kill 전 목록을 반드시 눈으로 확인).
   - **⚠ 빈 출력을 "없음"으로 읽기 전에 그 명령이 잡을 수 있는지부터 확인하라**: `pgrep`은 확장정규식이라 BSD grep 문법(`\|`)을 쓰면 **아무것도 매칭하지 못하고 조용히 0건**을 반환한다(실제 발생 — 리더가 이 빈 출력을 "프로세스 없음"으로 잘못 보고했고, 실제로는 7개가 살아 있었다). 살아 있음을 아는 대상 하나로 패턴이 실제로 매칭되는지(positive control) 먼저 확인한다. 관련 패턴: `knowledge/patterns/verify-the-checker.md`
4. `_workspace/` 보존 (산출물·감사 추적용)
5. **재개 트리거 정리**: 재개 체크포인트를 걸었으면 `_workspace/BUILD_COMPLETE.md`(완료 요약)를 쓰고 SessionStart 훅을 제거한다(`CronDelete` 도구는 이 런타임에 없다 — `harness-runtime.md`)
6. 사용자에게 최종 보고: 구현된 REQ 목록, 최종 QA 리포트 요약, 테스트 통과 현황, 코드 위치
> **Phase 6은 체크리스트다 — 1~6을 전부 끝내야 마무리다.** 완료 인증(1)만 하고 행위 검토(2)·정리(3·5)를 미루면 팀·트리거가 좀비로 남는다. **"사용자가 시켜야 하는 정리 작업"은 존재하지 않는다** — 빌드에 딸린 뒷정리는 전부 리더의 자동 의무다.

### Phase 7: 회고 (필수 · 리더 직접)
빌드가 끝나면 **반드시** `retrospective` 스킬을 실행해 하네스를 발전시킨다. 이 단계를 건너뛰면 같은 실수가 다음 프로젝트에 재발한다.

1. 팀을 정리한 직후, 대화 맥락이 살아있을 때 회고를 돈다 (맥락이 사라지면 신호를 못 캔다 — 그래서 별도 세션이 아니라 여기서 한다)
2. `retrospective` 스킬을 Skill 도구로 호출 — 이번 대화 + `_workspace/` 산출물(QA 리포트 반복 버그, 커버리지 누락, QA 라운드 수)에서 신호를 캐내 일반화한다
3. 회고 리포트(제안 변경)를 사용자에게 보여주고 **승인**받는다 (조용히 적용 금지)
4. 승인된 변경을 에이전트/스킬/오케스트레이터/description에 반영하고, 사용자 취향·반복 피드백은 글로벌 메모리에 저장한다
5. CLAUDE.md 변경 이력 + `.claude/retro/log.md`에 기록한다

## 판정 근거 규율 (리더 · 전원 · 전 Phase 공통)

빌드가 실패하는 가장 흔한 방식은 코드가 틀린 것이 아니라 **틀린 근거로 옳다고 판정하는 것**이다. 한 빌드에서 근거 붕괴가 여섯 유형으로 나왔고, 그중 셋은 리더 자신에게서 났다.

| # | 붕괴 유형 | 방지 |
|---|---|---|
| ① | **정적 분석을 실측으로 제시** — 코드를 읽고 "그러면 이렇게 동작한다"를 관측처럼 보고 | 동작 주장은 실행해서 낸다. 읽어서 안 것은 "코드상"이라고 밝힌다 |
| ② | **교란된 대조** — 재는 동안 대상이 변함(게이트 중 트리 수정, 측정 중 재빌드) | 측정 전 트리를 고정하고 커밋/해시를 근거에 병기. **움직이는 트리에서 돌린 게이트는 측정이 아니다** |
| ③ | **뒷받침 없는 단정** — 그럴듯한 기제를 확인된 원인으로 전달 | 원인 지목은 실측 후에만. 가설은 "가설"이라 부르고 **지시로 내리지 않는다** |
| ④ | **남의 낡은 측정을 현재로** | 타 영역 주장은 중계 전 1회 실측하거나 "○○ 통지 기준(시각)"으로 출처 명시 |
| ⑤ | **잘린 출력을 전체로 읽음** — `head`/`-c`/스크롤 잘림 | 개수 판정은 `wc -l`로, 목록 판정은 전체를 본 뒤에 |
| ⑥ | **자기 보고서에 자기 낡은 문장을 옮겨 실음** | 상태 문장은 **그 보고를 쓰는 시점에 잰 것만** 싣는다. 앞 메시지에서 복사하지 않는다 |
| ⑦ | **비결정적 절차의 통과를 안정성의 근거로** — 확률적으로 실패하는 실행이 이번엔 통과한 것 | 통과한 실행이 **결정적 경로였는지** 밝힌다. 아니면 "절반 확률의 동전을 이긴 것"이라고 적는다 |
| ⑧ | **시각 일치를 인과로** — 남의 편집 시각과 내 실패 시각이 겹쳤다는 이유로 원인 지목 | 기존 기록 조회 + 재현으로 가른다. **시각 일치는 근거가 아니다** |

> ④와 ⑥은 다르다 — **④는 남의 측정이 낡은 것, ⑥은 자기 측정을 자기가 갱신 안 한 것**이다.
>
> ⑦의 실례: 게이트가 `--no-parallel` 로 도는데 개발자가 기본값(병렬)으로 돌려 통과한 수치를 보고했다. 병렬은 7회 중 4회 SIGSEGV 로 죽는 경로였다 — **관측은 사실이지만 안정성의 근거가 아니고, 나중에 읽는 사람은 "이제 병렬도 괜찮다"로 읽는다.** 인증 문서가 그런 수치를 인용할 때는 **어느 경로에서 잰 것인지 함께 적는다.**

**판정 명령 3규칙** (같은 빌드에서 검사 사각이 아홉 번 났고, 전부 즉석 셸 명령에서 났다 — 자기검사를 가진 검사기에서는 0번):
1. **`2>/dev/null` 을 판정 명령에 쓰지 않는다.** "결과 없음"과 "명령 실패"가 구별되지 않는다(실제: `find -newermt` 가 이 시스템 `bfs` 에서 거부당하는 것을 스스로 지우고 "팀이 조용하다"를 반복 보고 — 실제로는 4파일 편집 중)
2. **0건은 positive control 통과 후에 믿는다** — 살아 있음을 아는 대상 하나로 쿼리가 매칭되는지 먼저 확인
3. **같은 질문을 두 번 이상 물을 것 같으면 스크립트로 승격하고 `--self-test` 를 붙인다**

관련 패턴: `knowledge/patterns/checker-self-test-or-not-a-checker.md` · `verify-the-checker.md` · `unenumerated-catch-all.md`

### 지시 규율 (리더 → 팀원)
- **가설과 지시를 분리한다.** 리더의 추측이 지시로 나가면 팀원은 그것을 *확인된 사실*로 코드와 주석에 embed 한다(실제: 리더의 미검증 주장이 시니어의 코드 주석에 근거로 박혀 결함이 됐다 — **"틀린 값보다 틀린 근거가 오래 산다"**).
- **철회는 즉시·명시적으로.** 잘못 내린 지시를 알아차리면 팀원이 착수하기 전에 취소 메시지를 보낸다. 조용히 다음 지시로 덮지 않는다.
- **"전수 확인" 주장은 축을 묻는다.** 한 축을 촘촘히 채운 것과 공간을 덮은 것은 다르다(실제: 26칸 전수 확인 후 다른 축이 0칸이라 다음 결함이 났다).

## 재개 체크포인트 (장시간 빌드 중단 대비)
다단계·다중 에이전트 빌드는 길어서 사용량 한도 소진/세션 종료로 중단될 수 있다. **어떤 세션이든 이어받게** 내구성 있는 재개 산출물을 유지한다.

1. **`_workspace/RESUME.md` 런북을 단계 경계마다 갱신**한다 — 현재 단계, 완료/남은 일, "새 세션에서 이어받는 절차"(문서·코드 위치, 실제 상태를 *테스트 실행으로* 검증하는 법, 죽은 팀이면 재스폰 vs 리더 직접 마무리), 환경 메모(필요 데몬·툴 경로). **수동 기동 런타임 의존(컴포즈 없는 dev DB 컨테이너 등)은 포트·env뿐 아니라 정확한 기동 명령**(예: `docker run -d --name <x> -e POSTGRES_DB=… -p 5433:5432 postgres:16`)**까지 적는다** — 재개자가 app 설정에서 역설계하지 않도록(실제 발생: Docker 재시작으로 dev DB 컨테이너 소실 → `docker run` 역설계).
2. **글로벌 프로젝트 메모리**에 빌드 상태 + RESUME 포인터를 남긴다(세션 시작 시 자동 로드되므로 후속 세션이 "계속"만으로 이어받음).
3. (선택) 무중단 자동 재개가 필요하면 **재개 트리거**를 건다: 프로젝트 로컬 **SessionStart 훅**(완전 종료 후 새 세션이 미완을 감지해 RESUME 지시 주입). `CronCreate` 는 이 런타임에 없으므로 훅이 유일한 수단이다(`harness-runtime.md`). 훅은 **멱등**이어야 한다 — 완료 마커(`_workspace/BUILD_COMPLETE.md`) 확인→자기 삭제, 이미 진행 중이면 중복 작업/스폰 금지, 죽은 팀일 때만 개입.
4. **Phase 6에서 빌드가 끝나면** `BUILD_COMPLETE.md`를 쓰고 재개 트리거(cron/훅)를 정리한다.
