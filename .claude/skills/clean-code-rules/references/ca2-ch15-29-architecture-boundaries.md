## 15장 아키텍처란? (What Is Architecture?)

### (도입부)

**R15-1**
- 규칙: 아키텍트(시니어) 역할도 실제 코드 작업을 계속 맡아라. 설계만 하고 구현에서 손을 떼지 마라.
- 근거: 자기가 다른 개발자에게 만드는 문제를 직접 겪지 않으면 아키텍처 일을 제대로 할 수 없다.
- 출처: 15장 · 도입부 · PDF p.117
- 태그: [모듈·아키텍처수준]

**R15-2**
- 규칙: 아키텍처를 "컴포넌트 분할 + 컴포넌트 배치 + 컴포넌트 간 통신 방식"으로 명시적으로 정의하고 문서화하라.
- 근거: 아키텍처는 시스템에 부여한 형태(shape)이며, 그 형태가 개발·배포·운영·유지보수를 돕는다.
- 출처: 15장 · 도입부 · PDF p.117
- 태그: [모듈·아키텍처수준]

**R15-3**
- 규칙: 구조 결정 시 "가능한 많은 선택지를 가능한 오래 열어 두는가"를 판단 기준으로 삼아라.
- 근거: 아키텍처의 전략은 선택지를 최대한 오래 열어 두는 것이다.
- 출처: 15장 · 도입부 · PDF p.117
- 태그: [모듈·아키텍처수준]

**R15-4**
- 규칙: 아키텍처 평가는 "동작하는가"가 아니라 이해·개발·유지보수·배포 용이성과 생애 비용 최소화로 하라.
- 근거: 끔찍한 아키텍처도 잘 동작한다. 문제는 배포·유지보수·지속 개발에서 생긴다.
- 출처: 15장 · 도입부 · PDF p.118
- 태그: [모듈·아키텍처수준]

### 개발 (DEVELOPMENT)

**R15-5**
- 규칙: 팀 구조(팀 수·규모)를 아키텍처 결정의 입력으로 고려하라. 여러 팀이 개발하면 잘 정의된 컴포넌트와 안정된 인터페이스로 나눠라.
- 근거: 다수 팀은 안정 인터페이스로 분할되지 않으면 진척이 없다.
- 출처: 15장 · DEVELOPMENT · PDF p.118
- 태그: [모듈·아키텍처수준]

**R15-6 (안티패턴: 팀당 컴포넌트, component-per-team)**
- 규칙: 개발 일정만 보고 "팀 하나당 컴포넌트 하나"로 경계를 정하지 마라. 배포·운영·유지보수 관점도 함께 평가하라.
- 근거: 팀당 컴포넌트 구조는 배포·운영·유지보수에 최선이 아닌 경우가 많다.
- 출처: 15장 · DEVELOPMENT · PDF p.118
- 태그: [모듈·아키텍처수준]

### 배포 (DEPLOYMENT)

**R15-7**
- 규칙: 시스템을 단일 동작(single action)으로 배포할 수 있게 설계하라.
- 근거: 배포 비용이 높을수록 시스템의 유용성이 떨어진다.
- 출처: 15장 · DEPLOYMENT · PDF p.118
- 태그: [모듈·아키텍처수준]

**R15-8**
- 규칙: 배포 전략을 초기 개발 단계에서부터 고려하라. 예: 마이크로서비스 개수와 연결·기동 순서 비용을 초기에 평가하라.
- 근거: 개발 편의만 보고 고른 마이크로서비스는 배포 시 연결 설정·기동 순서가 오류의 큰 원천이 된다.
- 위반 예 → 개선 예: 초기부터 서비스 수십 개 → 소수 서비스 + 프로세스 내부 컴포넌트 혼합, 상호연결의 통합 관리
- 출처: 15장 · DEPLOYMENT · PDF p.118–119
- 태그: [모듈·아키텍처수준]

### 운영 (OPERATION)

**R15-9**
- 규칙: 아키텍처 트레이드오프에서는 운영(하드웨어로 해결 가능)보다 개발·배포·유지보수 비용을 더 무겁게 따져라.
- 근거: 하드웨어는 싸고 사람은 비싸다.
- 출처: 15장 · OPERATION · PDF p.119
- 태그: [모듈·아키텍처수준]

**R15-10**
- 규칙: 유스케이스·기능·필수 동작을 일급 요소(클래스·모듈·패키지)로 만들어, 구조만 봐도 시스템의 운영 의도가 드러나게 하라.
- 근거: 아키텍처는 운영을 드러내야 하며, 유스케이스가 눈에 보이는 랜드마크여야 이해와 유지보수가 쉽다.
- 출처: 15장 · OPERATION · PDF p.119
- 태그: [모듈·아키텍처수준]

### 유지보수 (MAINTENANCE)

**R15-11**
- 규칙: 컴포넌트를 안정된 인터페이스로 분리·격리해 "어디를 고쳐야 하는지 찾는 비용(spelunking)"과 "의도치 않은 파손 위험(risk)"을 줄여라.
- 근거: 유지보수의 주 비용은 탐색과 위험이다.
- 출처: 15장 · MAINTENANCE · PDF p.119–120
- 태그: [모듈·아키텍처수준]

### 선택지 열어 두기 (KEEPING OPTIONS OPEN)

**R15-12**
- 규칙: 코드를 정책(policy: 업무 규칙·절차)과 세부사항(details: IO 장치·DB·웹 시스템·서버·프레임워크·통신 프로토콜)으로 나누고, 정책이 세부사항을 전혀 모르게 하라.
- 근거: 시스템의 진짜 가치는 정책에 있고, 세부사항은 정책의 동작에 영향을 주지 않는다.
- 출처: 15장 · KEEPING OPTIONS OPEN · PDF p.120
- 태그: [모듈·아키텍처수준]

**R15-13**
- 규칙: 상위 정책이 DB 종류(관계형·분산·계층·플랫 파일)를 몰라도 되게 짜서 DB 선택을 미뤄라.
- 근거: 상위 정책은 어떤 DB가 쓰이는지 신경 쓰지 않아야 한다.
- 출처: 15장 · KEEPING OPTIONS OPEN · PDF p.120
- 태그: [모듈·아키텍처수준]

**R15-14**
- 규칙: 상위 정책 코드에 HTML·AJAX·JSP 등 웹 전달 기술을 넣지 마라. 웹 서버·웹 프레임워크 선택(심지어 웹 여부)을 미뤄라.
- 근거: 상위 정책은 자신이 웹으로 전달된다는 사실을 몰라야 한다.
- 출처: 15장 · KEEPING OPTIONS OPEN · PDF p.120
- 태그: [모듈·아키텍처수준]

**R15-15**
- 규칙: REST·마이크로서비스·SOA 프레임워크 채택을 상위 정책이 의존하지 않게 하라. 외부 인터페이스에 대해 정책은 불가지(agnostic)여야 한다.
- 근거: 외부 세계와의 인터페이스 형태는 정책과 무관하다.
- 출처: 15장 · KEEPING OPTIONS OPEN · PDF p.120–121
- 태그: [모듈·아키텍처수준]

**R15-16**
- 규칙: 상위 정책 코드가 DI 프레임워크(어노테이션·컨테이너 API)에 의존하지 않게 하라.
- 근거: 상위 정책은 의존성이 어떻게 해결되는지 신경 쓰지 않아야 한다.
- 출처: 15장 · KEEPING OPTIONS OPEN · PDF p.121
- 태그: [코드수준]

**R15-17**
- 규칙: 세부사항 결정을 늦춰 정보가 더 쌓인 뒤 결정하고, 그 사이 여러 구현(DB 여러 개 등)을 붙여 성능·적합성 실험을 하라.
- 근거: 오래 미룰수록 실험을 더 하고 더 많은 정보로 결정할 수 있다.
- 출처: 15장 · KEEPING OPTIONS OPEN · PDF p.121
- 태그: [모듈·아키텍처수준]

**R15-18**
- 규칙: 회사가 이미 DB·웹 서버·프레임워크를 정했더라도, 그 결정이 아직 안 된 것처럼 구조를 짜서 교체·연기 가능성을 유지하라.
- 근거: 좋은 아키텍트는 내리지 않은 결정의 수를 최대화한다.
- 출처: 15장 · KEEPING OPTIONS OPEN · PDF p.121
- 태그: [모듈·아키텍처수준]

### 장치 독립성 (DEVICE INDEPENDENCE)

**R15-19 (안티패턴: 장치 종속 코드)**
- 규칙: 비즈니스 코드가 IO 장치를 직접 제어하지 말고, 추상 IO 서비스를 호출하게 하라(OCP).
- 근거: 카드 리더 직접 제어 코드는 자기 테이프로 바꿀 때 전부 재작성해야 했다. OS의 추상 단위 레코드 장치 덕에 무수정 교체가 가능해졌다.
- 출처: 15장 · DEVICE INDEPENDENCE · PDF p.121–122
- 태그: [코드수준]

### 정크 메일 (JUNK MAIL)

**R15-20**
- 규칙: IO 추상화에 맞춰 짜서 로컬 장치로 테스트하고 운영에서는 다른 장치로 바꿔 끼워라.
- 근거: 장치 독립성 덕에 라인 프린터로 테스트하고 테이프로 대량 출력했다. 정책(서식)과 세부사항(장치)이 분리됐다.
- 출처: 15장 · JUNK MAIL · PDF p.123
- 태그: [모듈·아키텍처수준]

### 물리 주소 지정 (PHYSICAL ADDRESSING)

**R15-21 (안티패턴: 물리 구조 하드와이어링)**
- 규칙: 업무 규칙에 저장소 물리 구조(실린더·헤드·섹터 등)를 하드코딩하지 마라. 상대 주소 같은 추상을 쓰고, 물리 구조를 아는 작은 변환 루틴 하나에만 지식을 가둬라.
- 근거: 모든 업무 규칙이 물리 구조를 알아 디스크 교체 때 코드 전체를 고쳐야 했다.
- 위반 예 → 개선 예: 업무 코드에 `cylinder/head/sector` 계산 → 선형 섹터 번호 + 변환 함수 1개
- 출처: 15장 · PHYSICAL ADDRESSING · PDF p.123–124
- 태그: [코드수준]

### 결론 (CONCLUSION)

**R15-22**
- 규칙: 정책을 세부사항과 철저히 분리해 정책이 세부사항을 어떤 식으로도 알거나 의존하지 않게 하라.
- 근거: 그래야 세부사항 결정을 최대한 미룰 수 있다.
- 출처: 15장 · CONCLUSION · PDF p.124
- 태그: [모듈·아키텍처수준]

## 16장 독립성 (Independence)

### (도입부)

**R16-1**
- 규칙: 아키텍처가 유스케이스·운영, 유지보수, 개발, 배포 네 가지를 모두 지원하는지 점검하라.
- 근거: 좋은 아키텍처는 이 네 가지를 지원해야 한다.
- 출처: 16장 · 도입부 · PDF p.125
- 태그: [모듈·아키텍처수준]

### 유스케이스 (USE CASES)

**R16-2**
- 규칙: 유스케이스를 최상위 구조에서 보이는 일급 요소(클래스·함수·모듈)로 두고, 기능을 명확히 설명하는 이름을 붙여라.
- 근거: 장바구니 앱은 장바구니 앱처럼 보여야 하고, 개발자가 동작을 찾아 헤매지 않아야 한다.
- 출처: 16장 · USE CASES · PDF p.125–126
- 태그: [모듈·아키텍처수준]

### 운영 (OPERATION)

**R16-3**
- 규칙: 처리량·응답시간 요구를 충족하도록 구조화하되, 컴포넌트 간 통신 수단(스레드·프로세스·서비스)을 가정하지 않게 격리해 나중에 전환할 수 있게 하라.
- 근거: 모놀리스 구조에 의존하는 시스템은 멀티프로세스·멀티스레드·마이크로서비스로 쉽게 업그레이드할 수 없다.
- 출처: 16장 · OPERATION · PDF p.126
- 태그: [모듈·아키텍처수준]

### 개발 (DEVELOPMENT)

**R16-4**
- 규칙: 여러 팀이 서로 간섭하지 않도록 독립 개발 가능한, 잘 격리된 컴포넌트로 분할하고 팀에 할당하라(콘웨이의 법칙, Conway's law).
- 근거: 시스템 구조는 조직의 커뮤니케이션 구조를 닮는다.
- 출처: 16장 · DEVELOPMENT · PDF p.126
- 태그: [모듈·아키텍처수준]

### 배포 (DEPLOYMENT)

**R16-5**
- 규칙: 빌드 직후 즉시 배포 가능하게 만들어라. 수십 개 설정 스크립트, 속성 파일 수정, 수동 디렉터리·파일 생성에 의존하지 마라.
- 근거: 목표는 "즉시 배포"다.
- 출처: 16장 · DEPLOYMENT · PDF p.126–127
- 태그: [모듈·아키텍처수준]

**R16-6**
- 규칙: 각 컴포넌트를 시작·통합·감독하는 마스터 컴포넌트를 둬서 배포를 단순화하라.
- 근거: 적절한 분할·격리 + 전체를 묶는 마스터 컴포넌트가 즉시 배포를 가능하게 한다.
- 출처: 16장 · DEPLOYMENT · PDF p.127
- 태그: [모듈·아키텍처수준]

### 선택지 열어 두기 (LEAVING OPTIONS OPEN)

**R16-7**
- 규칙: 유스케이스·운영 제약·팀 구조·배포 요구를 모두 모르거나 바뀔 것을 전제로, 비용이 싼 분할 원칙(격리된 컴포넌트)을 적용해 선택지를 열어 둬라.
- 근거: 목표는 모호하고 늘 바뀐다. 좋은 아키텍처는 바뀌어야 할 모든 방향으로 쉽게 바뀌게 한다.
- 출처: 16장 · LEAVING OPTIONS OPEN · PDF p.127
- 태그: [모듈·아키텍처수준]

- 태그: [코드수준]

**R17-13**
- 규칙: DB 인터페이스(`DatabaseInterface`)는 업무 규칙 컴포넌트에, 그 구현(`DatabaseAccess`)은 DB 컴포넌트에 두어라. 의존 화살표는 DB → 업무 규칙 방향이어야 한다.
- 근거: 경계는 인터페이스 바로 아래 상속 관계를 가로지른다. 쿼리 언어로 번역하는 코드가 업무 규칙을 안다.
- 위반 예 → 개선 예: `domain` 패키지가 `infra.JpaRepository` import → `domain.OrderRepository` 인터페이스 + `infra.JpaOrderRepository implements` 
- 출처: 17장 · WHICH LINES… · PDF p.137–139
- 태그: [코드수준]

**R17-14**
- 규칙: 다른 클래스들이 DB 구현 클래스의 존재 자체를 모르게 하라. 구현 클래스에서 나가는 화살표만 있게 하라.
- 근거: 화살표가 구현 클래스에서 나가기만 하면 아무도 구현 클래스를 모른다.
- 출처: 17장 · WHICH LINES… · PDF p.138
- 태그: [코드수준]

**R17-15**
- 규칙: DB 결정 전에 업무 규칙을 먼저 작성하고 테스트하라.
- 근거: 업무 규칙이 DB를 모르면 DB 결정을 미루고 업무 규칙에 집중할 수 있다.
- 출처: 17장 · WHICH LINES… · PDF p.139
- 태그: [모듈·아키텍처수준]

### 입력과 출력은? (WHAT ABOUT INPUT AND OUTPUT?)

**R17-16**
- 규칙: GUI를 시스템으로 착각하지 마라. IO는 무관하다(The IO is irrelevant). 모델(업무 규칙)이 인터페이스 없이도 동작하게 만들어라.
- 근거: 게임 모델은 화면에 표시되지 않아도 모든 이벤트를 모델링할 수 있다.
- 출처: 17장 · WHAT ABOUT INPUT AND OUTPUT? · PDF p.139–140
- 태그: [모듈·아키텍처수준]

**R17-17**
- 규칙: GUI 컴포넌트가 업무 규칙 컴포넌트에 의존하게 하라(반대 금지). 덜 중요한 쪽이 더 중요한 쪽에 의존한다.
- 근거: 그래야 GUI를 다른 인터페이스로 바꿔도 업무 규칙은 상관하지 않는다.
- 출처: 17장 · WHAT ABOUT INPUT AND OUTPUT? · PDF p.140
- 태그: [모듈·아키텍처수준]

### 플러그인 아키텍처 (PLUGIN ARCHITECTURE)

**R17-18**
- 규칙: UI와 DB를 핵심 업무 규칙에 꽂는 플러그인으로 설계하라. 선택적이거나 여러 형태로 구현될 수 있는 컴포넌트는 핵심과 독립시켜라.
- 근거: 플러그인 구조를 전제하면 웹·콘솔·SQL·NoSQL 등으로의 교체가 (쉽지 않더라도) 실현 가능해진다.
- 출처: 17장 · PLUGIN ARCHITECTURE · PDF p.140–141
- 태그: [모듈·아키텍처수준]

### 플러그인 논증 (THE PLUGIN ARGUMENT)

**R17-19**
- 규칙: 웹 페이지 형식·DB 스키마 변경이 업무 규칙을 깨지 않도록, 특정 모듈이 다른 모듈에 면역인 비대칭 의존 구조를 만들어라.
- 근거: ReSharper는 Visual Studio에 의존하므로 VS 팀에 영향을 줄 수 없다. 플러그인 구조는 변경이 퍼지지 않는 방화벽이다.

**R17-20**
- 규칙: 변경의 축(axis of change)이 있는 곳에 경계를 그어라. 다른 속도·다른 이유로 바뀌는 것끼리 갈라라(예: GUI↔업무 규칙, 업무 규칙↔DI 프레임워크). SRP가 경계 위치를 알려 준다.
- 근거: 경계 양쪽은 다른 시점·다른 이유로 바뀐다.
- 출처: 17장 · THE PLUGIN ARGUMENT · PDF p.142
- 태그: [모듈·아키텍처수준]

### 결론 (CONCLUSION)

**R17-21**
- 규칙: 시스템을 핵심 업무 규칙 컴포넌트와 플러그인 컴포넌트로 나누고, 컴포넌트 간 모든 화살표가 핵심 업무 쪽 한 방향을 가리키게 하라(DIP·SAP).
- 근거: 의존 화살표는 저수준 세부사항 → 고수준 추상으로 향해야 한다.
- 출처: 17장 · CONCLUSION · PDF p.142–143

## 18장 경계 해부학 (Boundary Anatomy)

### 경계 횡단 (BOUNDARY CROSSING)

**R18-1**
- 규칙: 경계 횡단을 설계할 때 소스 코드 의존성을 관리하는 데 집중하라. 한 모듈 변경이 다른 모듈의 수정·재컴파일·재배포를 강제하지 않게 하라.
- 근거: 런타임 경계 횡단은 함수 호출일 뿐이고, 경계의 목적은 변경에 대한 방화벽이다.
- 출처: 18장 · BOUNDARY CROSSING · PDF p.144
- 태그: [모듈·아키텍처수준]

### 두려운 모놀리스 (THE DREADED MONOLITH)

**R18-2**
- 규칙: 단일 실행 파일(모놀리스)이라도 함수와 데이터의 규율 있는 분리(소스 수준 경계)를 유지하라.
- 근거: 배포에서 경계가 안 보여도 독립 개발·조립 능력은 매우 가치가 있다.
- 출처: 18장 · THE DREADED MONOLITH · PDF p.144–145
- 태그: [모듈·아키텍처수준]

**R18-3**
- 규칙: 모놀리스 내부 의존성 관리는 동적 다형성(인터페이스·추상 클래스)으로 하라. 함수 포인터를 남발해 분리하지 마라.
- 근거: 함수 포인터를 많이 쓰는 것은 위험해서 결국 컴포넌트 분할을 포기하게 된다.
- 출처: 18장 · THE DREADED MONOLITH · PDF p.145
- 태그: [코드수준]

**R18-4**
- 규칙: 정적 다형성(제네릭·템플릿)은 모놀리스 안에서만 의존성 관리 수단으로 쓰고, 재컴파일·재배포로부터 보호가 필요한 경계에는 동적 다형성을 써라.
- 근거: 제네릭에 의한 분리는 동적 다형성처럼 재컴파일·재배포 필요를 막아 주지 못한다. 배포 컴포넌트 경계에서는 정적 다형성을 쓸 수 없다.
- 출처: 18장 · 각주 1·2 · PDF p.148
- 태그: [코드수준]

**R18-5**
- 규칙: 저수준 클라이언트가 고수준 서비스를 호출할 때는 호출되는 쪽(고수준)에 데이터 구조를 정의하라.
- 근거: 런타임 의존과 컴파일타임 의존이 모두 고수준을 향한다. 데이터 정의는 호출되는 쪽에 있다.
- 출처: 18장 · THE DREADED MONOLITH · PDF p.145
- 태그: [코드수준]

**R18-6**
- 규칙: 고수준 클라이언트가 저수준 서비스를 호출해야 하면, 고수준 쪽에 서비스 인터페이스와 데이터 구조를 정의하고 저수준 쪽이 구현하게 해서 제어 흐름과 반대로 의존을 뒤집어라.
- 근거: 동적 다형성으로 런타임 의존과 컴파일타임 의존을 반대로 만들고, 모든 의존이 고수준 쪽으로 경계를 넘는다. 데이터 구조는 호출하는 쪽에 정의된다.
- 위반 예 → 개선 예: `OrderService`가 `SmtpMailer`를 직접 생성 → `OrderService`가 소유한 `Notifier` 인터페이스 + 인프라의 `SmtpNotifier implements Notifier`
- 출처: 18장 · THE DREADED MONOLITH · PDF p.145–146
- 태그: [코드수준]

**R18-7**
- 규칙: 소스 수준 경계 간 통신은 싼 함수 호출이므로 잦은 호출(chatty)이 허용된다. 모놀리스 컴포넌트는 소스 코드로 전달된다는 점을 감안하라.
- 근거: 모놀리스 컴포넌트 간 통신은 매우 빠르고 싸다.
- 출처: 18장 · THE DREADED MONOLITH · PDF p.146
- 태그: [모듈·아키텍처수준]

### 배포 컴포넌트 (DEPLOYMENT COMPONENTS)

**R18-8**
- 규칙: 배포 수준 경계(DLL·jar·Gem·공유 라이브러리)에서도 모놀리스와 같은 분리·의존성 관리 전략을 적용하라. 함수 호출 기반이므로 잦은 통신이 가능하다.
- 근거: 배포 컴포넌트는 컴파일 없이 바이너리로 전달된다는 점만 빼면 모놀리스와 같다.
- 출처: 18장 · DEPLOYMENT COMPONENTS · PDF p.146–147
- 태그: [모듈·아키텍처수준]

### 스레드 (THREADS)

**R18-9**
- 규칙: 스레드를 아키텍처 경계나 배포 단위로 취급하지 마라. 스레드는 실행 일정과 순서를 조직하는 수단이다.
- 근거: 스레드는 한 컴포넌트 안에 있을 수도, 여러 컴포넌트에 걸칠 수도 있다.
- 출처: 18장 · THREADS · PDF p.147
- 태그: [모듈·아키텍처수준]

### 로컬 프로세스 (LOCAL PROCESSES)

**R18-10**
- 규칙: 로컬 프로세스 경계에서도 소스 의존은 항상 고수준 프로세스 쪽을 향하게 하라. 고수준 프로세스 소스에 저수준 프로세스의 이름·물리 주소·레지스트리 조회 키를 넣지 마라.
- 근거: 저수준 프로세스는 고수준 프로세스의 플러그인이어야 한다.
- 출처: 18장 · LOCAL PROCESSES · PDF p.147
- 태그: [모듈·아키텍처수준]

**R18-11**
- 규칙: 로컬 프로세스 간 통신은 OS 호출·마샬링·컨텍스트 스위치로 비용이 꽤 들므로 호출 횟수(chattiness)를 신중히 제한하라.
- 근거: 프로세스 간 통신은 적당히 비싸다.
- 출처: 18장 · LOCAL PROCESSES · PDF p.147
- 태그: [모듈·아키텍처수준]

### 서비스 (SERVICES)

**R18-12**
- 규칙: 서비스 경계에서는 모든 통신이 네트워크로 일어나고 지연이 크다(수십 ms~초)고 가정하고, 잦은 호출을 피하라.
- 근거: 서비스 경계 통신은 함수 호출보다 매우 느리다.
- 출처: 18장 · SERVICES · PDF p.147–148
- 태그: [모듈·아키텍처수준]

**R18-13**
- 규칙: 저수준 서비스는 고수준 서비스에 "꽂히게" 하고, 고수준 서비스 소스에 저수준 서비스의 물리적 정보(URI 등)를 하드코딩하지 마라.
- 근거: 로컬 프로세스와 같은 규칙이 서비스에도 적용된다.
- 위반 예 → 개선 예: 도메인 서비스에 `"http://billing-svc/charge"` 문자열 → 고수준이 정의한 포트 인터페이스 + 설정/어댑터에서 URI 주입
- 출처: 18장 · SERVICES · PDF p.148
- 태그: [코드수준]

### 결론 (CONCLUSION)

**R18-14**
- 규칙: 한 시스템 안에 경계 전략이 섞여 있음을 전제하고, 경계마다 잦은 통신이 허용되는 로컬 경계인지 지연을 고려해야 하는 경계인지 구분해 설계하라.
- 근거: 서비스는 대개 로컬 프로세스들의 파사드이고, 그 안은 소스 컴포넌트나 배포 컴포넌트로 이뤄진다.
- 출처: 18장 · CONCLUSION · PDF p.148
- 태그: [모듈·아키텍처수준]

## 19장 정책과 수준 (Policy and Level)

### (도입부)

**R19-1**
- 규칙: 프로그램을 여러 작은 정책(업무 규칙 계산·보고서 서식·입력 검증 등)으로 나누고, 같은 이유·같은 시점에 바뀌는 정책끼리 같은 컴포넌트에, 다른 것은 다른 컴포넌트에 둬라.
- 근거: 같은 이유·시점에 바뀌는 정책은 같은 수준에 있다.
- 출처: 19장 · 도입부 · PDF p.149
- 태그: [모듈·아키텍처수준]

**R19-2**
- 규칙: 컴포넌트 의존 그래프를 방향성 비순환 그래프(DAG)로 유지하라(순환 의존 금지).
- 근거: 노드는 같은 수준 정책의 컴포넌트, 간선은 다른 수준을 잇는 소스 의존이다.
- 출처: 19장 · 도입부 · PDF p.149
- 태그: [모듈·아키텍처수준]

**R19-3**
- 규칙: import/using/require 같은 컴파일타임 소스 의존의 방향을 컴포넌트 수준에 맞춰라. 저수준 컴포넌트가 고수준 컴포넌트에 의존하게 하라.
- 근거: 좋은 아키텍처에서 의존 방향은 연결하는 컴포넌트의 수준으로 결정된다.
- 출처: 19장 · 도입부 · PDF p.149–150
- 태그: [코드수준]

### 수준 (LEVEL)

**R19-4**
- 규칙: 정책의 수준을 "입력·출력으로부터의 거리"로 판단하라. IO를 다루는 정책은 가장 낮은 수준이다.
- 근거: 입출력에서 멀수록 수준이 높다.
- 출처: 19장 · LEVEL · PDF p.150
- 태그: [모듈·아키텍처수준]

**R19-5**
- 규칙: 소스 의존 방향을 데이터 흐름이 아니라 수준에 맞춰라.
- 근거: 데이터 흐름과 소스 의존이 항상 같은 방향일 필요는 없다.
- 출처: 19장 · LEVEL · PDF p.150
- 태그: [모듈·아키텍처수준]

**R19-6 (안티패턴: 고수준 함수가 저수준 IO 함수를 직접 호출)**
- 규칙: 고수준 함수가 저수준 IO 함수(readChar·writeChar 등)를 직접 호출하지 않게 하라. 고수준 쪽이 소유한 입출력 인터페이스(CharReader·CharWriter)를 통해 접근하고, 콘솔 구현은 그 인터페이스를 구현하게 하라.
- 근거: 고수준 encrypt가 저수준 함수에 의존하면 잘못된 아키텍처다. 인터페이스를 두면 경계를 넘는 모든 의존이 안쪽을 향한다.
- 위반 예 → 개선 예: `encrypt(){ while(true) writeChar(translate(readChar())); }` → `Encrypt(CharReader r, CharWriter w)` + `ConsoleReader/ConsoleWriter`가 구현
- 출처: 19장 · LEVEL · PDF p.150–151
- 태그: [코드수준]

**R19-7**
- 규칙: 자주·급하게 바뀌지만 덜 중요한 저수준 정책(IO)의 변경이 드물게·중요한 이유로 바뀌는 고수준 정책에 영향을 주지 않도록, 모든 소스 의존을 고수준 쪽으로 향하게 하라.
- 근거: 하찮지만 급한 저수준 변경이 상위의 중요한 수준에 거의 영향을 주지 않게 된다.
- 출처: 19장 · LEVEL · PDF p.151
- 태그: [모듈·아키텍처수준]

**R19-8**
- 규칙: 저수준 컴포넌트를 고수준 컴포넌트의 플러그인으로 만들어라. 고수준 컴포넌트(Encryption)는 저수준 컴포넌트(IODevices)를 전혀 모르게 하라.
- 근거: 고수준 정책을 다양한 맥락에서 재사용할 수 있게 된다.
- 출처: 19장 · LEVEL · PDF p.151–152
- 태그: [모듈·아키텍처수준]

### 결론 (CONCLUSION)

**R19-9**
- 규칙: 정책 분리 설계를 리뷰할 때 SRP·OCP·CCP·DIP·SDP·SAP 중 어떤 원칙이 어디에 적용됐는지 식별해 근거로 남겨라.
- 근거: 이 장의 논의는 이 원칙들의 혼합이다.
- 출처: 19장 · CONCLUSION · PDF p.152
- 태그: [모듈·아키텍처수준]

## 20장 업무 규칙 (Business Rules)

### (도입부)

**R20-1**
- 규칙: 자동화 여부와 무관하게 돈을 벌거나 아끼는 규칙(핵심 업무 규칙, Critical Business Rules)과 그 규칙이 쓰는 데이터(핵심 업무 데이터, Critical Business Data)를 식별해 다른 코드와 구분하라.
- 근거: 이자율 계산은 컴퓨터든 주판이든 존재하는 규칙이다.

**R20-2**

**R20-3**

**R20-4**

- 근거: 유스케이스는 사용자 입력·출력·처리 단계를 명세하는 애플리케이션 특화 규칙이다.

**R20-6**

- 근거: 유스케이스는 엔티티의 춤을 통제한다.

- 태그: [코드수준]

**R20-7**
- 규칙: 유스케이스 코드에 UI 표현 방식(웹·씩 클라이언트·콘솔·서비스)을 넣지 마라. 들어오고 나가는 데이터만 다뤄라.
- 근거: 유스케이스만 보고는 전달 방식을 알 수 없어야 한다. 데이터 입출력 방식은 유스케이스와 무관하다.

- 태그: [코드수준]

**R20-8**
- 규칙: 유스케이스를 객체로 구현하라. 애플리케이션 특화 규칙을 구현하는 함수와 입력·출력 데이터, 상호작용할 엔티티 참조를 가져라.
- 근거: 유스케이스는 객체다.

- 근거: 엔티티는 여러 애플리케이션에서 쓰이는 일반화라 IO에서 더 멀어 고수준이고, 유스케이스는 단일 애플리케이션 특화라 저수준이다(DIP).

- 근거: 모델이 의존성을 가지면 그것을 쓰는 유스케이스가 간접적으로 그 의존성에 묶인다.

- 근거: 두 객체의 목적은 다르고 다른 이유로 바뀌므로 묶으면 CCP·SRP 위반이며, 떠돌이 데이터(tramp data)와 조건문이 늘어난다.

## 21장 소리치는 아키텍처 (Screaming Architecture)

### (도입부)

**R21-1**
- 규칙: 최상위 디렉터리 구조와 최상위 패키지의 소스 파일 이름이 프레임워크(Rails·Spring/Hibernate·ASP)가 아니라 도메인("의료 시스템", "회계 시스템", "재고 관리")을 드러내게 하라.
- 근거: 건물 설계도가 "집"·"도서관"을 외치듯 소프트웨어 구조도 용도를 외쳐야 한다.
- 위반 예 → 개선 예: `src/controllers, src/models, src/views` → `src/patient, src/billing, src/appointment` (그 안에서 계층 분리)
- 출처: 21장 · 도입부 · PDF p.158
- 태그: [모듈·아키텍처수준]

### 아키텍처의 주제 (THE THEME OF AN ARCHITECTURE)

**R21-2**
- 규칙: 아키텍처를 유스케이스를 지원하는 구조로 만들고, 프레임워크가 아키텍처를 공급하게 두지 마라. 프레임워크는 쓰는 도구이지 따라야 할 아키텍처가 아니다.
- 근거: 아키텍처가 프레임워크 기반이면 유스케이스 기반일 수 없다.
- 출처: 21장 · THE THEME OF AN ARCHITECTURE · PDF p.158–159
- 태그: [모듈·아키텍처수준]

### 아키텍처의 목적 (THE PURPOSE OF AN ARCHITECTURE)

**R21-3**
- 규칙: 유스케이스 중심으로 구조를 설계하고 프레임워크·DB·웹 서버·도구 결정을 미루고 쉽게 바꿀 수 있게 하라. 유스케이스를 주변 관심사에서 분리하라.
- 근거: 집 설계자는 벽돌 여부보다 쓸모를 먼저 보장하고 외장재 결정은 미룬다.
- 출처: 21장 · THE PURPOSE OF AN ARCHITECTURE · PDF p.159
- 태그: [모듈·아키텍처수준]

### 웹은? (BUT WHAT ABOUT THE WEB?)

**R21-4**
- 규칙: 웹을 전달 메커니즘(IO 장치)인 세부사항으로 취급하라. 시스템 구조를 웹이 지배하지 않게 하고, 콘솔·웹·씩 클라이언트·웹 서비스 어느 것으로든 근본 구조 변경 없이 전달할 수 있게 하라.
- 근거: 웹 전달 여부는 미뤄야 할 결정이며, 시스템은 전달 방식에 최대한 무지해야 한다.
- 출처: 21장 · BUT WHAT ABOUT THE WEB? · PDF p.159
- 태그: [모듈·아키텍처수준]

### 프레임워크는 도구일 뿐 (FRAMEWORKS ARE TOOLS, NOT WAYS OF LIFE)

**R21-5 (안티패턴: 프레임워크가 다 하게 두기)**
- 규칙: 프레임워크 문서의 "프레임워크가 모든 것을 하게 하라"는 방식을 그대로 따르지 마라. 채택 시 비용과 자신을 프레임워크로부터 보호하는 방법을 먼저 정하고, 프레임워크가 아키텍처를 장악하지 못하게 하는 전략을 세워라.
- 근거: 프레임워크 저자·전도사의 예제는 신봉자 관점이다. 회의적으로 봐야 한다.
- 출처: 21장 · FRAMEWORKS ARE TOOLS, NOT WAYS OF LIFE · PDF p.159–160
- 태그: [모듈·아키텍처수준]

### 테스트 가능한 아키텍처 (TESTABLE ARCHITECTURES)

**R21-6**
- 규칙: 웹 서버나 DB 연결 없이 모든 유스케이스를 단위 테스트할 수 있게 하라.
- 근거: 유스케이스 중심이고 프레임워크를 떨어뜨려 두었다면 프레임워크 없이 테스트할 수 있어야 한다.
- 출처: 21장 · TESTABLE ARCHITECTURES · PDF p.160
- 태그: [코드수준]

**R21-7**
- 규칙: 엔티티는 프레임워크·DB 의존이 없는 순수 객체(plain old object)로 만들고, 유스케이스 객체가 엔티티를 조율하게 하라. 둘을 합쳐 프레임워크 없이 그 자리에서 테스트할 수 있어야 한다.
- 근거: 테스트 가능성이 아키텍처 품질을 검증한다.
- 출처: 21장 · TESTABLE ARCHITECTURES · PDF p.160
- 태그: [코드수준]

### 결론 (CONCLUSION)

**R21-8**
- 규칙: 새 개발자가 저장소를 보고 전달 방식(뷰·컨트롤러)을 몰라도 시스템의 모든 유스케이스를 파악할 수 있게 구조를 짜라.
- 근거: 아키텍처는 사용한 프레임워크가 아니라 시스템에 대해 말해야 한다.
- 출처: 21장 · CONCLUSION · PDF p.160
- 태그: [모듈·아키텍처수준]

## 22장 클린 아키텍처 (The Clean Architecture)

### (도입부)

**R22-1**
- 규칙: 최소한 업무 규칙 계층 하나와 사용자·시스템 인터페이스 계층 하나로 나눠 관심사를 분리하라(헥사고날/포트와 어댑터, DCI, BCE의 공통 원리).
- 근거: 이 아키텍처들은 모두 계층 분리로 관심사 분리를 달성한다.
- 출처: 22장 · 도입부 · PDF p.161
- 태그: [모듈·아키텍처수준]

**R22-2**
- 규칙: 결과 시스템이 프레임워크 독립·테스트 가능(UI·DB·웹 서버 없이 업무 규칙 테스트)·UI 독립·DB 독립·외부 기관 독립의 다섯 특성을 갖는지 검사하라.
- 근거: 이 특성들이 클린 아키텍처의 목표다.
- 출처: 22장 · 도입부 · PDF p.161–162
- 태그: [모듈·아키텍처수준]

### 의존성 규칙 (THE DEPENDENCY RULE)

**R22-3**
- 규칙: 소스 코드 의존성은 오직 안쪽(고수준 정책)으로만 향하게 하라.
- 근거: 의존성 규칙(Dependency Rule)이 이 아키텍처를 작동시키는 최우선 규칙이다. 바깥 원은 메커니즘, 안쪽 원은 정책이다.
- 출처: 22장 · THE DEPENDENCY RULE · PDF p.162
- 태그: [모듈·아키텍처수준]

**R22-4**
- 규칙: 안쪽 원의 코드에서 바깥 원에 선언된 이름(함수·클래스·변수 등 어떤 명명 요소든)을 언급하지 마라.
- 근거: 안쪽 원은 바깥 원에 대해 아무것도 몰라야 한다.
- 위반 예 → 개선 예: 유스케이스가 `import org.springframework.web...`, `import ...infra.UserJpaEntity` → 이런 import 0건
- 출처: 22장 · THE DEPENDENCY RULE · PDF p.162
- 태그: [코드수준]

**R22-5**
- 규칙: 바깥 원에서 선언된 데이터 형식, 특히 바깥 프레임워크가 생성한 형식을 안쪽 원에서 쓰지 마라.
- 근거: 바깥의 어떤 것도 안쪽에 영향을 주면 안 된다.
- 출처: 22장 · THE DEPENDENCY RULE · PDF p.162
- 태그: [코드수준]

**R22-6 (엔티티 계층)**
- 규칙: 엔티티에는 전사적 핵심 업무 규칙만 담고, 페이지 내비게이션·보안 같은 애플리케이션 운영 변경이 엔티티 계층에 영향을 주지 않게 하라. 단일 앱이면 엔티티는 그 앱의 업무 객체다.
- 근거: 엔티티는 가장 일반적·고수준 규칙이며 외부 변경에 가장 덜 바뀐다.
- 출처: 22장 · ENTITIES · PDF p.162–163
- 태그: [모듈·아키텍처수준]

**R22-7 (유스케이스 계층)**
- 규칙: 유스케이스 계층에 애플리케이션 특화 업무 규칙을 두고 엔티티로의 데이터 흐름을 조율하게 하라. 이 계층의 변경이 엔티티에 영향을 주지 않고, DB·UI·프레임워크 변경이 이 계층에 영향을 주지 않게 격리하라.
- 근거: 애플리케이션 동작 변경만이 유스케이스 계층을 바꿔야 한다.
- 출처: 22장 · USE CASES · PDF p.163
- 태그: [모듈·아키텍처수준]

**R22-8 (인터페이스 어댑터 계층)**
- 규칙: 프레젠터·뷰·컨트롤러(MVC 전체)와 영속성 변환, 외부 서비스 형식 변환을 인터페이스 어댑터 계층에 두어라. 모델은 컨트롤러→유스케이스→프레젠터·뷰로 전달되는 데이터 구조로 둬라.
- 근거: 이 계층은 유스케이스·엔티티에 편한 형식과 외부(DB·웹)에 편한 형식을 상호 변환한다.
- 출처: 22장 · INTERFACE ADAPTERS · PDF p.163
- 태그: [모듈·아키텍처수준]

**R22-9**
- 규칙: SQL은 인터페이스 어댑터 계층 중 DB 관련 부분에만 둬라. 그 안쪽 코드는 DB에 대해 아무것도 몰라야 한다.
- 근거: 이 원 안쪽은 DB를 전혀 몰라야 한다.
- 출처: 22장 · INTERFACE ADAPTERS · PDF p.163
- 태그: [코드수준]

**R22-10 (프레임워크와 드라이버 계층)**
- 규칙: 프레임워크·DB·웹 같은 세부사항은 최외곽 계층에 두고, 그 계층에는 안쪽 원과 통신하는 접착 코드(glue code)만 작성하라.
- 근거: 세부사항을 바깥에 두어야 해를 덜 끼친다.
- 출처: 22장 · FRAMEWORKS AND DRIVERS · PDF p.163–164
- 태그: [모듈·아키텍처수준]

### 원은 네 개뿐인가? (ONLY FOUR CIRCLES?)

**R22-11**
- 규칙: 계층 수는 필요에 따라 늘려도 되지만 의존성 규칙은 언제나 지켜라. 안쪽일수록 추상적·고수준, 바깥일수록 저수준 구체 세부사항이 되게 하라.
- 근거: 원 그림은 도식일 뿐이고 의존성 규칙만은 항상 적용된다.
- 출처: 22장 · ONLY FOUR CIRCLES? · PDF p.164
- 태그: [모듈·아키텍처수준]

### 경계 넘기 (CROSSING BOUNDARIES)

**R22-12**
- 규칙: 유스케이스가 프레젠터를 호출해야 하면 직접 호출하지 말고, 유스케이스 계층에 출력 포트(use case output port) 인터페이스를 정의하고 바깥의 프레젠터가 구현하게 하라.
- 근거: 직접 호출은 의존성 규칙 위반이다. DIP로 소스 의존을 제어 흐름과 반대로 만든다.
- 위반 예 → 개선 예: `interactor`가 `new WebPresenter()` 호출 → `interactor`는 `OutputBoundary` 호출, `WebPresenter implements OutputBoundary`
- 출처: 22장 · CROSSING BOUNDARIES · PDF p.164
- 태그: [코드수준]

**R22-13**
- 규칙: 제어 흐름이 어느 방향이든, 모든 경계 횡단에 동적 다형성(인터페이스·상속)을 써서 소스 의존이 안쪽을 향하게 하라.
- 근거: 같은 기법이 모든 경계에 쓰인다.
- 출처: 22장 · CROSSING BOUNDARIES · PDF p.164
- 태그: [코드수준]

### 경계를 넘는 데이터 (WHICH DATA CROSSES THE BOUNDARIES)

**R22-14**
- 규칙: 경계를 넘는 데이터는 격리된 단순 데이터 구조(struct·DTO·함수 인자·해시맵 등)로 하라. 엔티티 객체나 DB 행(row)을 넘기지 마라.
- 근거: 데이터 구조가 의존성 규칙을 어기는 의존을 가지면 안 된다.
- 출처: 22장 · WHICH DATA CROSSES THE BOUNDARIES · PDF p.164
- 태그: [코드수준]

**R22-15**
- 규칙: DB 프레임워크가 반환하는 행 구조(row structure, ResultSet·ORM 레코드)를 경계 안쪽으로 넘기지 마라.
- 근거: 안쪽 원이 바깥 원의 무언가를 알게 되어 의존성 규칙을 어긴다.
- 출처: 22장 · WHICH DATA CROSSES THE BOUNDARIES · PDF p.165
- 태그: [코드수준]

**R22-16**
- 규칙: 경계를 넘는 데이터는 항상 안쪽 원에 가장 편한 형식으로 만들어라.
- 근거: 안쪽이 형식을 소유해야 의존 방향이 지켜진다.
- 출처: 22장 · WHICH DATA CROSSES THE BOUNDARIES · PDF p.165
- 태그: [코드수준]

### 전형적인 시나리오 (A TYPICAL SCENARIO)

**R22-17**
- 규칙: 웹 요청 흐름을 "Controller가 입력을 순수 객체로 포장 → InputBoundary → UseCaseInteractor가 엔티티 조율 + DataAccessInterface로 데이터 적재 → OutputData(순수 객체) → OutputBoundary → Presenter → ViewModel → View" 구조로 구현하라.
- 근거: 이 흐름에서 모든 의존이 경계를 안쪽으로 넘는다.

## 23장 프레젠터와 험블 객체 (Presenters and Humble Objects)

### 험블 객체 패턴 (THE HUMBLE OBJECT PATTERN)

**R23-1**
- 규칙: 테스트하기 어려운 동작과 쉬운 동작을 두 모듈로 나눠라. 험블(humble) 쪽에는 테스트하기 어려운 동작만 최소한으로 남기고, 나머지 테스트 가능한 동작은 모두 다른 쪽으로 옮겨라.
- 근거: 험블 객체 패턴(Humble Object pattern)은 테스트 용이성을 위해 동작을 분리한다.
- 출처: 23장 · THE HUMBLE OBJECT PATTERN · PDF p.167
- 태그: [코드수준]

### 프레젠터와 뷰 (PRESENTERS AND VIEWS)

**R23-2**
- 규칙: 뷰(View)는 데이터를 GUI로 옮기기만 하고 데이터를 가공하지 않게 최대한 단순하게 유지하라.
- 근거: 뷰는 테스트하기 어려운 험블 객체다.
- 출처: 23장 · PRESENTERS AND VIEWS · PDF p.167–168
- 태그: [코드수준]

**R23-3**
- 규칙: 프레젠터(Presenter)가 애플리케이션 데이터를 받아 화면용으로 서식화해 뷰 모델(View Model)에 넣게 하라. 날짜→문자열, 통화→소수점·통화기호가 붙은 문자열, 음수면 빨간색 같은 표시 조건→boolean 플래그로 바꿔라.
- 근거: 프레젠터는 테스트 가능한 객체이므로 서식 로직을 여기에 모은다.
- 출처: 23장 · PRESENTERS AND VIEWS · PDF p.168
- 태그: [코드수준]

**R23-4**
- 규칙: 화면에 나타나고 애플리케이션이 제어하는 모든 것(버튼·메뉴·라디오·체크박스·텍스트 필드 이름, 비활성화 여부, 표의 숫자)을 뷰 모델의 문자열·boolean·enum으로 표현하라. 뷰에는 뷰 모델을 화면에 싣는 일만 남겨라.
- 근거: 그래야 뷰가 험블해지고 나머지는 모두 테스트 가능해진다.
- 위반 예 → 개선 예: 컴포넌트 안에서 `price.toFixed(2)`·`disabled={user.role!=='admin' && order.status==='CLOSED'}` 계산 → 프레젠터/셀렉터가 `priceText`, `isSubmitDisabled` 제공
- 출처: 23장 · PRESENTERS AND VIEWS · PDF p.168
- 태그: [코드수준]

### 테스트와 아키텍처 (TESTING AND ARCHITECTURE)

**R23-5**
- 규칙: 테스트 가능한 부분과 불가능한 부분이 갈리는 곳을 아키텍처 경계 후보로 삼아라.
- 근거: 테스트 용이성은 좋은 아키텍처의 속성이며, 그 분리가 종종 아키텍처 경계를 정의한다.
- 출처: 23장 · TESTING AND ARCHITECTURE · PDF p.168
- 태그: [모듈·아키텍처수준]

### 데이터베이스 게이트웨이 (DATABASE GATEWAYS)

**R23-6**
- 규칙: 유스케이스 인터랙터와 DB 사이에, 애플리케이션이 DB에 수행하는 모든 CRUD 연산마다 의도를 드러내는 메서드를 가진 다형적 게이트웨이 인터페이스를 둬라(예: `UserGateway.getLastNamesOfUsersWhoLoggedInAfter(Date)`).
- 근거: 유스케이스 계층에는 SQL을 허용하지 않는다.
- 출처: 23장 · DATABASE GATEWAYS · PDF p.168
- 태그: [코드수준]

**R23-7**
- 규칙: 게이트웨이 구현(DB 계층)은 SQL 등으로 데이터를 가져오는 험블 객체로 만들고, 인터랙터는 게이트웨이를 스텁·테스트 더블로 바꿔 테스트하라.
- 근거: 인터랙터는 업무 규칙을 담아 험블하지 않지만 게이트웨이 교체로 테스트 가능하다.
- 출처: 23장 · DATABASE GATEWAYS · PDF p.168–169
- 태그: [코드수준]

### 데이터 매퍼 (DATA MAPPERS)

**R23-8**
- 규칙: ORM을 객체-관계 매핑이 아니라 "테이블 → 데이터 구조로 적재하는 데이터 매퍼(data mapper)"로 취급하고, DB 계층(게이트웨이 인터페이스와 DB 사이의 험블 객체 경계)에 둬라.
- 근거: 객체는 사용자에게 연산의 집합이고, 데이터 구조는 동작 없는 공개 데이터다. ORM은 후자를 다룬다.
- 위반 예 → 개선 예: 도메인 엔티티에 `@Entity`/`@Table` → DB 계층에 영속 모델(JPA 엔티티) 별도, 게이트웨이 구현이 매핑
- 출처: 23장 · DATA MAPPERS · PDF p.169
- 태그: [코드수준]

### 서비스 리스너 (SERVICE LISTENERS)

**R23-9**
- 규칙: 외부 서비스와 통신할 때 애플리케이션은 단순 데이터 구조만 경계 너머로 넘기고, 경계 바깥 모듈이 서식화·전송을 맡게 하라. 입력 쪽에서는 서비스 리스너가 받은 데이터를 애플리케이션용 단순 데이터 구조로 변환해 넘기게 하라.
- 근거: 서비스 경계에도 험블 객체 패턴이 적용된다.
- 출처: 23장 · SERVICE LISTENERS · PDF p.169
- 태그: [코드수준]

### 결론 (CONCLUSION)

**R23-10**
- 규칙: 각 아키텍처 경계에서 단순 데이터 구조로 통신하고 테스트 어려운 것과 쉬운 것을 갈라 험블 객체 패턴을 적용하라.
- 근거: 경계에서의 험블 객체 패턴은 시스템 전체의 테스트 용이성을 크게 높인다.
- 출처: 23장 · CONCLUSION · PDF p.169
- 태그: [모듈·아키텍처수준]

## 24장 부분적 경계 (Partial Boundaries)

### (도입부)

**R24-1**
- 규칙: 완전한 아키텍처 경계(상호 다형 Boundary 인터페이스, 입출력 데이터 구조, 독립 컴파일·배포 의존성 관리)는 비싸다는 점을 인지하고, 비용이 너무 크지만 자리만은 남겨 두고 싶을 때 부분적 경계(partial boundary)를 고려하라.
- 근거: 완전한 경계는 구축·유지 비용이 크고, YAGNI와 "필요할지도"의 균형이 필요하다.
- 출처: 24장 · 도입부 · PDF p.171
- 태그: [모듈·아키텍처수준]

### 마지막 단계 건너뛰기 (SKIP THE LAST STEP)

**R24-2**
- 규칙: 독립 컴파일·배포에 필요한 인터페이스·입출력 데이터 구조를 모두 갖추되, 하나의 컴포넌트로 함께 컴파일·배포해 다중 컴포넌트 관리(버전 추적·릴리스 관리)를 생략하는 방식을 선택지로 써라.
- 근거: 코드량은 완전한 경계와 같지만 여러 컴포넌트 관리 부담이 없다.
- 출처: 24장 · SKIP THE LAST STEP · PDF p.171–172
- 태그: [모듈·아키텍처수준]

**R24-3 (위험: 부분 경계의 퇴화)**
- 규칙: 부분적 경계를 둔 경우 잘못된 방향의 의존이 선을 넘지 않는지 주기적으로 점검(가능하면 자동 검사)하라.
- 근거: FitNesse에서 분리 필요가 없어지자 의존이 잘못된 방향으로 넘어오기 시작했고 재분리가 어려워졌다.
- 출처: 24장 · SKIP THE LAST STEP · PDF p.172
- 태그: [모듈·아키텍처수준]

### 일차원 경계 (ONE-DIMENSIONAL BOUNDARIES)

**R24-4**

- 근거: 의존성 역전이 이미 갖춰져 있어 클라이언트와 구현이 격리된다.

**R24-5 (안티패턴: 역방향 백채널)**
- 규칙: 일차원 경계에서는 구현 쪽이 클라이언트를 직접 참조하는 백채널(backchannel)이 생기지 않는지 리뷰로 감시하라.

**R24-6**

### (도입부)

**R25-1**

**R25-5**

**R25-6**

**R25-7**

- 근거: Main은 시스템의 진입점이자 가장 지저분한 컴포넌트다.
- 출처: 26장 · THE ULTIMATE DETAIL · PDF p.181
- 태그: [모듈·아키텍처수준]

**R26-3**
- 규칙: DI 프레임워크를 쓴다면 의존성 주입은 Main 컴포넌트에서만 하고, Main 이후로는 프레임워크 없이 평범하게(생성자 인자 등) 의존성을 분배하라.
- 근거: 프레임워크 의존을 최외곽에 가둔다.

- 출처: 26장 · THE ULTIMATE DETAIL · PDF p.181
- 태그: [코드수준]

**R26-4**
- 규칙: 본체 코드가 알 필요 없는 문자열·설정 값(환경·이름 목록 등)은 Main에 모아 적재하라.
- 근거: Main 예시는 본체가 몰라야 할 문자열을 모두 Main에 둔다.

- 근거: `HtwFactory.makeGame("htw.game.HuntTheWumpusFacade", ...)`처럼 클래스 이름을 넘겨 의존을 끊는다.

**R26-6**
- 규칙: Main은 입력 스트림 생성·메인 루프·단순 입력 해석·초기 상태(맵 등) 구성까지만 하고, 실제 처리는 모두 고수준 컴포넌트에 위임하라.
- 근거: Main은 모든 것을 적재한 뒤 제어를 고수준 시스템에 넘기는 저수준 모듈이다.
- 출처: 26장 · THE ULTIMATE DETAIL · PDF p.183–184
- 태그: [코드수준]

### 결론 (CONCLUSION)

**R26-7**
- 규칙: Main을 애플리케이션의 플러그인으로 보고, 설정별로 여러 Main(Dev·Test·Production, 국가·관할·고객별)을 둬서 환경 구성 문제를 해결하라.
- 근거: Main을 경계 뒤의 플러그인으로 보면 구성 문제가 훨씬 쉬워진다.
- 위반 예 → 개선 예: 업무 코드 곳곳의 `if (env == "prod")` → 환경별 진입점/구성 모듈이 다른 구현을 조립
- 출처: 26장 · CONCLUSION · PDF p.184

### 서비스의 이점? — 결합 분리 오류 (THE DECOUPLING FALLACY)

**R27-3**
- 규칙: 서비스 간 공유 데이터 레코드(필드 추가·해석)가 서비스들을 강하게 결합시킨다는 점을 설계에 반영하라. 공유 자원(프로세서·네트워크) 결합도 고려하라.
- 근거: 레코드에 필드를 추가하면 그 필드를 쓰는 모든 서비스가 바뀌어야 하고, 해석에 강하게 합의해야 한다.
- 출처: 27장 · THE DECOUPLING FALLACY · PDF p.186
- 태그: [모듈·아키텍처수준]

**R27-4**
- 규칙: 서비스 인터페이스가 함수 인터페이스보다 더 엄격하다고 가정하지 마라.
- 근거: 서비스 인터페이스는 함수 인터페이스보다 더 형식적이지도, 엄밀하지도, 잘 정의되지도 않는다.
- 출처: 27장 · THE DECOUPLING FALLACY · PDF p.186
- 태그: [모듈·아키텍처수준]

### 독립 개발·배포 오류 (THE FALLACY OF INDEPENDENT DEVELOPMENT AND DEPLOYMENT)

**R27-5**
- 규칙: 확장성을 위해 반드시 서비스로 가야 한다고 보지 마라. 데이터·동작으로 결합된 서비스는 개발·배포·운영을 조율해야 한다는 점을 계획에 포함하라.
- 근거: 대형 시스템은 모놀리스·컴포넌트 기반으로도 만들어졌고, 결합된 만큼 조율이 필요하다.
- 출처: 27장 · THE FALLACY OF INDEPENDENT DEVELOPMENT AND DEPLOYMENT · PDF p.186–187
- 태그: [모듈·아키텍처수준]

### 고양이 문제 (THE KITTY PROBLEM)

**R27-6 (안티패턴: 기능 분해식 서비스 분할 + 횡단 관심사)**
- 규칙: 서비스(또는 모듈)를 기능 단계별(Finder·Selector·Dispatcher 등)로만 쪼개지 마라. 새 기능이 모든 단계를 가로지르면 모든 서비스를 동시에 고쳐야 한다.
- 근거: 새끼 고양이 배달 기능 하나로 모든 서비스가 바뀌어야 했고, 개발·배포를 정밀하게 조율해야 했다.
- 출처: 27장 · THE KITTY PROBLEM · PDF p.187–188
- 태그: [모듈·아키텍처수준]

**R27-7 (안티패턴: 마이크로서비스 수 ≈ 개발자 수)**
- 규칙: 팀·개발자 수에 맞춰 마이크로서비스 수를 정하지 마라.
- 근거: 작은 팀마다 서비스를 맡기면 서비스 수가 개발자 수와 비슷해지는 풍자적 결과가 된다.
- 출처: 27장 · THE KITTY PROBLEM · 각주 1 · PDF p.187, PDF p.191
- 태그: [모듈·아키텍처수준]

### 객체가 구하러 온다 (OBJECTS TO THE RESCUE)

**R27-8**
- 규칙: 횡단 기능에 대비해 SOLID에 따라 다형적으로 확장 가능한 추상 기반 클래스를 두고, 기능별 로직(Rides·Kittens)은 템플릿 메서드(Template Method)나 전략(Strategy) 패턴으로 그 기반을 확장하는 별도 컴포넌트에 둬라. 이 컴포넌트들도 의존성 규칙을 따르게 하라.
- 근거: 그러면 새 기능 추가 시 기존 컴포넌트는 그대로 두고 새 jar/Gem/DLL만 추가된다.
- 출처: 27장 · OBJECTS TO THE RESCUE · PDF p.188–189
- 태그: [코드수준]

**R27-9**
- 규칙: 기능 구현 클래스는 UI(최외곽)가 통제하는 팩토리로 생성하게 하라.
- 근거: 그래야 새 기능 추가 시 UI와 새 컴포넌트만 바뀐다.
- 출처: 27장 · OBJECTS TO THE RESCUE · PDF p.188–189
- 태그: [코드수준]

### 컴포넌트 기반 서비스 (COMPONENT-BASED SERVICES)

**R27-10**
- 규칙: 서비스를 작은 모놀리스로 만들지 말고, 내부를 SOLID 컴포넌트 구조로 설계해 새 기능을 기존 추상 클래스를 확장하는 새 컴포넌트(jar 등) 추가만으로 배포할 수 있게 하라(OCP).
- 근거: 새 기능 배포가 서비스 재배포가 아니라 로드 경로에 새 파일 추가가 된다.
- 출처: 27장 · COMPONENT-BASED SERVICES · PDF p.189–190
- 태그: [모듈·아키텍처수준]

### 횡단 관심사 (CROSS-CUTTING CONCERNS)

**R27-11**
- 규칙: 아키텍처 경계를 서비스 사이가 아니라 서비스 내부를 관통하는 컴포넌트 경계로 그어라. 서비스 내부 컴포넌트가 의존성 규칙을 따르게 설계하라.
- 근거: 서비스가 아니라 서비스 안의 컴포넌트가 시스템의 아키텍처 경계를 정의한다.
- 출처: 27장 · CROSS-CUTTING CONCERNS · PDF p.190–191
- 태그: [모듈·아키텍처수준]

### 결론 (CONCLUSION)

**R27-12**
- 규칙: 아키텍처를 물리적 통신·실행 메커니즘(서비스·프로세스)으로 정의하지 말고 시스템 안에 그은 경계와 그것을 넘는 의존으로 정의하라. 서비스는 단일 컴포넌트일 수도, 여러 컴포넌트일 수도 있다.
- 근거: 서비스는 확장성·개발 용이성에 유용하지만 그 자체로 아키텍처상 중요한 요소가 아니다.
- 출처: 27장 · CONCLUSION · PDF p.191
- 태그: [모듈·아키텍처수준]

## 28장 테스트 경계 (The Test Boundary)

### (도입부)

**R28-1**
- 규칙: 테스트를 시스템의 일부로 보고 아키텍처 설계에 포함하라.
- 근거: 테스트도 다른 부분처럼 아키텍처에 참여한다.
- 출처: 28장 · 도입부 · PDF p.192
- 태그: [모듈·아키텍처수준]

### 시스템 컴포넌트로서의 테스트 (TESTS AS SYSTEM COMPONENTS)

**R28-2**
- 규칙: 테스트를 가장 바깥 원으로 취급하라. 테스트는 안쪽(테스트 대상 코드)에 의존하되, 시스템의 어떤 코드도 테스트 코드에 의존하지 않게 하라.
- 근거: 테스트는 본질적으로 의존성 규칙을 따른다. 단위·통합·인수 테스트 모두 아키텍처상 같다.
- 위반 예 → 개선 예: 프로덕션 코드가 `test` 패키지의 픽스처·헬퍼를 import → 금지
- 출처: 28장 · TESTS AS SYSTEM COMPONENTS · PDF p.192
- 태그: [코드수준]

**R28-3**
- 규칙: 테스트는 운영 배포물과 독립적으로 배포(테스트 시스템에서 실행)되게 하라.
- 근거: 테스트는 독립 배포 가능하며, 운영에 필요 없다.
- 출처: 28장 · TESTS AS SYSTEM COMPONENTS · PDF p.192–193
- 태그: [모듈·아키텍처수준]

### 테스트 용이성을 위한 설계 (DESIGN FOR TESTABILITY)

**R28-4**
- 규칙: 테스트를 시스템 설계 바깥으로 취급하지 마라. 테스트와 시스템의 결합을 설계 대상으로 다뤄라.
- 근거: 설계에 통합되지 않은 테스트는 깨지기 쉽고 시스템을 경직시킨다.
- 출처: 28장 · DESIGN FOR TESTABILITY · PDF p.193
- 태그: [모듈·아키텍처수준]

**R28-5 (안티패턴: 깨지기 쉬운 테스트 문제, Fragile Tests Problem)**
- 규칙: 공통 컴포넌트의 사소한 변경이 수백~수천 개 테스트를 깨뜨리는 구조를 만들지 마라.
- 근거: 깨지기 쉬운 테스트는 개발자가 변경을 거부하게 만들어 시스템을 경직시킨다.
- 출처: 28장 · DESIGN FOR TESTABILITY · PDF p.193
- 태그: [모듈·아키텍처수준]

**R28-6**
- 규칙: 변동성이 큰 것(volatile things)에 의존하지 마라. 업무 규칙을 GUI(로그인 화면부터 내비게이션)를 거쳐 검증하는 테스트를 만들지 말고, GUI 없이 업무 규칙을 테스트할 수 있게 시스템과 테스트를 설계하라.
- 근거: 소프트웨어 설계의 첫 규칙은 변동성 있는 것에 의존하지 않는 것이다. GUI는 변동성이 크다.
- 위반 예 → 개선 예: 할인 규칙을 E2E로 로그인→장바구니→결제 화면까지 클릭해 검증 → 유스케이스/테스트 API로 직접 검증, E2E는 소수 스모크만
- 출처: 28장 · DESIGN FOR TESTABILITY · PDF p.193
- 태그: [코드수준]

### 테스트 API (THE TESTING API)

**R28-7**
- 규칙: 테스트가 모든 업무 규칙을 검증하는 데 쓰는 전용 테스트 API를 만들어라. 이 API는 보안 제약 우회·비싼 자원(DB) 우회·특정 테스트 상태 강제 같은 "초능력"을 가지며, UI가 쓰는 인터랙터·인터페이스 어댑터의 상위 집합이게 하라.
- 근거: 테스트 API의 목적은 테스트를 애플리케이션에서 분리하는 것이다.
- 출처: 28장 · THE TESTING API · PDF p.193
- 태그: [모듈·아키텍처수준]

**R28-8**
- 규칙: 테스트를 UI에서 떼는 것을 넘어, 테스트의 구조를 애플리케이션의 구조와 분리하라.
- 근거: 그것이 테스트 API의 목표다.
- 출처: 28장 · THE TESTING API · PDF p.194
- 태그: [모듈·아키텍처수준]

### 구조적 결합 (STRUCTURAL COUPLING)

**R28-9 (안티패턴: 프로덕션 클래스당 테스트 클래스, 메서드당 테스트 메서드)**
- 규칙: 프로덕션 클래스마다 테스트 클래스, 프로덕션 메서드마다 테스트 메서드를 1:1로 대응시키는 구조적 결합을 피하라. 테스트는 테스트 API(행위)를 통해 검증하게 하라.
- 근거: 구조적 결합은 가장 강하고 교활한 테스트 결합이며, 프로덕션 변경마다 다수 테스트가 바뀌어 테스트는 깨지기 쉽고 프로덕션 코드는 경직된다.
- 출처: 28장 · STRUCTURAL COUPLING · PDF p.194
- 태그: [코드수준]

**R28-10**
- 규칙: 테스트 API로 애플리케이션 구조를 테스트에서 숨겨, 프로덕션 리팩터링이 테스트에 영향을 주지 않고 테스트 리팩터링도 프로덕션에 영향을 주지 않게 하라.
- 근거: 시간이 지나면 테스트는 더 구체적이 되고 프로덕션은 더 추상적·일반적이 되므로, 두 진화를 분리해야 한다.
- 출처: 28장 · STRUCTURAL COUPLING · PDF p.194
- 태그: [모듈·아키텍처수준]

### 보안 (SECURITY)

**R28-11**
- 규칙: 테스트 API의 위험한 초능력이 운영에 배포되지 않도록, 테스트 API와 그 위험한 구현 부분을 별도의 독립 배포 컴포넌트로 분리하라.
- 근거: 초능력이 운영 시스템에 배포되면 위험하다.
- 출처: 28장 · SECURITY · PDF p.194
- 태그: [모듈·아키텍처수준]

### 결론 (CONCLUSION)

**R28-12**
- 규칙: 테스트를 시스템의 잘 설계된 부분으로 유지하라. 그렇지 않으면 유지보수가 어려워 결국 버려진다.
- 근거: 설계되지 않은 테스트는 깨지기 쉽고, 유지보수가 너무 어려워 폐기된다.
- 출처: 28장 · CONCLUSION · PDF p.194
- 태그: [모듈·아키텍처수준]

## 29장 클린 임베디드 아키텍처 (Clean Embedded Architecture, James Grenning)

### (도입부)

**R29-1**
- 규칙: 하드웨어·펌웨어에 대한 의존을 관리하지 않은 채 두지 마라. 소프트웨어가 하드웨어 진화로 함께 낡지 않게 하라.
- 근거: 소프트웨어는 닳지 않지만, 펌웨어·하드웨어에 대한 관리되지 않은 의존으로 안에서부터 파괴될 수 있다.
- 출처: 29장 · 도입부 · PDF p.195
- 태그: [임베디드특화]

**R29-2**
- 규칙: "펌웨어"를 저장 위치(ROM)가 아니라 "무엇에 의존하며 하드웨어 진화에 따라 바꾸기 얼마나 어려운가"로 판단하라. 펌웨어는 줄이고 소프트웨어를 늘려라.
- 근거: 펌웨어인지 여부는 의존 대상과 변경 난이도로 정해진다.
- 출처: 29장 · 도입부 · PDF p.196
- 태그: [임베디드특화]

**R29-3 (안티패턴: 비임베디드 코드의 펌웨어화)**
- 규칙: 업무 코드에 SQL을 묻거나 플랫폼 의존(예: Android API)을 코드 전체에 퍼뜨리지 마라. 업무 로직을 플랫폼 API에서 분리하라.
- 근거: 그렇게 하면 비임베디드 개발자도 사실상 펌웨어를 쓰는 셈이다.
- 출처: 29장 · 도입부 · PDF p.196
- 태그: [코드수준]

**R29-4 (안티패턴: 레거시 코드가 명세)**
- 규칙: 기술(TDM 등)과 업무 로직을 위에서 아래까지 뒤섞지 마라. 업무 규칙을 기술 독립적으로 분리해, 기존 코드를 뒤지지 않고도 동작 규칙을 알 수 있게 하라.
- 근거: TDM→VoIP 전환 때 분리가 없어 엉킨 레거시 코드가 새 제품의 명세가 됐고 풀어낼 수 없었다.
- 출처: 29장 · 도입부 · PDF p.196
- 태그: [모듈·아키텍처수준]

**R29-5**
- 규칙: 메시지 파서·디스패처 같은 프로토콜 로직을 하드웨어(UART 등) 접근 코드와 같은 파일에 두지 마라.
- 근거: UART 세부사항에 오염된 메시지 처리기는 오래 쓸 수 있는 소프트웨어가 될 기회를 잃는다.
- 위반 예 → 개선 예: `uart_dispatch.c`에 레지스터 접근 + 메시지 파싱 → `message_dispatcher.c`(하드웨어 무지) + `uart_driver.c`
- 출처: 29장 · 도입부 · PDF p.196–197
- 태그: [임베디드특화]

### 앱티튜드 테스트 (APP-TITUDE TEST)

**R29-6**
- 규칙: "먼저 동작하게, 그다음 올바르게(리팩터링), 그다음 빠르게(필요한 성능만)" 순서를 따르라. 동작만 확인하고 끝내지 마라.
- 근거: 앱을 동작하게만 하는 것은 제품과 고용주에게 해가 된다(App-titude test). "하나는 버릴 계획을 세워라"와 같은 조언이다.
- 출처: 29장 · APP-TITUDE TEST · PDF p.197
- 태그: [코드수준]

**R29-7 (안티패턴: 곳곳의 마이크로 최적화)**
- 규칙: 기회가 있을 때마다 마이크로 최적화를 넣지 마라. 필요한 성능에 대해서만 최적화하라.
- 근거: "빠르게"에 대한 집착이 구조를 해친다.
- 출처: 29장 · APP-TITUDE TEST · PDF p.197
- 태그: [코드수준]

**R29-8**
- 규칙: 한 파일에 도메인 로직·하드웨어 설정(ISR·슬립)·버튼 처리·A/D 입력·영속 저장을 섞지 말고, 관심사별로 묶어 분리하라.
- 근거: 예시 파일은 관심사가 뒤섞여 이해를 방해하고, 타깃에서만 테스트할 수 있었다.
- 출처: 29장 · APP-TITUDE TEST · PDF p.197–199

**R29-9**
- 규칙: 함수 이름이 실제 동작과 일치하게 하라(예: `Sensor_init`이 초기화 외의 일을 하지 않게).
- 근거: 이름이 말하는 일을 하지 않는 함수가 이해를 방해하는 요인으로 지적됐다.
- 출처: 29장 · APP-TITUDE TEST · PDF p.198

**R29-10**
- 규칙: 모든 코드가 특정 마이크로프로세서·툴체인의 "확장" C 구문을 알지 않게 하라. 타깃에서만 테스트 가능한 파일 구조를 만들지 마라.
- 근거: 그런 코드는 하드웨어 환경이 바뀌면 오래 살 수 없다.
- 출처: 29장 · APP-TITUDE TEST · PDF p.198–199
- 태그: [임베디드특화]

### 타깃 하드웨어 병목 (THE TARGET-HARDWARE BOTTLENECK)

**R29-11**
- 규칙: 타깃 하드웨어에서만 테스트할 수 있는 구조를 피하라. 하드웨어가 동시 개발 중이거나 결함이 있어도 오프타깃에서 개발·테스트할 수 있게 하라.
- 근거: 타깃이 유일한 테스트 장소면 타깃 하드웨어 병목(target-hardware bottleneck)이 개발을 늦춘다. 임베디드도 이 책의 원칙이 적용된다.
- 출처: 29장 · THE TARGET-HARDWARE BOTTLENECK · PDF p.199
- 태그: [임베디드특화]

### 클린 임베디드 아키텍처는 테스트 가능한 임베디드 아키텍처 — 계층 (Layers)

**R29-12**
- 규칙: 최소한 하드웨어 / 펌웨어 / 소프트웨어 계층으로 나누고, 어떤 모듈이 다른 모듈의 무엇을 알아도 되는지 통제해 하드웨어 지식이 전체 코드를 오염시키지 않게 하라.
- 근거: 하드웨어는 반드시 바뀌며, 하드웨어 변경뿐 아니라 사용자 요청·버그 수정 때도 코드가 바꾸기 어려워진다.
- 출처: 29장 · Layers · PDF p.199–200
- 태그: [임베디드특화]

**R29-13 (안티패턴: 소프트웨어·펌웨어 혼재)**
- 규칙: 소프트웨어와 펌웨어를 뒤섞지 마라. 외부 계측 자동 테스트를 만들어 수동 회귀 테스트에 의존하지 마라.
- 근거: 혼재 코드는 변경에 저항하고 변경이 위험해 사소한 변경에도 전체 회귀 테스트가 필요하다.
- 출처: 29장 · Layers · PDF p.200
- 태그: [임베디드특화]

### 하드웨어는 세부사항이다 (The Hardware Is a Detail)

**R29-14**
- 규칙: 소프트웨어와 펌웨어 사이의 경계를 하드웨어 추상화 계층(HAL)으로 명확히 하라.
- 근거: 소프트웨어/펌웨어 선은 코드/하드웨어 선보다 흐릿하므로 이를 단단히 하는 것이 임베디드 개발자의 일이다.
- 출처: 29장 · The Hardware Is a Detail · PDF p.200–201
- 태그: [임베디드특화]

**R29-15**
- 규칙: HAL API는 그 위의 소프트웨어 요구에 맞춰 설계하라. 예: 플래시의 바이트 쓰기가 아니라 이름/값 쌍 저장 서비스를 제공하고, 저장 매체는 숨겨라.
- 근거: HAL은 서비스를 제공할 뿐 어떻게 하는지 드러내지 않는다. 플래시 구현은 숨겨야 할 세부사항이다.
- 출처: 29장 · The Hardware Is a Detail · PDF p.201
- 태그: [임베디드특화]

**R29-16**
- 규칙: HAL의 추상 수준을 하드웨어 관점(`Led_TurnOn(5)`)이 아니라 제품 관점(`Indicate_LowBattery()`)으로 올려라. GPIO 할당 같은 세부사항을 숨겨라. 계층 안에 계층이 반복되는 프랙털 구조를 허용하라.
- 근거: HAL은 애플리케이션이 필요한 서비스를 표현해야 한다.
- 위반 예 → 개선 예: 앱 코드에서 `Led_TurnOn(5)` → `Indicate_LowBattery()`
- 출처: 29장 · The Hardware Is a Detail · PDF p.201–202
- 태그: [임베디드특화]

### HAL 사용자에게 하드웨어 세부사항을 드러내지 마라 (DON'T REVEAL HARDWARE DETAILS TO THE USER OF THE HAL)

**R29-17**
- 규칙: HAL이 오프타깃 테스트를 위한 이음새(seam)·대체 지점(substitution point)을 제공하게 하라. 소프트웨어는 타깃 하드웨어 밖에서 테스트할 수 있어야 한다.
- 근거: 성공적인 HAL은 오프타깃 테스트를 가능하게 하는 대체 지점이다.
- 출처: 29장 · DON'T REVEAL HARDWARE DETAILS… · PDF p.202
- 태그: [임베디드특화]

### 프로세서는 세부사항이다 (The Processor Is a Detail)

**R29-18**
- 규칙: 벤더 컴파일러의 C 확장 키워드·레지스터 전역 변수를 아는 파일을 제한하라.
- 근거: 그런 코드는 더 이상 C가 아니며 다른 프로세서·컴파일러에서 컴파일되지 않는다.
- 출처: 29장 · The Processor Is a Detail · PDF p.202
- 태그: [임베디드특화]

**R29-19**
- 규칙: 벤더 타입 헤더(`acmetypes.h`)를 직접 쓰지 말고 `stdint.h`를 써라. 타깃 컴파일러에 없으면 벤더 헤더를 감싸는 자체 `stdint.h`를 작성해 타깃 빌드에서만 쓰게 하라.
- 근거: 벤더 헤더를 직접 쓰면 특정 DSP에 묶이고, 오프타깃 테스트 시 정수 크기가 틀리며, 이식이 어려워진다.
- 출처: 29장 · The Processor Is a Detail · PDF p.202–203
- 태그: [임베디드특화]

**R29-20**
- 규칙: 소프트웨어 계층은 전부 프로세서 독립이게 하라(펌웨어 일부만 프로세서 종속 허용).
- 근거: 모든 소프트웨어는 프로세서 독립이어야 하지만 펌웨어 전부가 그럴 수는 없다.
- 출처: 29장 · The Processor Is a Detail · PDF p.203
- 태그: [임베디드특화]

**R29-21**
- 규칙: 장치 접근 레지스터(IE·SBUF0·TI_0 등)는 극소수 위치에서만 직접 쓰고 펌웨어 안에 완전히 가둬라. 표준 C가 아닌 이진 리터럴(`0b...`) 같은 비표준 구문과 의미 없는 매직 값(0x68 등)을 흩뿌리지 마라.
- 근거: 레지스터를 아는 모든 코드는 펌웨어가 되어 실리콘에 묶이고, 안정 하드웨어 전 개발과 프로세서 이전을 방해한다.
- 출처: 29장 · The Processor Is a Detail · PDF p.203–204
- 태그: [임베디드특화]

**R29-22**
- 규칙: 마이크로컨트롤러 저수준 기능을 프로세서 추상화 계층(PAL)으로 격리해 PAL 위 펌웨어를 오프타깃 테스트 가능하게 하라.
- 근거: PAL 위의 펌웨어는 오프타깃 테스트가 가능해 덜 "firm"해진다.
- 출처: 29장 · The Processor Is a Detail · PDF p.204
- 태그: [임베디드특화]

### 운영체제는 세부사항이다 (The Operating System Is a Detail)

**R29-23**
- 규칙: RTOS·임베디드 Linux/Windows를 쓰는 경우 OS를 세부사항으로 보고, 소프트웨어가 OS를 직접 쓰지 않고 운영체제 추상화 계층(OSAL)을 통해 쓰게 하라.
- 근거: OS 공급사 인수·로열티 인상·품질 저하·기능 부족 시 구문뿐 아니라 의미 수준까지 많은 코드를 바꿔야 한다. OSAL이 있으면 호환 OSAL만 새로 쓰면 된다.
- 출처: 29장 · The Operating System Is a Detail · PDF p.204–206
- 태그: [임베디드특화]

**R29-24**
- 규칙: OSAL을 OS 사용 관련 중복을 가두는 곳이자 공통 구조(예: 스레드마다 직접 짜는 동시성 대신 메시지 전달 메커니즘)를 제공하는 곳으로 활용하라.
- 근거: 계층은 코드 비대보다 중복의 격리 장소가 되며, 애플리케이션에 공통 구조를 장려한다.
- 출처: 29장 · The Operating System Is a Detail · PDF p.206
- 태그: [임베디드특화]

**R29-25**
- 규칙: OSAL이 오프타깃·오프OS 테스트를 위한 이음새·대체 지점을 제공하게 하라.
- 근거: 클린 임베디드 소프트웨어는 타깃 OS 밖에서 테스트할 수 있다.
- 출처: 29장 · The Operating System Is a Detail · PDF p.206
- 태그: [임베디드특화]

### 인터페이스 프로그래밍과 대체 가능성 (PROGRAMMING TO INTERFACES AND SUBSTITUTABILITY)

**R29-26**
- 규칙: 각 주요 계층 안에서도 관심사 분리·인터페이스 프로그래밍·대체 가능성 원칙을 적용하라. 모듈 간 상호작용은 인터페이스를 통해 해서 서비스 제공자를 바꿔 끼울 수 있게 하라(예: 표준과 같은 인터페이스의 자체 printf).
- 근거: 계층 아키텍처는 인터페이스 프로그래밍에 기반한다.
- 출처: 29장 · PROGRAMMING TO INTERFACES AND SUBSTITUTABILITY · PDF p.206
- 태그: [코드수준]

**R29-27**
- 규칙: 헤더 파일을 인터페이스 정의로 쓰되, 함수 선언과 그 함수에 필요한 상수·구조체 이름만 넣어라. 구현에서만 필요한 데이터 구조·상수·typedef는 인터페이스 헤더에 넣지 마라.
- 근거: 그런 잡동사니는 원치 않는 의존을 만든다. 구현 세부를 아는 곳이 적을수록 변경 시 추적·수정할 곳이 적다.
- 출처: 29장 · PROGRAMMING TO INTERFACES AND SUBSTITUTABILITY · PDF p.206
- 태그: [코드수준]

**R29-28**
- 규칙: 구현 세부사항의 가시성을 제한하고 그것이 바뀔 것이라고 예상하라.
- 근거: 세부를 아는 코드가 적을수록 수정할 곳이 적다.
- 출처: 29장 · PROGRAMMING TO INTERFACES AND SUBSTITUTABILITY · PDF p.206
- 태그: [코드수준]

**R29-29**
- 규칙: 모든 인터페이스를 오프타깃 테스트용 이음새로 설계해 계층 내부에서도 테스트 가능하게 하라.
- 근거: 모듈이 인터페이스로 상호작용하므로 계층 안에서 테스트할 수 있다.
- 출처: 29장 · PROGRAMMING TO INTERFACES AND SUBSTITUTABILITY · PDF p.206
- 태그: [임베디드특화]

### 조건부 컴파일 지시문 DRY (DRY CONDITIONAL COMPILATION DIRECTIVES)

**R29-30 (안티패턴: 반복된 #ifdef)**
- 규칙: 대상 하드웨어·OS 구분용 조건부 컴파일(`#ifdef BOARD_V2` 등)을 코드 곳곳에 반복하지 마라(DRY 위반). 하드웨어 종류를 HAL 아래 세부로 숨기고, 링커나 런타임 바인딩으로 소프트웨어와 하드웨어 구현을 연결하라.
- 근거: 한 번은 문제가 아니지만 수천 번 반복은 극단적 문제다.
- 위반 예 → 개선 예: 수천 곳의 `#ifdef BOARD_V2` → `hal_board.h` 인터페이스 + `hal_board_v1.c`/`hal_board_v2.c`를 빌드 시 링크로 선택
- 출처: 29장 · DRY CONDITIONAL COMPILATION DIRECTIVES · PDF p.206–207
- 태그: [임베디드특화]

**R29-31**
- 규칙: 모든 코드가 펌웨어가 되거나 타깃 하드웨어에서만 테스트 가능한 상태를 허용하지 마라.
- 근거: 둘 다 제품의 장기 건강에 나쁘고, 클린 임베디드 아키텍처가 장기 건강에 좋다.
