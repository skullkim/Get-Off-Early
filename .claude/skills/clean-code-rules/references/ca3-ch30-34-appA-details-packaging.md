## 30장 데이터베이스는 세부사항이다 (The Database Is a Detail)

### (도입부)
**R30-1**
- 규칙: 데이터 모델(data model)과 데이터베이스(database)를 구분하라. 데이터 모델은 아키텍처적으로 중요한 요소로 설계하고, DB 제품과 엔진은 저수준 메커니즘(mechanism)으로 다뤄라.
- 근거: DB는 데이터에 접근하게 해 주는 유틸리티일 뿐이며, 아키텍처 관점에서는 문 손잡이 같은 존재다. 데이터에 부여한 구조는 아키텍처적으로 중요하다.
- 출처: 30장 도입부, p.277–278
- 태그: [모듈·아키텍처수준]

**R30-2**
- 규칙: 저수준 메커니즘이 시스템 아키텍처를 오염시키지 않게 하라.
- 근거: 좋은 아키텍트는 저수준 메커니즘이 아키텍처를 오염시키도록 놔두지 않는다.
- 출처: 30장 도입부, p.278
- 태그: [모듈·아키텍처수준]

### 관계형 데이터베이스 (Relational Databases)
**R30-3**
- 규칙: 데이터가 테이블·행 구조로 되어 있다는 지식은 아키텍처 바깥 원(outer circles)의 최하위 유틸리티 함수 안에만 두어라. 유스케이스(use case)는 이 구조를 알지도, 신경 쓰지도 않아야 한다.
- 근거: 관계형 모델이 아무리 훌륭해도 하나의 기술이고, 기술은 세부사항이다.
- 출처: 30장 Relational Databases, p.278
- 태그: [모듈·아키텍처수준]

**R30-4**
- 규칙: DB의 행과 테이블을 객체(ORM 엔티티, ResultSet, Row 객체)로 만들어 시스템 전체에 돌리지 마라. 경계에서 도메인 구조로 변환하라.
- 근거: 이렇게 넘기면 유스케이스와 비즈니스 규칙, 심지어 UI까지 관계형 구조에 결합된다. 책은 이것을 "아키텍처 오류"라고 부른다.
- 위반 예 → 개선 예: 컨트롤러·서비스·뷰가 `@Entity OrderRow`를 직접 받는다 → 리포지토리 구현체 안에서 `Order` 도메인 객체나 응답 DTO로 매핑한 뒤 내보낸다.
- 출처: 30장 Relational Databases, p.278
- 태그: [코드수준]

### 데이터베이스 시스템은 왜 이렇게 널리 쓰이는가? (Why Are Database Systems So Prevalent?)
**R30-5**
- 규칙: 저장 기술은 접근 패턴에 맞춰 골라라. 이름으로 문서를 통째로 저장하고 찾으면 파일·문서 저장소를, 내용으로 레코드를 찾고 연관 지으면 내용 기반(content based) 저장소를 쓴다. 그리고 그 선택이 코어로 새어 들어오지 않게 하라.
- 근거: 파일 시스템은 문서 기반이라 내용 검색에 약하고, RDBMS는 내용 기반이라 불투명한 문서를 저장하는 데 약하다. 둘 다 느린 디스크를 보완하려고 만든 인덱스·캐시 체계일 뿐이다.
- 출처: 30장 Why Are Database Systems So Prevalent?, p.279–280
- 태그: [모듈·아키텍처수준]

### 디스크가 없다면? (What If There Were No Disk?)
**R30-6**
- 규칙: 메모리 안에서는 데이터를 문제에 맞는 자료구조(리스트, 트리, 해시 테이블, 스택, 큐)로 재구성해서 다뤄라. 비즈니스 코드를 저장소 형식(테이블, 파일)에 맞춰 짜지 마라.
- 근거: 프로그래머는 이미 데이터를 RAM으로 읽어 들여 자기 편한 구조로 바꿔 쓰고 있다. 테이블이나 파일 형태 그대로 쓰는 경우는 드물다.
- 출처: 30장 What If There Were No Disk?, p.280–281
- 태그: [코드수준]

### 세부사항 (Details)
**R30-7**
- 규칙: 아키텍처 관점에서는 데이터가 디스크 위에서 어떤 형태인지 신경 쓰지 말고, 코어가 디스크의 존재 자체를 알지 못하게 하라.
- 근거: DB는 디스크와 RAM 사이에서 데이터를 옮기는 메커니즘, 즉 장기 보관용 "비트 양동이"에 불과하다.
- 출처: 30장 Details, p.281
- 태그: [모듈·아키텍처수준]

### 그렇다면 성능은? (But What About Performance?)
**R30-8**
- 규칙: 저장소 성능 문제(인덱스, 쿼리 최적화, 캐시)는 저수준 데이터 접근 계층 안에 캡슐화해서 해결하라. 성능을 이유로 비즈니스 규칙에 저장소 관련 코드를 섞지 마라.
- 근거: 성능은 아키텍처적 관심사가 맞지만, 데이터 저장에 관해서는 비즈니스 규칙과 완전히 분리하고 캡슐화할 수 있는 저수준 관심사다.
- 출처: 30장 But What About Performance?, p.281
- 태그: [코드수준] [모듈·아키텍처수준]

### 일화 (Anecdote)
**R30-9**
- 규칙: 비기술적 요구(마케팅·고객이 체크박스처럼 요구하는 RDBMS 등)도 실재하는 요구로 받아들여라. 다만 코어에 넣지 말고 옆에 붙이고(bolt on the side), 좁고 안전한 데이터 접근 채널로만 연결하라.
- 근거: 저자는 엔지니어링 측면에서는 옳았지만, 고객이 RDBMS를 기대했기 때문에 결국 틀렸다. 그가 꼽은 정답은 코어는 그대로 두고 RDBMS를 측면에 붙인 뒤 좁은 접근 채널을 두는 것이었다.
- 출처: 30장 Anecdote, p.281–283
- 태그: [교훈] [모듈·아키텍처수준]

**R30-10**
- 규칙: 데이터에 내용 기반 관계가 거의 없으면 굳이 RDBMS를 기본값으로 쓰지 말고, RAM에 올려 다루기 가장 편한 형태로 저장하는 방안을 검토하라.
- 근거: 일화 속 시스템은 랜덤 액세스 파일 안에 트리와 연결 리스트를 두는 쪽이 더 나았다.
- 출처: 30장 Anecdote, p.281–282
- 태그: [교훈]

**R30-11**
- 규칙: "enterprise", "SOA" 같은 유행어나 마케팅 구호를 아키텍처 결정의 근거로 삼지 마라.
- 근거: 이런 말들은 현실보다 마케팅과 더 관련이 깊다.
- 출처: 30장 Anecdote, p.283
- 태그: [교훈]

### 결론 (Conclusion)
**R30-12**
- 규칙: 아키텍처 리뷰에서는 데이터의 조직 구조(데이터 모델)를 검토 대상으로 삼고, 데이터를 저장 매체에 넣고 빼는 기술(DB 제품)은 교체 가능한 세부사항으로 취급하라.
- 근거: "데이터는 중요하다. 데이터베이스는 세부사항이다."
- 출처: 30장 Conclusion, p.283
- 태그: [모듈·아키텍처수준]

## 31장 웹은 세부사항이다 (The Web Is a Detail)

### (도입부) / 끝없는 진자 (The Endless Pendulum)
**R31-1**
- 규칙: 연산 능력을 어디에 둘지(서버 중앙화 대 클라이언트 분산)를 둘러싼 업계의 진동은 단기 이슈로 보고, 비즈니스 규칙 코어에서 멀리 밀어내라.
- 근거: 웹은 1960년대부터 이어진 중앙화와 분산 사이 진동 가운데 하나일 뿐이다. 아키텍트는 장기적으로 봐야 한다.
- 출처: 31장 The Endless Pendulum, p.285–286
- 태그: [모듈·아키텍처수준] [교훈]

**R31-2**
- 규칙: UI의 외관과 동작이 통째로 바뀌는 상황(마케팅 결정, OS의 룩앤필 변경)에 대비해 비즈니스 규칙을 UI와 분리해 두어라.
- 근거: Q사는 데스크톱 앱을 브라우저처럼 바꿨다가 다시 되돌렸고, A사는 OS 업그레이드로 모든 앱의 룩앤필이 바뀌었다. UI와 결합된 지점이 생기면 언제든 비용이 된다.
- 출처: 31장 The Endless Pendulum, p.286–287
- 태그: [모듈·아키텍처수준] [교훈]

### 결론적으로 (The Upshot)
**R31-3**
- 규칙: GUI와 웹은 세부사항이다. 경계 뒤에 두어 코어 비즈니스 로직과 분리하라.
- 근거: GUI는 세부사항이고 웹은 GUI이므로 웹도 세부사항이다.
- 출처: 31장 The Upshot, p.288
- 태그: [모듈·아키텍처수준]

**R31-4**
- 규칙: 웹을 IO 장치로 보고 장치 독립성(device independence)을 지켜라.
- 근거: 1960년대에 배운 장치 독립성의 동기는 지금도 그대로이며, 웹이 예외는 아니다.
- 출처: 31장 The Upshot, p.288
- 태그: [모듈·아키텍처수준]

**R31-5**
- 규칙: UI와 애플리케이션 사이의 수다스러운(chatty) 상호작용(검증, 드래그앤드롭, AJAX)까지 억지로 추상화하려 하지 마라. 대신 유스케이스 경계를 추상화하라. 입력이 완성된 시점에 입력 데이터 구조로 유스케이스를 실행하고, 결과를 출력 데이터 구조로 돌려주어라.
- 근거: GUI별 상호작용은 추상화하기 어렵지만, 유스케이스는 입력·처리·출력으로 기술할 수 있다. 유스케이스가 UI라는 IO 장치를 장치 독립적으로 조작하게 만들 수 있다.
- 위반 예 → 개선 예: 유스케이스가 `HttpServletRequest`를 받는다 → 컨트롤러가 요청을 `PlaceOrderRequest` 같은 평범한 데이터 구조로 바꾼 뒤 `PlaceOrderUseCase.execute(req)`를 호출하고 `PlaceOrderResponse`를 받는다.
- 출처: 31장 The Upshot, p.288–289
- 태그: [코드수준] [모듈·아키텍처수준]

### 결론 (Conclusion)
**R31-6**
- 규칙: UI와 유스케이스 사이의 추상화는 한 번에 완벽하게 만들 수 없다는 전제로 여러 번 반복해 다듬어라.
- 근거: 쉽지 않고 여러 번 반복해야 맞아떨어지지만, 가능하고 자주 필요하다.
- 출처: 31장 Conclusion, p.289
- 태그: [교훈]

## 32장 프레임워크는 세부사항이다 (Frameworks Are Details)

### (도입부)
**R32-1**
- 규칙: 프레임워크를 아키텍처로 착각하지 마라. 아키텍처는 직접 설계하고, 프레임워크는 그 안에서 쓰는 도구로 두어라.
- 근거: 프레임워크는 아키텍처가 아니다. 그런 척하는 것도 있을 뿐이다.
- 출처: 32장 도입부, p.291–292
- 태그: [모듈·아키텍처수준]

### 프레임워크 제작자 (Framework Authors)
**R32-2**
- 규칙: 프레임워크를 채택하기 전에, 그 프레임워크가 풀려는 문제와 우리 문제가 겹치는 정도를 평가하고 겹치는 범위 안에서만 의존하라.
- 근거: 제작자는 우리를 모르고, 자신과 주변 사람의 문제를 풀려고 프레임워크를 만들었다.
- 출처: 32장 Framework Authors, p.292
- 태그: [교훈]

### 비대칭적인 결혼 (Asymmetric Marriage)
**R32-3**
- 규칙: 프레임워크 문서가 권하는 결합 방식(베이스 클래스 상속, 비즈니스 객체 안으로 프레임워크 기능 import, 프레임워크 중심으로 아키텍처 감싸기)을 그대로 따르지 마라. 결합이 깊어지면 리스크는 전부 우리가 진다.
- 근거: 우리는 큰 헌신을 하지만 제작자는 아무런 헌신도 하지 않는 일방적인 결혼이다. 제작자 입장에서는 결합이 리스크가 아니지만 우리에게는 리스크다.
- 출처: 32장 Asymmetric Marriage, p.292–293
- 태그: [모듈·아키텍처수준]

### 위험 요인 (The Risks)
**R32-4**
- 규칙: 엔티티(Entities)와 비즈니스 객체가 프레임워크 코드를 상속하거나 프레임워크 타입을 참조하지 않게 하라.
- 근거: 프레임워크는 의존성 규칙(Dependency Rule)을 어기고 가장 안쪽 원에 결합하려 하는 경향이 있다. 한번 들어오면 빠지지 않는다.
- 출처: 32장 The Risks, p.293
- 태그: [코드수준]

**R32-5**
- 규칙: 프레임워크 결합도는 다음 네 위험을 기준으로 평가하라. ① 깨끗하지 않은 아키텍처 ② 제품이 성숙하면서 프레임워크 기능을 넘어서는 것 ③ 원치 않는 방향으로의 진화, 필요 없는 업그레이드 강제, 기능 제거·변경 ④ 더 나은 프레임워크가 나와도 갈아탈 수 없는 것.
- 근거: 책에 열거된 프레임워크 위험이다.
- 출처: 32장 The Risks, p.293–294
- 태그: [교훈]

### 해결책 (The Solution)
**R32-6**
- 규칙: 프레임워크와 결혼하지 마라(Don't marry the framework). 사용하되 결합하지 말고, 바깥 원의 세부사항으로 두어 팔 길이만큼 거리를 유지하라. 안쪽 원에는 들이지 마라.
- 근거: 프레임워크를 코어 코드에 들이지 말고, 의존성 규칙에 따라 코어에 꽂히는 플러그인 컴포넌트에 통합하라.
- 출처: 32장 The Solution, p.294
- 태그: [모듈·아키텍처수준]

**R32-7**
- 규칙: 프레임워크가 비즈니스 객체에 자기 베이스 클래스 상속을 요구하면 거절하라. 대신 프록시(proxy)를 상속하고, 그 프록시는 비즈니스 규칙에 꽂히는 플러그인 컴포넌트에 두어라.
- 근거: 상속은 가장 강한 결합이다. 프록시는 그 결합을 바깥 원에 가둬 둔다.
- 위반 예 → 개선 예: `class Order extends FrameworkEntity` → 순수한 `Order`를 두고, 어댑터 모듈에 `OrderRecord extends FrameworkEntity`와 매퍼를 둔다.
- 출처: 32장 The Solution, p.294
- 태그: [코드수준]

**R32-8**
- 규칙: DI 프레임워크의 애너테이션(예: `@Autowired`)을 비즈니스 객체 곳곳에 뿌리지 마라. 비즈니스 객체는 DI 프레임워크를 몰라야 한다. 와이어링은 Main 컴포넌트(구성 루트, composition root)에서만 하라.
- 근거: Main은 아키텍처에서 가장 지저분한 최하위 컴포넌트라서 Spring을 알아도 괜찮다.
- 위반 예 → 개선 예: 도메인 서비스 필드에 `@Autowired` → 생성자 주입을 받는 순수 클래스로 두고, `@Configuration`이나 Main에서 `new`하거나 빈으로 등록한다.
- 출처: 32장 The Solution, p.294
- 태그: [코드수준]

### 이제 선언합니다… (I Now Pronounce You …)
**R32-9**
- 규칙: 피할 수 없는 프레임워크(C++의 STL, Java 표준 라이브러리 등)와의 결혼도 의식적인 결정으로 내리고, 그 결정은 애플리케이션 수명 내내 되돌릴 수 없다는 전제로 기록하라.
- 근거: 그런 결혼은 정상이지만 그래도 결정이어야 한다. 가볍게 들어설 약속이 아니다.
- 출처: 32장 I Now Pronounce You …, p.295
- 태그: [교훈] [모듈·아키텍처수준]

### 결론 (Conclusion)
**R32-10**
- 규칙: 프레임워크와는 바로 결혼하지 말고 한동안 연애하라(date it). 가능하다면, 가능한 한 오래 아키텍처 경계 뒤에 두어라.
- 근거: 소를 사지 않고도 우유를 얻는 방법을 찾을 수 있을지도 모른다.
- 출처: 32장 Conclusion, p.295
- 태그: [모듈·아키텍처수준]

## 33장 사례 연구: 비디오 판매 (Case Study: Video Sales)

### 제품 (The Product)
**R33-1**
- 규칙: 초기 아키텍처를 정하는 첫 단계로 액터(actor)와 유스케이스를 먼저 식별하라.
- 근거: 사례 연구에서 좋은 아키텍트가 밟는 절차의 첫 단계다.
- 출처: 33장 The Product, p.298
- 태그: [모듈·아키텍처수준]

### 유스케이스 분석 (Use Case Analysis)
**R33-2**
- 규칙: 각 액터를 변경의 주요 원천으로 보고, 한 액터를 위한 변경이 다른 액터에 영향을 주지 않도록 시스템을 분할하라(SRP).
- 근거: 기능이 추가되거나 바뀔 때마다 그 변경은 어느 한 액터를 위한 것이다.
- 출처: 33장 Use Case Analysis, p.299
- 태그: [모듈·아키텍처수준]

**R33-3**
- 규칙: 매우 비슷한 유스케이스(예: 시청자용 카탈로그 보기와 구매자용 카탈로그 보기)는 분석 초기에 추상 유스케이스(abstract use case)로 공통 정책을 묶어 통합하라.
- 근거: 추상 유스케이스는 일반 정책을 정하고 다른 유스케이스가 그것을 구체화한다. 유사성을 일찍 인식해 통합하는 편이 현명하다.
- 출처: 33장 Use Case Analysis, p.299–300
- 태그: [모듈·아키텍처수준]

### 컴포넌트 아키텍처 (Component Architecture)
**R33-4**
- 규칙: 컴포넌트를 두 축으로 나눠라. ① 기술 역할(뷰, 프레젠터, 인터랙터, 컨트롤러)과 경계 ② 액터.
- 근거: 그림 33.2는 views/presenters/interactors/controllers 분할을 다시 액터별로 쪼갠 구조다.
- 출처: 33장 Component Architecture, p.300–301
- 태그: [모듈·아키텍처수준]

**R33-5**
- 규칙: 추상 유스케이스는 추상 클래스(예: Catalog View, Catalog Presenter)를 담은 별도 컴포넌트로 구현하고, 구체 컴포넌트가 그것을 상속하게 하라.
- 근거: 상속하는 컴포넌트가 추상 뷰·프레젠터 클래스를 확장하는 방식으로 공통 정책을 재사용한다.
- 출처: 33장 Component Architecture, p.300–301
- 태그: [코드수준] [모듈·아키텍처수준]

**R33-6**
- 규칙: 컴파일·빌드 환경을 독립 배포 가능한 단위(jar/dll, 모듈)로 잘게 나눠라. 실제 배포 단위는 필요에 따라 더 적은 수로 합칠 권리를 남겨 두어라(예: 5개 jar, 뷰+프레젠터/나머지 2개 jar).
- 근거: 이렇게 선택지를 열어 두면 시스템이 변하는 양상에 맞춰 배포 방식을 조정할 수 있다.
- 출처: 33장 Component Architecture, p.301
- 태그: [모듈·아키텍처수준]

### 의존성 관리 (Dependency Management)
**R33-7**
- 규칙: 제어 흐름과 무관하게 경계를 넘는 모든 의존성은 한 방향으로, 더 높은 수준의 정책을 담은 컴포넌트 쪽을 향하게 하라.
- 근거: 제어 흐름은 오른쪽에서 왼쪽(controller→interactor→presenter→view)이지만, 화살표 대부분은 의존성 규칙에 따라 왼쪽에서 오른쪽을 가리킨다.
- 출처: 33장 Dependency Management, p.302
- 태그: [모듈·아키텍처수준]

**R33-8**
- 규칙: 사용 관계(using)는 제어 흐름과 같은 방향으로, 상속·구현 관계(inheritance)는 제어 흐름의 반대 방향으로 두어(OCP·DIP) 저수준 세부사항의 변경이 고수준 정책으로 번지지 않게 하라.
- 근거: 열린 화살표는 제어 흐름 방향, 닫힌 화살표는 반대 방향이다. 이것이 OCP 적용의 모습이다.
- 출처: 33장 Dependency Management, p.302
- 태그: [코드수준] [모듈·아키텍처수준]

### 결론 (Conclusion)
**R33-9**
- 규칙: 서로 다른 이유(액터)로, 서로 다른 속도(정책 수준)로 변하는 컴포넌트를 분리하라. 이유는 SRP로, 속도는 의존성 규칙으로 나눈다.
- 근거: 그림 33.2의 두 분리 차원이다. 이렇게 구조화하면 배포 단위를 마음대로 조합하고 상황에 따라 쉽게 바꿀 수 있다.
- 출처: 33장 Conclusion, p.302
- 태그: [모듈·아키텍처수준]

**R33-10**
- 규칙: 표기 표준(예: UML 스테레오타입)은 유용할 때만 따르라. 의미 전달이 목적이다.
- 근거: 저자는 `<<abstract>>` 대신 자기 표기를 썼다. 요즘에는 그런 표준 준수가 그다지 유용하지 않다고 본다(각주 1).
- 출처: 33장 각주 1, p.302
- 태그: [교훈]

## 34장 빠져 있는 장 (The Missing Chapter, Simon Brown)

### (도입부)
**R34-1**
- 규칙: 설계를 마쳤으면 그 설계를 코드 구조(패키지, 모듈, 접근 제한자)에 어떻게 매핑할지까지 결정하라. 구현 세부에서 설계가 무너진다.
- 근거: 경계와 의존성을 잘 설계해도 구현 세부를 생각하지 않으면 마지막 허들에서 넘어지기 쉽다.
- 출처: 34장 도입부, p.303–304
- 태그: [모듈·아키텍처수준]

### 계층 기반 패키지 (Package by Layer)
**R34-2**
- 규칙: 계층 기반 패키지(web/service/repository 수평 분할)는 빠른 시작용으로만 쓰고, 규모와 복잡도가 커지면 더 세분화해 모듈화하라.
- 근거: 시작은 빠르고 단순하지만(Fowler), 커지면 큰 양동이 세 개로는 부족하다.
- 출처: 34장 Package by Layer, p.304–306
- 태그: [모듈·아키텍처수준]

**R34-3**
- 규칙: 최상위 코드 구조가 기술 계층이 아니라 비즈니스 도메인을 드러내게(scream) 하라.
- 근거: 계층형 아키텍처는 도메인에 대해 아무것도 말해 주지 않는다. 서로 다른 두 도메인의 코드가 놀랄 만큼 비슷해 보인다.
- 출처: 34장 Package by Layer, p.306
- 태그: [모듈·아키텍처수준]

**R34-4**
- 규칙: 엄격한 계층형(strict layered)에서는 각 계층이 바로 아래 인접 계층에만 의존하게 하라.
- 근거: strict layered architecture의 정의다.
- 출처: 34장 Package by Layer, p.304
- 태그: [모듈·아키텍처수준]

### 기능 기반 패키지 (Package by Feature)
**R34-5**
- 규칙: 기능, 도메인 개념, 애그리거트 루트(aggregate root) 단위로 수직 분할하고, 패키지 이름은 묶은 개념을 반영하라. 다만 이것도 최적은 아니라는 점을 인지하라.
- 근거: 최상위 구조가 도메인을 드러내고 한 유스케이스의 변경 지점이 한곳에 모인다. 그래도 계층 기반과 기능 기반 모두 차선책이다.
- 출처: 34장 Package by Feature, p.306–307
- 태그: [모듈·아키텍처수준]

### 포트와 어댑터 (Ports and Adapters)
**R34-6**
- 규칙: 코드베이스를 안쪽(도메인)과 바깥쪽(인프라: UI, DB, 외부 연동)으로 나누고, 바깥쪽이 안쪽에 의존하게 하라. 그 반대는 절대 안 된다.
- 근거: 포트와 어댑터, 육각형(hexagonal), BCE의 핵심 규칙이다.
- 출처: 34장 Ports and Adapters, p.308
- 태그: [모듈·아키텍처수준]

**R34-7**
- 규칙: 안쪽(도메인)에 있는 것은 모두 유비쿼터스 도메인 언어(ubiquitous domain language)로 이름 지어라. 기술 접미사를 붙이지 마라.
- 근거: 도메인을 이야기할 때는 "orders repository"가 아니라 "orders"라고 말한다(DDD).
- 위반 예 → 개선 예: `OrdersRepository`(도메인 인터페이스) → `Orders`. 기술 구현체는 바깥에 `JdbcOrdersRepository`로 둔다.
- 출처: 34장 Ports and Adapters, p.309
- 태그: [코드수준]

**R34-8**
- 규칙: 경계를 넘는 데이터는 인터랙터와 마셜링(marshal)용 객체를 통해 전달하라.
- 근거: 그림 34.4는 단순화된 것이고, 실제로는 인터랙터와 경계 너머로 데이터를 옮기는 객체가 필요하다.
- 출처: 34장 Ports and Adapters, p.310
- 태그: [모듈·아키텍처수준]

### 컴포넌트 기반 패키지 (Package by Component)
**R34-9**
- 규칙: 아키텍처 원칙(예: "웹 컨트롤러는 리포지토리에 직접 접근하지 않는다")을 명시적으로 정의하라.
- 근거: 신입이 컨트롤러에 리포지토리를 직접 주입해 서비스 계층을 우회하는 일이 생긴다(relaxed layered architecture). 그러면 레코드 단위 권한 검사 같은 비즈니스 로직이 우회된다.
- 출처: 34장 Package by Component, p.311–312
- 태그: [모듈·아키텍처수준]

**R34-10**
- 규칙: 비즈니스 로직 계층을 건너뛰는 의존(컨트롤러→리포지토리)은 금지하라. CQRS처럼 의도된 경우에만 명시적 결정으로 허용하라.
- 근거: relaxed layered는 경우에 따라 의도된 결과일 수 있지만, 대부분은 바람직하지 않다.
- 출처: 34장 Package by Component, p.311
- 태그: [코드수준] [모듈·아키텍처수준]

**R34-11**
- 규칙: 비순환 의존 그래프(acyclic dependency graph)라고 해서 아키텍처를 지켰다고 판단하지 마라. 바람직하지 않은 의존은 비순환을 유지한 채로도 들어올 수 있다.
- 근거: 화살표가 모두 아래를 향해도 서비스를 우회하는 "속임수"가 가능하다.
- 출처: 34장 Package by Component, p.310–311
- 태그: [교훈]

**R34-12**
- 규칙: 아키텍처 규칙 준수를 "규율과 코드 리뷰"에만 맡기지 마라. 최소한 빌드 시점 정적 분석(NDepend, Structure101, Checkstyle, ArchUnit 류, 예: "`**/web`의 타입은 `**/data`에 접근 금지")으로 위반 시 빌드를 실패시켜라.
- 근거: 마감이 다가오면 규율은 무너진다. 사후 도구는 조잡하지만 효과는 있다.
- 출처: 34장 Package by Component, p.312–313
- 태그: [모듈·아키텍처수준]

**R34-13**
- 규칙: 가능하면 컴파일러로 아키텍처를 강제하라. 규율이나 사후 도구는 실수할 수 있고 피드백 루프가 길다.
- 근거: 방치하면 코드베이스가 큰 진흙 공(big ball of mud)이 된다.
- 출처: 34장 Package by Component, p.313; Organization Versus Encapsulation, p.319
- 태그: [모듈·아키텍처수준]

**R34-14**
- 규칙: 컴포넌트 기반 패키지에서는 한 굵은 단위(coarse-grained) 컴포넌트의 비즈니스 로직과 영속 코드를 하나의 패키지에 묶어라. 공개 인터페이스(예: `OrdersComponent`) 하나만 노출하고, UI(웹)는 그 컴포넌트 바깥에 분리하라.
- 근거: 주문을 다룰 코드는 갈 곳이 한 군데다. 내부의 관심사 분리(비즈니스와 영속성)는 소비자가 몰라도 되는 구현 세부사항이다.
- 출처: 34장 Package by Component, p.313–315
- 태그: [모듈·아키텍처수준]

**R34-15**
- 규칙: 컴포넌트는 "실행 환경 안에서, 깔끔한 인터페이스 뒤에 묶인 관련 기능의 묶음"으로 정의하라(C4 모델: 컨테이너→컴포넌트→클래스). jar 분리 여부는 직교하는 별도 관심사로 다뤄라.
- 근거: Simon Brown의 C4 정의다. 별도 jar 여부는 직교 관심사다.
- 출처: 34장 Package by Component, p.314–315
- 태그: [모듈·아키텍처수준]

**R34-16**
- 규칙: 모놀리스 안의 잘 정의된 컴포넌트를 마이크로서비스로 가는 디딤돌로 설계하라. 서비스와의 차이는 디커플링 모드뿐이다.
- 근거: 별도 OrdersService(SOA, 마이크로서비스)와 핵심 차이는 디커플링 모드다.
- 출처: 34장 Package by Component, p.315
- 태그: [모듈·아키텍처수준]

### 악마는 구현 세부사항에 있다 (The Devil Is in the Implementation Details)
**R34-17**
- 규칙: `public`을 반사적으로 붙이지 마라. 타입마다 패키지 바깥에서 들어오는 의존(inbound dependency)이 실제로 있는지 확인하고, 있을 때만 `public`으로 하라.
- 근거: 모든 타입을 public으로 하면 언어의 캡슐화 기능을 버리는 셈이다. 누구든 구현 클래스를 직접 인스턴스화해 의도한 아키텍처를 깰 수 있다.
- 위반 예 → 개선 예: `public class JdbcOrdersRepository` → `class JdbcOrdersRepository`(package-private), 인터페이스만 public으로 둔다.
- 출처: 34장 The Devil Is in the Implementation Details, p.315–316
- 태그: [코드수준]

### 조직화 대 캡슐화 (Organization Versus Encapsulation)
**R34-18**
- 규칙: 패키지를 폴더 같은 정리 수단이 아니라 캡슐화 수단으로 써라.
- 근거: 모든 타입이 public이면 패키지는 의미가 없어진다. 계층, 기능, 포트·어댑터, 컴포넌트 네 방식이 문법적으로 같아지고, 결국 전통적인 수평 계층 구조를 네 가지로 묘사한 것에 불과해진다.
- 출처: 34장 Organization Versus Encapsulation, p.316–317
- 태그: [코드수준] [모듈·아키텍처수준]

**R34-19**
- 규칙: 구현 클래스(`*Impl`, `Jdbc*Repository`)는 package-private으로 두고 런타임에 DI로 주입하라. 인터페이스 중에서도 다른 패키지에서 의존하는 것만 public으로 하라.
- 근거: 구현 클래스는 아무도 알 필요 없는 구현 세부사항이다.
- 출처: 34장 Organization Versus Encapsulation, p.317–318
- 태그: [코드수준]

**R34-20**
- 규칙: 기능 기반 패키지에서 컨트롤러만 public 진입점으로 두고 나머지를 숨긴다면, 다른 코드가 해당 도메인 데이터에 컨트롤러를 거쳐야만 접근하게 된다는 트레이드오프를 의식적으로 받아들일지 판단하라.
- 근거: 이 방식은 바람직할 수도, 아닐 수도 있다.
- 출처: 34장 Organization Versus Encapsulation, p.317
- 태그: [모듈·아키텍처수준]

**R34-21**
- 규칙: public 타입 수를 최소화하라. public 타입이 적을수록 잠재적 의존의 수가 줄어든다. 목표는 컴포넌트 인터페이스 하나만 public으로 두는 것이다.
- 근거: 그러면 패키지 바깥에서 `OrdersRepository`를 직접 쓸 방법이 사라져 컴파일러가 원칙을 강제한다. .NET에서는 `internal`과 컴포넌트별 어셈블리로 같은 효과를 낸다.
- 출처: 34장 Organization Versus Encapsulation, p.318–319
- 태그: [코드수준]

**R34-22**
- 규칙: 리플렉션(reflection)으로 접근 제한을 우회하지 마라.
- 근거: "리플렉션으로 속이지 않는 한… 제발 그러지 마라"(각주 9).
- 출처: 34장 각주 9, p.321
- 태그: [코드수준]

**R34-23**
- 규칙: Java 하위 패키지는 상위 패키지와 접근 권한 관계가 없다는 점을 전제로 설계하라. 패키지 계층은 이름과 디렉터리상의 구조일 뿐이므로, 하위 패키지로 쪼개면 package-private 캡슐화가 깨진다.
- 근거: 패키지와 하위 패키지 관계에 따른 접근 제한은 만들 수 없다(각주 8).
- 출처: 34장 각주 8, p.321
- 태그: [코드수준]

**R34-24**
- 규칙: 단일 소스 트리 모놀리스에서는 자기 규율이나 사후 컴파일 도구보다 컴파일러(접근 제한자)에 의존해 아키텍처 원칙을 강제하라.
- 근거: 모놀리스를 만드는 사람에게 저자가 명시적으로 권하는 방법이다.
- 출처: 34장 Organization Versus Encapsulation, p.319
- 태그: [모듈·아키텍처수준]

### 다른 디커플링 모드 (Other Decoupling Modes)
**R34-25**
- 규칙: 모듈 시스템(Java 9 모듈, OSGi)을 쓸 때는 public 타입과 공개(published, exported) 타입을 구분하라. 외부 소비용으로는 작은 부분집합만 export하라.
- 근거: 모듈 시스템을 제대로 쓰면 public과 published를 구분할 수 있다.
- 출처: 34장 Other Decoupling Modes, p.319
- 태그: [모듈·아키텍처수준]

**R34-26**
- 규칙: 소스 코드 트리(빌드 도구의 모듈, 프로젝트: Maven/Gradle/MSBuild)를 나눠 컴파일 시점 의존을 강제하라. 예: 도메인(기술 독립), 웹, 영속성. 웹과 영속성이 도메인에 의존하고 도메인은 아무것도 모르게 한다.
- 근거: 소스 수준 디커플링이다. 이상적으로는 컴포넌트마다 소스 트리를 두지만, 성능·복잡도·유지보수 비용이 따른다.
- 출처: 34장 Other Decoupling Modes, p.319–320
- 태그: [모듈·아키텍처수준]

**R34-27**
- 규칙: 소스 트리를 도메인/인프라 둘로만 나눴다면, 인프라 안에서 어댑터끼리 직접 호출하는 일(웹 컨트롤러→DB 리포지토리)을 접근 제한자나 규칙으로 막아라. 이른바 페리페리크 안티패턴(Périphérique anti-pattern)이다.
- 근거: 인프라 코드가 한 트리에 모여 있으면 도메인을 거치지 않고 바깥 순환도로로 돌아가는 호출이 가능해진다. 접근 제한자를 잊었다면 특히 그렇다.
- 출처: 34장 Other Decoupling Modes, p.320–321
- 태그: [모듈·아키텍처수준] [코드수준]

### 결론: 빠져 있는 조언 (Conclusion: The Missing Advice)
**R34-28**
- 규칙: 설계를 정할 때 네 가지를 함께 결정하라. ① 코드 구조로의 매핑 ② 코드 조직 방식 ③ 런타임 디커플링 모드 ④ 컴파일 타임 디커플링 모드.
- 근거: 구현 전략의 미묘한 부분을 고려하지 않으면 최선의 설계 의도도 순식간에 무너진다.
- 출처: 34장 Conclusion: The Missing Advice, p.321
- 태그: [모듈·아키텍처수준]

**R34-29**
- 규칙: 선택지는 적절한 곳에서 열어 두되 실용적으로 판단하라. 팀 규모, 숙련도, 솔루션 복잡도, 시간과 예산 제약을 함께 고려하라.
- 근거: 이상적인 분할에는 실제 비용이 있다.
- 출처: 34장 Conclusion: The Missing Advice, p.321
- 태그: [교훈]

**R34-30**
- 규칙: 패키지와 코드 의존만 보지 말고 데이터 모델 같은 다른 영역에서 생기는 결합도 점검하라.
- 근거: "watch out for coupling in other areas, such as data models."
- 출처: 34장 Conclusion: The Missing Advice, p.321
- 태그: [모듈·아키텍처수준]

**R34-31**
- 규칙: `*ServiceImpl` 같은 이름은 나쁜 이름으로 보고 피하라. 구현 클래스가 package-private으로 숨겨져 있다면 영향은 줄어든다.
- 근거: 각주 1은 "논쟁의 여지없이 끔찍한 클래스 이름이지만, 보게 되듯 별로 중요하지 않을 수도 있다"고 한다. 숨겨진 구현 세부라서 그렇다.
- 출처: 34장 각주 1, p.321
- 태그: [코드수준]

## 부록 A 아키텍처 고고학 (Architecture Archaeology)

### 조합 회계 시스템 (Union Accounting System) / 미니컴퓨터 고아원 (The Minicomputer Orphanage)
**RA-1**
- 규칙: 애플리케이션 출력은 추상 인터페이스(문자열을 감독자·서비스에 넘기기)로 내보내라. 애플리케이션이 실제 출력 장치(30cps 터미널 등)의 종류를 알지 못하게 하라.
- 근거: 문자 출력 경계는 의존성이 정상 방향(제어 흐름과 같은 방향)이었고, 애플리케이션이 출력 장치의 종류를 모르게 막아 주었다.
- 출처: 부록 A Union Accounting System, p.333–334
- 태그: [모듈·아키텍처수준]

**RA-2**
- 규칙: 상위 시스템이 하위 플러그인을 시작해야 할 때는 고정된 진입점(다형적 인터페이스)만 알게 하고, 컴파일 시점에는 플러그인에 의존하지 않게 하라(의존성 역전 경계).
- 근거: 감독자는 모든 애플리케이션을 같은 메모리 주소로 점프해 시작했다. 시작 지점 외에는 애플리케이션에 대해 아무것도 몰랐다.
- 출처: 부록 A Union Accounting System, p.334
- 태그: [모듈·아키텍처수준]

### 레이저 트림 (Laser Trim)
**RA-3**
- 규칙: 계층 사이 경계를 양방향 호출로 흐리지 마라. 하위 계층(MOP)을 특정 상위 계층에 맞춰 수정하거나 상위로 콜백시키지 마라.
- 근거: 유틸리티 계층과 MOP는 서로 호출하며 강하게 결합되어 사실상 분리된 계층이 아니었다. 결합이 곳곳에 퍼져 있었다.
- 출처: 부록 A Laser Trim, p.336–338
- 태그: [교훈] [모듈·아키텍처수준]

**RA-4**
- 규칙: 공유 코드를 팀이나 부서마다 포크(fork)해 수작업으로 변경을 주고받지 마라. 단일 소스로 관리하라.
- 근거: 디비전마다 MOP를 포크해서 갱신 내용을 손으로 표시한 리스팅을 주고받으며 수작업으로 통합했다.
- 출처: 부록 A Laser Trim, p.336
- 태그: [교훈]

**RA-5**
- 규칙: DSL이나 격리 계층(가상 머신 인터페이스)을 만들면 하위 계층의 특이사항이 DSL에 새지 않게 경계를 강제하라.
- 근거: 그 DSL은 하위 계층과 깊이 결합된 특이점이 많았고, 시스템 코드와 DSL 애플리케이션 사이 경계도 제대로 강제되지 않았다.
- 출처: 부록 A Laser Trim, p.337–338
- 태그: [모듈·아키텍처수준]

### 알루미늄 다이캐스트 모니터링 (Aluminum Die-Cast Monitoring)
**RA-6**
- 규칙: 협력적(비선점) 스케줄링 환경에서는 오래 걸리는 작업이 명시적으로 양보(yield)하게 해서, 대기 중인 다른 작업이 처리될 수 있게 하라.
- 근거: SPI 명령으로 더 낮은 우선순위 인터럽트를 처리하게 할 수 있었다. 오늘날 Java의 `Thread.yield()`에 해당한다.
- 출처: 부록 A Aluminum Die-Cast Monitoring, p.339
- 태그: [코드수준] [교훈]

### 4-TEL
**RA-7**
- 규칙: 변하는 이유와 배치 요구가 다른 책임(회선 다이얼·측정 대 결과 분석·리포트)은 별도 시스템이나 컴포넌트로 분리하고, 그 사이를 짧은 명령 패킷(작은 DSL, 예: "DIAL XXXX", "MEASURE") 같은 좁은 인터페이스로 연결하라.
- 근거: SAC와 COLT 분리는 메모리를 크게 줄이고 응답 속도를 높였다. 경계가 깨끗하고 디커플링이 잘 되어 있었다.
- 출처: 부록 A 4-TEL, p.340–341
- 태그: [모듈·아키텍처수준]

**RA-8**
- 규칙: 바이너리 하나로 이루어진 모놀리스를 피하라. 독립적으로 컴파일·배포할 수 있는 단위로 나누고, 단위 사이 호출은 간접 참조(vector table, 인터페이스, 다형적 디스패치)를 거치게 하라. 그래야 한 단위만 바꿔도 다른 단위를 다시 배포하지 않는다.
- 근거: 30K 단일 바이너리에서는 사소한 변경에도 주소가 밀려 칩 30개를 모두 교체해야 했다. "벡터화(Vectorization)"로 칩마다 따로 배포할 수 있게 되었다. 다형적 디스패치와 객체, 플러그인 아키텍처를 발명한 셈이었다.
- 출처: 부록 A 4-TEL, p.341–344
- 태그: [모듈·아키텍처수준]

**RA-9**
- 규칙: 새 기능을 플러그인으로 꽂으면 자동으로 바인딩되게(메뉴 노출, 메인과 연결) 설계해서, 기능 추가가 코어 수정 없이 이루어지게 하라.
- 근거: 기능 칩을 빈 소켓에 꽂으면 메뉴가 자동으로 나타나고 메인 애플리케이션과 자동으로 연결되었다.
- 출처: 부록 A 4-TEL, p.344

### 로즈 (ROSE) / 토론은 계속되었다 (The Debates Continued) / … 다른 이름으로 (... By Any Other Name)
**RA-38**
- 규칙: 계층 사이 의존은 제어 흐름 방향(GUI→표현→조작 규칙→DB)이 아니라 고수준 정책 쪽을 향하게 하라.
- 근거: ROSE는 계층 간 의존 규칙을 엄격하게 강제했지만 전통적인 제어 흐름 방향을 따랐다. 정책 쪽으로 의존을 향하게 하지 못한 것이 제품 몰락을 거들었다.

**RA-40**

### 건축사 등록 시험 (Architects Registry Exam)
**RA-42**
- 규칙: 첫 애플리케이션을 만들면서 미리 "재사용 프레임워크"를 설계하지 마라. 재사용 가능한 프레임워크는 여러 재사용 애플리케이션과 함께(최소 몇 개를 동시에) 만들어야 한다.
- 근거: 애플리케이션 하나를 기준으로 만든 4.5만 줄 프레임워크는 다른 애플리케이션에 맞지 않았다. 네 애플리케이션을 동시에 만들며 다시 짠 프레임워크는 맞았다. "사용 가능한 프레임워크를 먼저 만들기 전에는 재사용 가능한 프레임워크를 만들 수 없다."
- 출처: 부록 A Architects Registry Exam, p.371–373
- 태그: [교훈] [모듈·아키텍처수준]

**RA-43**
- 규칙: "깨끗한 OO 코드를 쓰면 저절로 재사용 가능해진다"는 믿음을 버려라. 재사용은 실제 재사용 사례로 검증하라.
- 근거: OO의 재사용 약속을 믿었다가 1년이 지연되었다.
- 출처: 부록 A Architects Registry Exam, p.371–372
- 태그: [교훈]

**RA-44**
- 규칙: 프레임워크를 만들 때는 고수준 정책을 담은 쪽에 의존이 향하게 하라. GUI처럼 정책이 프레임워크에 있으면 애플리케이션이 프레임워크에 꽂히는 플러그인(glue)이 되고, 채점처럼 정책이 애플리케이션에 있으면 프레임워크가 애플리케이션에 꽂힌다.
- 근거: GUI 쪽은 비네트가 프레임워크의 플러그인이었고, 채점 쪽은 채점 프레임워크가 비네트에 꽂혔다. 정적 링크였지만 의존 방향은 의존성 규칙과 일치했다.
- 출처: 부록 A Architects Registry Exam, p.372
- 태그: [모듈·아키텍처수준]

**RA-45**
- 규칙: 공통 부분을 추출할 때는 기존 코드를 차용하되, 모든 소비자에 "수정 없이" 맞도록 다시 다듬어라.
- 근거: 옛 프레임워크의 아이디어와 코드를 빌려 네 비네트 모두에 수정 없이 맞도록 재작업했다.
- 출처: 부록 A Architects Registry Exam, p.372
