## 5장 형식 맞추기 (Formatting)

### (도입부) p.76

**R-1** 규칙: 단순한 형식 규칙 집합을 정하고 모든 코드에 일관되게 적용하라.
- 근거: 엉망인 형식은 프로젝트 전반의 부주의를 드러내고 신뢰를 떨어뜨린다.
- 출처: 5장 도입부, p.75–76 · 태그: [일반]

**R-2** 규칙: 팀은 단 하나의 형식 규칙에 합의하고 모든 구성원이 따르라.
- 근거: 팀 작업은 한 사람이 쓴 것처럼 일관되어야 한다.
- 출처: 5장 도입부, p.76 · 태그: [일반]

**R-3** 규칙: 형식 규칙을 자동으로 적용하는 도구(포매터)를 사용하라.
- 근거: 도구가 규칙 적용을 대신해 일관성을 보장한다.
- 출처: 5장 도입부, p.76 · 태그: [일반]

### 형식을 맞추는 목적 (The Purpose of Formatting) p.76

**R-4** 규칙: "동작하게 만들기"보다 가독성(의사소통)을 우선 과제로 취급하라 — 형식은 무시하지도, 종교처럼 집착하지도 말라.
- 근거: 기능은 다음 릴리스에 바뀌지만 스타일과 가독성은 이후 모든 변경의 유지보수성에 영향을 준다.
- 출처: 5장 The Purpose of Formatting, p.76 · 태그: [일반]

### 적절한 행 길이를 유지하라 (Vertical Formatting) p.76–77

**R-5** 규칙: 소스 파일은 대체로 200행 내외로 유지하고 500행을 상한으로 삼아라(엄격한 규칙은 아니지만 매우 바람직).
- 근거: 큰 시스템(FitNesse 약 5만 행)도 작은 파일로 구성 가능하며, 작은 파일이 이해하기 쉽다.
- 출처: 5장 Vertical Formatting, p.77 · 태그: [일반]

### 신문 기사처럼 작성하라 (The Newspaper Metaphor) p.77–78

**R-6** 규칙: 파일(모듈) 이름은 단순하면서도 그 이름만으로 올바른 모듈인지 판단할 수 있도록 설명적으로 지어라.
- 근거: 신문의 표제처럼 이름이 읽을지 말지 결정하게 해준다.
- 출처: 5장 The Newspaper Metaphor, p.77 · 태그: [일반]

**R-7** 규칙: 파일 위쪽에 고수준 개념과 알고리즘을 두고, 아래로 내려갈수록 세부 사항을 늘려 맨 끝에 최저수준 함수를 배치하라.
- 근거: 신문 기사처럼 위에서 요지를 파악하고 필요할 때만 세부로 내려간다.
- 출처: 5장 The Newspaper Metaphor, p.77–78 · 태그: [일반]

**R-8** 규칙: 하나의 거대한 파일보다 작은 단위(대부분 작은 기사)로 나누어 구성하라.
- 근거: 신문이 대부분 짧은 기사로 구성되기에 읽을 수 있다.
- 출처: 5장 The Newspaper Metaphor, p.78 · 태그: [일반]

### 개념은 빈 행으로 분리하라 (Vertical Openness Between Concepts) p.78–79

**R-9** 규칙: 완결된 생각(패키지 선언, import 묶음, 각 함수) 사이는 빈 행으로 분리하라.
- 근거: 빈 행은 새로운 개념의 시작을 알리는 시각적 단서다.
- 위반 예 → 개선 예: 패키지·import·함수가 빈 행 없이 붙어 있음 → 각 사이에 빈 행 삽입
- 출처: 5장 Vertical Openness Between Concepts, p.78–79 · 태그: [일반]

### 세로 밀집도 (Vertical Density) p.79–80

**R-10** 규칙: 서로 밀접한 코드 행은 세로로 붙여 두고, 그 사이를 쓸모없는 주석 등으로 끊지 말라.
- 근거: 세로 밀집도는 연관성을 표현하며 "한눈에" 들어오게 한다.
- 위반 예 → 개선 예: 두 인스턴스 변수 사이에 `/** The class name ... */` 같은 무의미한 Javadoc → 주석 제거하고 붙여 쓰기
- 출처: 5장 Vertical Density, p.79–80 · 태그: [일반]

### 수직 거리 (Vertical Distance) p.80–84

**R-11** 규칙: 서로 밀접한 개념은 세로로 가까이 두라 [G10].
- 근거: 독자가 함수·변수를 찾아 파일과 상속 체인을 오르내리게 하면 이해에 쓸 에너지를 낭비한다.
- 출처: 5장 Vertical Distance, p.80 · 태그: [일반]

**R-12** 규칙: 밀접한 개념은 아주 타당한 이유가 없는 한 서로 다른 파일로 분리하지 말라.
- 근거: 파일을 넘나들게 하면 이해가 어렵다.
- 출처: 5장 Vertical Distance, p.80 · 태그: [일반]

**R-13** 규칙: protected 변수 사용을 피하라.
- 근거: 밀접한 개념(변수 정의)을 상속 계층 너머로 흩어 놓아 수직 거리를 늘린다.
- 출처: 5장 Vertical Distance, p.80 · 태그: [일반]

**R-14** 규칙: 같은 파일 안 개념 간 세로 간격은 서로의 이해에 얼마나 중요한지에 비례하도록(중요할수록 가깝게) 배치하라.
- 근거: 독자가 소스 파일 안을 이리저리 뛰어다니지 않게 한다.
- 출처: 5장 Vertical Distance, p.80 · 태그: [일반]

**R-15** 규칙: 지역 변수는 사용 위치에 최대한 가깝게 선언하라(짧은 함수라면 함수 맨 처음).
- 근거: 변수 선언 (Variable Declarations) — 사용처와 선언의 거리를 최소화한다.
- 출처: 5장 Vertical Distance – Variable Declarations, p.80 · 태그: [일반]

**R-16** 규칙: 루프 제어 변수는 루프 문 안에서 선언하라.
- 근거: 변수의 범위와 사용처가 일치한다.
- 위반 예 → 개선 예: `int i; ... for(i=0;...)` → `for (Test each : tests)`
- 출처: 5장 Vertical Distance – Variable Declarations, p.80–81 · 태그: [일반]

**R-17** 규칙: 긴 함수에서 블록 전체에서 쓰이는 변수는 예외적으로 블록 상단이나 루프 직전에 선언할 수 있다.
- 근거: 드문 경우 사용 범위가 블록 전체라 그 위치가 가장 가깝다.
- 출처: 5장 Vertical Distance – Variable Declarations, p.81 · 태그: [일반]

**R-18** 규칙: 인스턴스 변수는 클래스 맨 위 한 곳에 모아 선언하라(언어 관례를 따르되 모두가 아는 단일 위치에).
- 근거: 잘 설계된 클래스는 대부분의 메서드가 인스턴스 변수를 쓰므로 거리 증가가 없고, 모두가 선언 위치를 알아야 한다.
- 위반 예 → 개선 예: JUnit TestSuite처럼 클래스 중간에 `private String fName;` 숨김 → 클래스 최상단으로 이동
- 출처: 5장 Vertical Distance – Variable Declarations, p.81–82 · 태그: [일반]

**R-19** 규칙: 한 함수가 다른 함수를 호출하면 두 함수를 세로로 가깝게 두고, 가능하면 호출하는 함수를 호출되는 함수보다 위에 배치하라.
- 근거: 종속 함수 (Dependent Functions) — 자연스러운 흐름이 생기고, 독자는 정의가 곧 뒤따름을 신뢰할 수 있다.
- 출처: 5장 Vertical Distance – Dependent Functions, p.82–83 · 태그: [일반]

**R-20** 규칙: 상수는 그 값을 알아야 마땅한 적절한 수준에서 정의하고, 실제 사용하는 저수준 함수로 인자로 전달하라 — 잘 알려진 상수를 저수준 함수 안에 묻지 말라 [G35].
- 근거: "FrontPage" 같은 기대된 상수를 저수준 함수에 숨기면 찾기 어렵다.
- 위반 예 → 개선 예: `getPageNameOrDefault(request)` 내부에 "FrontPage" 하드코딩 → `getPageNameOrDefault(request, "FrontPage")`
- 출처: 5장 Vertical Distance – Dependent Functions, p.83 · 태그: [일반]

**R-21** 규칙: 개념적 친화도(직접 의존, 변수 사용, 비슷한 동작·공통 명명 체계)가 높은 코드일수록 세로로 가깝게 배치하라.
- 근거: 개념적 유사성 (Conceptual Affinity) — assertTrue/assertFalse 변형들은 서로 호출하지 않더라도 함께 있어야 한다.
- 출처: 5장 Vertical Distance – Conceptual Affinity, p.84 · 태그: [일반]

### 세로 순서 (Vertical Ordering) p.84–85

**R-22** 규칙: 함수 호출 의존성이 아래 방향을 향하게 하라 — 호출되는 함수를 호출하는 함수 아래에 두어 고수준→저수준 흐름을 만들어라.
- 근거: 가장 중요한 개념을 먼저, 세부는 마지막에 두어 처음 몇 함수만 훑어도 요지를 파악하게 한다(Pascal/C/C++의 선언 순서와 반대).
- 출처: 5장 Vertical Ordering, p.84–85 · 태그: [일반]

### 가로 형식 맞추기 (Horizontal Formatting) p.85–86

**R-23** 규칙: 행은 짧게 유지하고 최대 100–120자를 넘기지 말라(저자 한도 120).
- 근거: 프로그래머는 짧은 행을 선호하며, 120자를 넘는 것은 대개 부주의다.
- 출처: 5장 Horizontal Formatting, p.85–86 · 태그: [일반]

**R-24** 규칙: 폰트를 줄여 200자씩 한 화면에 넣는 식으로 긴 행을 정당화하지 말라.
- 근거: 모니터 폭과 무관하게 긴 행은 읽기 어렵다.
- 출처: 5장 Horizontal Formatting, p.85–86 · 태그: [일반]

### 가로 공백과 밀집도 (Horizontal Openness and Density) p.86

**R-25** 규칙: 할당 연산자 양쪽에 공백을 넣어 좌변과 우변을 분리하라.
- 근거: 할당문은 왼쪽·오른쪽 두 요소가 핵심이며 공백이 이를 강조한다.
- 출처: 5장 Horizontal Openness and Density, p.86 · 태그: [일반]

**R-26** 규칙: 함수 이름과 여는 괄호 사이에는 공백을 넣지 말라.
- 근거: 함수와 인수는 밀접하므로 떨어뜨리면 별개로 보인다.
- 출처: 5장 Horizontal Openness and Density, p.86 · 태그: [일반]

**R-27** 규칙: 함수 호출의 인수 사이 쉼표 뒤에 공백을 넣어 인수가 별개임을 보여라.
- 근거: 쉼표를 강조해 인수 구분을 명확히 한다.
- 출처: 5장 Horizontal Openness and Density, p.86 · 태그: [일반]

**R-28** 규칙: 공백으로 연산자 우선순위를 드러내라 — 우선순위 높은 곱셈 인수 사이는 붙이고, 낮은 덧셈·뺄셈 항 사이는 띄워라(포매터가 지울 수 있음을 인지).
- 근거: `b*b - 4*a*c`처럼 수식이 자연스럽게 읽힌다.
- 출처: 5장 Horizontal Openness and Density, p.86 · 태그: [일반]

### 가로 정렬 (Horizontal Alignment) p.87–88

**R-29** 규칙: 변수 선언의 이름이나 할당문의 우변을 세로로 맞추는 가로 정렬을 하지 말라.
- 근거: 정렬은 엉뚱한 부분(이름만, 우변만)을 강조해 타입·할당 연산자를 놓치게 하고, 자동 포매터가 어차피 지운다.
- 위반 예 → 개선 예: `private Socket            socket;` → `private Socket socket;`
- 출처: 5장 Horizontal Alignment, p.87–88 · 태그: [일반]

**R-30** 규칙: 정렬이 필요할 만큼 선언 목록이 길다면 정렬하지 말고 클래스를 쪼개라.
- 근거: 문제는 정렬 부족이 아니라 목록의 길이(클래스가 너무 큼)다.
- 출처: 5장 Horizontal Alignment, p.87 · 태그: [일반]

### 들여쓰기 (Indentation) p.88–89

**R-31** 규칙: 범위(파일→클래스→메서드→블록) 계층에 비례해 각 수준을 한 단계씩 들여써라.
- 근거: 들여쓰기가 없으면 프로그램은 사실상 읽을 수 없고, 들여쓰기로 범위를 빠르게 건너뛸 수 있다.
- 출처: 5장 Indentation, p.88–89 · 태그: [일반]

**R-32** 규칙: 짧은 if문·while문·함수라도 한 행으로 범위를 접지 말고 펼쳐서 들여써라.
- 근거: 들여쓰기 무시하기 (Breaking Indentation) — 저자는 접었다가 거의 항상 다시 들여쓰기를 되돌렸다.
- 위반 예 → 개선 예: `public String render() throws Exception {return ""; }` → 여러 행으로 펼침
- 출처: 5장 Indentation – Breaking Indentation, p.89 · 태그: [일반]

### 가짜 범위 (Dummy Scopes) p.90

**R-33** 규칙: 본문이 빈 while/for 문은 가능하면 피하고, 불가피하면 빈 본문(세미콜론)을 다음 행에 들여써 두거나 중괄호로 감싸라.
- 근거: 같은 행 끝에 붙은 세미콜론은 눈에 띄지 않아 속기 쉽다.
- 위반 예 → 개선 예: `while (dis.read(buf, 0, n) != -1);` → `while (...)\n  ;`
- 출처: 5장 Dummy Scopes, p.90 · 태그: [일반]

### 팀 규칙 (Team Rules) p.90

**R-34** 규칙: 개인 선호보다 팀이 합의한 형식(중괄호 위치, 들여쓰기 크기, 클래스·변수·메서드 명명)을 따르고, 그 규칙을 IDE 포매터에 인코딩하라.
- 근거: 독자는 한 파일에서 본 형식이 다른 파일에서도 같은 의미임을 신뢰할 수 있어야 하며, 개인 스타일의 뒤범벅은 복잡도를 더한다.
- 출처: 5장 Team Rules, p.90 · 태그: [일반]

### 밥 아저씨의 형식 규칙 (Uncle Bob's Formatting Rules) p.90–92

**R-35** 규칙: 코딩 표준은 문서보다 그 표준을 따르는 예시 코드로 보여라.
- 근거: 코드 자체가 최고의 코딩 표준 문서다(Listing 5-6).
- 출처: 5장 Uncle Bob's Formatting Rules, p.90 · 태그: [일반]

**R-36** 규칙: 도달할 수 없는 지점에는 조용히 넘어가지 말고 명시적 오류를 던져라.
- 근거: Listing 5-6의 `throw new Error("Cannot get here")`가 보여주는 관행.
- 출처: 5장 Uncle Bob's Formatting Rules (Listing 5-6), p.92 · 태그: [일반]

## 6장 객체와 자료 구조 (Objects and Data Structures)

### (도입부) p.93

**R-37** 규칙: private 변수에 기계적으로 getter/setter를 붙여 공개하지 말라.
- 근거: 변수를 private으로 두는 이유는 남이 의존하지 않게 해 타입·구현을 자유롭게 바꾸기 위함이다.
- 출처: 6장 도입부, p.93 · 태그: [일반]

### 자료 추상화 (Data Abstraction) p.93–95

**R-38** 규칙: 구현(예: 직교/극 좌표)을 드러내지 않는 추상 인터페이스로 데이터를 노출하라.
- 근거: 사용자는 구현을 몰라도 데이터의 본질을 조작할 수 있어야 한다.
- 위반 예 → 개선 예: `public double x, y;` → `interface Point { getX(); setCartesian(x,y); getR(); setPolar(r,theta); }`
- 출처: 6장 Data Abstraction, p.93–94 · 태그: [일반]

**R-39** 규칙: 인터페이스 메서드로 접근 정책을 강제하라(예: 읽기는 개별로, 쓰기는 원자적으로 함께).
- 근거: Point 인터페이스는 좌표를 함께 설정하도록 강제한다.
- 출처: 6장 Data Abstraction, p.94 · 태그: [일반]

**R-40** 규칙: 변수 하나당 getter/setter 하나를 붙이는 것을 "구현 은닉"으로 간주하지 말라 — 은닉은 함수 계층이 아니라 추상화의 문제다.
- 근거: private 변수 + 단일 변수 접근자도 여전히 구현을 노출한다.
- 출처: 6장 Data Abstraction, p.94 · 태그: [일반]

**R-41** 규칙: 구체적 단위 대신 추상 개념으로 데이터를 표현하라.
- 근거: 데이터 형태를 드러내지 않는 것이 바람직하며, 최악은 생각 없이 getter/setter를 추가하는 것이다.
- 위반 예 → 개선 예: `getFuelTankCapacityInGallons(); getGallonsOfGasoline();` → `getPercentFuelRemaining();`
- 출처: 6장 Data Abstraction, p.94–95 · 태그: [일반]

### 자료/객체 비대칭 (Data/Object Anti-Symmetry) p.95–97

**R-42** 규칙: 객체(데이터를 숨기고 동작을 공개)와 자료 구조(데이터를 공개하고 의미 있는 동작이 없음)를 명확히 구분해 설계하라.
- 근거: 두 정의는 정반대이며 그 차이가 광범위한 결과를 낳는다.
- 출처: 6장 Data/Object Anti-Symmetry, p.95 · 태그: [일반]

**R-43** 규칙: 새 자료 타입이 자주 추가될 영역에는 객체/다형성을, 새 함수(동작)가 자주 추가될 영역에는 자료 구조+절차적 코드를 선택하라.
- 근거: 절차적 코드는 함수 추가가 쉽고 타입 추가가 어렵고, OO는 그 반대다.
- 위반 예 → 개선 예: 도형 타입이 자주 늘어나는데 `Geometry.area()`의 instanceof 분기 → `Shape.area()` 다형성
- 출처: 6장 Data/Object Anti-Symmetry, p.95–97 · 태그: [일반]

**R-44** 규칙: "모든 것은 객체"라는 신화를 따르지 말고, 필요하면 단순 자료 구조와 그것을 다루는 프로시저를 사용하라.
- 근거: 성숙한 프로그래머는 때로 단순 자료 구조가 맞다는 것을 안다.
- 출처: 6장 Data/Object Anti-Symmetry, p.97 · 태그: [일반]

**R-45** 규칙: 비지터(VISITOR)/이중 디스패치로 OO의 함수 추가 어려움을 우회할 때는 그 비용(구조가 절차적으로 회귀)을 인지하고 선택하라.
- 근거: 각주 — 이 기법들은 자체 비용이 있다.
- 출처: 6장 Data/Object Anti-Symmetry 각주 1, p.96 · 태그: [일반]

### 디미터 법칙 (The Law of Demeter) p.97–98

**R-46** 규칙: 모듈은 자신이 조작하는 객체의 내부 구조를 알지 말아야 하며, 객체는 접근자로 내부 구조를 노출하지 말라.
- 근거: 객체는 데이터를 숨기고 연산을 공개해야 한다.
- 출처: 6장 The Law of Demeter, p.97 · 태그: [일반]

**R-47** 규칙: 클래스 C의 메서드 f는 C 자신, f가 생성한 객체, f의 인수로 전달된 객체, C의 인스턴스 변수에 담긴 객체의 메서드만 호출하라 — 허용된 메서드가 반환한 객체의 메서드는 호출하지 말라("낯선 사람이 아닌 친구와만 대화하라").
- 근거: 디미터 법칙의 정확한 정의.
- 위반 예: `ctxt.getOptions().getScratchDir().getAbsolutePath()`
- 출처: 6장 The Law of Demeter, p.97–98 · 태그: [일반]

### 기차 충돌 (Train Wrecks) p.98–99

**R-48** 규칙: 여러 호출을 줄줄이 잇는 "기차 충돌" 체인을 피하고, 필요하면 지역 변수로 나눠라 [G36].
- 근거: 이런 체인은 일반적으로 조잡한 스타일로 간주된다.
- 위반 예 → 개선 예: `a.getB().getC().getD()` → `B b = a.getB(); C c = b.getC(); D d = c.getD();`
- 출처: 6장 Train Wrecks, p.98 · 태그: [일반]

**R-49** 규칙: 디미터 위반 여부는 대상이 객체인지 자료 구조인지로 판단하라 — 객체면 내부 탐색은 위반, 동작 없는 자료 구조면 디미터가 적용되지 않는다.
- 근거: 자료 구조는 본래 내부 구조를 노출한다.
- 출처: 6장 Train Wrecks, p.98 · 태그: [일반]

**R-50** 규칙: 자료 구조는 public 변수만, 객체는 private 변수와 public 함수만 갖게 해 둘의 구분을 명확히 하라(프레임워크가 bean 접근자를 강제하는 경우는 예외).
- 근거: 자료 구조에 접근자를 붙이면 디미터 위반 여부가 혼란스러워진다(`ctxt.options.scratchDir.absolutePath`라면 혼동 없음).
- 출처: 6장 Train Wrecks, p.98–99 · 태그: [일반]

### 잡종 구조 (Hybrids) p.99

**R-51** 규칙: 중요한 동작 함수와 public 변수(또는 사실상 public인 접근자/설정자)를 함께 가진 절반 객체·절반 자료 구조 잡종을 만들지 말라.
- 근거: 함수 추가도 타입 추가도 어려운 최악의 조합이며, 외부 함수가 변수를 절차적으로 쓰도록 유혹한다(기능 욕심, Feature Envy).
- 출처: 6장 Hybrids, p.99 · 태그: [일반]

### 구조체 감추기 (Hiding Structure) p.99–100

**R-52** 규칙: 객체에게는 내부를 묻지 말고 무언가를 하라고 시켜라(Tell, Don't Ask) — 내부 값을 꺼내려는 의도(목적)를 파악해 그 일을 객체 메서드로 위임하라.
- 근거: 객체가 내부를 숨기고 호출자의 디미터 위반을 막는다.
- 위반 예 → 개선 예: `outputDir = ctxt.getOptions().getScratchDir().getAbsolutePath(); new FileOutputStream(outputDir + ...)` → `ctxt.createScratchFileStream(classFileName)`
- 출처: 6장 Hiding Structure, p.99–100 · 태그: [일반]

**R-53** 규칙: 내부 탐색을 피하려고 `ctxt.getAbsolutePathOfScratchDirectoryOption()` 같은 메서드를 무한정 추가하는 방식은 피하라.
- 근거: 객체 메서드의 폭발을 낳는다.
- 출처: 6장 Hiding Structure, p.99 · 태그: [일반]

**R-54** 규칙: 한 코드 안에 서로 다른 추상화 수준(점, 슬래시, 확장자, File 객체 조합 등)을 섞지 말라 [G34][G6].
- 근거: 세부 수준 혼합은 의도를 흐린다.
- 출처: 6장 Hiding Structure, p.99 · 태그: [일반]

### 자료 전달 객체 (Data Transfer Objects) p.100–101

**R-55** 규칙: DB 통신·소켓 메시지 파싱 등 원시 데이터를 애플리케이션 객체로 변환하는 첫 단계에는 public 변수만 있고 함수가 없는 DTO를 사용하라.
- 근거: DTO는 자료 구조의 정수이며 이런 경계에서 매우 유용하다.
- 출처: 6장 Data Transfer Objects, p.100 · 태그: [일반]

**R-56** 규칙: 빈(bean) 형태의 private 변수+getter/setter가 진짜 캡슐화를 제공한다고 착각하지 말라.
- 근거: bean의 준캡슐화는 OO 순수주의자의 기분을 낫게 할 뿐 다른 이점은 거의 없다.
- 출처: 6장 Data Transfer Objects, p.100 · 태그: [일반]

### 활성 레코드 (Active Record) p.101

**R-57** 규칙: 활성 레코드(save/find 같은 탐색 메서드를 가진 DTO)에 비즈니스 규칙 메서드를 넣지 말고, 자료 구조로 취급하며 비즈니스 규칙은 내부 데이터(활성 레코드 인스턴스)를 숨기는 별도 객체에 두어라.
- 근거: 비즈니스 규칙을 넣으면 자료 구조와 객체의 잡종이 된다.
- 출처: 6장 Active Record, p.101 · 태그: [일반]

### 결론 (Conclusion) p.101

**R-58** 규칙: 시스템의 각 부분마다 필요한 유연성(새 타입 추가 vs 새 동작 추가)에 따라 객체와 자료 구조 중 편견 없이 선택하라.
- 근거: 좋은 개발자는 편견 없이 당면 작업에 최선인 접근을 고른다.
- 출처: 6장 Conclusion, p.101 · 태그: [일반]

## 7장 오류 처리 (Error Handling)

### (도입부) p.103

**R-59** 규칙: 오류 처리 코드가 본래 로직을 가리지 않게 하라.
- 근거: 오류 처리는 중요하지만, 로직을 흐린다면 잘못된 것이다.
- 출처: 7장 도입부, p.103 · 태그: [일반]

### 오류 코드보다 예외를 사용하라 (Use Exceptions Rather Than Return Codes) p.104–105

**R-60** 규칙: 오류 플래그를 설정하거나 오류 코드를 반환하지 말고 예외를 던져라.
- 근거: 오류 코드는 호출자가 즉시 확인해야 하고 잊기 쉬우며 호출자를 어지럽힌다.
- 위반 예 → 개선 예: `if (handle != DeviceHandle.INVALID) {...} else logger.log(...)` → `try { tryToShutDown(); } catch (DeviceShutDownError e) { logger.log(e); }`
- 출처: 7장 Use Exceptions Rather Than Return Codes, p.104 · 태그: [일반]

**R-61** 규칙: 알고리즘 로직과 오류 처리를 별도 함수로 분리하라(예: `sendShutDown`의 try/catch와 `tryToShutDown`의 본 로직).
- 근거: 얽혀 있던 두 관심사를 분리하면 각각 독립적으로 이해할 수 있다.
- 출처: 7장 Use Exceptions Rather Than Return Codes, p.104–105 · 태그: [일반]

### Try-Catch-Finally 문부터 작성하라 (Write Your Try-Catch-Finally Statement First) p.105–106

**R-62** 규칙: 예외가 발생할 수 있는 코드를 작성할 때는 try-catch-finally 문부터 작성해 범위를 정의하라.
- 근거: try 블록은 트랜잭션과 같아서 catch는 try에서 무슨 일이 있든 프로그램을 일관된 상태로 남겨야 하며, 호출자가 기대할 바를 정의한다.
- 출처: 7장 Write Your Try-Catch-Finally Statement First, p.105 · 태그: [일반]

**R-63** 규칙: 먼저 예외를 강제하는 테스트를 작성하고, 그 테스트를 만족시키도록 핸들러에 동작을 추가하라(TDD로 try 블록의 트랜잭션 범위를 먼저 구축).
- 근거: 트랜잭션 성격의 범위를 먼저 만들고 유지하게 된다.
- 위반 예 → 개선 예: 예외 테스트 없이 구현 → `@Test(expected = StorageException.class) retrieveSectionShouldThrowOnInvalidFileName()` 먼저
- 출처: 7장 Write Your Try-Catch-Finally Statement First, p.105–106 · 태그: [일반]

**R-64** 규칙: catch하는 예외 타입을 실제로 던져지는 구체 타입으로 좁혀라.
- 근거: 리팩터링 단계에서 `Exception` → `FileNotFoundException`으로 좁혔다.
- 출처: 7장 Write Your Try-Catch-Finally Statement First, p.106 · 태그: [일반]

**R-65** 규칙: 하위 예외를 잡아 의미 있는 도메인 예외로 다시 던질 때 원인 예외를 함께 전달하라.
- 근거: `throw new StorageException("retrieval error", e)` 처럼 원인을 보존한다.
- 출처: 7장 Write Your Try-Catch-Finally Statement First, p.106 · 태그: [일반]

### 미확인 예외를 사용하라 (Use Unchecked Exceptions) p.106–107

**R-66** 규칙: 일반 애플리케이션 개발에서는 확인된 예외(checked exception) 대신 미확인 예외를 사용하라.
- 근거: 확인된 예외는 개방-폐쇄 원칙(OCP)을 위반해 하위 변경이 상위 모든 시그니처를 연쇄 수정하게 하고, 캡슐화를 깬다.
- 출처: 7장 Use Unchecked Exceptions, p.106–107 · 태그: [Java특화]

**R-67** 규칙: 호출자가 반드시 잡아야 하는 핵심 라이브러리를 작성할 때만 확인된 예외를 고려하라.
- 근거: 그런 경우엔 유용할 수 있지만 일반적으로 의존성 비용이 이점보다 크다.
- 출처: 7장 Use Unchecked Exceptions, p.107 · 태그: [Java특화]

**R-68** 규칙: 저수준 함수의 예외 세부를 throw 경로상의 모든 함수가 알아야 하는 설계를 피하라.
- 근거: 예외의 목적은 멀리 떨어진 곳에서 오류를 처리하는 것인데 경로 전체가 저수준 세부를 알게 되면 캡슐화가 깨진다.
- 출처: 7장 Use Unchecked Exceptions, p.107 · 태그: [일반]

### 예외에 의미를 제공하라 (Provide Context with Exceptions) p.107

**R-69** 규칙: 던지는 모든 예외에 오류의 원인과 위치를 판단할 수 있는 맥락을 담고, 오류 메시지에 실패한 연산과 실패 유형을 명시하라.
- 근거: 스택 트레이스는 실패한 연산의 의도를 알려주지 않는다.
- 출처: 7장 Provide Context with Exceptions, p.107 · 태그: [일반]

**R-70** 규칙: 애플리케이션이 로깅을 한다면 catch에서 오류를 로깅할 수 있을 만큼 충분한 정보를 예외와 함께 넘겨라.
- 근거: catch 지점에서 의미 있는 로그를 남기기 위함.
- 출처: 7장 Provide Context with Exceptions, p.107 · 태그: [일반]

### 호출자를 고려해 예외 클래스를 정의하라 (Define Exception Classes in Terms of a Caller's Needs) p.107–109

**R-71** 규칙: 예외 클래스는 출처나 유형이 아니라 호출자가 어떻게 잡는가를 기준으로 정의하라.
- 근거: 대부분의 처리 작업은 원인과 무관하게 비슷하다(오류 기록 후 진행).
- 출처: 7장 Define Exception Classes in Terms of a Caller's Needs, p.107–108 · 태그: [일반]

**R-72** 규칙: 서드파티 API가 여러 예외를 던져 catch가 중복되면, API를 감싸는 래퍼에서 예외를 공통 타입 하나로 변환하라.
- 근거: 중복을 제거하고 호출 코드가 단순해진다.
- 위반 예 → 개선 예: `catch (DeviceResponseException) {...} catch (ATM1212UnlockedException) {...} catch (GMXError) {...}` → `LocalPort`가 모두 `PortDeviceFailure`로 변환
- 출처: 7장 Define Exception Classes in Terms of a Caller's Needs, p.108–109 · 태그: [일반]

**R-73** 규칙: 서드파티 API는 래퍼로 감싸라.
- 근거: 의존성을 최소화해 라이브러리 교체가 쉬워지고, 테스트 시 모킹이 쉬우며, 벤더 API 설계에 묶이지 않고 원하는 API를 정의할 수 있다.
- 출처: 7장 Define Exception Classes in Terms of a Caller's Needs, p.109 · 태그: [일반]

**R-74** 규칙: 한 코드 영역에는 예외 클래스 하나로 충분한 경우가 많다 — 예외 정보로 오류를 구분하고, 한 예외는 잡고 다른 예외는 통과시켜야 할 때만 별도 클래스를 만들어라.
- 근거: 불필요한 예외 클래스 증식을 막는다.
- 출처: 7장 Define Exception Classes in Terms of a Caller's Needs, p.109 · 태그: [일반]

### 정상 흐름을 정의하라 (Define the Normal Flow) p.109–110

**R-75** 규칙: 오류 감지는 프로그램 가장자리로 밀어내라 — 외부 API를 감싸 자체 예외를 던지고, 코드 위에 처리기를 정의해 중단된 계산을 다뤄라.
- 근거: 비즈니스 로직과 오류 처리가 잘 분리되어 본 코드가 깔끔한 알고리즘처럼 보인다.
- 출처: 7장 Define the Normal Flow, p.109 · 태그: [일반]

**R-76** 규칙: 예외가 정상적인 비즈니스 분기(특수 사례)를 표현하는 데 쓰이고 있다면 특수 사례 패턴 (SPECIAL CASE PATTERN)으로 대체해 클라이언트가 예외 상황을 처리하지 않게 하라.
- 근거: 특수 사례 동작을 객체 안에 캡슐화하면 클라이언트 코드가 단순해진다.
- 위반 예 → 개선 예: `try { m_total += dao.getMeals(id).getTotal(); } catch (MealExpensesNotFound e) { m_total += getMealPerDiem(); }` → DAO가 항상 `MealExpenses`(없으면 `PerDiemMealExpenses`) 반환
- 출처: 7장 Define the Normal Flow, p.109–110 · 태그: [일반]

### null을 반환하지 마라 (Don't Return Null) p.110–111

**R-77** 규칙: 메서드에서 null을 반환하지 말고 예외를 던지거나 특수 사례 객체를 반환하라.
- 근거: null 반환은 호출자에게 null 확인 부담을 떠넘기고, 확인 하나만 빠져도 NullPointerException으로 애플리케이션이 통제를 잃는다.
- 출처: 7장 Don't Return Null, p.110 · 태그: [일반]

**R-78** 규칙: 코드에 null 확인이 과도하게 많다면 "확인 누락"이 아니라 "null 반환 설계"를 문제로 보고 고쳐라.
- 근거: 문제는 null 확인이 빠진 것이 아니라 너무 많은 것이다.
- 출처: 7장 Don't Return Null, p.110 · 태그: [일반]

**R-79** 규칙: null을 반환하는 서드파티 API는 예외를 던지거나 특수 사례 객체를 반환하는 메서드로 감싸라.
- 근거: null이 내 코드로 새어 들어오지 않게 한다.
- 출처: 7장 Don't Return Null, p.110 · 태그: [일반]

**R-80** 규칙: 컬렉션을 반환하는 메서드는 결과가 없을 때 null 대신 빈 컬렉션(예: `Collections.emptyList()`)을 반환하라.
- 근거: 호출자의 null 확인이 사라지고 NPE 가능성이 최소화된다.
- 위반 예 → 개선 예: `if (employees != null) for(...)` → `for (Employee e : getEmployees())`
- 출처: 7장 Don't Return Null, p.111 · 태그: [일반]

**R-81** 규칙: NullPointerException을 최상위에서 잡는 방식에 의존하지 말라.
- 근거: 애플리케이션 깊은 곳에서 던져진 NPE에 대해 할 수 있는 마땅한 대응이 없다.
- 출처: 7장 Don't Return Null, p.110 · 태그: [일반]

### null을 전달하지 마라 (Don't Pass Null) p.111–112

**R-82** 규칙: null을 기대하는 API가 아니라면 메서드 인수로 null을 전달하지 말라.
- 근거: null 반환보다 null 전달이 더 나쁘다.
- 출처: 7장 Don't Pass Null, p.111 · 태그: [일반]

**R-83** 규칙: 기본적으로 null 전달을 금지하는 정책을 채택하고, 인수 목록의 null을 문제의 신호로 취급하라.
- 근거: 호출자가 실수로 넘긴 null을 처리할 좋은 방법이 대부분 언어에 없다 — 새 예외 타입은 처리기 정의가 애매하고, assert는 문서화일 뿐 런타임 오류를 막지 못한다.
- 출처: 7장 Don't Pass Null, p.111–112 · 태그: [일반]

### 결론 (Conclusion) p.112

**R-84** 규칙: 오류 처리를 주 로직과 독립적으로 볼 수 있는 별도 관심사로 다뤄라.
- 근거: 그래야 깨끗하면서도 견고한 코드를 쓸 수 있고 유지보수성이 크게 향상된다.
- 출처: 7장 Conclusion, p.112 · 태그: [일반]

## 8장 경계 (Boundaries)

### 외부 코드 사용하기 (Using Third-Party Code) p.114–115

**R-85** 규칙: Map 같은 범용 경계 인터페이스를 시스템 곳곳에 넘기지 말고, 애플리케이션 요구에 맞춰 제한된 인터페이스를 가진 클래스(예: `Sensors`)로 감싸라.
- 근거: 범용 인터페이스는 원치 않는 능력(clear(), 임의 타입 저장)을 노출하고, 인터페이스가 바뀌면 고칠 곳이 많아진다.
- 위반 예 → 개선 예: `Sensor s = (Sensor) sensors.get(id);` 를 곳곳에 → `class Sensors { Sensor getById(String id) }`
- 출처: 8장 Using Third-Party Code, p.114–115 · 태그: [일반]

**R-86** 규칙: 형변환과 타입 관리(제네릭 사용 여부 등)는 경계를 감싼 클래스 내부의 구현 세부로 숨겨라.
- 근거: 클라이언트가 형변환 책임을 반복해서 지지 않고, 경계가 바뀌어도 영향이 적다.
- 출처: 8장 Using Third-Party Code, p.115 · 태그: [일반]

**R-87** 규칙: 경계 인터페이스(Map 등)는 그것을 사용하는 클래스나 가까운 클래스 계열 안에만 두고, 공개 API의 반환값이나 인수로 쓰지 말라.
- 근거: 모든 Map 사용을 감쌀 필요는 없지만 경계 인터페이스를 시스템 전역에 퍼뜨리면 안 된다.
- 출처: 8장 Using Third-Party Code, p.115 · 태그: [일반]

**R-88** 규칙: 경계를 감싼 클래스에서 설계·비즈니스 규칙을 강제하라.
- 근거: 이해하기 쉽고 오용하기 어려운 코드가 된다.
- 출처: 8장 Using Third-Party Code, p.115 · 태그: [일반]

### 경계 살피고 익히기 (Exploring and Learning Boundaries) p.116

**R-89** 규칙: 서드파티 코드를 프로덕션 코드에서 바로 시험하지 말고, 우리가 사용하려는 방식대로 API를 호출하는 학습 테스트 (learning tests)를 먼저 작성해 이해를 검증하라.
- 근거: 학습과 통합을 동시에 하면 두 배로 어렵고, 버그가 우리 코드인지 그들 코드인지 헤맨다.
- 출처: 8장 Exploring and Learning Boundaries, p.116 · 태그: [일반]

### log4j 익히기 (Learning log4j) p.116–118

**R-90** 규칙: 학습 테스트로 알아낸 서드파티 사용법을 자체 클래스로 캡슐화해 나머지 애플리케이션을 경계 인터페이스로부터 격리하라.

**R-92** 규칙: 서드파티 패키지의 새 버전이 나오면 학습 테스트를 실행해 동작 차이를 확인하라.
- 근거: 새 릴리스마다 위험이 따르며, 비호환 변경을 즉시 발견할 수 있다.
- 출처: 8장 Learning Tests Are Better Than Free, p.118 · 태그: [일반]

**R-93** 규칙: 학습 필요 여부와 무관하게, 깨끗한 경계는 프로덕션 코드와 같은 방식으로 인터페이스를 사용하는 아웃바운드(경계) 테스트 묶음으로 뒷받침하라.
- 근거: 경계 테스트가 없으면 마이그레이션이 어려워 구버전에 필요 이상으로 머물게 된다.
- 출처: 8장 Learning Tests Are Better Than Free, p.118 · 태그: [일반]

### 아직 존재하지 않는 코드를 사용하기 (Using Code That Does Not Yet Exist) p.118–119

**R-94** 규칙: 상대 API가 아직 정의되지 않았다면 막히지 말고 "우리가 바라는 인터페이스"를 직접 정의해 그에 맞춰 개발하라.
- 근거: 우리가 통제하는 인터페이스라 클라이언트 코드가 읽기 쉽고 목적에 집중된다.
- 출처: 8장 Using Code That Does Not Yet Exist, p.118–119 · 태그: [일반]

**R-95** 규칙: 실제 API가 정해지면 어댑터 (ADAPTER)로 우리 인터페이스와 실제 API를 연결해, API 변경 시 수정할 곳을 한 곳으로 만들어라.
- 근거: 어댑터가 API와의 상호작용을 캡슐화한다(TransmitterAdapter).
- 출처: 8장 Using Code That Does Not Yet Exist, p.119 · 태그: [일반]

**R-96** 규칙: 자체 인터페이스가 만드는 이음새 (seam)를 활용해 가짜 구현(FakeTransmitter)으로 클라이언트를 테스트하고, 실제 API가 생기면 올바른 사용을 확인하는 경계 테스트를 추가하라.
- 근거: 테스트하기 편리한 이음새가 생긴다.
- 출처: 8장 Using Code That Does Not Yet Exist, p.119 · 태그: [일반]

### 깨끗한 경계 (Clean Boundaries) p.120

**R-97** 규칙: 서드파티 세부 사항을 아는 코드를 최소화하라 — 통제 불가능한 것보다 통제 가능한 것에 의존하라.
- 근거: 그렇지 않으면 통제 못하는 것이 결국 우리를 통제한다.
- 출처: 8장 Clean Boundaries, p.120 · 태그: [일반]

**R-98** 규칙: 서드파티 경계를 참조하는 위치를 코드 내 극소수로 제한하라(Map처럼 감싸거나 ADAPTER로 변환).
- 근거: 코드 가독성이 좋아지고, 경계 사용이 일관되며, 서드파티 변경 시 유지보수 지점이 줄어든다.
- 출처: 8장 Clean Boundaries, p.120 · 태그: [일반]

**R-99** 규칙: 경계 코드는 명확히 분리하고 기대 동작을 정의하는 테스트를 갖춰라.
- 근거: 경계에서는 변경이 일어나며, 미래 변경 비용을 낮춰야 한다.
- 출처: 8장 Clean Boundaries, p.120 · 태그: [일반]

## 9장 단위 테스트 (Unit Tests)

### (도입부) p.121–122

**R-100** 규칙: 테스트를 일회용 수동 드라이버로 끝내지 말고 자동화된 테스트로 작성해 코드와 함께 같은 소스 패키지에 체크인하라.
- 근거: 다른 사람도 편하게 실행할 수 있어야 한다.
- 출처: 9장 도입부, p.122 · 태그: [일반]

**R-101** 규칙: 시간·OS 같은 외부 요소는 코드와 격리하고 모킹해, 테스트에서 시간을 직접 제어(진행)하며 상태 변화를 검증하라.
- 근거: 저자가 타이머를 지금 테스트한다면 표준 시간 함수를 모킹해 절대적 통제권을 가질 것이라 함.
- 출처: 9장 도입부, p.122 · 태그: [일반]

### TDD 법칙 세 가지 (The Three Laws of TDD) p.122–123

**R-102** 규칙: 실패하는 단위 테스트를 작성하기 전에는 프로덕션 코드를 작성하지 말라 (제1법칙).
- 근거: 테스트가 프로덕션 코드를 앞서 이끈다.
- 출처: 9장 The Three Laws of TDD, p.122 · 태그: [일반]

**R-103** 규칙: 실패하기에 충분한 만큼만 단위 테스트를 작성하라 — 컴파일 실패도 실패다 (제2법칙).
- 근거: 테스트와 코드가 수십 초 주기로 함께 작성된다.
- 출처: 9장 The Three Laws of TDD, p.122 · 태그: [일반]

**R-104** 규칙: 현재 실패하는 테스트를 통과시킬 만큼만 프로덕션 코드를 작성하라 (제3법칙).
- 근거: 테스트가 거의 모든 프로덕션 코드를 커버하게 된다.
- 출처: 9장 The Three Laws of TDD, p.122–123 · 태그: [일반]

### 깨끗한 테스트 코드 유지하기 (Keeping Tests Clean) p.123–124

**R-105** 규칙: 테스트 코드를 프로덕션 코드와 동일한 품질 기준(좋은 이름, 짧고 설명적인 함수, 좋은 설계)으로 유지하라 — "빠르고 지저분한" 테스트를 허용하지 말라.
- 근거: 지저분한 테스트는 테스트가 없는 것과 같거나 더 나쁘다 — 변경이 어려워 결국 버려지고, 테스트를 잃으면 결함이 늘고 코드가 썩는다.
- 출처: 9장 Keeping Tests Clean, p.123–124 · 태그: [일반]

### 테스트는 유연성, 유지보수성, 재사용성을 제공한다 (Tests Enable the -ilities) p.124

**R-106** 규칙: 프로덕션 코드를 커버하는 자동화 단위 테스트 묶음을 유지해 두려움 없이 변경·리팩터링하라.
- 근거: 테스트가 있어야 변경을 두려워하지 않으며, 테스트가 모든 "-ility"를 가능하게 한다.
- 출처: 9장 Tests Enable the -ilities, p.124 · 태그: [일반]

### 깨끗한 테스트 코드 (Clean Tests) p.124–127

**R-107** 규칙: 테스트의 최우선 가치는 가독성이다 — 명료함·단순함·표현 밀도로 적은 표현에 많은 의미를 담아라.
- 근거: 가독성은 프로덕션 코드보다 테스트에서 더 중요하다.
- 출처: 9장 Clean Tests, p.124 · 태그: [일반]

**R-108** 규칙: 테스트에서 테스트 의도와 무관한 세부(문자열→경로 변환, 응답 생성·형변환 등)를 도우미 함수로 숨겨라.
- 근거: 무관한 세부는 의도를 흐리고 독자를 압도한다.
- 위반 예 → 개선 예: `crawler.addPage(root, PathParser.parse("PageOne"))` 반복 → `makePages("PageOne", "PageOne.ChildOne", "PageTwo")`
- 출처: 9장 Clean Tests, p.124–126 · 태그: [일반]

**R-109** 규칙: 테스트에서 중복 코드 [G5]를 제거하라.
- 근거: addPage, assertSubString 반복 호출이 테스트를 이해하기 어렵게 만든다.
- 출처: 9장 Clean Tests, p.124 · 태그: [일반]

**R-110** 규칙: 각 테스트를 BUILD-OPERATE-CHECK 패턴(테스트 데이터 구성 → 조작 → 결과 확인) 세 부분으로 명확히 나눠라.
- 근거: 구조가 분명해 누구나 빨리 이해한다.
- 출처: 9장 Clean Tests, p.127 · 태그: [일반]

**R-111** 규칙: 테스트는 꼭 필요한 데이터 타입과 함수만 사용하라.
- 근거: 곧장 요점으로 가며 오해·압도를 피한다.
- 출처: 9장 Clean Tests, p.127 · 태그: [일반]

### 도메인에 특화된 테스트 언어 (Domain-Specific Testing Language) p.127

**R-112** 규칙: 시스템 조작 API를 감싸는 함수·유틸리티로 테스트 전용 도메인 특화 언어(테스트 API)를 만들어 테스트를 작성하라.
- 근거: 테스트 작성이 편하고 나중에 읽기 쉬워진다.
- 출처: 9장 Domain-Specific Testing Language, p.127 · 태그: [일반]

**R-113** 규칙: 테스트 API는 미리 설계하지 말고 세부로 오염된 테스트 코드를 계속 리팩터링하며 진화시켜라.
- 근거: 숙련된 개발자는 테스트 코드를 더 간결하고 표현력 있는 형태로 리팩터링한다.
- 출처: 9장 Domain-Specific Testing Language, p.127 · 태그: [일반]

### 이중 표준 (A Dual Standard) p.127–130

**R-114** 규칙: 테스트 코드는 단순·간결·표현력 있어야 하지만 프로덕션만큼 효율적일 필요는 없다 — 메모리·CPU 효율은 양보해도 깨끗함은 절대 양보하지 말라.
- 근거: 테스트 환경과 프로덕션 환경의 요구가 다르다(예: 테스트에선 StringBuffer 대신 문자열 += 허용).
- 출처: 9장 A Dual Standard, p.127–130 · 태그: [일반]

**R-115** 규칙: 상태 이름과 assertTrue/assertFalse 사이를 눈이 오가야 하는 단언 나열은, 상태를 압축 표현하는 값(예: 대문자=on 소문자=off 문자열 "HBchL")과 단일 비교로 바꾸는 것을 고려하라.
- 근거: 의미를 알면 결과를 한눈에 해석할 수 있다(정신적 매핑 규칙 위반에 가깝지만 이 경우엔 적절).
- 위반 예 → 개선 예: `assertTrue(hw.heaterState()); assertTrue(hw.blowerState()); assertFalse(hw.coolerState()); ...` → `wayTooCold(); assertEquals("HBchL", hw.getState());`
- 출처: 9장 A Dual Standard, p.128–129 · 태그: [일반]

**R-116** 규칙: 테스트에서 의도와 무관한 저수준 동작(예: `tic()`)은 의도를 드러내는 이름의 함수(`wayTooCold()`)로 감춰라.
- 근거: 독자는 시스템 최종 상태가 조건과 일치하는지에만 집중하면 된다.
- 출처: 9장 A Dual Standard, p.128 · 태그: [일반]

### 테스트 당 assert 하나 (One Assert per Test) p.130–131

**R-117** 규칙: 테스트 함수당 assert 수를 최소화하라(하나가 좋은 지침이나, 과도한 메커니즘이 필요하면 여러 개도 허용).
- 근거: 단일 결론은 빠르고 쉽게 이해되지만, 분리에 따른 중복 제거가 과하면 오히려 손해다.
- 출처: 9장 One Assert per Test, p.130–131 · 태그: [일반]

**R-118** 규칙: 테스트 함수 이름에 given-when-then 관례를 사용하는 것을 고려하라.
- 근거: 테스트를 더 읽기 쉽게 만든다.
- 예: `givenPages(...); whenRequestIsIssued(...); thenResponseShouldBeXML();`
- 출처: 9장 One Assert per Test, p.130 · 태그: [일반]

**R-119** 규칙: 테스트 분리로 생긴 중복은 TEMPLATE METHOD(given/when은 기반 클래스, then은 파생 클래스) 또는 @Before에 given/when을 두는 방식으로 제거할 수 있지만, 사소한 문제에 과한 메커니즘이면 쓰지 말라.
- 근거: 저자는 결국 Listing 9-2의 다중 assert를 선호했다.
- 출처: 9장 One Assert per Test, p.130 · 태그: [일반]

### 테스트 당 개념 하나 (Single Concept per Test) p.131–132

**R-120** 규칙: 테스트 함수 하나에는 개념 하나만 테스트하라 — 잡다한 것을 연달아 테스트하는 긴 함수는 독립된 테스트로 쪼개라.
- 근거: 여러 개념을 합치면 독자가 각 구간의 존재 이유를 추론해야 한다.
- 위반 예 → 개선 예: `testAddMonths()`에 세 시나리오 → 시나리오별 테스트 3개
- 출처: 9장 Single Concept per Test, p.131–132 · 태그: [일반]

**R-121** 규칙: 개념 단위로 시나리오를 서술해 숨은 일반 규칙을 찾고, 그로부터 누락된 테스트(예: 2월 28일에 월 더하기)를 추가하라.
- 근거: 개념별로 쓰면 "월을 더해도 날짜는 그 달의 마지막 날을 넘을 수 없다"는 규칙과 빠진 테스트가 드러난다.
- 출처: 9장 Single Concept per Test, p.132 · 태그: [일반]

**R-122** 규칙: 개념당 assert 수를 최소화하라.
- 근거: 문제는 assert 개수가 아니라 개념이 여러 개인 것이다.
- 출처: 9장 Single Concept per Test, p.132 · 태그: [일반]

### F.I.R.S.T. p.132–133

**R-123** 규칙: 테스트는 빨라야 한다 (Fast).
- 근거: 느리면 자주 돌리지 않고, 문제를 늦게 발견하며, 정리를 주저해 코드가 썩는다.
- 출처: 9장 F.I.R.S.T., p.132 · 태그: [일반]

**R-124** 규칙: 테스트는 서로 독립적이어야 한다 (Independent) — 한 테스트가 다음 테스트의 조건을 준비하지 말고, 각각 단독·임의 순서로 실행 가능해야 한다.
- 근거: 의존하면 첫 실패가 연쇄 실패를 일으켜 진단을 어렵게 하고 후속 결함을 숨긴다.
- 출처: 9장 F.I.R.S.T., p.132 · 태그: [일반]

**R-125** 규칙: 테스트는 어떤 환경(프로덕션, QA, 네트워크 없는 노트북)에서도 반복 가능해야 한다 (Repeatable).
- 근거: 그렇지 않으면 실패에 핑계가 생기고 환경이 없을 때 실행할 수 없다.
- 출처: 9장 F.I.R.S.T., p.132 · 태그: [일반]

**R-126** 규칙: 테스트는 자가 검증해야 한다 (Self-Validating) — 성공/실패 boolean 결과를 내고, 로그를 읽거나 파일을 수동 비교하게 하지 말라.
- 근거: 그렇지 않으면 실패 판정이 주관적이 되고 긴 수작업 평가가 필요하다.
- 출처: 9장 F.I.R.S.T., p.132 · 태그: [일반]

**R-127** 규칙: 테스트는 적시에 작성하라 (Timely) — 그 테스트를 통과시킬 프로덕션 코드 직전에 작성하라.
- 근거: 나중에 쓰면 프로덕션 코드가 테스트하기 어렵게 설계되기 쉽다.
- 출처: 9장 F.I.R.S.T., p.133 · 태그: [일반]

### 결론 (Conclusion) p.133

**R-128** 규칙: 테스트를 항상 깨끗하고 표현력 있고 간결하게 유지하며, 도메인 특화 언어 역할을 하는 테스트 API를 고안하라.
- 근거: 테스트가 썩으면 코드도 썩는다.
- 출처: 9장 Conclusion, p.133 · 태그: [일반]

## 10장 클래스 (Classes)

### 클래스 체계 (Class Organization) p.136

**R-129** 규칙: 클래스는 변수 목록으로 시작하라 — public static 상수 → private static 변수 → private 인스턴스 변수 순으로 배치하라.
- 근거: 표준 자바 관례.
- 출처: 10장 Class Organization, p.136 · 태그: [Java특화]

**R-130** 규칙: public 변수는 거의 두지 말라.
- 근거: public 변수가 필요한 합당한 이유는 드물다.
- 출처: 10장 Class Organization, p.136 · 태그: [일반]

**R-131** 규칙: 변수 목록 다음에 public 함수를 두고, public 함수가 호출하는 private 유틸리티는 그 public 함수 바로 뒤에 배치하라.
- 근거: 내려가기 규칙(stepdown rule)을 따라 신문 기사처럼 읽힌다.
- 출처: 10장 Class Organization, p.136 · 태그: [일반]

### 캡슐화 (Encapsulation) p.136

**R-132** 규칙: 변수와 유틸리티 함수는 private으로 두되, 같은 패키지의 테스트가 접근해야 하면 protected/패키지 범위로 완화할 수 있다 — 단, 먼저 비공개를 유지할 방법을 찾고 캡슐화 완화는 최후 수단으로 하라.
- 근거: 테스트가 우선이지만 캡슐화를 풀어주는 결정은 언제나 최후의 수단이다.
- 출처: 10장 Encapsulation, p.136 · 태그: [일반]

### 클래스는 작아야 한다! (Classes Should Be Small!) p.136–138

**R-133** 규칙: 클래스는 작게, 그리고 그보다 더 작게 만들어라 — 크기는 행 수가 아니라 책임 수로 측정하라.
- 근거: 메서드 5개짜리 클래스도 책임이 둘이면 너무 크다.
- 출처: 10장 Classes Should Be Small!, p.136–138 · 태그: [일반]

**R-134** 규칙: 수십 개의 public 메서드를 가진 "만능 클래스 (God class)"를 만들지 말라.
- 근거: SuperDashboard(public 메서드 약 70개)는 지나치게 크다.
- 출처: 10장 Classes Should Be Small!, p.136 · 태그: [일반]

**R-135** 규칙: 클래스 이름은 그 클래스의 책임을 기술해야 하며, 간결한 이름이 떠오르지 않으면 클래스가 너무 크다고 판단하라.
- 근거: 이름이 모호할수록 책임이 많을 가능성이 크다.
- 출처: 10장 Classes Should Be Small!, p.138 · 태그: [일반]

**R-136** 규칙: Processor, Manager, Super 같은 모호한 단어(weasel words)를 클래스 이름에 쓰지 말라.
- 근거: 이런 단어는 여러 책임을 떠안은 신호다.
- 출처: 10장 Classes Should Be Small!, p.138 · 태그: [일반]

**R-137** 규칙: 클래스 설명을 "if", "and", "or", "but" 없이 약 25단어로 쓸 수 있는지 확인하고, 그럴 수 없으면 책임이 너무 많다고 보라.
- 근거: SuperDashboard 설명의 첫 "and"가 책임 과다의 신호다.
- 출처: 10장 Classes Should Be Small!, p.138 · 태그: [일반]

### 단일 책임 원칙 (The Single Responsibility Principle) p.138–140

**R-138** 규칙: 클래스나 모듈은 변경할 이유가 하나, 단 하나뿐이어야 한다 (SRP).
- 근거: 책임의 정의이자 클래스 크기의 지침이다.
- 출처: 10장 The Single Responsibility Principle, p.138 · 태그: [일반]

**R-139** 규칙: 변경 이유(책임)를 식별해 분리 가능한 책임은 별도 클래스로 추출하라.
- 근거: 더 나은 추상화를 발견하게 되고 재사용성이 높아진다.
- 위반 예 → 개선 예: SuperDashboard의 버전 메서드 3개 → `Version` 클래스로 추출
- 출처: 10장 The Single Responsibility Principle, p.139 · 태그: [일반]

**R-140** 규칙: 프로그램이 동작하게 만든 뒤 멈추지 말고, 정리 관심사로 전환해 비대한 클래스를 단일 책임의 분리된 단위로 쪼개라.
- 근거: 많은 개발자가 동작하면 끝났다고 생각해 SRP가 가장 많이 무시된다.
- 출처: 10장 The Single Responsibility Principle, p.139 · 태그: [일반]

**R-141** 규칙: 시스템을 소수의 큰 클래스가 아니라, 각각 단일 책임을 캡슐화하고 소수의 다른 클래스와 협력하는 많은 작은 클래스로 구성하라.
- 근거: 작은 클래스가 많아도 배울 양은 같으며, 개발자가 어디를 봐야 할지 알고 직접 영향받는 복잡성만 이해하면 된다.
- 출처: 10장 The Single Responsibility Principle, p.139–140 · 태그: [일반]

### 응집도 (Cohesion) p.140–141

**R-142** 규칙: 클래스의 인스턴스 변수 수를 적게 유지하고, 각 메서드가 하나 이상의 인스턴스 변수를 사용하도록 하라(응집도를 높게).
- 근거: 메서드가 더 많은 변수를 사용할수록 응집도가 높고, 높은 응집도는 메서드와 변수가 논리적 단위로 묶여 있음을 뜻한다.
- 출처: 10장 Cohesion, p.140 · 태그: [일반]

**R-143** 규칙: 일부 메서드만 사용하는 인스턴스 변수가 늘어나면, 그 변수와 메서드를 더 응집된 별도 클래스로 분리하라.
- 근거: 이는 거의 항상 큰 클래스 안에서 다른 클래스가 빠져나오려 한다는 신호다.
- 출처: 10장 Cohesion, p.140–141 · 태그: [일반]

### 응집도를 유지하면 작은 클래스 여럿이 나온다 (Maintaining Cohesion Results in Many Small Classes) p.141–146

**R-144** 규칙: 큰 함수를 쪼갤 때 인수 전달을 피하려고 지역 변수를 인스턴스 변수로 승격했다면, 그 변수를 공유하는 함수들을 새 클래스로 분리하라 — 응집도를 잃으면 클래스를 쪼개라.
- 근거: 몇몇 함수만 공유하는 변수 집합은 그 자체로 하나의 클래스다.
- 출처: 10장 Maintaining Cohesion Results in Many Small Classes, p.141 · 태그: [일반]

**R-145** 규칙: 하나의 거대한 함수(깊은 들여쓰기, 이상한 변수, 강한 결합)는 의미 있는 이름의 작은 함수와 클래스로 분리하라.
- 근거: PrintPrimes → PrimePrinter / RowColumnPagePrinter / PrimeGenerator로 나누어 각 클래스가 변경 이유 하나(실행 환경 / 출력 형식 / 소수 알고리즘)를 갖게 됐다.
- 출처: 10장 Maintaining Cohesion Results in Many Small Classes, p.141–146 · 태그: [일반]

**R-146** 규칙: 축약·의미 없는 대문자 변수명(M, RR, CC, J, K)을 서술적 이름(NUMBER_OF_PRIMES, ROWS_PER_PAGE 등)으로 바꿔라.
- 근거: 리팩터링 후 길어진 원인 중 하나가 더 길고 서술적인 이름이며, 이는 가독성을 높인다.
- 출처: 10장 Maintaining Cohesion Results in Many Small Classes, p.143, 146 · 태그: [일반]

**R-147** 규칙: 함수·클래스 선언을 코드에 설명을 덧붙이는 수단으로 활용하라(코드가 길어지더라도).
- 근거: 리팩터링된 프로그램은 함수·클래스 선언을 주석처럼 사용해 길어졌지만 더 읽기 쉽다.
- 출처: 10장 Maintaining Cohesion Results in Many Small Classes, p.146 · 태그: [일반]

**R-148** 규칙: 출력 대상(PrintStream 등)은 하드코딩하지 말고 교체 가능하게(setter/주입) 만들어라.
- 근거: RowColumnPagePrinter의 `setOutput(PrintStream)`이 보여주는 관행 — 테스트·변경 용이.
- 출처: 10장 Maintaining Cohesion Results in Many Small Classes (Listing 10-7), p.144 · 태그: [일반]

**R-149** 규칙: 구조 개선은 재작성이 아니라, 기존 동작을 정밀하게 검증하는 테스트 묶음을 먼저 작성한 뒤 한 번에 하나씩 작은 변경을 하고 매번 동작이 변하지 않았는지 실행해 확인하는 방식으로 하라.
- 근거: PrintPrimes 리팩터링은 같은 알고리즘을 유지한 채 작은 단계로 변환됐다.
- 출처: 10장 Maintaining Cohesion Results in Many Small Classes, p.146 · 태그: [일반]

### 변경하기 쉬운 클래스 (Organizing for Change) p.147–149

**R-150** 규칙: 변경에 따른 위험을 줄이도록 클래스를 조직하라.
- 근거: 클래스를 "열어" 수정할 때마다 다른 코드가 깨질 위험이 있고 전체를 재테스트해야 한다.
- 출처: 10장 Organizing for Change, p.147 · 태그: [일반]

**R-151** 규칙: 클래스의 일부 기능에만 관련된 private 메서드가 있으면 책임 분리 대상의 신호로 보라.
- 근거: Sql의 `selectWithCriteria`는 select에만 관련 — SRP 위반을 조직 관점에서 발견하는 휴리스틱.
- 출처: 10장 Organizing for Change, p.147 · 태그: [일반]

**R-152** 규칙: 논리적으로 완결되고 당분간 변경 계획이 없는 클래스는 그대로 두되, 클래스를 열어 수정해야 하는 시점이 오면 설계 개선을 고려하라.
- 근거: 행동의 주된 계기는 실제 시스템 변경이어야 한다.
- 출처: 10장 Organizing for Change, p.147 · 태그: [일반]

**R-153** 규칙: 새 기능은 기존 코드를 수정하지 말고 확장(새 서브클래스/구현 추가)으로 넣을 수 있게 설계하라 — 개방-폐쇄 원칙 (Open-Closed Principle, OCP).
- 근거: Sql을 CreateSql/SelectSql/InsertSql… 파생 클래스로 나누면 UpdateSql 추가 시 기존 클래스를 건드리지 않는다.
- 출처: 10장 Organizing for Change, p.147–149 · 태그: [일반]

**R-154** 규칙: 일부 하위 클래스만 쓰는 private 메서드는 그것이 필요한 클래스로 옮기고, 공통 private 동작은 별도 유틸리티 클래스(Where, ColumnList)로 분리하라.
- 근거: 각 클래스가 극도로 단순해지고 서로 격리되어 테스트가 쉬워진다.
- 출처: 10장 Organizing for Change, p.147–149 · 태그: [일반]

### 변경으로부터 격리 (Isolating from Change) p.149–150

**R-155** 규칙: 구체 클래스(구현 세부)에 직접 의존하지 말고 인터페이스나 추상 클래스를 도입해 세부 변경의 영향을 격리하라.
- 근거: 구체 세부에 의존하는 클라이언트는 세부가 바뀔 때 위험에 처한다.
- 출처: 10장 Isolating from Change, p.149 · 태그: [일반]

**R-156** 규칙: 변동성 있는 외부 의존(예: TokyoStockExchange)은 인터페이스(StockExchange) 뒤에 두고 생성자 인수로 주입받아, 테스트에서 고정값을 반환하는 스텁으로 대체하라.
- 근거: 5분마다 답이 바뀌는 대상으로는 테스트를 쓰기 어렵다.
- 위반 예 → 개선 예: Portfolio가 TokyoStockExchange를 직접 생성 → `Portfolio(StockExchange exchange)` + `FixedStockExchangeStub`
- 출처: 10장 Isolating from Change, p.149–150 · 태그: [일반]

**R-157** 규칙: 클래스는 구체적 세부가 아니라 추상화에 의존하게 하라 — 의존성 역전 원칙 (Dependency Inversion Principle, DIP).
- 근거: 결합도가 낮아져 테스트 가능하고 유연하며 재사용성이 높아지고 각 요소를 이해하기 쉬워진다.
- 출처: 10장 Isolating from Change, p.150 · 태그: [일반]

## 11장 시스템 (Systems)

### 도시를 세운다면? (How Would You Build a City?) p.154

**R-158** 규칙: 시스템 수준에서도 적절한 추상화 수준과 모듈성을 갖춰 각 구성원이 큰 그림을 몰라도 자기 부분을 효과적으로 다룰 수 있게 하라.
- 근거: 도시가 작동하는 이유는 관심사 분리와 추상화 수준 덕분이다.
- 출처: 11장 How Would You Build a City?, p.154 · 태그: [일반]

### 시스템 제작과 시스템 사용을 분리하라 (Separate Constructing a System from Using It) p.154–155

**R-159** 규칙: 애플리케이션 객체를 생성하고 의존성을 연결하는 시작 단계와, 시작 이후의 런타임 로직을 분리하라.
- 근거: 관심사 분리는 가장 오래되고 중요한 설계 기법이다.
- 출처: 11장 Separate Constructing a System from Using It, p.154 · 태그: [일반]

**R-160** 규칙: 런타임 로직 안에 `if (service == null) service = new MyServiceImpl(...)` 같은 지연 초기화로 구체 구현을 하드코딩하지 말라.
- 근거: 구체 클래스에 컴파일 의존이 생기고, 테스트 시 테스트 더블 주입이 번거로우며, 생성과 사용 두 책임을 가져 SRP를 깨고, 그 클래스가 전역 맥락을 알아야 한다.
- 출처: 11장 Separate Constructing a System from Using It, p.154–155 · 태그: [일반]

**R-161** 규칙: 편리한 설정 관용구가 곳곳에 흩어져 모듈성을 깨지 않도록, 객체 생성·연결 과정을 런타임 로직과 별도로 모듈화하고 주요 의존성 해결에 전역적·일관된 전략을 사용하라.
- 근거: 흩어진 설정 관용구는 중복과 모듈성 붕괴를 낳는다.
- 출처: 11장 Separate Constructing a System from Using It, p.155 · 태그: [일반]

### Main 분리 (Separation of Main) p.155

**R-162** 규칙: 생성 관련 코드는 모두 main이나 main이 호출하는 모듈로 옮기고, 나머지 시스템은 모든 객체가 이미 생성·연결되었다고 가정하고 설계하라.
- 근거: 의존성 화살표가 main에서 애플리케이션 쪽 한 방향으로만 향해 애플리케이션은 생성 과정을 모른다.
- 출처: 11장 Separation of Main, p.155 · 태그: [일반]

### 팩토리 (Factories) p.155–156

**R-163** 규칙: 애플리케이션이 객체 생성 시점을 결정해야 할 때는 추상 팩토리 (ABSTRACT FACTORY)를 사용해, 생성 시점 제어는 애플리케이션에 두고 생성 세부는 main 쪽 구현에 두어라.
- 근거: 애플리케이션은 LineItem 생성 방법과 분리되면서도 생성 시점과 인수를 통제한다.
- 출처: 11장 Factories, p.155–156 · 태그: [일반]

### 의존성 주입 (Dependency Injection) p.157

**R-164** 규칙: 객체가 의존성을 직접 인스턴스화하지 말고, main이나 전용 컨테이너 같은 "권위 있는" 메커니즘에 그 책임을 넘겨라(제어 역전, IoC).
- 근거: 부차적 책임을 전담 객체로 옮겨 SRP를 지원한다.
- 출처: 11장 Dependency Injection, p.157 · 태그: [일반]

**R-165** 규칙: 서비스 로케이터(JNDI 조회처럼 객체가 능동적으로 의존성을 찾는 방식)보다, 클래스가 완전히 수동적으로 생성자 인수나 setter로 의존성을 주입받는 진정한 DI를 선호하라.
- 근거: JNDI 조회는 "부분적" DI일 뿐 호출 객체가 여전히 의존성을 능동적으로 해결한다.
- 출처: 11장 Dependency Injection, p.157 · 태그: [일반]

**R-166** 규칙: 어떤 의존 객체를 쓸지는 설정 파일이나 전용 생성 모듈에서 지정하라.
- 근거: DI 컨테이너가 생성 시 필요한 객체를 만들고 연결한다.
- 출처: 11장 Dependency Injection, p.157 · 태그: [일반]

**R-167** 규칙: 지연 초기화는 최적화일 뿐(어쩌면 섣부른 최적화)임을 인지하고, 필요하면 DI 컨테이너의 지연 생성·팩토리·프록시 기능으로 처리하라.
- 근거: 대부분의 DI 컨테이너는 필요할 때까지 객체를 만들지 않는다.
- 출처: 11장 Dependency Injection 및 각주 5, p.157 · 태그: [일반]

### 확장 (Scaling Up) p.157–160

**R-168** 규칙: 시스템을 "처음부터 올바르게" 만들려 하지 말고, 오늘의 스토리만 구현한 뒤 내일 리팩터링·확장하라.
- 근거: 반복적·점진적 애자일의 본질이며, 관심사를 적절히 분리하면 소프트웨어 아키텍처도 점진적으로 성장할 수 있다.
- 출처: 11장 Scaling Up, p.158 · 태그: [일반]

**R-169** 규칙: 비즈니스 로직을 무거운 컨테이너/프레임워크에 강하게 결합시키지 말라(컨테이너 타입 상속 강제, 빈 생명주기 메서드 다수 구현 등).
- 근거: EJB2처럼 결합되면 격리된 단위 테스트가 어렵고, 아키텍처 밖 재사용이 불가능하며, OO 자체가 훼손된다.
- 출처: 11장 Scaling Up, p.158–160 · 태그: [Java특화] (EJB2 사례이나 원칙은 일반)

**R-170** 규칙: 같은 데이터를 담은 중복 타입(행위 없는 DTO)을 양산하고 복사 상용구를 쓰게 만드는 구조를 피하라.
- 근거: EJB2에서 흔한 DTO 남용은 중복 타입과 보일러플레이트 복사 코드를 낳는다.
- 출처: 11장 Scaling Up, p.160 · 태그: [Java특화]

### 횡단(cross-cutting) 관심사 (Cross-Cutting Concerns) p.160–161

**R-171** 규칙: 영속성·트랜잭션·보안 같은 횡단 관심사는 여러 객체에 같은 코드를 흩뿌리지 말고, 관점 지향 프로그래밍 (AOP) 또는 그와 유사한 메커니즘으로 모듈화하라.
- 근거: 횡단 관심사는 도메인 객체 경계를 가로질러 같은 전략 코드가 퍼지는 문제를 낳는다.
- 출처: 11장 Cross-Cutting Concerns, p.160 · 태그: [일반]

**R-172** 규칙: 횡단 관심사는 대상 코드를 수동 편집하지 않고(비침투적) 선언적 또는 프로그래밍적 메커니즘으로 적용하라.
- 근거: AOP의 aspect는 어느 지점의 동작을 일관되게 수정할지 간결하게 명시한다.
- 출처: 11장 Cross-Cutting Concerns, p.160–161 · 태그: [일반]

**R-173** 규칙: 영속성 같은 전략은 일관되게 적용하라(DBMS 선택, 테이블·컬럼 명명 관례, 일관된 트랜잭션 의미).
- 근거: 모든 객체를 대체로 같은 전략으로 영속화하길 원한다.
- 출처: 11장 Cross-Cutting Concerns, p.160 · 태그: [일반]

### 자바 프록시 (Java Proxies) p.161–163

**R-174** 규칙: JDK 동적 프록시는 개별 객체/클래스의 메서드 호출을 감싸는 단순한 경우에만 쓰고, 횡단 관심사의 시스템 전체 적용에는 쓰지 말라.
- 근거: 코드량과 복잡도가 커서 깨끗한 코드를 만들기 어렵고, 시스템 전체의 실행 "지점"을 명시하는 메커니즘이 없다. JDK 프록시는 인터페이스만 지원(클래스는 CGLIB/ASM/Javassist 필요).
- 출처: 11장 Java Proxies, p.161–163 · 태그: [Java특화]

**R-175** 규칙: AOP를 그 구현 기법(메서드 가로채기, 프록시 래핑)과 혼동하지 말라 — AOP의 가치는 시스템 동작을 간결하고 모듈화된 방식으로 명시하는 데 있다.
- 근거: 각주 11.
- 출처: 11장 Java Proxies 각주 11, p.163 · 태그: [일반]

### 순수 자바 AOP 프레임워크 (Pure Java AOP Frameworks) p.163–166

**R-176** 규칙: 비즈니스 로직은 엔터프라이즈 프레임워크에 의존하지 않는 POJO(순수 도메인 객체)로 작성하라.
- 근거: POJO는 개념적으로 단순하고 테스트 주도하기 쉬우며 스토리 구현 정확성 확인과 유지보수가 쉽다.
- 출처: 11장 Pure Java AOP Frameworks, p.163 · 태그: [일반]

**R-177** 규칙: 영속성·트랜잭션·보안·캐싱·장애조치 같은 인프라는 선언적 설정 파일이나 API로 통합하고, 이 선언이 DI 컨테이너를 구동하게 하라.
- 근거: 프레임워크가 프록시/바이트코드 처리를 투명하게 해 준다.
- 출처: 11장 Pure Java AOP Frameworks, p.163 · 태그: [일반]

**R-178** 규칙: 부가 동작(트랜잭션, 캐싱 등)은 도메인 객체를 감싸는 데코레이터 (DECORATOR) 계층으로 추가하라.
- 근거: Bank POJO → DAO → DataSource의 "러시아 인형" 구조로 기본 동작을 확장한다.
- 출처: 11장 Pure Java AOP Frameworks, p.164 · 태그: [일반]

**R-179** 규칙: 애플리케이션 코드의 프레임워크 특화 코드는 최소 몇 줄(최상위 객체 요청)로 제한해 프레임워크로부터 거의 완전히 분리하라.
- 근거: 그래야 EJB2식 강결합 문제가 사라진다.
- 출처: 11장 Pure Java AOP Frameworks, p.164 · 태그: [일반]

**R-180** 규칙: 영속성 매핑 등 인프라 정보는 애너테이션 안에만 국한하거나, 순수 POJO가 필요하면 외부 배치 기술자(XML)로 옮겨라.
- 근거: 애너테이션 밖으로 정보가 새지 않으면 코드는 깨끗하고 테스트·유지보수가 쉽다(EJB3).
- 출처: 11장 Pure Java AOP Frameworks, p.165–166 · 태그: [Java특화]

### AspectJ 관점 (AspectJ Aspects) p.166

**R-181** 규칙: 관점 도구는 필요에 맞게 고르라 — 대부분(80–90%)은 순수 자바 AOP(Spring AOP, JBoss AOP)로 충분하며, AspectJ는 풍부한 기능이 필요할 때 새 도구·언어 학습 비용을 감수하고 채택하라.
- 근거: AspectJ의 단점은 새 도구·언어 구성·관용구 도입이다(애너테이션 형식으로 일부 완화).
- 출처: 11장 AspectJ Aspects, p.166 · 태그: [Java특화]

### 테스트 주도 시스템 아키텍처 구축 (Test Drive the System Architecture) p.166–167

**R-182** 규칙: 도메인 로직을 아키텍처 관심사와 분리된 POJO로 작성해, 아키텍처를 테스트 주도로 단순한 것에서 정교한 것으로 필요에 따라 진화시켜라.
- 근거: 관심사가 분리되면 소프트웨어는 급진적 변경이 경제적으로 가능하다.
- 출처: 11장 Test Drive the System Architecture, p.166–167 · 태그: [일반]

**R-183** 규칙: 구현 전에 모든 것을 설계하는 BDUF(Big Design Up Front)를 하지 말라(단, 적절한 사전 설계와는 구분).
- 근거: 기존 노력을 버리기 싫은 심리적 저항과 초기 선택이 이후 사고를 제약해 변경 적응을 막는다.
- 출처: 11장 Test Drive the System Architecture 및 각주 18, p.167 · 태그: [일반]

**R-184** 규칙: "순진할 만큼 단순하지만" 잘 분리된 아키텍처로 시작해 동작하는 스토리를 빨리 전달하고, 규모가 커지면 인프라를 추가하라 — 단, 범위·목표·일정·전반 구조에 대한 기대는 갖되 방향을 바꿀 능력을 유지하라.
- 근거: 대형 웹사이트도 최소 결합 설계 덕에 캐싱·보안·가상화를 유연하게 추가했다.
- 출처: 11장 Test Drive the System Architecture, p.167 · 태그: [일반]

**R-185** 규칙: 실제로 필요하지 않은 과설계 API·프레임워크를 도입하지 말라 — 좋은 API는 대부분의 시간에 시야에서 사라져 팀이 스토리 구현에 집중하게 해야 한다.
- 근거: 그렇지 않으면 아키텍처 제약이 고객 가치 전달을 막는다.
- 출처: 11장 Test Drive the System Architecture, p.167 · 태그: [일반]

**R-186** 규칙: 관심사 도메인을 모듈화해 각각 POJO로 구현하고, 최소 침투적인 관점(또는 유사 도구)으로 통합하라.
- 근거: 최적의 시스템 아키텍처이며 코드처럼 테스트 주도할 수 있다.
- 출처: 11장 Test Drive the System Architecture, p.167 · 태그: [일반]

### 의사 결정을 최적화하라 (Optimize Decision Making) p.167–168

**R-187** 규칙: 책임은 가장 자격 있는 사람에게 맡기고, 결정은 가능한 마지막 순간까지 미뤄라.
- 근거: 섣부른 결정은 최선이 아닌 지식(고객 피드백·성찰·경험 부족)으로 내린 결정이다.
- 출처: 11장 Optimize Decision Making, p.167–168 · 태그: [일반]

**R-188** 규칙: 모듈화와 관심사 분리로 분산된 관리·의사결정이 가능하게 하라.
- 근거: 충분히 큰 시스템에서는 한 사람이 모든 결정을 내릴 수 없다.
- 출처: 11장 Optimize Decision Making, p.167 · 태그: [일반]

### 명백한 가치가 있을 때 표준을 현명하게 사용하라 (Use Standards Wisely, When They Add Demonstrable Value) p.168

**R-189** 규칙: 표준이라는 이유만으로 채택하지 말고, 더 가볍고 단순한 설계로 충분한지 먼저 검토해 표준이 입증 가능한 가치를 더할 때만 사용하라.
- 근거: 많은 팀이 표준(EJB2)이라서 썼다가 고객 가치 구현에 집중하지 못했다. 표준은 재사용·채용·아이디어 캡슐화에 유리하나 실제 요구와 동떨어질 수 있다.
- 출처: 11장 Use Standards Wisely..., p.168 · 태그: [일반]

### 시스템은 도메인 특화 언어가 필요하다 (Systems Need Domain-Specific Languages) p.168–169

**R-190** 규칙: 도메인 로직은 도메인 전문가가 쓰는 언어로 읽히도록 도메인 특화 언어(DSL: 별도 스크립트 언어 또는 표준 언어 내 API)로 표현하라.
- 근거: 도메인 개념과 구현 사이 "의사소통 간극"을 줄여 잘못 번역할 위험을 낮추고, 추상화 수준을 관용구·패턴 위로 끌어올린다.
- 출처: 11장 Systems Need Domain-Specific Languages, p.168–169 · 태그: [일반]

### 결론 (Conclusion) p.169

**R-191** 규칙: 침투적 아키텍처로 도메인 로직을 가리지 말고, 모든 추상화 수준에서 의도가 명확하게 하라(POJO + 관점 유사 메커니즘).
- 근거: 도메인 로직이 흐려지면 버그가 숨기 쉬워지고 스토리 구현이 어려워지며 애자일성과 TDD 이점을 잃는다.
- 출처: 11장 Conclusion, p.169 · 태그: [일반]

**R-192** 규칙: 시스템이든 모듈이든 실현 가능한 가장 단순한 방법을 사용하라.
- 근거: "the simplest thing that can possibly work."
- 출처: 11장 Conclusion, p.169 · 태그: [일반]

## 12장 창발성 (Emergence)

### 창발적 설계로 깔끔한 코드를 구현하자 (Getting Clean via Emergent Design) p.171–172

**R-193** 규칙: 켄트 벡의 단순한 설계 4규칙을 중요도 순서대로 따르라 — ① 모든 테스트를 실행한다 ② 중복을 없앤다 ③ 프로그래머 의도를 표현한다 ④ 클래스와 메서드 수를 최소화한다.
- 근거: 이 규칙들은 좋은 설계의 창발을 촉진하고 SRP·DIP 적용을 쉽게 한다.
- 출처: 12장 Getting Clean via Emergent Design, p.171–172 · 태그: [일반]

### 단순한 설계 규칙 1: 모든 테스트를 실행하라 (Simple Design Rule 1: Runs All the Tests) p.172

**R-194** 규칙: 시스템을 철저히 테스트하고 모든 테스트를 항상 통과시켜라 — 검증할 수 없는 시스템은 배포하지 말라.
- 근거: 테스트 불가능한 시스템은 검증 불가능하다.
- 출처: 12장 Simple Design Rule 1, p.172 · 태그: [일반]

**R-195** 규칙: 테스트 가능성을 설계 압력으로 활용하라 — 테스트하기 어렵다면 클래스를 작고 단일 목적으로, 결합을 낮추도록(DIP, DI, 인터페이스, 추상화) 설계를 고쳐라.
- 근거: 테스트를 많이 쓸수록 낮은 결합도·높은 응집도로 설계가 개선된다.
- 출처: 12장 Simple Design Rule 1, p.172 · 태그: [일반]

### 단순한 설계 규칙 2–4: 리팩터링 (Simple Design Rules 2–4: Refactoring) p.172

**R-196** 규칙: 코드 몇 줄을 추가할 때마다 멈춰서 설계가 나빠졌는지 점검하고, 나빠졌다면 정리한 뒤 테스트를 돌려 아무것도 깨지지 않았음을 확인하라.
- 근거: 테스트가 정리에 대한 두려움을 없애 점진적 리팩터링을 가능하게 한다.
- 출처: 12장 Simple Design Rules 2–4: Refactoring, p.172 · 태그: [일반]

**R-197** 규칙: 리팩터링 단계에서 응집도 향상, 결합도 감소, 관심사 분리, 시스템 관심사 모듈화, 함수·클래스 축소, 더 나은 이름 선택 등을 적용하라.
- 근거: 좋은 설계에 관한 모든 지식을 이 단계에서 활용할 수 있다.
- 출처: 12장 Simple Design Rules 2–4: Refactoring, p.172 · 태그: [일반]

### 중복을 없애라 (No Duplication) p.173–175

**R-198** 규칙: 몇 줄짜리라도 중복을 제거하라 — 똑같은 코드뿐 아니라 비슷한 코드(더 비슷하게 다듬어 리팩터링)와 구현 중복도 포함한다.
- 근거: 중복은 좋은 설계의 주적이며 추가 작업·위험·불필요한 복잡도를 낳는다.
- 출처: 12장 No Duplication, p.173 · 태그: [일반]

**R-199** 규칙: 한 메서드를 다른 메서드의 정의로 표현할 수 있으면 별도 구현을 두지 말라(구현 중복 제거).
- 근거: 상태를 따로 추적하면 같은 개념이 두 번 구현된다.
- 위반 예 → 개선 예: isEmpty가 별도 boolean 추적 → `boolean isEmpty() { return 0 == size(); }`
- 출처: 12장 No Duplication, p.173 · 태그: [일반]

**R-200** 규칙: 여러 메서드에 반복되는 몇 줄(예: dispose/gc/교체)은 private 메서드로 추출하라.
- 근거: 작은 수준의 공통점 추출이 SRP 위반 인식과 재사용으로 이어진다.
- 위반 예 → 개선 예: scaleToOneDimension과 rotate 끝의 `image.dispose(); System.gc(); image = newImage;` → `replaceImage(newImage)`
- 출처: 12장 No Duplication, p.173–174 · 태그: [일반]

**R-201** 규칙: 추출한 메서드가 SRP를 위반하면 다른 클래스로 옮기고, 다른 맥락에서도 재사용하도록 추상화하라("소규모 재사용").
- 근거: 소규모 재사용은 시스템 복잡도를 극적으로 줄이며 대규모 재사용의 기반이다.
- 출처: 12장 No Duplication, p.174 · 태그: [일반]

**R-202** 규칙: 알고리즘 골격은 같고 일부 단계만 다른 고수준 중복은 템플릿 메서드 (TEMPLATE METHOD) 패턴으로 제거하라(공통 단계는 기반 클래스, 달라지는 단계는 추상 메서드로 서브클래스가 채움).
- 근거: 서브클래스는 중복되지 않는 정보만 공급한다.
- 위반 예 → 개선 예: accrueUSDivisionVacation/accrueEUDivisionVacation 거의 동일 → `VacationPolicy.accrueVacation()` + `abstract alterForLegalMinimums()`
- 출처: 12장 No Duplication, p.174–175 · 태그: [일반]

### 표현하라 (Expressive) p.175–176

**R-203** 규칙: 코드는 작성자의 의도를 명확히 표현해야 한다 — 작성 당시 자신만 이해하는 코드를 남기지 말라.
- 근거: 소프트웨어 비용 대부분은 장기 유지보수이며, 명확할수록 결함과 유지보수 비용이 준다.
- 출처: 12장 Expressive, p.175 · 태그: [일반]

**R-204** 규칙: 좋은 이름을 선택해, 클래스·함수 이름을 듣고 그 책임을 알았을 때 놀라지 않게 하라.
- 근거: 이름이 표현의 첫 수단이다.
- 출처: 12장 Expressive, p.175 · 태그: [일반]

**R-205** 규칙: 함수와 클래스를 작게 유지해 이름 짓기·작성·이해를 쉽게 하라.
- 근거: 작은 클래스와 함수는 대개 이름 짓기 쉽고 이해하기 쉽다.
- 출처: 12장 Expressive, p.175 · 태그: [일반]

**R-206** 규칙: 표준 명명법을 사용하라 — 디자인 패턴을 구현한 클래스 이름에 COMMAND, VISITOR 같은 표준 패턴 이름을 넣어라.
- 근거: 패턴 이름으로 다른 개발자에게 설계를 간결하게 전달한다.
- 출처: 12장 Expressive, p.175 · 태그: [일반]

**R-207** 규칙: 단위 테스트를 예시에 의한 문서로 작성해, 테스트만 읽어도 클래스의 역할을 빠르게 이해할 수 있게 하라.
- 근거: 잘 쓴 단위 테스트도 표현력이 있다.
- 출처: 12장 Expressive, p.175 · 태그: [일반]

**R-208** 규칙: 코드가 동작하면 곧바로 다음 문제로 넘어가지 말고, 다음 사람(아마 미래의 자신)이 읽기 쉽도록 이름을 개선하고 큰 함수를 쪼개는 등 시간을 들여 다듬어라.
- 근거: 표현력을 높이는 가장 중요한 방법은 노력하는 것이다.
- 출처: 12장 Expressive, p.176 · 태그: [일반]

### 클래스와 메서드 수를 최소로 줄여라 (Minimal Classes and Methods) p.176
