# Clean Code Rules — 코드를 작성하는 모든 에이전트의 공통 규칙

**대상**: 코드를 쓰는 모든 주체. backend-senior·backend-junior·frontend-senior·frontend-junior, 그리고 takeover로 직접 구현하는 리더. qa는 이 규칙을 **판정 기준**으로 쓴다. qa는 코드를 직접 고치지 않는다.

**원전**: `docs/pdf/` 의 두 책을 서문부터 색인까지 한 줄도 빼지 않고 읽었다.
- Clean Code (2008): 규칙 753개. 17장 냄새 코드 66개를 전부 담았고, 부록 C 교차참조표와 기계적으로 대조해 일치를 확인했다.
- Clean Architecture (2017): 규칙 482개.

이 파일은 **핵심 점검표**다. 규칙 전문과 근거, 출처 쪽수는 `references/` 에 있다(§5 색인).

## 0. 우선순위: 충돌하면 무엇이 이기는가 (사용자 결정, 2026-10-31)

**1순위: 사용자가 정한 규칙**(`tdd-implementation` 의 "코딩 컨벤션"과 "코드 리뷰 규칙"). **2순위: 이 스킬.** **3순위: 언어·프레임워크 관례.**
책과 기존 규칙이 부딪히는 자리는 아래에 모두 적었다. 여기 없는 충돌을 발견하면 임의로 정하지 말고 리더에게 보고한다.

**두 층 (사용자 결정, 2026-10-31)**: 규칙 본문의 단일 소스는 이 스킬이다. 하네스가 *무엇을 왜 채택하고 기각했는지*와 그 대가를 치른 빌드 실적은 하네스 층 두 파일에 있다. 구현 쪽은 `.claude/skills/tdd-implementation/references/clean-code-rules.md`, 아키텍처 판정 쪽은 `.claude/skills/architecture-and-delegation/references/clean-architecture-rules.md` 이다. 두 책에 없는 패턴(Saga·CQRS·Retry 등)도 아키텍처 쪽 파일이 맡는다. 그 파일들의 기각표가 이 §0과 어긋나면 **§0이 맞다.**

| 주제 | 책 | 이기는 규칙 (적용 방법) |

| 주석 | 주석은 실패다. 코드로 표현하라 (cc1 4장) | **블록마다 "무엇을·왜" 짧은 주석**(기존). 단, 책의 금지 항목은 그대로 지킨다: 코드를 그대로 되풀이하는 줄 단위 주석(`i++ // i 증가`), 주석 처리된 코드, 작성자·이력 주석, 낡은 주석, 닫는 괄호 주석, 소음 Javadoc. 책도 의도 설명·경고·TODO 주석은 허용한다 |

| `final` | 인자·지역변수의 `final`은 잡동사니 (cc3 16장) | **기각. 불변을 기본으로 한다**(Kotlin `val`, TS `const`). 타입 시스템이 읽는 정보이지 잡동사니가 아니다 |
| 함수·파일 줄 수 | 함수는 2–4줄, 20줄도 드물게 (cc1 3장) / 파일 200줄 지향·500줄 상한 (cc2 5장) | **수치는 참고값이며 게이트에 넣지 않는다.** 판정은 "한 가지만 하는가"(G30)와 "추상화 수준이 하나인가"(G34)로 한다. 파일 크기는 "클래스당 파일 하나" 규칙이 이미 제약한다 |
| Java 특화 | checked 예외·JUnit3·EJB 등 `[Java특화]` 태그 | 그 언어에 해당할 때만 적용한다. 원리(예: "오류 처리를 비즈니스 로직과 분리")는 언어와 무관하게 적용한다 |
| 함수 이름 길이 | 긴 범위에는 긴 이름 (N5) | 30자 지향보다 **명시성이 우선**(기존 규칙 자체가 이렇게 정한다) |

## 1. 사용 절차

1. **코드를 쓰기 전에** 이 파일의 §2(Clean Code)와 §3(Clean Architecture)을 읽는다. 세션이 길어져 기준이 흐려지면 다시 읽는다.
2. **작업 영역에 해당하는 참조 파일을 읽는다**(§5 색인). 예: 동시성 코드면 `cc3`의 13장과 부록 A, 패키지 구조를 정하면 `ca1`의 12–14장과 `ca3`의 34장.
3. **Refactor 단계의 완료 조건 = §4 자가 점검 통과.** 테스트만 초록이면 완료가 아니다.
4. **리뷰·QA는 위반 근거로 규칙 ID를 인용한다.** 예: `cc3:G30 함수가 검증·저장·알림 세 가지를 한다 (OrderService.kt:42)`. 근거 없는 취향 지적은 하지 않는다.

## 2. Clean Code 핵심 규칙

### 2.1 이름 (cc1 2장, cc3 N1–N7)
- 의도를 드러내는 이름을 쓴다: 존재 이유·하는 일·사용법이 이름에 보여야 한다. 이름에 주석이 필요하면 이름이 틀린 것이다.
- 그릇된 정보를 피한다: `accountList` 가 List가 아니면 안 된다. 비슷한 이름을 미세하게 다르게 짓지 않는다. `l`·`O` 단독 사용 금지.
- 의미 있게 구분한다: `a1/a2`, `Info/Data/Manager` 같은 불용어로 구분하지 않는다.
- 발음할 수 있고 검색할 수 있는 이름을 쓴다. 이름 길이는 범위 크기에 비례시킨다(N5).
- 인코딩 금지: 헝가리식 표기, `m_` 접두어, `I` 인터페이스 접두어(N6).
- 클래스는 명사, 메서드는 동사. 한 개념에 한 단어만 쓴다(fetch/get/retrieve 혼용 금지). 같은 단어를 다른 개념에 쓰지 않는다(말장난 금지).
- 해법 영역 용어(패턴·알고리즘)와 문제 영역 용어(도메인)를 적절히 쓴다. 도메인 용어는 용어집에서 가져온다(기존 규칙).
- 이름은 구현이 아니라 추상화 수준을 나타낸다(N2). 부수 효과도 이름에 드러낸다(N7: `getOos` → `createOrReturnOos`).

### 2.2 함수 (cc1 3장, cc3 F1–F4·G30·G34)
- 작게, 더 작게. 블록과 들여쓰기는 1–2단계로 제한한다.
- **한 가지만 한다**(G30). 의미 있는 이름으로 다른 함수를 추출할 수 있다면 두 가지 일을 하고 있는 것이다.
- **함수당 추상화 수준은 하나**(G34). 위에서 아래로 내려가며 읽히게 한다(내려가기 규칙: 호출되는 함수를 호출하는 함수 바로 아래에 둔다).
- switch는 저수준 클래스에 묻고 다형성으로 한 번만 쓴다(ONE SWITCH, G23).
- 인수는 0개가 최선이고 3개가 상한이다(F1). 플래그 인수 금지(F3). 출력 인수 금지(F2). 인수가 많으면 객체로 묶는다.
- 부수 효과를 숨기지 않는다. 숨은 시간적 결합은 인수로 드러낸다(G31).
- 명령과 조회를 분리한다: 상태를 바꾸는 함수는 값을 묻지 않고, 묻는 함수는 상태를 바꾸지 않는다.
- 오류 코드 대신 예외를 쓴다. try/catch 블록은 별도 함수로 뽑는다. 오류 처리도 "한 가지 일"이다.
- 반복하지 않는다(DRY, G5). 죽은 함수는 삭제한다(F4).
- 처음부터 완벽하게 쓰지 않는다. 동작하게 만든 뒤 테스트를 유지한 채 다듬는다.

### 2.3 주석 (cc1 4장, cc3 C1–C5) — §0의 우선순위를 먼저 본다
- 나쁜 코드에 주석을 달지 말고 코드를 고친다. 코드로 의도를 표현할 수 있으면 그렇게 한다.
- 허용: 법적 고지, 의도 설명, 결과 경고, TODO(추적 가능한 것), 공개 API 문서, 중요성 강조. 그리고 기존 규칙의 블록 단위 "무엇을·왜".
- 금지: 중얼거림, 같은 말 반복(C3), 오해 소지, 의무적 Javadoc, 이력·작성자 주석(C1), 소음, 위치 표시 배너, 닫는 괄호 주석, 주석 처리된 코드(C5), HTML 주석, 다른 곳을 설명하는 비지역 정보, TMI.
- 낡은 주석은 발견 즉시 고치거나 지운다(C2).

### 2.4 형식 (cc2 5장)
- 팀 규칙 하나를 정하고 포매터로 강제한다(프론트는 기존 ESLint+husky 게이트).
- 파일은 신문처럼 쓴다: 위에는 고수준 개념, 아래로 갈수록 세부. 책은 파일 200줄 안팎을 권하지만, 이 수치는 참고값이다(§0).
- 개념 사이에는 빈 줄을 넣는다. 밀접한 코드는 세로로 가깝게 둔다. 변수는 사용하는 곳 가까이 선언한다(G10). 호출하는 함수가 호출되는 함수보다 위에 온다.
- 가로 길이는 120자 이내. 들여쓰기를 무시하지 않는다(한 줄 if·빈 while 본문도 들여쓴다).

### 2.5 객체와 자료 구조 (cc2 6장)
- 객체는 추상화 뒤로 데이터를 숨기고 동작을 공개한다. 자료 구조는 데이터를 공개하고 동작이 없다. **둘을 섞은 잡종을 만들지 않는다.**
- 새 타입 추가가 잦으면 객체(다형성)를, 새 동작 추가가 잦으면 자료 구조와 절차를 쓴다.
- 디미터 법칙: 메서드는 자기 클래스·자기가 만든 객체·인수·인스턴스 변수의 메서드만 호출한다. `a.getB().getC().do()` 같은 기차 충돌 금지(G36).
- DTO와 Active Record에는 비즈니스 규칙을 넣지 않는다.

### 2.6 오류 처리 (cc2 7장)
- 오류 코드 대신 예외. 테스트에서 try-catch-finally부터 쓴다.
- 미확인(unchecked) 예외를 쓴다. 예외에 의미 있는 맥락(실패한 연산과 유형)을 담는다.
- 호출자 관점에서 예외 클래스를 정의한다: 외부 API를 감싸 예외 유형을 하나로 모은다.
- 특수 사례 객체로 정상 흐름을 유지한다(Special Case 패턴).
- **null을 반환하지 않는다**(빈 컬렉션·특수 사례·Optional/nullable 타입). **null을 전달하지 않는다.**

### 2.7 경계 (cc2 8장)
- 외부·서드파티 API는 감싸서 쓴다. `Map` 같은 경계 인터페이스를 시스템 전체에 돌리지 않는다.
- 외부 라이브러리는 **학습 테스트**로 익히고, 그 테스트를 버전 업 회귀 검사로 남긴다.
- 아직 없는 API는 원하는 인터페이스를 먼저 정의하고 어댑터로 잇는다.

### 2.8 단위 테스트 (cc2 9장, cc3 T1–T9)
- TDD 3법칙: 실패하는 테스트 없이 프로덕션 코드를 쓰지 않는다. 실패할 만큼만 테스트를 쓴다. 통과할 만큼만 프로덕션 코드를 쓴다.
- 테스트 코드도 프로덕션 코드만큼 깨끗하게 쓴다. 가독성이 최우선이다: BUILD-OPERATE-CHECK(Given-When-Then) 구조, 도메인 특화 테스트 언어.
- 테스트 하나에 개념 하나. assert 수는 최소로.
- **F.I.R.S.T.**: 빠르게(Fast), 서로 독립적으로(Independent), 어느 환경에서나 반복 가능하게(Repeatable), 결과는 통과·실패로 스스로 판정하게(Self-Validating), 프로덕션 코드 직전에 적시에(Timely).
- 깨질 수 있는 것은 모두 테스트한다(T1). 커버리지 도구로 빈틈을 찾는다(T2). 사소한 테스트도 쓴다(T3). 경계 조건(T5), 버그 주변(T6)은 철저히 테스트한다.

### 2.9 클래스 (cc2 10장)
- 순서: 상수 → static 변수 → 인스턴스 변수 → public 함수 → (그 함수가 부르는) private 함수.
- 캡슐화를 유지한다. 테스트 때문에 가시성을 넓히는 것은 최후 수단이다(기존 "가시성 최소" 규칙과 같다).
- **작게. 크기는 책임 수로 잰다.** 이름에 Processor·Manager·Super가 붙거나, 25단어 안에 "그리고/만약" 없이 설명할 수 없으면 너무 크다.
- **SRP**: 변경할 이유가 하나뿐이어야 한다. 큰 클래스 몇 개보다 작은 클래스 여럿이 낫다.
- 응집도를 높인다: 메서드가 인스턴스 변수를 많이 쓸수록 좋다. 응집도가 떨어지면 클래스를 나눈다.
- 변경에 맞춰 조직한다(OCP): 새 기능은 기존 코드 수정이 아니라 확장으로 추가한다. 구체 클래스가 아니라 추상화에 의존한다(DIP).

### 2.10 시스템 (cc2 11장)
- 생성(시작)과 사용을 분리한다: 객체 생성은 main이나 팩토리, DI로 모으고, 지연 초기화 관용구를 곳곳에 흩뿌리지 않는다.
- 횡단 관심사(트랜잭션·보안·영속성)는 POJO 도메인과 분리한다(AOP·프록시·데코레이터).
- 시스템은 점진적으로 키운다. 명백한 가치가 있을 때만 표준을 도입한다. 도메인 특화 언어로 도메인 개념을 코드에 드러낸다.

### 2.11 창발적 설계: 단순한 설계 4규칙 (cc2 12장, 우선순위 순)
1. 모든 테스트를 실행한다(통과한다).
2. 중복을 없앤다.
3. 프로그래머의 의도를 표현한다.
4. 클래스와 메서드 수를 최소로 줄인다. 1–3이 우선이며, 교조적인 클래스 쪼개기는 하지 않는다.

### 2.12 동시성 (cc3 13장·부록 A)
- 동시성 코드는 다른 코드와 분리한다(SRP). 공유 데이터의 범위를 최소로 줄인다. 데이터 사본을 쓴다. 스레드는 가능한 한 독립적으로 만든다.
- 스레드 안전 컬렉션 등 라이브러리를 안다. 실행 모델(생산자-소비자·읽기-쓰기·식사하는 철학자)을 알아 둔다.
- 동기화하는 메서드 사이의 의존성을 피한다. synchronized 구역은 작게 한다. 종료 코드를 일찍부터 고민한다.
- 테스트: 일회성 실패를 "우연"으로 넘기지 않는다. 비동기 코드도 먼저 순차로 동작하게 만든다. 스레드 코드를 다양한 설정·플랫폼에서 돌리고, 지터(jiggle)로 실패를 유도한다.
- 데드락 4조건(상호 배제·잠금 후 대기·선점 불가·순환 대기) 중 하나를 깨서 막는다.

### 2.13 점진적 개선 (cc4 14–16장, cc5 부록 B)
- 동작하는 코드를 바로 다음 단계로 넘기지 않는다. 깨끗하게 만든 뒤 넘긴다.
- **아주 작은 단계로** 리팩터링하고 단계마다 전체 테스트를 돌린다. 테스트가 없으면 먼저 테스트로 감싼다(Bob의 SerialDate 첫 단계).
- 대규모 재설계는 하지 않는다. 시스템을 동작하는 상태로 유지하면서 조금씩 고친다.

## 3. Clean Architecture 핵심 규칙 — §0에 따라 ADR의 평가 기준으로 쓴다

### 3.1 목표와 가치 (ca1 1–2장)
- 아키텍처의 목표는 시스템을 만들고 유지하는 데 드는 **인력을 최소화**하는 것이다. "빨리 가려면 제대로 가라." 지저분하게 짜면 나중이 아니라 지금 느려진다.
- 동작(긴급)보다 구조(중요)를 지킨다. 아키텍처를 지키는 것은 개발자의 책임이다.

### 3.2 패러다임 (ca1 3–6장)
- 구조적 프로그래밍: 기능을 증명 가능한(테스트로 반증 가능한) 작은 단위로 분해한다. 무분별한 goto 같은 점프는 쓰지 않는다.
- 객체 지향의 핵심은 **다형성을 이용한 의존성 역전**이다. 소스 의존 방향을 원하는 대로 제어해 플러그인 아키텍처를 만든다.
- 함수형: 가변 상태를 분리한다. 불변 컴포넌트를 최대화하고, 가변 상태는 트랜잭션 메모리 등으로 보호한다. 이벤트 소싱을 고려할 수 있다.

### 3.3 SOLID (ca1 7–11장)
- **SRP**: 모듈은 **하나의 액터**에게만 책임진다. 다른 액터가 쓰는 코드를 한 클래스에 섞지 않는다(우발적 중복 공유·병합 충돌 방지).
- **OCP**: 확장에는 열리고 변경에는 닫힌다. 컴포넌트를 계층으로 나누고 고수준 컴포넌트를 저수준 변경에서 보호한다.
- **LSP**: 하위 타입은 상위 타입을 완전히 대체할 수 있어야 한다. 정사각형/직사각형 문제가 대표 예다. REST URI 같은 인터페이스 계약에도 적용한다. 특수 처리 if가 생기면 위반이다.
- **ISP**: 사용하지 않는 것에 의존하지 않는다. 필요한 것만 담은 좁은 인터페이스로 나눈다.
- **DIP**: 소스 의존은 추상에 둔다. 변동성 큰 구체 클래스를 참조·상속하지 않고, 구체 함수를 오버라이드하지 않는다. 구체적이고 변동성 큰 것의 이름을 언급하지 않는다. 생성은 추상 팩토리로 한다. 위반은 main 같은 구체 컴포넌트 안으로 모은다.

### 3.4 컴포넌트 원칙 (ca1 12–14장)
- 응집: **REP**(재사용 단위 = 릴리스 단위), **CCP**(같은 이유·같은 시점에 바뀌는 것을 묶는다. 컴포넌트 수준의 SRP), **CRP**(함께 쓰지 않는 것을 강요하지 않는다. 컴포넌트 수준의 ISP). 셋의 긴장 관계에서 현재 단계에 맞는 균형을 고른다.
- 결합: **ADP**(컴포넌트 의존 그래프에 순환이 없다. 순환은 DIP나 새 컴포넌트로 끊는다), **SDP**(더 안정된 쪽으로 의존한다), **SAP**(안정적인 컴포넌트는 추상적이어야 한다).
- 지표: 불안정성 `I = Fan-out / (Fan-in + Fan-out)`, 추상화 `A = 추상 클래스 수 / 전체 클래스 수`, 주계열 거리 `D = |A + I − 1|`. D가 0에서 멀면 고통의 구역(구체+안정)이나 쓸모없는 구역(추상+불안정)에 있다.
- 컴포넌트 구조는 하향식으로 먼저 설계하지 않는다. 빌드 가능성과 유지보수성에 맞춰 진화시킨다.

### 3.5 경계와 의존성 규칙 (ca2 15–28장)
- 좋은 아키텍처는 유스케이스·운영·개발·배포를 지원하고, **세부사항(DB·웹·프레임워크·장치)에 대한 결정을 최대한 미룬다.**
- **의존성 규칙**: 소스 의존은 항상 **안쪽(고수준 정책)** 을 향한다. 안쪽 원의 코드는 바깥 원에 선언된 이름(클래스·함수·변수·데이터 형식)을 언급하지 않는다.
- 엔티티(핵심 업무 규칙·데이터)와 유스케이스(애플리케이션 특화 규칙)는 프레임워크·DB·UI 타입을 import하지 않는다. 경계를 넘는 데이터는 단순 구조로, 안쪽에 편한 형식으로 만든다. DB 행이나 엔티티를 그대로 넘기지 않는다.
- 정책의 수준은 입출력에서 떨어진 거리로 판단한다. 같은 이유·같은 시점에 바뀌는 정책끼리 묶는다.
- **소리치는 아키텍처**: 최상위 구조가 프레임워크가 아니라 **유스케이스(도메인)** 를 말해야 한다.
- 진짜 중복과 **우발적 중복**을 구분한다. 서로 다른 이유로 바뀌는 비슷한 코드는 합치지 않는다.
- **험블 객체**: 테스트하기 어려운 부분(뷰·DB·외부 서비스)은 얇게 만들고, 로직은 테스트 가능한 쪽(프레젠터·인터랙터)으로 옮긴다. 프레젠터는 표시용 문자열과 플래그를 미리 만든다.
- 부분적 경계(마지막 단계 생략·일차원 경계·퍼사드)는 비용이 정당할 때 쓴다. 경계 결정은 시스템을 관찰하며 계속 재평가한다(YAGNI와 균형).
- **Main 컴포넌트**는 가장 지저분한 최하위 플러그인이다. 생성·설정·주입을 여기에 모은다.
- 서비스로 나누는 것 자체가 아키텍처는 아니다. 서비스 내부도 의존성 규칙을 따르는 컴포넌트로 설계한다. 횡단 기능은 서비스를 가로지르는 컴포넌트 경계로 다룬다.
- **테스트 경계**: 테스트는 가장 바깥 원이다. 시스템 코드는 테스트에 의존하지 않는다. 테스트 전용 API로 테스트를 구조에서 분리해 **깨지기 쉬운 테스트**를 막는다. 테스트 전용 위험 기능은 운영 배포물과 분리한다.
- 임베디드: 하드웨어·OS는 세부사항이다. HAL·OSAL 뒤에 두고 오프타깃에서 테스트할 수 있게 한다(ca2 29장).

### 3.6 세부사항과 패키지 구조 (ca3 30–34장·부록 A)
- DB·웹·프레임워크는 세부사항이다. 프레임워크와 결혼하지 않는다. 프레임워크 클래스를 도메인 객체가 상속하지 않게 하고, 프레임워크를 바깥 원에 두어 교체할 수 있게 한다.
- 패키지 구조 선택지(계층별·기능별·포트와 어댑터·컴포넌트별)는 ADR로 하나를 고른다. **어떤 구조든 접근 제어자로 강제한다**: 모든 것을 public으로 두면 구조는 장식이 된다. 컴파일러나 린터가 규칙을 강제하게 한다.
- 부록 A의 교훈: 테스트 불가능한 구조, 세부사항(장치·DB)에 묶인 정책, 미리 만든 재사용 프레임워크는 실패했다. 재사용 프레임워크는 실제로 쓰는 앱 셋을 만들어 본 뒤에 뽑는다.

## 4. 자가 점검 (Refactor 완료 조건 · 리뷰 체크리스트)

변경한 코드에 대해 하나씩 확인한다. 한 칸이라도 "아니오"면 Refactor가 끝나지 않은 것이다.
- [ ] 이름만 읽고 의도를 알 수 있는가. 축약어·인코딩·불용어가 없는가 (2.1)
- [ ] 각 함수가 한 가지 일만, 한 추상화 수준에서 하는가. 인수는 3개 이하이고 플래그·출력 인수가 없는가 (2.2)
- [ ] 중복이 없는가. 우발적 중복은 억지로 합치지 않았는가 (G5, 3.5)
- [ ] 주석이 §0의 규칙을 따르는가. 주석 처리된 코드·이력 주석·낡은 주석이 없는가 (2.3)
- [ ] null을 반환하거나 전달하지 않는가. 예외에 맥락이 담겨 있는가 (2.6)
- [ ] 외부 API를 감쌌는가. 경계 타입이 시스템 전체로 새지 않는가 (2.7)
- [ ] 테스트가 F.I.R.S.T.를 지키고 경계 조건을 다루는가 (2.8)
- [ ] 클래스의 변경 이유(액터)가 하나인가. 응집도가 높은가 (2.9, 3.3)
- [ ] 소스 의존이 고수준 정책 쪽을 향하는가. 도메인 코드가 프레임워크·DB·UI 타입을 모르는가 (3.5)
- [ ] 매직 넘버·죽은 코드·잡동사니·경고 끄기가 없는가 (G25·G9·G12·G4)
- [ ] 이번 변경이 요청 범위 안에 머무는가 (§0 보이스카우트 행)
