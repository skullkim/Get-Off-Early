# TDD Implementation — 요구사항 기반 테스트 주도 개발

모든 개발자(backend/frontend, senior/junior)가 공유하는 구현 규율. 이 프로젝트에서 개발은 **무조건** 이 절차를 따른다.

## 절대 원칙
1. **테스트 없이 프로덕션 코드를 작성하지 않는다.** 실패하는 테스트가 먼저 있어야 한다
2. **모든 요구사항(REQ-ID)은 테스트로 커버되어야 한다 (100%).** 테스트가 없는 REQ는 "구현 안 됨"으로 간주한다
3. **전체 테스트가 통과(100%)해야 QA로 넘길 수 있다.** 이 게이트는 우회하지 않는다

## 왜 이렇게 하는가
요구사항을 먼저 테스트로 옮기면, 테스트 묶음 자체가 "요구사항이 충족되었는가"의 실행 가능한 증거가 된다. 구현이 끝났다는 주장은 믿을 수 없지만, "이 REQ를 검증하는 테스트가 통과한다"는 검증 가능하다. QA는 이 증거 위에서 통합·동작을 검증한다.

## Red-Green-Refactor 사이클

작업(보통 REQ-ID 단위)마다 반복한다:

### Red — 실패하는 테스트 작성
1. 맡은 REQ의 수용 기준(Given-When-Then)을 테스트로 옮긴다
2. 각 수용 기준(AC)마다 최소 1개 테스트. 엣지/에러 케이스 AC도 빠뜨리지 않는다
3. 테스트에 **어떤 REQ를 커버하는지 주석/명명으로 표시**한다 (예: 테스트명에 `REQ-003` 포함, 또는 `// covers: REQ-003 AC-2`)
4. 테스트를 실행해 **실패하는 것을 확인**한다 (아직 구현이 없으니 실패해야 정상 — 통과하면 테스트가 잘못된 것)

### Green — 통과시키는 최소 구현
1. 테스트를 통과시키는 **최소한의** 코드를 작성한다 (과도한 일반화 금지)
2. 테스트를 실행해 통과를 확인한다

### Refactor — 정리
1. 테스트가 통과하는 상태를 유지하며 중복 제거·명명 개선
2. 매 리팩터 후 테스트 재실행으로 회귀 없음 확인

## 코딩 컨벤션 (모든 구현에 적용 — Green/Refactor 단계의 완료 조건)
- **명시적 이름 (프론트·백엔드 공통)**: 클래스·변수·함수 이름은 역할이 그대로 드러나게 짓는다. **축약어를 만들어 쓰지 않는다**(`id`, `url`, `dto`처럼 널리 통용되는 것만 예외). **사용자와 합의되지 않은 도메인 이름을 새로 만들지 않는다** — 도메인 용어는 `01_requirements.md`의 용어집(또는 사용자가 실제로 쓴 표현)에서 가져오고, 거기 없는 개념이 필요하면 이름을 지어내기 전에 리더/PM을 통해 사용자와 합의한다. **합의를 거쳐 새 도메인 용어를 정했다면 용어집 파일에 등재하고, 그 용어를 쓰는 코드 위치에는 해설 주석을 단다** — 이름만 보고 의미를 추측하게 만들지 않는다.
- **백엔드: 클래스 하나당 파일 하나**. controller·service·repository·entity와 DTO를 한 파일에 넣지 않는다 — DTO도 각자 파일로 분리한다. 언어가 한 파일 다중 클래스를 허용하더라도(Kotlin, Java 등) 이 규칙이 우선한다.
- **백엔드: 아키텍처 스타일을 혼합하지 않는다**. ADR(architecture-and-delegation §3.5)로 정한 단일 스타일(레이어드/헥사고날 등)을 코드베이스 전체에 일관 적용한다. **사용자가 결정한 아키텍처가 있으면 임의로 다른 아키텍처를 섞지 않는다.** 다른 스타일이 필요하면 코드에 섞지 말고 ADR 갱신으로.
- **백엔드: 목적 하나당 라이브러리 하나**. 같은 목적의 라이브러리를 중복 도입하지 않는다 — 예: DB 접근을 JPA로 정했으면 **사용자의 별도 지시가 없는 한** JDBC Template을 추가 설치·혼용하지 않는다. 예외가 필요하면 ADR로 근거를 남기고 리더를 통해 확인한다.
- **특정 버전 의존 금지 (공통)**: 특정 버전에서만 동작하는 방식(버전 종속 내부 API·실험 플래그·deprecated 경로)으로 라이브러리·프레임워크를 사용하지 않는다. 안정된 공개 API 기준으로 구현해 버전 업그레이드에 깨지지 않게 한다.
- **프론트엔드: React 모범 지침 준수**. React 구현은 vercel-labs `agent-skills`의 react-best-practices 지침(https://github.com/vercel-labs/agent-skills/tree/main/skills/react-best-practices)을 따른다. 프론트엔드 시니어(frontend-senior)는 구현 착수 전 이 지침을 조회해 적용 항목을 팀 규칙으로 공유한다. ESLint + husky pre-commit 자동 lint 필수는 기존 게이트 규칙(architecture-and-delegation §3) 그대로다.

## 프론트엔드 TDD 주의
- 컴포넌트의 **모든 상태**(빈/로딩/에러/성공/권한없음)를 각각 테스트한다 (디자인 명세의 상태 = 테스트 케이스)
- API 응답을 소비하는 부분은 **계약의 정확한 shape**으로 목(mock)을 만든다. 임의 shape으로 목을 만들면 경계면 버그를 못 잡는다
- 백엔드 계약과 다른 shape을 가정했다면 그건 테스트가 아니라 추측이다 — 시니어에게 확인한다

## 비동기 파이프라인 통합 테스트 격리 (공유 DB·큐·가변 상태)
비동기 파이프라인(Kafka 디스패치 등) + 공유 가변 싱글턴(인메모리 behavior store 등)을 쓰는 통합 테스트는 **격리 단독으론 통과해도 풀스위트에선 교차 폴루션으로 flake**한다 — 다른 테스트의 잔여 큐 메시지가 이 테스트 윈도우에 디스패치되거나, 공유 store가 async 시점에 다른 값이거나, 하드코딩 ID가 충돌(실제: stats 카운트 4≠3, settlement message_id 중복). 규율:
- **집계/통계/카운트 단언은 동기 결정적 시드**로 한다 — 비동기 발송(ingest→Kafka→dispatch) 대신 도메인 행을 **직접 repo save(상태·채널 명시)** 해서 검증(예: `messages.save(Message(status=SENT, finalChannel=SMS, …))`). async 발송 자체를 검증하는 테스트와 분리.
- **per-test 시간 윈도우 + 고유 식별자**(고유 `createdAt` 윈도우로 조회 필터, 고유 message_id/Idempotency-Key, 필요시 테스트 전용 클라이언트)로 공유 DB에서 결정성을 확보한다.
- **공유 가변 store가 async 디스패치 시점에 내가 set한 값일 것**이라 가정하지 않는다(다른 테스트가 reset/덮어쓸 수 있음). ScriptedBehavior 등은 attemptNo 인덱싱처럼 호출 무상태로.

## 버그 수정 시 (QA 반려 후)
1. **먼저 실패를 재현하는 테스트를 추가**한다 (그 버그가 다시 나면 잡히도록)
2. 그 테스트가 실패하는 것을 확인한다
3. 수정해서 통과시킨다
4. 전체 테스트를 재실행해 회귀가 없음을 확인한다

이 순서가 회귀를 막는다. 테스트 없이 고치면 같은 버그가 재발한다.

## 추적 매트릭스 (REQ ↔ 테스트)

`_workspace/04_coverage_matrix.md`를 작성·갱신한다. 모든 개발자가 자기 기여분을 추가한다:

```markdown
# 요구사항-테스트 추적 매트릭스

| REQ-ID | 영역 | 커버하는 테스트 | 담당 | 테스트 상태 |
|--------|------|---------------|------|-----------|
| REQ-001 | backend | test_login_success, test_login_wrong_pw | backend-senior | PASS |
| REQ-002 | frontend | DashboardEmpty.test, DashboardLoaded.test | frontend-junior | PASS |
| REQ-NF-001 | backend | test_list_response_under_200ms | backend-senior | PASS |

## 게이트 상태
- 전체 REQ 수: N
- 테스트로 커버된 REQ 수: N (목표 100%)
- 미커버 REQ: 없음 (있으면 나열 — QA 인계 불가)
- 전체 테스트: M개 / 통과 M개 / 실패 0 (실패 있으면 QA 인계 불가)
- 테스트 실행 명령: `{command}` / 마지막 실행 결과: {요약}
```

## TDD 게이트 (QA 인계 조건)
다음 두 조건을 **모두** 충족해야 QA로 넘긴다:
1. **커버리지 100%** — `01_requirements.md`의 모든 in-scope REQ가 매트릭스에서 1개 이상 테스트에 매핑됨
2. **통과 100%** — 전체 테스트 묶음을 실제로 실행했고 모두 통과 (출력으로 확인, "통과할 것이다"는 추측 금지)

하나라도 미충족이면 QA로 넘기지 않는다. 미커버 REQ가 있으면 테스트를 추가하고, 실패가 있으면 고친다.

## 검증 습관
- "테스트를 작성했다"가 아니라 "실행해서 통과를 봤다"로 말한다. 실행 결과 없이 완료를 주장하지 않는다
- 매트릭스의 REQ 목록과 요구사항 명세의 REQ 목록을 대조해 빠진 게 없는지 확인한다
