# Clean Code — 우리 하네스의 채택·기각 판정 (구현 층)

> **두 층의 역할 분담 (사용자 결정, 2026-10-31):**
> - **규칙 본문의 단일 소스 = `clean-code-rules` 스킬**(`.claude/skills/clean-code-rules/`). 두 책
>   전권 규칙 1,235개 + 쪽수 + 냄새 코드 66개 전문. **규칙을 알고 싶으면 그 스킬을 읽는다.**
> - **이 파일 = 하네스 층.** 그 규칙 중 **우리가 무엇을 추가로 채택했고, 무엇을 기각했고(사유),
>   무엇이 이미 수렴했는지**를 기록한다. 이름이 같아 혼동하기 쉬우니 분명히 해 둔다 —
>   **이 파일은 규칙의 출처가 아니다.**
>
> 충돌 판정의 권위는 `clean-code-rules` 스킬 **§0 우선순위표**에 있다(1순위 사용자 지정 규칙 →
> 2순위 스킬 → 3순위 언어 관례). 아래 §B 기각표가 그 §0과 어긋나면 **§0이 맞다** — 어긋난 것을
> 발견하면 임의로 정하지 말고 리더에게 보고한다.

## A. 채택 — 기존 컨벤션에 **없던** 것 (구현 중 자기검사용)

규칙 설명은 스킬에 있다. 여기 있는 것은 **우리 실적과의 연결**이다 — 왜 이 규칙이 우리에게
특별히 중요한지를 모르면 체크리스트의 한 줄로만 지나간다.

| # | 채택한 규칙 | 우리에게 무슨 값을 치르게 했나 | 스킬 참조 |
|---|---|---|---|
| 1 | **F.I.R.S.T.** — 특히 Independent·Repeatable | message-platform 빌드의 **async 테스트 flake = Repeatable 위반**, **동시 Testcontainers Docker 크래시 = Independent 위반**(테스트가 공유 런타임으로 결합). 당시 처방(동기 시드 + 시간 윈도우, 단일 러너 + reuse)은 맞았고, 이제 그 처방의 상위 규칙에 이름이 생겼다 | §2.8 |
| 2 | 테스트 코드도 생산 코드만큼 깨끗하게 — **단 효율 기준만 다르다** | 축이 둘이다: **청결도는 같은 기준, 효율은 다른 기준.** 테스트에서 비효율은 허용, 불명확은 불허 | §2.8 |
| 3 | **학습 테스트를 남긴다** | 우리 §3.6(선행 spike)은 "가정을 먼저 실측하라"까지였고 스파이크의 **처분**을 정하지 않았다. 추가분: **버리지 말고 learning test로 레포에 남긴다** → 라이브러리 업그레이드 때 우리 가정이 깨졌는지 자동으로 알려 주는 회귀 방어선 | §2.7 |
| 4 | 단순한 설계 4규칙의 **우선순위** | "더 쪼개라(②③)"와 "개수를 줄여라(④)"가 부딪히면 **②③이 이긴다.** ④는 넷 중 가장 낮다 — 교조적 쪼개기를 막는 조항이지 쪼개기를 막는 조항이 아니다 | §2.11 |
| 5 | **커버리지 빈 구역이 버그 위치를 가리킨다** (T2·T7·T8) | code-navigator-mac의 "테스트는 초록인데 기능이 죽어 있다" **8회 중 3회가 같은 catch-all 한 줄**이었고 그 안은 커버리지 0이었다. 미실행 구역을 먼저 봤다면 더 일찍 잡았다. 짝 규칙 T6: **버그 하나 찾은 함수는 전수 테스트**(버그는 뭉쳐 있다) | §2.8 · §2.14 |
| 6 | **동시성 코드는 SRP로 격리** · 서버 락 권장 · 순환대기 깨기 | 데드락 4조건 중 **순환대기 깨기**(모든 스레드가 자원을 같은 순서로 획득)가 우리 `knowledge/patterns/` 비관적 락 정렬 패턴의 근거다 — 왜 그게 통하는지가 이제 설명된다. 간헐 실패를 일회성으로 치부하지 않는 규율은 우리 "0건은 positive control 후에만 신뢰"의 동시성 버전 | §2.12 |
| 7 | **논리적 의존을 물리적으로** (G22) | `harness-runtime.md`의 네 행이 틀려 있었고 그 가정이 **7곳에 지시로** 박혀 있었다(서브에이전트에 없는 도구를 지시). 처방(표에 재측정 절차를 같은 파일에 박기)이 "가정하지 말고 물어서 받아라"의 문서판이었다 | §2.14 G22 |
| 8 | **경계 조건 캡슐화** (G33) | 기존 "매직넘버 → 상수"의 **off-by-one 버전**: 명세값이 아니라 *계산된 경계*(`level+1`)에도 이름을 붙인다 | §2.14 G33 |
| 9 | 먼저 동작하게, 그 다음 바르게 — **아주 작은 단계로** | 게이트는 "최종 상태가 그린"을 요구하지 중간의 지저분한 상태를 금지하지 않는다. **중간 상태를 숨기려 리팩터를 미루는 것이 오히려 규율 위반.** 단 작은 단계마다 테스트를 돌린다 | §2.13 |

## B. 기각 — 책 쪽을 채택하지 않는 규칙과 **사유**

**이 절이 존재하는 이유**: 사유를 적어 두지 않으면 다음 에이전트가 책을 근거로 우리 규칙을
되돌린다. (스킬 §0이 같은 충돌을 다루는 자리 — 두 표가 어긋나면 §0이 맞다.)

| 책의 규칙 | 책의 주장 | **우리 결정** | 사유 |
|---|---|---|---|
| `J1` 와일드카드 import | `import package.*`가 결합을 줄인다 | **기각.** 프로젝트 린터·언어 관례를 따른다(= 사실상 명시적 import) | 현대 린터·IDE·트리셰이킹이 모두 명시적 import 전제. 우리 프론트 게이트가 `eslint` 0 error를 요구하고 기본 룰셋이 와일드카드를 막는다. 책의 "no true dependency" 논증은 Java 클래스패스 특유의 것이고 TS/Kotlin에선 성립하지 않는다 |
| CC 16장 `final` 제거 | 인자·지역변수의 `final`은 잡동사니 | **기각.** 불변 기본 유지 | 저자 본인이 "관례와 정면으로 어긋남"을 인정하며 근거로 "내 단위 테스트가 그 오류를 잡는다"를 든다. 우리는 Kotlin `val`/TS `const` 기본이고, 그건 잡동사니가 아니라 타입시스템이 읽는 정보다 |
| CC 4장 "주석은 언제나 실패다" | 주석은 표현 실패의 보상 | **부분 채택** | 책 자신이 같은 장에서 **좋은 주석 7종**(법적·정보·**의도 설명**·명료화·결과 경고·TODO·공개 API)을 허용한다. 우리 "논리블록 빈줄 + 의도 주석"은 그중 **의도 설명**이라 유지. 채택되는 것은 **C1·C2·C3·C5 삭제**(이력·낡은·중복·주석 처리된 코드) |
| CC 3장 "함수는 20줄도 드물게" | 함수는 2~4줄이 이상 | **수치를 규칙으로 쓰지 않는다** | 저자가 "근거 논문을 제시할 수 없다"고 명시. 우리 판정은 **이름이 구현의 재진술이 되는지**(G30)이고, 그게 줄 수 세기보다 결정적이다 |
| CC 5장 "파일 200줄 지향·500줄 상한" | 작은 파일이 이해하기 쉽다 | **참고값으로만** | 우리 규칙 "클래스당 파일 하나"가 파일 크기를 이미 간접 제약한다. 줄 수 상한을 게이트에 넣지 않는다(DTO 분리로 파일이 많아지는 것이 정상) |

## D. 긴장 — 해소 방침

**리팩터 중 되돌림 ↔ 계약 동결.** CC 15·16장은 "한 리팩터가 다음을 부르고 그게 첫 리팩터를
되돌린다"를 두 번 정상이라고 말한다. 우리는 계약이 2회 교차하면 리더가 파일에 **동결**한다.
**선**: **내부 구조**의 되돌림은 자유(게이트만 그린이면 된다). **경계면 계약**의 되돌림은 다른
에이전트의 작업을 무효화하므로 소유자·동결 규칙을 따른다. 되돌림 자유도는 **혼자 되돌릴 수 있는
범위**까지다. (아키텍처 층의 같은 선: `.claude/skills/architecture-and-delegation/references/clean-architecture-rules.md` §4 긴장 3.)
