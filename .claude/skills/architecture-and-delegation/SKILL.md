# Architecture & Delegation — 시니어의 설계와 위임

시니어 개발자가 기술 방향을 정하고, 경계면을 합의하고, 작업을 주니어에게 위임하는 절차. backend-senior와 frontend-senior가 공유한다.

## 왜 이렇게 하는가
- **스택은 런타임 결정이다.** 이 툴킷은 특정 스택에 고정되지 않는다. 요구사항(비기능 요구 포함)에 맞는 스택을 시니어가 선택하고 근거를 남긴다
- **API 계약이 가장 흔한 버그의 진원지다.** 백엔드와 프론트엔드가 응답 shape을 따로 가정하면 런타임에 깨진다. 그래서 코드를 짜기 전에 계약을 먼저 합의한다
- **위임은 명확해야 재작업이 없다.** 주니어에게 "무엇을, 어떤 인터페이스로, 무엇이 통과해야 완료인지"를 주지 않으면 추측이 들어가고 그게 버그가 된다

## 절차

### 1. 요구사항·디자인 흡수
`01_requirements.md`와 `02_design.md`를 읽는다. 자신의 영역(backend/frontend)에 해당하는 REQ를 모두 추린다.

### 2. 스택 선택 (런타임 결정)
> **결정 전 prior-art 조회**: 스택·아키텍처·계약을 정하기 전에 `recall-knowledge` 절차로 `knowledge/INDEX.md` 를 확인해 과거 프로젝트의 채택 패턴과 반복 Gotcha 를 반영한다.

요구사항·비기능 요구·디자인 데이터 요구를 근거로 스택을 선택한다. 선택 시 고려:
- 요구의 성격(웹/API/실시간/배치), 성능·보안 요구
- 테스트 용이성 — TDD가 강제이므로 **테스트 프레임워크와 실행 명령**을 반드시 함께 정한다
- 사용자가 제약을 줬으면 그 안에서, 없으면 합리적 기본을 택하고 근거를 남긴다

스택과 테스트 실행 명령(예: 테스트 커맨드, 커버리지 확인 방법)을 아키텍처 문서에 명시한다 — 이것이 TDD 게이트 검증의 기반이다.

**빌드/테스트 실행 프로토콜 (공유 워크스페이스 직렬화).** 여러 개발자(시니어+주니어)가 같은 디렉토리·툴체인을 공유하면 풀빌드/테스트를 **동시에** 돌릴 때 빌드 락·데몬·포트(예: Gradle 빌드 락, 테스트 DB 포트) 충돌로 **가짜 실패**가 난다(이번 빌드에서 실제 발생). 셋업 단계에서 실행 프로토콜을 정해 아키텍처 문서에 명시한다:
- **게이트 판정 풀빌드는 시니어가 단독 1회** 실행해 그린·테스트 수를 확정한다 — 그 시점에 다른 팀원은 같은 워크스페이스에서 풀빌드를 돌리지 않는다.
- 개발자는 작업 중 **스코프 테스트**(특정 테스트 클래스/파일 패턴)만 돌리고, 풀빌드가 필요하면 시간을 겹치지 않게 조율한다.
- 가능하면 데몬/캐시 충돌을 줄이는 옵션(예: `--no-daemon`)을 쓴다.
- **무거운 공유 테스트 런타임(Testcontainers Kafka+PG+Redis 등)은 동시 실행 시 팬텀을 넘어 Docker 호스트를 크래시시킨다**(실제: 시니어+주니어 동시 gradle이 각자 컨테이너 세트를 띄워 Docker 데몬 다운). → ①**단일 지정 테스트러너**(백엔드 gradle은 시니어만 실행; 주니어는 코드+실패테스트 작성만 하고 "이거 돌려달라"고 시니어에 요청) ②**Testcontainers 재사용 활성**(`~/.testcontainers.properties`에 `testcontainers.reuse.enable=true` + 컨테이너 `.withReuse(true)` 또는 `@ServiceConnection` 싱글턴 컨테이너)로 매 런마다 새 컨테이너를 안 띄운다.
- **게이트 정의 (무엇이 "그린"인가) — 게이트 그린은 테스트만이 아니다.**
  - 백엔드: `./gradlew clean test`(컴파일+테스트 포함).
  - 프론트(TS+Vite): **`tsc -b`(0 error) + `vite build`(성공) + `vitest`(전 통과) 셋 다 그린**이어야 게이트 충족. `vitest`만 그린이고 `tsc`/`build`를 안 본 채 "게이트 통과"로 보고하지 않는다.
  - **게이트는 최종 편집 직후 1회 실행해 보고**한다 — 이전 시점에 그린이었어도 이후 편집으로 드리프트할 수 있다(실제: 팀이 "tsc 0/build OK" 보고 후 최종 편집서 미사용 import로 tsc 2에러 → 리더 풀게이트 재실행이 포착). "예전에 그린이었다"는 게이트 근거가 아니다.

### 3. 구조 설계
- 백엔드: 레이어/모듈 구조, 데이터 모델(스키마), 에러 처리 전략
- 프론트엔드: 컴포넌트 구조, 상태관리, 라우팅, 데이터 계층(API 소비 훅/서비스). 스캐폴드(Vite/CRA 등)로 부트스트랩하면 **템플릿 기본 스타일/자산(예: 기본 index.css의 색·다크모드·#root 정렬)이 디자인 토큰과 충돌**할 수 있으니 정리/제거해 디자인 시스템과 일치시킨다
  - **스타일 완료 정의**: 디자인 토큰(변수) 정의에 그치지 말고, 컴포넌트가 쓰는 **모든 className에 대응하는 실제 CSS 규칙 + 반응형(미디어쿼리/clamp)** 을 구현해야 완료다. 토큰만 있고 컴포넌트 스타일이 없으면 미스타일로 나간다(테스트는 시각을 검증하지 않음 — QA 스크린샷 점검으로 확인). 스타일링도 위임 작업의 명시적 완료 기준에 포함한다.

### 3.5 아키텍처 결정 기준 + 경량 ADR (관례 기본값에 안주하지 않기)
코드 레벨 아키텍처는 정답이 여럿이다(레이어드/헥사고날/CQRS, 모듈 경계, 상태관리 선택 등). **익숙한 기본을 고르고 근거를 사후에 붙이지 말고, 핵심 결정은 이 프로젝트의 힘에 비춰 대안과 비교**한 뒤 택한다.

**평가할 힘 (이 프로젝트 기준으로 가중):**
- **테스트 용이성** — TDD가 강제. 위험·핵심 로직을 순수 함수/단위로 떼어낼 수 있는가(예: 게임 규칙을 DB/프레임워크 없이 단위 테스트).
- **단순성(복잡도 예산)** — 요구 규모 대비 과한 추상화인가. 작으면 단순한 쪽.
- **변경·확장 가능성** — 바뀔 가능성이 높은 축(요구가 가리키는 변동점)을 격리했는가.
- **위임 적합성** — 경계가 REQ-ID 단위 위임(시니어/주니어)으로 깔끔히 쪼개지는가.
- **되돌릴 수 있는가(reversibility)** — 되돌리기 쉬운 결정은 빠르게, 어려운 결정(데이터 모델·경계면·인증)은 신중히.

**경량 ADR (핵심 결정마다 1블록).** 아키텍처적으로 의미 있는 결정(예: 핵심 로직 배치, 상태관리 선택, 영속 형태, 인증 방식, 모듈 경계)은 `03_*_architecture.md`에 **결정 / 고려한 대안 2~3 / 트레이드오프(위 힘 기준) / 왜 이 프로젝트엔 이것**을 남긴다. **트레이드오프가 실재하고 다르게 갈 수 있었던 결정에만** 쓴다(평범한 관례엔 과용 금지).

### 4. API 계약 합의 (경계면 — 가장 중요)
백엔드 시니어가 초안을 만들고 프론트엔드 시니어와 **SendMessage로 합의**한다. 계약에 반드시 포함:
- 엔드포인트 목록 (메서드 + 경로)
- 각 요청/응답의 정확한 shape — **래핑 여부**(`{ items: [...] }` vs 배열), **필드명 규칙**(camelCase 일관성), 타입
- 상태 코드, 에러 응답 형식
- 페이지네이션/정렬/필터 형식
- 비동기/즉시 응답 구분 (202 즉시 응답 vs 최종 결과 shape)

**계약 하드닝 체크리스트 (프레임워크 기본값에 속지 않기):**
- **날짜/시간 필드는 포맷 + 타임존을 못박는다** (예: UTC ISO-8601 `...Z`, date-only는 `YYYY-MM-DD`). 직렬화기를 프레임워크 기본값에 맡기지 말고 계약에 맞게 설정한다 — 기본 직렬화가 로컬 오프셋을 누출하면 경계면이 어긋난다.
- **에러 상태 코드 매핑을 명시하고, catch-all/전역 예외 핸들러가 프레임워크 4xx를 500으로 마스킹하지 않게** 한다 (잘못된 path 변수→400, 없는 리소스→404, 잘못된 메서드→405). 존재 비노출이 필요하면 의도적으로 404로 통일하되 500 뭉개기는 금지.
- **cross-origin/CORS**: 브라우저가 백엔드에 어떻게 도달하는지(동일 출처 / dev 프록시 / CORS allowlist)를 정하고, **실제 구동·프리뷰 경로의 origin(로컬·터널·배포 도메인)이 처리되는지** 확인한다. allowlist를 `localhost`만으로 박아두면 실제 환경(터널·배포)에서 403으로 깨진다 — 라이브 E2E 스모크로 검증한다(브라우저는 Origin/프리플라이트를 보내지만 curl은 안 보냄).

**계약의 단일 소스 = 백엔드 아키텍처 문서(`03_backend_architecture.md §3`), 소유자 = 백엔드 시니어.** 프론트엔드 시니어는 SendMessage로 **제안만** 하고, 합의값을 문서에 반영하는 것은 백엔드 시니어가 **1회** 한다. 양쪽이 각자 문서를 고치거나 서로 양보(상대 값 채택)를 반복하면 오히려 어긋난다 — 실제 발생: leaderboard 래핑/best 경로가 상호 양보로 **교차(swap)**해 미스매치. 협상 중 문서를 양쪽이 동시에 편집하지 않는다.

이 계약(문서 §3)이 QA의 통합 정합성 검증 기준이 된다. 계약 변경은 양쪽 시니어 동시 합의 후 **백엔드 시니어가 문서에 1회 반영**한다. **합의가 2회 교차/불일치하면 즉시 리더에게 에스컬레이션** — 리더가 값을 정해 **문서(파일)에 동결**한다(메시지로만 정하면 stale 문서를 재읽기해 또 뒤집힌다 — 파일이 권위).

**엔드포인트/빈당 단일 소유자.** 한 라우트(예: `GET /api/stats`)나 빈은 정확히 한 곳에서만 구현한다. 병렬 작업스트림(시니어가 주니어 작업 흡수, 계약 갭 동결로 재구현 등)이 **같은 엔드포인트를 두 컨트롤러에 중복 매핑**하면 `requestMappingHandlerMapping` ambiguous mapping으로 **컨텍스트 로드가 실패해 전 통합테스트가 캐스케이드 실패**한다(실제: 중복 `/api/stats` 컨트롤러 → 82 테스트 동시 실패). → 흡수/재구현 시 **기존 구현을 먼저 제거**하고, **게이트 전 중복 라우트/빈 충돌을 점검**한다(`grep '@GetMapping("/api/...")'` 중복 확인 등).

### 5. 작업 분해 (REQ-ID 단위)
각 REQ를 구현 작업으로 쪼갠다. 각 작업에:
- 충족 REQ-ID
- 복잡도/위험도 추정
- 담당: senior(직접) | junior(위임)

**위임 판단 기준:**
| 시니어가 직접 | 주니어에게 위임 |
|-------------|---------------|
| 아키텍처적 결정이 필요 | 결정이 이미 내려져 있고 명확 |
| 위험/핵심 경로 | 격리되어 영향 범위가 작음 |
| 경계면(API 계약) 정의 | 정의된 계약을 소비하는 구현 |
| 여러 모듈에 걸친 작업 | 단일 모듈/컴포넌트 |

### 6. 위임 실행 (팀 모드 — 중첩 불가 우회)
주니어를 직접 스폰할 수 없으므로 공유 작업 목록으로 위임한다:
- `TaskCreate`로 주니어에게 작업 생성. description에 **REQ-ID + 인터페이스 + 통과해야 할 테스트(완료 기준)**를 명시
- `SendMessage`로 상세 스펙(기대 동작, 입출력, 디자인 참조)을 전달
- 주니어가 막히면 질문에 답하고, 완료 보고 시 코드·테스트를 리뷰한다. 미흡하면 구체적 수정 지시와 함께 반려

backend-senior → `_workspace/03_backend_architecture.md`
frontend-senior → `_workspace/03_frontend_architecture.md`

```markdown
- 언어/런타임: ... (근거)
- 프레임워크: ...
- 테스트: {프레임워크} / 실행 명령: `{command}` / 커버리지 확인: `{command}`

## 2. 구조
- {레이어/모듈 또는 컴포넌트/상태관리}
- 데이터 모델 / 상태 모델

## 2.5 핵심 아키텍처 결정 (ADR — 트레이드오프 실재한 것만)
### ADR-1: {결정 주제}
- 결정: {택한 것}
- 고려한 대안: {A / B / C}
- 트레이드오프: {각 대안의 장단점 — 테스트용이성/단순성/변경가능성/위임/되돌림 기준}
- 채택 이유(이 프로젝트 기준): {이 요구·규모에서 이걸 고른 이유}

## 3. API 계약 (경계면) — 백엔드가 정의, 양 시니어 합의
### {METHOD} {경로}
- 요청: {shape}
- 응답(성공): {정확한 shape — 래핑/필드명/타입}
- 응답(에러): {상태코드 + 형식}

## 4. 작업 분해
| 작업 | REQ-ID | 복잡도 | 담당 | 완료 기준(통과 테스트) |
|------|--------|--------|------|---------------------|
| ... | REQ-001 | 높음 | senior | ... |
| ... | REQ-002 | 낮음 | junior | ... |
```

## 품질 게이트
- 자기 영역의 모든 REQ가 작업으로 분해되었는가? (누락 = QA에서 미구현으로 드러남)
- API 계약의 응답 shape이 정확한가? (래핑/필드명까지)
- 테스트 실행 명령이 명시되었는가? (TDD 게이트 검증의 전제)
- 빌드/테스트 실행 프로토콜(공유 워크스페이스 직렬화)과 계약 하드닝(날짜 타임존·프레임워크 4xx 비마스킹)이 문서에 반영되었는가?
- 트레이드오프가 실재한 핵심 아키텍처 결정에 경량 ADR(대안·트레이드오프·채택 이유)이 기록되었는가?

## 재실행 시
기존 아키텍처 문서가 있으면 읽고, 변경된 REQ/QA 피드백에 해당하는 부분만 수정한다. API 계약 변경은 반드시 양 시니어 합의 후 반영한다.
