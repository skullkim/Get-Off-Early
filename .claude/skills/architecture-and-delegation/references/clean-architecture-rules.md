# Clean Architecture — 우리 하네스의 채택 판정과 판례 (아키텍처 층)

> **두 층의 역할 분담 (사용자 결정, 2026-10-31):**
> - **규칙 본문의 단일 소스 = `clean-code-rules` 스킬**(`.claude/skills/clean-code-rules/`). 두 책 전권
>   규칙 1,235개 + 쪽수. 책과 사용자 지정 규칙이 충돌할 때 **무엇이 이기는지도 그 스킬 §0**이 정한다.
> - **이 파일 = 하네스 층.** 그 규칙 중 *아키텍처 결정 시 반드시 판정해야 하는 것*을 체크리스트로
>   뽑고, 우리 빌드 판례와 하네스 절차와의 긴장을 기록한다.
>
> **같은 규칙을 다시 쓰지 않는다.** 아래 판정 항목은 설명이 아니라 **포인터 + 판정 방법**이다.
> 상세·근거·쪽수가 필요하면 링크된 스킬 절을 읽는다. 두 문서가 어긋나면 **스킬이 규칙의 권위**이고
> 이 파일은 *우리가 그걸 어떻게 판정하는지*의 권위다.
>
> 이 파일에만 있는 것(스킬에 없음): ① 책에 없는 패턴군 11개의 결정 경로 ② 우리 빌드 판례표
> ③ 하네스 절차와의 긴장 4건.

## 1. 결정 경로 — 책이 다루지 않는 패턴은 차트가 담당한다

`clean-code-rules` 스킬 §3은 **의존 방향·SOLID·컴포넌트 원칙**을 다룬다. 반면 Saga·CQRS·API
Gateway·Strangler Fig·Retry·Timeout·Rate Limiting·DI·Plugin·MVC·Sharding **11개 패턴은 두 책에
없다**(실측: 스킬 전체에서 "Saga"·"Rate Limiting"·"Strangler" 히트 0건). 그래서 §3.5의 결정
절차는 이 순서다:

1. **후보 좁히기** — [architecture-decision-chart.md](architecture-decision-chart.md) §1. force 추출 → **단위 판별**(시스템 구조/전술/설계/데이터) → 결정 표 매칭. 단위를 건너뛰면 다른 층위의 패턴을 비교한다.
2. **금지 조건 확인** — 각 후보의 "적용 금지/보류" 열. 걸리면 후보에서 빼거나 선행 조치 먼저. 조합이면 차트 §4 상호작용표. 구현 리스크는 [architecture-patterns-guide.md](architecture-patterns-guide.md)의 패턴별 "구현 시 신경 쓸 점 / 적용하면 안 되는 때".
3. **구조 검증** — 좁힌 안이 의존 방향 측면에서 성립하는지 §2의 판정 항목으로 확인한다.
   차트와 `clean-code-rules` 스킬이 충돌하면 **스킬이 우선**한다(차트는 패턴 라우터, 스킬은 불변식).

## 2. 아키텍처 결정 시 **반드시 판정**하는 항목 (위반 시 설계 반려)

규칙의 내용은 `clean-code-rules` 스킬에 있다. 여기 있는 것은 **우리가 그걸 어떻게 판정하는지**다 —
"읽고 지켜라"는 지켜지지 않고, "무엇을 세어서 몇이면 위반인가"는 지켜진다.

| # | 판정 | 방법 (기계적으로) | 규칙 출처 |
|---|---|---|---|
| A-1 | 의존 방향이 안쪽(고수준)으로만 향한다 | 도메인·유즈케이스 패키지에서 프레임워크·ORM·HTTP·드라이버 타입을 import하는 줄 수를 센다. **1건이라도 있으면 위반.** 끊지 말고 역전시킨다(안쪽이 인터페이스 선언, 바깥이 구현) | 스킬 §3.5 의존성 규칙 · §3.3 DIP |
| A-2 | 경계를 넘는 데이터가 안쪽에 편한 단순 구조다 | 유즈케이스 시그니처에 ORM 엔티티·DB 행·HTTP DTO 타입이 나타나는가 | 스킬 §3.5 |
| A-3 | 엔티티와 유즈케이스가 분리됐다 | **PM 산출물이 이미 나눠 줬다** — `01_requirements.md`의 **불변식(INV)=엔티티**, **상태 전이표·수용 시나리오=유즈케이스**(`define-requirements` §6). 둘이 한 클래스에 있으면 요구사항이 분리해 준 것을 코드가 다시 합친 것이다 | 스킬 §3.5 |
| A-4 | 프레임워크를 상속하지 않고 도구로 쓴다 | 도메인 타입이 프레임워크 기반 클래스를 `extends`하는가. **예외**: 사용자가 그 프레임워크의 관례 아키텍처를 지시했다면 그것이 결정이고(§3.5 기본값), 단 **ADR에 "이 결합을 받아들인다"를 명시** | 스킬 §3.6 |
| A-5 | 업무 규칙 테스트가 UI·HTTP·DB를 경유하지 않는다 | 경유하면 험블 객체로 깎아 테스트 가능 경계를 만든다. 프론트에서 가장 자주 걸리는 항목 — 단 **시각 충실도는 이걸로 대체되지 않는다**(스크린샷 대조 유지) | 스킬 §3.5 험블 객체 · 테스트 경계 |
| A-6 | 중복을 합치기 전에 **우발적 중복**인지 판별했다 | 판정 질문: 이 둘은 **같은 이유로 같은 시점에** 바뀌는가. 아니면 남겨 둔다. (G5 "중복은 최대 악"은 *진짜* 중복에만 적용) | 스킬 §3.5 · G5 |
| A-7 | 컴포넌트 의존 그래프에 순환이 없다 | 모듈 import 그래프의 강연결 성분이 1을 넘는 것이 있는가. 있으면 DIP로 역전하거나 공통 의존 컴포넌트를 추출 | 스킬 §3.4 ADP |

**ADR에 기록하는 평가 항목**(판정이 아니라 선택): 디커플링 모드와 왜 더 가벼운 모드가 아닌지 ·
미룬 결정 목록 · 컴포넌트 묶는 축(REP/CCP/CRP 중 어디에 기울었고 무엇을 포기했는지) · 경계를 안
그었다면 나중에 그을 자리를 남겼는지. 형식은 [document-template.md](document-template.md)가 단일 소스다.

> **자동화하지 못한 것 (정직하게 남긴다)**: `I`·`A`·`D = |A+I−1|` 주계열 거리 지표는 import
> 분석기가 필요해 **이번 범위에 없다**. 지금은 "많이 의존받는 모듈이 구체 클래스 덩어리인가"를
> 시니어가 눈으로 보고 ADR에 쓴다. 지표 자동화는 별도 작업으로 남긴다.

## 3. 판례 — 우리에게 일어난 일 ↔ 책의 어느 규칙

규칙만 있으면 다음 에이전트는 그 규칙이 *우리에게* 무슨 값을 치르게 했는지 모른다. 이 표가 그 연결이다.

| # | 우리 빌드에서 일어난 일 | 해당 규칙 | 교훈 |
|---|---|---|---|
| 1 | shop: 두 시니어가 상호 양보해 계약이 교착하고 문서가 thrash → 리더가 백엔드 파일 §3에 값을 **동결** | CA 경계 비용(부분적 경계·경계 재평가) | 경계는 비싸다. 비용을 양쪽이 협상으로 나누려 하면 교착한다 — **경계의 소유자를 한쪽으로 정하는 것**이 그 비용을 치르는 방식이다 |
| 2 | message-platform: 동시 Testcontainers가 Docker를 크래시, async 테스트 flake | 테스트 경계 · F.I.R.S.T.(Independent·Repeatable) | 테스트가 **공유 런타임**에 의존하면 테스트끼리 결합된다. 단일 러너 + reuse는 "테스트 컴포넌트의 의존 정리"였다 |
| 3 | code-navigator: 라우트 파일·등록·전체 그린이 다 있는데 엔드포인트 하나가 TODO로 비어 있었고 **테스트가 0건** | 테스트 경계 · T1(불충분한 테스트) | 그린은 **존재하는 테스트의** 그린이다. 계약 표면과 구현의 전수 대조가 경계를 실재하게 만든다 |
| 4 | code-navigator-mac: catch-all 한 줄이 기능을 죽이고도 테스트를 통과 (같은 원인 3회) | G9(죽은 코드)·T8(커버리지 패턴)·G4(안전장치 무력화) | 삼켜진 예외는 경계 밖에서 **관측 불가**다. 그 catch 안은 커버리지 0이었다 — 미실행 구역이 먼저 가리켰다 |
| 5 | **잘된 판례(보존)**: minesweeper/shop에서 게임·결제 규칙을 DB·프레임워크 없이 단위 테스트할 수 있게 떼어낸 것 | 엔티티/유스케이스 분리 · 의존성 규칙 | §3.5의 "테스트 용이성" 힘이 이미 이걸 묻고 있다. 바꾸지 말 것 |
| 6 | `harness-runtime.md`의 네 행이 틀려 있었고, 그 가정이 **7곳에 지시로** 박혀 있었다(서브에이전트에 없는 도구) | G22(논리적 의존을 물리적으로) | 모듈이 다른 모듈의 동작을 **가정**하면 깨져도 컴파일은 통과한다. 처방(표에 재측정 절차를 같은 파일에 박기)은 "물어서 받아라"의 문서판이었다 |

## 4. 긴장 — 해소 방침 (덮지 않고 명시한다)

### 긴장 1 — "컴포넌트 구조는 하향식으로 설계하지 않는다" ↔ Phase 3의 선행 아키텍처 문서
책은 컴포넌트 의존 구조가 빌드·배포 가능성에 맞춰 **진화하는 지도**이고 처음에 설계하는 것이
아니라고 한다. 우리 `build-project` Phase 3은 구현 착수 전에 `03_*_architecture.md`와 ADR을 요구한다.

**해소**: 층위가 다르다. Phase 3이 고정하는 것은 **경계면(API 계약)과 의존 방향**이고, 이건 두
에이전트가 병렬로 일하려면 선행 합의가 불가피하다(계약 교착·반쪽 수정의 비용이 실측됐다).
반면 **컴포넌트 묶는 축(REP/CCP/CRP 균형)과 배포 단위는 Phase 3에서 확정하지 않고 ADR의
"미룬 결정"에 남긴다.** 즉 Phase 3은 *의존 방향*을 정하고, *컴포넌트 분할*은 자라면서 조정한다.

### 긴장 2 — "테스트를 생산 구조에 1:1로 묶으면 깨지기 쉬워진다" ↔ 커버리지 매트릭스
우리 `04_coverage_matrix.md`는 **REQ-ID ↔ 테스트**를 추적하므로 클래스가 아니라 **요구사항**에
묶여 있다 — 구조적으로는 책과 같은 편이다.

**남는 위험**: 매트릭스를 "테스트 수"로 채우면 REQ 하나에 클래스별 테스트를 늘려 칸을 메우는
압력이 생긴다. **방침**: 매트릭스의 칸은 *그 REQ의 수용 기준을 입증하는 테스트*를 가리키고,
구현 클래스 목록이 아니다. 리팩터로 클래스가 쪼개져도 그 칸은 **바뀌지 않아야** 정상이다 —
바뀐다면 테스트가 구조에 붙어 있다는 신호다.

### 긴장 3 — "리팩터 중 앞선 결정을 되돌리는 것은 정상" ↔ 계약 동결
Clean Code 15·16장은 "한 리팩터가 다음을 부르고 그게 첫 리팩터를 되돌린다"를 두 번 정상이라고
말한다. 우리는 계약이 2회 교차하면 리더가 파일에 **동결**한다.

**선**: **내부 구조**의 되돌림은 자유다(게이트만 그린이면 된다). **경계면 계약**의 되돌림은 다른
에이전트의 작업을 무효화하므로 소유자·동결 규칙을 따른다. 되돌림 자유도는 **혼자 되돌릴 수 있는
범위**까지다.

### 긴장 4 — "보이스카우트 규칙" ↔ "무관 변경 최소화"
`clean-code-rules` 스킬 §0이 이미 판정했다(정리는 *이번에 수정하는 함수 안에서만*). 여기 다시
적지 않고, **이 긴장이 아키텍처 층위에서 나타나는 형태만** 덧붙인다: 설계 문서·ADR을 고칠 때도
같다. 남의 영역 ADR을 "정리"하지 않는다 — ADR의 소유자는 그 영역 시니어다(§3.5).
