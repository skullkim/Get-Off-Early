# 1. 시스템 구조 수준

## 1-1. Saga

**정의.** 여러 서비스에 걸친 하나의 업무를 **로컬 트랜잭션의 연쇄**로 나누고, 중간
단계가 실패하면 앞선 단계를 **보상 트랜잭션(compensation)**으로 되돌려 전체 정합성을
맞추는 패턴.

**추구하는 바.** 분산 환경에서 **2PC(분산 락)를 피하면서** 여러 서비스의 데이터를
업무적으로 일관되게 유지. 가용성과 서비스 자율성을 지키는 대신 **최종 일관성**을 받아들임.

**해결하려는 문제.** 서비스마다 DB가 분리된 마이크로서비스에서 "주문 생성 → 결제 →
재고 차감 → 배송"처럼 여러 서비스를 하나로 묶어야 하는데, 전역 ACID 트랜잭션을 걸 수
없는 상황.

**구현 시 신경 쓸 점.**
- **조정 방식 선택**: *오케스트레이션*(중앙 오케스트레이터가 단계를 호출·보상 — 흐름이 명시적이고 디버깅 쉬움, 오케스트레이터에 결합) vs *코레오그래피*(각 서비스가 이벤트로 다음 단계를 트리거 — 결합 낮지만 전체 흐름 추적이 어려움). 단계가 많고 분기가 복잡하면 오케스트레이션이 유리.
- **보상 가능성**: 모든 단계에 **의미 있는 보상**이 정의돼야 함. "이메일 발송"처럼 되돌릴 수 없는 단계는 사가 **뒤쪽**에 배치하거나 pending 상태로 처리.
- **멱등성**: 재시도·중복 이벤트로 각 단계와 보상이 **여러 번 실행**될 수 있음. 모든 핸들러를 멱등하게(처리 ID/상태 체크).
- **격리(isolation) 부재 대응**: 사가는 ACID의 I가 없어 중간 상태가 외부에 노출됨. 대응책 — *semantic lock*(진행 중 상태 플래그), *commutative updates*(교환 가능한 연산 설계), *pessimistic view*(민감 단계 순서 조정), *reread value*(수정 전 값 재확인), *by value*(요청 위험도에 따라 사가/분산 트랜잭션 선택).
- **상태·관측성**: 사가 인스턴스의 상태(어느 단계까지 성공/보상했는지)를 **영속화**하고, 실패·보상 흐름을 추적할 수 있게 로깅·대시보드.
- **타임아웃/교착**: 응답 없는 단계에 타임아웃과 보상 트리거. 무한 대기 금지.

**적용하면 안 되는 때.** 단일 서비스/단일 DB로 충분할 때, 즉시 강한 일관성이 필수인
코어(일부 금전 원장), 보상이 원천적으로 불가능한 작업만으로 구성될 때.

**함께 쓰는 패턴.** CQRS(진행 상태 조회), Outbox(이벤트 발행 원자성), Retry/Timeout.

## 1-2. CQRS (Command Query Responsibility Segregation)

**정의.** **쓰기(Command) 모델과 읽기(Query) 모델을 분리**해, 각각을 다른 목적에 맞게
설계·확장하는 패턴.

**추구하는 바.** 읽기와 쓰기의 **서로 다른 요구(모델 형태, 부하, 확장 축)**를 독립적으로
최적화. 복잡한 도메인에서 쓰기 불변식과 읽기 편의를 분리.

**해결하려는 문제.** 하나의 모델로 쓰기(정규화·불변식 중심)와 읽기(비정규화·조회 편의
중심)를 모두 만족시키기 어렵고, 읽기 부하가 쓰기보다 훨씬 커서 같이 확장하기 비효율인 상황.

**구현 시 신경 쓸 점.**
- **최종 일관성 수용**: 쓰기 모델 → 읽기 모델 반영에 지연이 생김. 사용자/호출자가 방금 쓴 것을 즉시 못 볼 수 있음(read-your-writes 필요하면 별도 처리).
- **프로젝션(동기화)**: 이벤트/변경을 읽기 모델로 투영하는 경로를 설계. 동기 투영(간단, 쓰기 지연↑) vs 비동기 투영(확장·탄력, 지연·순서·중복 처리 필요).
- **읽기 모델 재구축**: 읽기 스키마 변경·버그 복구를 위해 **처음부터 재생성(rebuild)**할 수 있어야 함. 이벤트 소싱과 결합하면 쉬움(단, CQRS ≠ 이벤트 소싱, 필수 아님).
- **중복·순서**: 비동기 투영은 메시지 중복·순서 역전에 대비(멱등 업서트, 버전/시퀀스).
- **복잡도 비용**: 모델·배포·운영이 둘로 늘어남. 이득이 복잡도를 넘는 영역에만 국소 적용.

**적용하면 안 되는 때.** 읽기/쓰기 모델이 거의 같고 단순 CRUD로 충분할 때. 전역 도입은
과설계이며, **바운디드 컨텍스트 단위로 선택 적용**이 정석.

**함께 쓰는 패턴.** Event Sourcing(선택), Saga, 캐시, API Gateway(읽기 전용 엔드포인트 집계).

## 1-3. API Gateway

**정의.** 클라이언트와 내부 서비스 사이의 **단일 진입점**으로, 라우팅·인증·집계 등
cross-cutting 관심사를 한곳에서 처리하는 패턴.

**추구하는 바.** 클라이언트를 내부 서비스 토폴로지에서 **분리**하고, 공통 관심사
(인증·인가, 레이트 리밋, 로깅, 응답 집계, 프로토콜 변환)를 **집중**.

**해결하려는 문제.** 클라이언트가 수많은 내부 서비스를 직접 호출하면서 생기는 결합,
중복된 cross-cutting 처리, 다수 왕복으로 인한 성능 저하.

**구현 시 신경 쓸 점.**
- **병목·단일 장애점 방지**: 게이트웨이가 전 트래픽의 통로가 됨. **수평 확장·HA·격리**는 필수. 상태는 가능한 한 두지 않음(stateless).
- **"스마트 게이트웨이, 멍청한 파이프" 경계**: 비즈니스 로직을 게이트웨이에 쌓으면 분산 모놀리식이 됨. 라우팅·집계·보안까지만.
- **BFF(Backend for Frontend)**: 클라이언트 종류(웹/모바일)별 요구가 다르면 게이트웨이를 BFF로 분리.
- **복원력 집중 적용 지점**: 타임아웃·재시도·레이트 리밋·서킷 브레이커를 적용하기 좋은 위치지만, 다운스트림 장애가 게이트웨이로 전파되지 않게 격리.
- **지연 예산**: 게이트웨이의 집계·변환이 추가 지연을 만듦. 응답 집계 시 부분 실패 처리(일부 서비스 실패해도 가능한 응답).
- **버저닝·계약**: 클라이언트-게이트웨이 API 버전 관리, 내부 서비스 변경이 외부 계약을 깨지 않게.

**적용하면 안 되는 때.** 서비스가 소수이고 클라이언트 결합이 단순할 때. 게이트웨이가
조직·배포 병목이 될 위험이 이득보다 클 때.

**함께 쓰는 패턴.** Rate Limiting · Timeout · Retry · Circuit Breaker · BFF.

## 1-4. Strangler Fig

**정의.** 레거시 시스템 앞에 **파사드/프록시**를 두고 기능을 조금씩 새 시스템으로
옮기며, 최종적으로 레거시를 **점진적으로 대체·폐기**하는 마이그레이션 패턴.

**추구하는 바.** **빅뱅 재작성의 리스크 없이** 운영을 멈추지 않고 레거시를 교체. 각
단계가 작아 롤백과 검증이 쉬움.

**해결하려는 문제.** 크고 중요한 레거시를 한 번에 재작성하면 리스크·기간·실패 비용이
과도한 상황.

**구현 시 신경 쓸 점.**
- **라우팅 파사드**: 요청을 레거시/신규로 나누는 프록시(또는 게이트웨이)를 둠. 기능 단위로 신규로 **점진 전환**, 문제 시 즉시 레거시로 복귀.
- **데이터 전략(핵심 리스크)**: 전환 기간 동안 레거시-신규가 **같은 데이터**를 봐야 함. 이중 쓰기(dual-write) + 정합성 검증, 또는 CDC로 동기화, 소유권(어느 쪽이 source of truth인지) 명확화.
- **수직 슬라이스**: 기능을 얇은 end-to-end 조각으로 잘라 옮김(UI→로직→데이터). 경계가 애매한 기능은 먼저 리팩터링해 분리.
- **진척 측정·종료 조건**: 무엇을 어디까지 옮겼는지 추적하고, **레거시 폐기 시점**을 명시적으로 계획. 반쯤 전환된 채 영구 공존하는 것을 경계.
- **관측성**: 두 시스템의 동작·정합성을 비교(shadow traffic, 결과 대조).

**적용하면 안 되는 때.** 시스템이 작아 한 번에 재작성이 더 싸고 안전할 때. 레거시를
곧 폐기할 예정이라 투자 가치가 없을 때.

**함께 쓰는 패턴.** API Gateway(라우팅 파사드), CDC/Outbox(데이터 동기화), Anti-corruption Layer.

# 2. 전술 수준(복원력)

## 2-1. Retry

**정의.** 실패한 호출을 **다시 시도**해 일시적 오류를 극복하는 패턴.

**추구하는 바.** 네트워크 순단·일시적 5xx·순간 과부하 같은 **transient 실패**를
호출자가 흡수해 성공률을 높임.

**해결하려는 문제.** 복구 가능한 일시 장애에서 한 번 실패를 그대로 사용자 오류로
노출하는 문제.

**구현 시 신경 쓸 점.**
- **멱등성(가장 중요)**: 재시도는 **같은 연산이 여러 번** 실행될 수 있음. 조회/삭제(멱등)는 안전하나, 생성/결제 같은 비멱등 쓰기는 **멱등키(idempotency key)**로 서버가 중복을 흡수하게 해야 함. 멱등 보장 없는 재시도는 중복 결제·중복 주문을 만듦.
- **백오프 + 지터**: 고정 간격 재시도는 동시 실패한 클라이언트들이 같은 시점에 몰려 **thundering herd**를 만듦. **지수 백오프 + 랜덤 지터**로 분산.
- **재시도 조건 구분**: 재시도해도 소용없는 오류(400, 인증 실패, 검증 오류)는 **즉시 실패**. 재시도는 일시적 오류(일부 5xx, 타임아웃, 커넥션 리셋)로 한정.
- **상한·예산**: 최대 재시도 횟수 + 전체 **retry budget**(일정 비율 이상 재시도하면 차단)으로 폭주 증폭 방지.
- **타임아웃과 결합**: 재시도마다 타임아웃이 곱해져 총 지연이 늘어남. **전체 데드라인** 안에서만 재시도.
- **대상 보호**: 이미 과부하인 대상에 재시도를 퍼부으면 장애를 키움. 서킷 브레이커와 결합.

**적용하면 안 되는 때.** 비멱등 작업에 멱등 보장이 없을 때, 영구적(비일시적) 오류,
이미 포화된 다운스트림에 대한 무제한 재시도.

**함께 쓰는 패턴.** Timeout · Circuit Breaker · 멱등키 · 백오프.

## 2-2. Timeout

**정의.** 호출이 일정 시간 안에 끝나지 않으면 **중단**해, 자원이 무한정 묶이는 것을
막는 패턴.

**추구하는 바.** 느리거나 죽은 의존성 때문에 **스레드·커넥션·메모리가 고갈**되는 연쇄
장애를 예방. 실패를 "빠르게" 확정(fail fast).

**해결하려는 문제.** 응답 없는 외부 호출이 호출 스레드를 붙잡아 풀 고갈 → 상위
서비스까지 전파되는 cascading failure.

**구현 시 신경 쓸 점.**
- **무한 대기 금지**: 모든 외부 I/O(HTTP, DB, 캐시, 메시지)에 타임아웃을 **명시**. 많은 클라이언트의 기본값은 무한이거나 과도하게 큼.
- **연결 vs 읽기 타임아웃 구분**: connect timeout(연결 수립)과 read/socket timeout(응답 대기)을 분리 설정.
- **값 설정 근거**: 임의 추정 금지. 다운스트림의 **지연 분포(p99 등)**를 근거로, 정상 범위는 통과하되 이상치는 끊게. 외부 API라 상대 지연을 모르면 보수적으로 잡고 관측 후 조정.
- **데드라인 전파(budget)**: 호출 체인 전체에 **남은 시간 예산**을 전파. 상위 타임아웃이 1초인데 하위가 3초면 의미 없음. 하위는 "남은 예산"을 넘지 않게.
- **취소(cancellation)**: 타임아웃 시 실제 작업/커넥션을 **취소·반납**해야 함. 타임아웃만 반환하고 백그라운드로 계속 돌면 자원 누수.
- **재시도와의 상호작용**: 타임아웃 × 재시도 = 지연 누적. 전체 예산 안에서 조율.

**적용하면 안 되는 때.** (사실상 항상 적용) 단, 정당한 장시간 작업(대용량 처리)은
타임아웃 대신 **비동기/폴링**으로 설계.

**함께 쓰는 패턴.** Retry · Circuit Breaker · Bulkhead · Deadline propagation.

---

## 2-3. Rate Limiting

**정의.** 단위 시간당 허용 **요청 수를 제한**해 자원을 보호하고 공정성을 확보하는 패턴.

**추구하는 바.** 과부하·남용·비용 폭증으로부터 시스템을 보호하고, 다수 사용자 간 자원을
**공정하게** 분배.

**해결하려는 문제.** 특정 클라이언트의 폭주·오용, 트래픽 스파이크, 과금 통제 부재로
시스템이 무너지거나 비용이 폭증하는 상황.

**구현 시 신경 쓸 점.**
- **알고리즘 선택**: *Token Bucket*(버스트 허용 + 평균 속도 제한, 가장 흔함), *Leaky Bucket*(출력 평활화), *Fixed Window*(간단하나 경계에서 2배 버스트), *Sliding Window(log/counter)*(정확하나 비용↑). 버스트 허용 여부로 고름.
- **적용 지점·키**: 게이트웨이/엣지에서 전역, 또는 사용자·API 키·IP·테넌트 단위. 보호 대상(특정 백엔드/DB)에 가깝게.
- **분산 환경 일관성**: 여러 노드가 한도를 공유하려면 **중앙 저장소(예: Redis)**에 카운터를 두고 **원자적**으로 증가(Redis Lua 스크립트/INCR+EXPIRE)해 레이스 방지.
- **초과 응답 규약**: HTTP `429 Too Many Requests` + `Retry-After`/`RateLimit-*` 헤더로 클라이언트가 백오프하도록. 조용히 드롭하지 말 것.
- **버스트·공정성**: 순간 버스트 허용량과 평균 속도를 분리 설계. 한 테넌트가 전체를 소진하지 않게 테넌트별 한도.
- **관측·튜닝**: 차단율·누가 걸리는지 모니터링. 정상 트래픽을 깎지 않게 한도 보정.

**적용하면 안 되는 때.** 내부 신뢰 구간에 과도 적용해 정상 흐름을 막을 때. (대신 큐·백프레셔가 나을 수 있음)

**함께 쓰는 패턴.** API Gateway · Load Shedding · Backpressure · Circuit Breaker.

# 3. 설계 수준

> DI·Plugin·MVC는 코드 구조에 가깝습니다. iSAQB는 아키텍처 패턴(R3)으로 분류하나
> 디자인 패턴과 경계에 있습니다. "컴포넌트 내부" 결정으로 다루세요.

## 3-1. Dependency Injection

**정의.** 객체가 자신의 의존성을 **직접 생성하지 않고 외부에서 주입**받게 해, 제어의
역전(IoC)을 구현하는 패턴.

**추구하는 바.** **결합도 감소**와 **테스트 용이성**. 구현체 교체·목(mock) 주입을 쉽게.

**해결하려는 문제.** 하드코딩된 `new`로 생긴 강결합 — 구현체 교체 불가, 단위 테스트 시
실제 의존성에 묶이는 문제.

**구현 시 신경 쓸 점.**
- **생성자 주입 선호**: 필수 의존성은 **생성자 주입**(불변·null 안전·테스트 쉬움). 필드/세터 주입은 숨은 의존성·가변성 문제로 지양(Spring 권장도 생성자 주입).
- **Service Locator 회피**: 컨테이너를 직접 조회하는 서비스 로케이터는 의존성을 숨겨 DI 이점을 깎음.
- **스코프·생명주기**: 싱글턴/요청/프로토타입 스코프를 의도대로. 싱글턴에 요청 스코프를 잘못 주입하면 상태 오염.
- **순환 의존성**: 순환은 설계 냄새. 인터페이스 분리·이벤트·중재자로 끊음(생성자 주입에선 순환이 기동 실패로 드러나 오히려 조기 발견에 유리).
- **과주입(over-injection)**: 의존성이 너무 많은 클래스는 책임 과다 신호(SRP 위반). 분해.
- **추상화 비용**: 바뀔 일 없는 사소한 의존까지 인터페이스로 추상화하면 간접화만 늘어남.

**적용하면 안 되는 때.** 바뀌지 않는 단순 값/유틸까지 과도 추상화할 때.

**함께 쓰는 패턴.** Strategy · Factory · Plugin(주입을 통한 확장).

## 3-2. Plugin

**정의.** 핵심(코어)을 수정하지 않고 **확장점(extension point)**에 모듈을 끼워 기능을
더하는 패턴.

**추구하는 바.** **개방-폐쇄 원칙(OCP)** 실현 — 핵심은 닫혀 있고 확장은 열려 있음.
제3자·팀이 기능을 독립적으로 추가.

**해결하려는 문제.** 다양한/예측 불가한 확장 요구를 핵심 코드 수정 없이 수용해야 하는
상황(에디터 확장, 결제 수단 추가 등).

**구현 시 신경 쓸 점.**
- **안정적 확장 인터페이스(SPI)**: 플러그인이 구현할 **계약을 명확·안정적으로** 정의. 코어 내부 구현을 노출하지 말 것(그러면 버전 호환이 깨짐).
- **발견·로딩**: 플러그인 등록/탐색 메커니즘(설정, 디렉터리 스캔, `ServiceLoader`, DI 등록). 지연 로딩으로 기동 비용 관리.
- **격리·안전성**: 제3자 플러그인은 **신뢰 경계** 밖. 리소스·권한 격리(가능하면 샌드박스), 예외가 코어를 죽이지 않게 방어. 악성/버그 플러그인 대비.
- **버전 호환**: 코어-플러그인 API 버전 정책. 하위 호환 깨짐을 관리(semver, deprecation).
- **생명주기**: 로드/초기화/활성/언로드 훅과 상태 관리. 언로드 시 자원 정리.
- **관측성**: 어떤 플러그인이 로드됐고 무엇을 하는지 로깅(디버깅·감사).

**적용하면 안 되는 때.** 확장 요구가 없는데 선제적으로 플러그인화할 때(복잡도·보안면
증가). 내부 변형이 소수로 고정이면 Strategy 정도로 충분.

**함께 쓰는 패턴.** Dependency Injection · Strategy · Microkernel(플러그인 아키텍처).

---

## 3-3. MVC (Model-View-Controller)

**정의.** 애플리케이션을 **Model(도메인/데이터)·View(표현)·Controller(입력 제어/조정)**로
나눠 관심사를 분리하는 패턴.

**추구하는 바.** 표현과 비즈니스 로직의 **분리**로 변경 영향 축소·테스트성·협업 용이.

**해결하려는 문제.** UI·제어·도메인 로직이 한곳에 뒤섞여 변경이 어렵고 테스트가 안 되는
문제(특히 웹 요청-응답 계층).

**구현 시 신경 쓸 점.**
- **얇은 컨트롤러**: 컨트롤러는 **입력 검증·조정·위임**만. 비즈니스 로직은 Model/서비스 계층으로. "fat controller"는 가장 흔한 안티패턴.
- **도메인 로직 위치**: 핵심 규칙은 도메인/서비스에 둠. View·Controller에서 도메인 불변식을 다루지 말 것.
- **프레임워크 매핑 이해**: Spring MVC 등은 Controller-서비스-리포지토리 계층과 매핑됨. 프레임워크의 바인딩·검증·예외 처리 흐름을 그대로 활용.
- **전 계층에 확대 금지**: MVC는 **표현 계층**의 분리 패턴. 시스템 전체 아키텍처로 오해해 모든 것을 여기에 끼워 넣지 말 것(레이어드/헥사고날과 혼동 주의).
- **View-Model 결합**: View가 도메인 모델에 과결합되면 변경이 전파됨. 필요 시 DTO/ViewModel로 분리.

**적용하면 안 되는 때.** 표현 계층이 없거나 사소한 경우. 전체 시스템 구조 결정으로
남용할 때.

**함께 쓰는 패턴.** DTO · Layered Architecture · DI.

# 4. 데이터 기법

## 4-1. Sharding

**정의.** 데이터를 **샤드 키** 기준으로 여러 노드에 **수평 분할**해, 단일 DB의 용량·처리량
한계를 넘는 기법.

**추구하는 바.** 단일 노드로 감당 못 하는 **데이터량·쓰기 처리량**을 수평 확장으로 분산.

**해결하려는 문제.** 단일 DB가 저장 용량 또는 쓰기 처리량의 한계에 도달해 수직 확장으로는
한계인 상황.

**구현 시 신경 쓸 점.**
- **샤드 키 선택(가장 중요)**: 키가 분포·접근 패턴을 결정. **핫스팟**(특정 샤드 집중)을 피하도록 카디널리티 높고 고르게 분산되는 키. 단조 증가 키(auto-increment, 타임스탬프)는 최신 샤드 쏠림을 유발.
- **분할 전략**: 범위(range) 기반(범위 질의 유리, 핫스팟 위험) vs 해시 기반(고른 분산, 범위 질의 불리) vs **consistent hashing**(노드 증감 시 재배치 최소화).
- **크로스 샤드 질의·조인·트랜잭션**: 샤드를 넘는 조인·집계·트랜잭션은 비싸거나 불가. **샤드 키를 업무 경계에 맞춰** 크로스 샤드를 최소화. 넘는 일관성은 다시 Saga/2PC 문제로 환원됨.
- **라우팅**: 애플리케이션/프록시가 키→샤드 매핑을 알아야 함. 매핑 변경 시 영향 관리.
- **리샤딩(재분할)의 난이도**: 샤드 추가/재배치는 운영상 가장 어려운 작업(데이터 이동·무중단). 초기부터 **재분할을 염두**에 둔 설계(가상 버킷, consistent hashing).
- **운영 복잡도**: 백업·스키마 변경·모니터링이 샤드 수만큼 복잡. 분산 ID 생성 전략 필요.
- **조기 샤딩 경계**: 비용이 큼. **먼저** 읽기 복제·캐시·인덱스·쿼리 튜닝·수직 확장·파티셔닝을 소진. 한계가 **입증**된 뒤 도입.

**적용하면 안 되는 때.** 단일 노드로 충분하거나 한계가 입증되지 않았을 때(조기 최적화).
크로스 샤드 트랜잭션/조인이 지배적인 워크로드.

**함께 쓰는 패턴.** Read Replica · Caching · Consistent Hashing · CQRS(읽기 분리) · Saga(크로스 샤드 일관성).

# 부록 A. 패턴 비교 한눈표

| 패턴 | 단위 | 추구하는 바 | 대표 트레이드오프 |
|---|---|---|---|
| Saga | 시스템 구조 | 분산 일관성(2PC 회피) | 최종 일관성·격리 없음·보상 복잡도 |
| CQRS | 시스템 구조 | 읽기/쓰기 독립 최적화 | 최종 일관성·모델 이원화 복잡도 |
| API Gateway | 시스템 구조 | 단일 진입점·공통 관심사 집중 | 단일 병목·장애점 위험 |
| Strangler Fig | 시스템 구조 | 무중단 점진 마이그레이션 | 전환기 데이터 동기화·공존 비용 |
| Retry | 전술 | 일시적 실패 흡수 | 중복 실행·폭주 증폭(멱등 필수) |
| Timeout | 전술 | 자원 고갈 방지(fail fast) | 값 설정 난이도·조기 실패 |
| Rate Limiting | 전술 | 과부하·남용 보호·공정성 | 정상 트래픽 차단·분산 일관성 비용 |
| DI | 설계 | 결합도↓·테스트성 | 과추상화·간접화 비용 |
| Plugin | 설계 | 핵심 수정 없는 확장 | 확장 API 안정성·보안·호환 부담 |
| MVC | 설계 | 표현·로직 분리 | fat controller·전 계층 오남용 |
| Sharding | 데이터 | 수평 확장 | 샤드 키·크로스 샤드·리샤딩 난이도 |

# 부록 B. 공통 교훈

- **단위가 다르면 비교 축도 다르다.** 시스템 구조 패턴끼리, 전술 패턴끼리 비교하세요. 서로 다른 단위는 **조합**의 대상이지 택일이 아닙니다.
- **대부분의 전술 패턴은 멱등성과 데드라인 위에서만 안전**합니다(Retry·Saga 특히).
- **시스템 구조 패턴은 거의 항상 "강한 일관성 → 최종 일관성"의 교환**을 동반합니다. ADR에 이 교환을 명시하세요.
- **데이터/설계 기법은 "먼저 더 싼 수단을 소진했는가"**를 확인하세요(샤딩 전 복제/캐시, 플러그인 전 Strategy).
- 크기는 달라도, 이 패턴들은 모두 **반복되는 문제에 대한 검증된 해법**입니다.
