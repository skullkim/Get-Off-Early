# 아키텍처 문서 출력 형식

> `architecture-and-delegation` 스킬의 참조 파일. 본문에서 떼어 둔 이유는 이 내용이 **특정 국면에서만** 필요하기 때문이다 — 스킬이 트리거될 때마다 컨텍스트에 올리지 않는다.

## 출력 형식

backend-senior → `_workspace/03_backend_architecture.md`
frontend-senior → `_workspace/03_frontend_architecture.md`

```markdown
# {백엔드|프론트엔드} 아키텍처: {프로젝트명}

## 1. 기술 스택 (선택 근거 포함)
- 언어/런타임: ... (근거)
- 프레임워크: ...
- 테스트: {프레임워크} / 실행 명령: `{command}` / 커버리지 확인: `{command}`

## 2. 구조
- {레이어/모듈 또는 컴포넌트/상태관리}
- 데이터 모델 / 상태 모델

## 2.5 핵심 아키텍처 결정 (ADR 목록 — 본문은 프로젝트 레포 docs/adr/ 이 단일 소스)
- [ADR-0001 {결정 주제}](../{프로젝트}/docs/adr/0001-{제목}.md) — {결정 한 줄 요약}
- [ADR-0002 …](…) — …

(ADR 파일 본문 형식 — `docs/adr/NNNN-<제목>.md` 각각에. **이 형식이 ADR의 단일 소스다** —
패턴 차트·규칙 파일은 이 형식을 채우는 입력이고, 자기 형식을 따로 갖지 않는다:)
- 상태: {제안 | 채택 | 대체됨(→ NNNN)}
- 결정: {택한 것 — 단위 + 패턴, 조합이면 조합 전체}
- 근거(Forces): {요구·ADR Context에서 추출한 핵심 force 2~4개 — 일관성/지연/처리량/실패모드/제약/변경빈도}
- 고려한 대안: {A / B / C}
- 검토했으나 제외: {후보} — {제외 이유. 차트의 "적용 금지/보류"에 걸렸으면 그 조항을 적는다}
- 트레이드오프: {각 대안의 장단점 — 테스트용이성/단순성/변경가능성/위임/되돌림 기준}
- 채택 이유(이 프로젝트 기준): {이 요구·규모에서 이걸 고른 이유}
- 결과(Consequences): + {얻는 것} / − {감수하는 것: 최종 일관성·운영 복잡도·지연 증가 등}
- 디커플링 모드: {소스 | 배포 | 서비스} — 왜 더 가벼운 모드로는 안 되는가 {이유}
- 미룬 결정: {무엇을 / 언제까지 / 무엇을 알면 결정}
- 구현 시 확인: `architecture-patterns-guide.md`의 "{패턴}" 체크리스트 + `clean-architecture-rules.md` §A 판정

## 3. API 계약 (경계면) — 백엔드가 정의, 양 시니어 합의
### {METHOD} {경로}
- 요청: {shape}
- 응답(성공): {정확한 shape — 래핑/필드명/타입}
- 응답(에러): {상태코드 + 형식}

## 4. 작업 분해
| 작업 | REQ-ID | 복잡도 | 담당 | 완료 기준(통과 테스트) |
|------|--------|--------|------|---------------------|
| ... | REQ-001 | 높음 | senior | ... |
| ... | REQ-002 | 낮음 | junior | ... |
```
