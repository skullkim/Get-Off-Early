# Harness Runtime Adapter — 런타임 종속부 매핑 (단일 소스)

이 하네스의 절차(스킬)는 **역할(role)**로 서술하는 것을 지향하고, 역할이 어떤 런타임 도구에 대응하는지는 **이 표가 단일 소스**다.
런타임(Claude Code → 다른 에이전트 CLI)을 교체할 때 고치는 곳이 이 표 한 장에 머무는지가 이식성의 판정 기준이다.

## ⚠ 이 표는 측정해야 유효하다

**2026-10-31 실측에서 이 표의 네 행이 틀려 있었다.** 표에 `TaskCreate`·`TaskList`·`TaskUpdate`·`Grep`·`Glob`·`AskUserQuestion`·`CronCreate` 가 적혀 있었지만, 스폰된 서브에이전트에게 그 도구들이 **존재하지 않았다.** 즉 시니어의 위임 메커니즘("`TaskCreate`로 주니어에게 작업 생성")이 **작동할 수 없는 상태로 일곱 군데에 지시되어 있었다.**

표가 틀렸다는 것을 아무도 몰랐던 이유는 **아무도 다시 재지 않았기 때문**이다. 그래서 측정 절차를 표와 같은 파일에 둔다.

### 재측정 절차 (런타임 업데이트 후 · 새 세션 시작 시)

1. 서브에이전트 하나를 스폰해 **도구를 호출하지 말고** 자기 도구 이름 전체를 보고하게 한다 (즉시 가능 / 지연 / 없음 셋으로 구분).
2. 아래 표의 "도구" 열과 대조한다. 어긋나면 **표를 고치고**, 그 도구를 지시하는 스킬·에이전트 자리를 전부 찾아 고친다:
   `rg -n 'TaskCreate|TaskList|TaskUpdate|Grep|Glob|AskUserQuestion|CronCreate' .claude CLAUDE.md`
3. 아래 **반영 시점** 표를 보고, 새 세션이 필요한 변경이면 재시작한 뒤 1번을 다시 돌린다.

### 반영 시점 (단일 소스 · 2026-10-31 실측)

무엇을 고쳤을 때 언제 효력이 생기는지. **README 는 이 표를 가리키기만 한다** — 같은 사실이 두 곳에 살면 한쪽만 고쳐진다.

| 바꾼 것 | 반영 시점 | 근거 |
|---|---|---|
| `.claude/settings.json` (훅 등록) | **즉시** | 실측 — 편집 직후 `PreToolUse` 탐침이 발동했다 |
| `.claude/hooks/*.sh` | **즉시** (다음 발동부터) | 훅은 발동할 때 스크립트를 실행한다 |
| `.claude/skills/*/SKILL.md` **본문** | **다음 스킬 호출** | 실측 — 세션 중 편집한 문장이 호출 결과에 나왔다 |
| `.claude/skills/*/SKILL.md` **description** | 새 세션 | 설명은 세션 시작 시 스킬 목록으로 주입된다. **세션 안에서는 관측할 수 없어 미실측** |
| `.claude/agents/*.md` (`tools`·`effort` 등) | **새 세션** | 실측 — `pm.md` 에 `tools:` 제한을 걸고 즉시 스폰했으나 제한 전 도구를 그대로 가졌다. 새로 만든 에이전트 파일은 스폰조차 되지 않았다 |
| `CLAUDE.md` | 새 세션 | 세션 시작 시 로드 |
| `knowledge/cards`·`patterns` | `node knowledge/generate.mjs` 후 즉시 | 색인 재생성물 |

## 작업 목록 — 파일로 한다

`TaskCreate` 계열이 없으므로 위임은 `_workspace/00_tasks.md` 한 장으로 한다. 이 하네스는 이미 계약에 같은 원칙을 쓴다 — *"메시지 말고 파일이 권위"*. 작업 목록도 같다.

```markdown
| ID | 소유자 | REQ-ID | 무엇 | 완료 기준 | 상태 |
|----|--------|--------|------|-----------|------|
| T-01 | backend-junior | REQ-003 | 주문 생성 엔드포인트 | OrderServiceTest 4건 통과 | done |
| T-02 | frontend-junior | REQ-007 | 주문 목록 화면 4상태 | 빈/로딩/에러/성공 테스트 통과 | wip |
```

- **소유자 열이 소유권의 단일 소스다.** 다른 사람이 소유한 행의 파일을 고치지 않는다(파일 충돌 3회의 처방).
- 상태는 `todo`·`wip`·`review`·`done`·`blocked`. 완료 보고는 상태 갱신 + `SendMessage` 1회.
- 리더가 소유권을 재배정할 때도 이 파일을 고치고 통지한다.

## 운영 규율 (점진 적용)
- 스킬을 **새로 쓰거나 수정할 때**, 런타임 도구명을 쓰는 자리에는 가능하면 역할명을 병기한다 — 예: "작업 목록(`00_tasks.md`)에 등록".
- 전면 소급 치환은 하지 않는다 — 수정이 닿는 부분부터 점진적으로.
- 런타임 교체 시: **먼저 §재측정 절차를 돌리고** 이 표의 도구 열을 갱신한 뒤, 스킬의 역할명을 새 매핑으로 해석한다. 스킬 본문을 대량 수정해야 한다면 그 부분이 "런타임 종속부 누수"이므로 회고에서 격리 대상으로 올린다.
- **판정 기준**: 런타임 교체 작업에서 고친 파일이 이 표 + 소수 스킬 라인에 머무는가. (모델 교체가 "설정 변경 수준"이어야 하는 것과 같은 원칙 — 모델명·도구명을 하네스에 하드코딩하지 않는다.)
