§1AI 에이전트의 정의

"에이전트"라는 말이 남용되는 시대에, 진짜 에이전트를 가르는 기준.

저자의 정의: 독립적으로 데이터를 분석하고, 환경을 해석하고, 맥락 기반 결정을 내리는 지능형 시스템. 다만 자율성(agency)은 이분법이 아니라 스펙트럼이다 — 스크립트 실행기부터 완전 자율 시스템까지 연속선 위에 있다.

진짜 에이전트의 판별 기준: 정해진 스크립트를 따르는가, 실제 의사결정을 하는가? — p.1, Defining AI Agents

책 전체에서 쓰는 용어 agentic system은 에이전트가 실제로 동작하게 하는 전체 구성을 가리킨다. 즉 모델 하나가 아니라 아래 루프 전체가 시스템이다.

Q. 그럼 파운데이션 모델이 곧 에이전트인가?

아니다 — 모델은 에이전트의 부품이다. 세 가지 근거:

  • 같은 모델로 다른 에이전트 여럿을 만들 수 있다. 모델 하나로 고객지원 에이전트와 코드리뷰 에이전트를 동시에 운영할 수 있다 — 에이전트를 가르는 것은 역할(시스템 프롬프트) + 도구 권한 + 컨텍스트다.
  • 모델을 갈아끼워도 같은 에이전트다. 모델 세대가 바뀌어도 에이전트의 정체성(역할·절차·도구)은 유지된다 — 모델은 교체 가능한 부품이다.
  • 툴 없는 모델은 행동할 수 없다. 자율성은 모델 단독이 아니라 결정→실행→관찰 루프에서 나온다. 루프가 없으면 단발 LLM 호출일 뿐이다.

그리고 "시스템 안에 에이전트 박스가 여러 개"인 그림은 실제로 존재한다 — 그게 8장의 멀티에이전트 시스템이다. 위 그림의 녹색 박스(에이전트)가 시스템 안에 여러 개 들어가 서로 통신하는 구조로 확장된다.

Q. 그럼 에이전틱 시스템 안에 "에이전트 루프"가 여러 개 있을 수 있나?

있다 — 루프 1개면 단일 에이전트 시스템, 여러 개면 멀티에이전트 시스템(8장)이다. 루프를 나누는 이유는 세 가지: 컨텍스트 격리(PM과 QA의 머릿속이 분리되어야 독립 검증이 성립), 전문화(역할별 프롬프트 + 도구 권한), 병렬성(루프끼리 동시 실행).

루프 간 조율은 통신으로 이뤄지고(A2A 프로토콜·메시지 브로커 — 8장), 조율 구조에도 패턴이 있다: 매니저형·민주형·계층형·액터-크리틱형. 예컨대 "가상 개발팀"형 시스템이라면 리더 에이전트가 PM·개발·QA 루프를 지휘하는 매니저형이 된다. 단 "에이전트는 최후의 선택지" 원칙은 개수에도 적용된다 — 8장 첫 절 제목이 How Many Agents Do I Need?인 이유. 루프 수도 기본은 최소다.

§2사전학습 혁명

에이전트 패턴이 지금 폭발한 근본 원인.

전통 ML은 데이터셋 수집·정제가 일의 대부분이었다. 사전학습된 파운데이션 모델은 추가 학습 없이 API 호출 한 번으로 광범위한 태스크를 처리한다 — "ML 엔지니어 고용 + 데이터 수집 + 학습 + 배포"가 호출 하나로 줄었다.

결정적 전환점은 모델이 구조화된 함수 시그니처와 파라미터를 생성하게 된 것. 오케스트레이션 프레임워크가 이를 실행하면서 데이터 조회, 외부 시스템 조작, 실제 액션 수행이 가능해졌다. 대표 역량: 맥락 해석·의사결정, 툴 사용, 적응형 계획, 정보 요약, 비구조 데이터 처리, 코드 생성, 반복 업무 자동화, 멀티모달 분석.

Q. 유형 분류란 결국 "저런 방식의 루프를 만들 수 있다"는 뜻인가?

거의 맞다 — 단, 유형은 아키텍처 분류가 아니라 용도(시장) 분류다. 아키텍처 관점에서 보면 대부분 §1의 루프 골격은 동일하고, 루프에 무엇을 꽂았는가가 다르다:

  • 툴이 다르다 — Research는 검색·문서읽기 툴, Developer는 파일 편집·테스트 실행 툴, Browser-using은 클릭·입력 툴을 꽂은 루프. 루프가 "관찰"하는 것도 따라 달라진다 (검색 결과 / 테스트 결과·컴파일 에러 / 스크린샷·DOM)
  • 모달리티가 다르다 — Voice·Video는 같은 루프의 앞뒤에 음성 인식/합성·아바타 렌더링이 붙은 래퍼
  • 도메인 지식이 다르다 — Domain-specific은 법률·의료 지식과 절차를 프롬프트·지식베이스에 넣은 루프

주의할 예외가 하나 있다: Business-task(RPA)형은 대부분 진짜 루프가 아니다. "결정론적 액션 시퀀스를 최소한의 맥락 추론으로 실행"한다고 책이 명시하는데, 이는 §6 스펙트럼의 ② 워크플로우에 해당한다 — "에이전트" 라벨이 남용되는 대표 사례이자, §1에서 자율성이 스펙트럼이라고 말한 이유다.

§4모델 선택

선택지 폭발 시대의 실용주의.

정답은 없지만, 가장 합리적인 시작점은 주요 프로바이더의 최신 범용 모델을 그대로 쓰는 것. 커스터마이징 거의 없이도 놀랄 만큼 멀리 간다 (HELM 리더보드, Table 1-1).

모델 선택 최적화에 막대한 노력을 쏟을 수 있지만, 규모나 제약이 요구하기 전엔 단순하게 시작하라. 미래는 거의 확실히 멀티모델이다 — 지금부터 유연하게 설계하라. — p.6, Model Selection

§5동기 → 비동기 전환

에이전트가 바꾸는 것은 속도가 아니라 일의 성격.

에이전트는 비동기로 설계된다: 병렬 작업 관리, 새 정보에 즉시 적응, 동적 우선순위 조정. 실질적 의미는 "미리 준비된 채 도착한다" — 이메일이 답장 초안과 함께, 티켓이 해결 코드·테스트가 첨부된 채, 보안 알림이 이미 조사·보강이 끝난 채 도착한다.

인간의 역할 전환: 작업 실행자(task executor) → 작업 관리자(task manager). 반응적 업무에서 능동적 업무로. — p.7, From Synchronous to Asynchronous Operations

Q. 비동기 실행 = 오케스트레이터가 일을 시켜놓고 다른 조율을 하다가, 결과를 받아 다시 조율하는 것?

맞다 — 그리고 그 패턴은 세 층위에서 똑같이 반복된다. 어느 층위든 공통 구조는 "위임 → 막히지 않고 계속 진행 → 완료 통지 → 재조율"이다:

  • 인간 ↔ 시스템 — 1장이 강조하는 층위. 사람이 에이전트에게 일을 넘기고 자기 일을 하다가, "미리 준비된 결과"(답장 초안이 붙은 이메일, 코드가 첨부된 티켓)를 받는다. 실행자 → 관리자 전환의 실체
  • 오케스트레이터 ↔ 에이전트 루프들 — 리더 루프가 하위 루프를 논블로킹으로 스폰하고 다른 조율을 계속하다, 완료 통지를 받아 재조율한다 (8장 멀티에이전트 조정)
  • 루프 ↔ 툴 — 한 루프 안에서도 모델이 독립적인 툴 호출 여러 개를 동시에 던지고 결과가 도착하는 대로 관찰한다 (5장 병렬 툴 실행)

대비되는 동기 방식은 위임 후 블로킹 — 하위 작업이 끝날 때까지 오케스트레이터가 멈춰 기다리는 것이다. 이러면 전체 소요 시간이 하위 작업의 합이 되고, 새 정보에 따른 재우선순위도 불가능하다. 비동기의 대가는 조율 복잡성: 완료 통지·상태 추적·부분 실패 처리가 필요해진다.

§7효과적인 에이전틱 시스템의 5원칙

각 원칙에는 "위반하면 어떻게 되는가"가 함께 붙어 있다.

Continuous Learning

피드백 루프가 없는 에이전트는 같은 실수를 무한 반복한다. 인컨텍스트 학습과 사용자 피드백 반영을 구조에 넣어라.

Modularity

툴을 하드코딩하면 툴 하나 수정에도 전체 재배포가 필요하다. 교체 가능한 컴포넌트와 명확한 인터페이스로 설계하라.

Resilience

API 호출 하나의 실패로 전체가 죽으면 안 된다. 재시도·폴백·타임아웃 등 우아한 에러 처리를 갖춰라.

Scalability

분당 10건을 처리하던 에이전트가 1,000건 스파이크에 다운되지 않도록 — 분산 아키텍처와 오토스케일링으로 대비하라.

Future-proofing

특정 벤더의 프롬프트 포맷·모델에 강결합하면 교체가 고통스럽다. 개방 표준과 모듈러 설계로 미래에 대비하라.

§9핵심 3문장

  1. 에이전트의 판별 기준은 "실제 의사결정을 하는가" — 스크립트 실행은 에이전트가 아니다.
  2. 에이전트는 최후의 선택지다 — 코드 → 워크플로우 → RAG로 충분하지 않을 때만 쓴다.
  3. 단순하게 시작하고 유연하게 설계하라 — 모델 선택을 과최적화하지 말고, 멀티모델 미래에 대비해 모듈러하게.

§1첫 에이전트 시스템

30쪽 설계 문서가 아니라, 다루기 좋은 슬라이스(전체 업무에서 잘라낸 작은 조각) 하나로 시작한다.

실무자는 거대한 설계 문서로 시작하지 않는다 — 지저분한 문제 + API 키 + 대략적인 아이디어로 시작한다. 책의 예제는 이커머스 고객지원 업무 중 주문 취소만 잘라낸 에이전트다. 사람이 2분 걸려 하던 반복 작업(메일 읽기 → 주문 조회 → API 호출 → 확인 메일)을 그대로 코드로 옮긴다.

스코핑(scoping) — 범위를 정하는 균형 잡기

스코핑 = 에이전트가 무엇을 하고, 무엇을 하지 않을지 범위를 정하는 일. 고객지원에는 환불·취소·배송지 변경·청구 분쟁·추천 등 수십 가지 업무가 있는데, 그중 어디까지를 이 에이전트의 일로 자를지 정하는 것이다. 개발자에게 익숙한 말로는 MVP 범위 정의·유저 스토리 쪼개기와 같은 개념인데, 에이전트에서 특히 중요한 이유는 범위가 넓어질수록 입력의 가변성이 폭발해 시스템 전체의 난이도 계층(1장 §6)이 올라가기 때문이다. 세 방향 모두에 함정이 있다:

스코프무엇이 문제인가
너무 좁게"취소만" — 다른 고빈도 요청을 놓쳐 실질 임팩트가 제한됨
너무 넓게"모든 문의 자동화" — 청구 분쟁·추천·기술지원 엣지케이스에 익사
모호하게"고객 만족 개선" — 성공했는지 영영 알 수 없음
올바른 슬라이스구체적 입력 · 구조화된 출력 · 빠른 피드백 루프 — 작고, 테스트 가능하고, 즉시 유용
An untested agent is an untrusted agent. — 테스트되지 않은 에이전트는 신뢰할 수 없는 에이전트다. — p.20, Our First Agent System

§5베스트 프랙티스 3종

반복 설계 · 평가 전략 · 실환경 테스트.

① 반복 설계

완벽한 초기 설계 대신 작동하는 작은 프로토타입 → 평가 → 개선. MVP(최소 기능 제품)에서 점진 성장하며 결함을 조기에 잡는다.

② 평가 전략

기능 테스트(정확성·극단 입력을 넣어보는 경계 테스트·태스크 지표) + 일반화 평가(설계 시나리오 밖 입력) + UX 평가(만족도·완료율) + human-in-the-loop(사람이 중간 검토자로 참여하는 검증).

③ 실환경 테스트

통제 환경은 실사용자의 예측 불가 입력을 못 잡는다. 단계적 배포 → KPI 모니터링 → 피드백 수집 → 반복.

평가 신호 중 놓치기 쉬운 것: 명시적 신호(👍👎, 별점, 결과 수정)뿐 아니라 암묵적 신호 — 상호작용 로그에서 오해·지연·감정·부적절 응답을 캐내는 것도 평가다.

§6핵심 3문장

  1. "30쪽 계획은 필요 없다 — 하지만 약간의 선견은 멀리 간다." 다루기 좋은 슬라이스로 시작해 작고, 테스트 가능하고, 즉시 유용한 것을 만들어라.
  2. "테스트되지 않은 에이전트는 신뢰할 수 없는 에이전트다." 평가는 9장의 일이 아니라 첫날의 일이다 — assert 두 줄이면 시작된다.
  3. 좋은 시스템 = 아키텍처 + 규율 있는 엔지니어링 + 빠른 피드백 루프. 부분의 합보다 크다.

§1상호작용 모달리티

기술력이 아니라 사용자와의 상호작용이 채택과 신뢰를 결정한다.

모달리티보급도예시적합한 상황
텍스트매우 흔함고객지원 챗봇, CLI 도구명확·비동기·검색 가능한 소통
GUI흔함워크플로우 대시보드, Cursor시각 구조·다단계 워크플로우
음성덜 흔함Siri, Alexa, 콜센터 자동화핸즈프리·자연 대화
영상드묾가상 튜터, 아바타시각 시연·풍부한 표현

텍스트 — CLI의 르네상스와 발견 가능성 문제

텍스트는 단순·친숙하고 동기/비동기를 모두 지원하며 추적 가능한 기록을 남긴다. Warp·Claude Code·Gemini CLI가 자연어로 터미널을 "다시 새롭게" 만들고 있다. 핵심 한계는 발견 가능성(discoverability)인데, 이걸 이해하려면 용어 하나를 먼저 잡아야 한다.

어포던스(affordance) = 사물이 "나를 이렇게 사용할 수 있다"고 스스로 보여주는 단서. 납작한 판이 붙은 문은 "미세요"라고, 봉이 달린 문은 "당기세요"라고 형태 자체가 말한다 — 설명서 없이 사용법이 보이는 성질이다 (심리학자 깁슨의 용어를 디자이너 돈 노먼이 유명하게 만듦). UI에서는 눌러 보이게 튀어나온 버튼, 밑줄 친 링크, 깜빡이는 입력 커서가 어포던스다.

GUI는 이런 단서가 화면에 가득하지만, 텍스트·음성 에이전트는 빈 입력창 하나가 전부다 — 어포던스가 없으니 사용자는 에이전트의 능력 범위를 추측하고, 범위 밖 요청에 거절당하고, 결국 능력의 일부만 쓴다. 이것이 발견 가능성 문제다. 대응: 온보딩 인사에 능력 명시("주문 취소·배송 조회·계정 변경을 도울 수 있어요"), 제안 버튼, 대화 중 동적 제안.

GUI · 음성 · 영상 · 결합

생성형 UI(Generative UI)가 GUI의 새 프런티어 — 정적 레이아웃 대신 질의에 맞춰 지식 카드·표·폼을 동적 생성한다(Perplexity). 음성은 중단 처리("아 잠깐, 내일로 바꿔줘")와 툴 통합으로 크게 도약했지만 물리적 제약이 있다: 말하기 150–180 wpm vs 읽기 250–300+ wpm — 밀도 높은 정보엔 텍스트가 빠르다. 영상은 표현력이 최고지만 언캐니 밸리(uncanny valley: 사람 같지만 미묘하게 어긋나 불쾌해지는 지점)·대역폭·프라이버시 과제. 진짜 목표는 결합: 운전 중 음성 → 걸으며 텍스트 → 책상에서 대시보드로, 상태·컨텍스트가 끊기지 않게.

§2자율성 슬라이더 ⭐

사용자가 에이전트의 자율성 수준을 부드럽게 조절할 수 있어야 한다 (Karpathy).

설계 원칙 5가지: ① 자율성 단계를 직관적 언어로 노출 ② 단계 간 매끄러운 전환 ③ 단계별 예측 가능한 행동(부분 자율이면 "초안은 만들되 실행 전 승인") ④ 각 단계의 위험·이익 전달 ⑤ 신뢰·성공 이력에 따라 자율성 상향을 시스템이 제안.

§3동기 vs 비동기 경험

어느 쪽 경험인지 의식적으로 분류하라 — 1장 §5(비동기 전환)의 UX 버전.

동기비동기
형태채팅·음성·실시간 협업이메일형·작업 알림·완료 후 리포트
핵심 가치즉각성·명료함·짧은 응답·턴테이킹(언제 답하고 언제 기다릴지)유연성·지속성·상태의 명확한 전달
필수 장치타이핑 표시·진행 스피너 / 모호하면 명확화 질문시작 통지·예상 소요 시간·단계 표시·완료 요약
어떤 경험이 어느 쪽인지 의식적으로 분류하라 — 사용자가 빙글빙글 도는 무한 로딩(pinwheel)을 기다리게 하지 마라. — p.58, Synchronous Versus Asynchronous Agent Experiences

능동적 vs 침입적의 균형도 여기 속한다: 고위험 화상회의 중 알림은 방해, 이메일로 온 완료 통지는 적절. 알림 빈도·채널·임계값의 제어권을 사용자에게 줘라. 저자의 표현으로는 "기술 역량이 아니라 사용자의 워크플로우와 정신 상태에 대한 공감의 문제".

§4컨텍스트 유지와 연속성

"Context is UX" — 기억이 협력자와 도구를 가른다.

개인화는 컨텍스트 유지의 다음 단계다: 선호 기억(설정·자주 쓰는 옵션) → 행동 적응(관찰된 패턴에 맞춰 응답 스타일 조정) → 능동 지원(과거 기반 선제 제안). 최고의 개인화는 "티 나지 않게 유용한" 것이고, 사용자는 언제든 재설정·무시할 수 있어야 한다.

§5능력·불확실성 전달, 우아한 실패

보이지 않는 기능을 보이는 어포던스(사용법을 스스로 보여주는 단서 — §1에서 정의)로 바꾸는 것이 에이전트 UX의 절반이다.

능력 전달

제안 액션 버튼·능력 카드·입력 중 동적 제안. 범위 밖 요청엔 불투명한 거절 대신 대안 제시: "결제는 못 하지만 청구 설정 변경은 가능해요". 프로그레시브 디스클로저(처음엔 핵심만, 익숙해지면 고급 기능 노출)로 압도 방지.

확신도 전달

명시적 문장("90% 확신") · 시각 단서(게이지) · 행동 조정(확신 낮으면 단정 대신 제안형). 과신은 신뢰를 부수고, 저위험 상황의 과도한 얼버무림은 무능해 보이게 한다.

명확화 질문

모호하면 위험한 가정 대신 집중된 질문("편도인가요 왕복인가요?"). 왜 묻는지 설명하고, 한 번에 다 묻지 말고 중요한 것부터 순서대로.

우아한 실패

투명한 인정 + 설명 + 실행 가능한 다음 단계("담당자 연결해드릴까요?"). 예측 가능한 실패엔 사전 정의된 폴백(음성 실패 → 텍스트 제안). 다단계 작업 실패 시 진행 상태 보존 — 처음부터 다시 시키지 말 것. 실패 로그는 개발 루프로 환류.

§6신뢰

3장 전체가 결국 이 한 문장으로 수렴한다.

Trust is gained in drops and lost in buckets. — 신뢰는 방울방울 쌓이고 양동이로 잃는다. — p.66, Trust in Interaction Design
기둥내용
투명성행동의 이유를 설명 (어떻게 이 추천에 도달했나, 왜 거절했나). 단, 모든 추론 과정을 다 보여주면 인지 과부하 — 확신에 필요한 만큼만
예측 가능성같은 조건 같은 질문 = 같은 응답. LLM의 확률적 가변성이 불가피하면 불확실함을 신호로 표시
신뢰성엣지케이스의 예측 가능한 처리 · 장애 시 통지+설명+다음 단계(조용한 실패 금지) · 약속한 것은 매번 지키기 — 과잉 약속 후 미달이 한계 인정보다 신뢰를 더 크게 부순다

§7핵심 3문장

  1. "신뢰는 방울방울 쌓이고 양동이로 잃는다." 투명성·예측 가능성·우아한 실패가 신뢰의 인프라다.
  2. 자율성 슬라이더는 기능이 아니라 신뢰 구축 장치다. 통제권의 양을 사용자가 정하게 하라.
  3. 동기든 비동기든 "지금 무슨 일이 일어나는지"를 항상 보여줘라. 사용자가 무한 로딩을 기다리게 하지 마라.

§1툴의 기초

모델은 수다만 떨 수 있다 — 실제 변경을 실행하는 것은 툴이다.

툴 = 에이전트가 원하는 결과를 얻기 위해 수행할 수 있는 구체적 능력·액션의 집합. LangChain 골격으로 보면: @tool 데코레이터가 함수를 등록하며 시그니처·docstring에서 스키마를 자동 생성 → .bind_tools()로 모델에 연결 → 모델이 툴과 파라미터를 선택 → 실행 결과를 대화에 붙여 최종 응답을 만든다 (1장에서 본 "루프"의 실행 절반).

이제 어떤 프로그램을 어떤 파라미터로 실행할지 파운데이션 모델에게 맡기는 것이다. 모델이 해보다 득이 되게만 실행할 툴만 바인딩하는 것 — 그것이 에이전트 개발자의 가장 중대한 책임이다. — p.75, Local Tools

로컬 툴 — 메타데이터가 로직만큼 중요하다

모델의 전통적 약점(산술·시간대·달력·지도)을 보완하는 룰 기반 함수. 핵심 통찰: 모델은 툴의 메타데이터(이름·설명·스키마)를 보고 호출을 결정한다. 그래서 ① 정확하고 좁은 이름(너무 일반적이면 불필요할 때도 호출됨) ② 서로 구별되는 명확한 설명(겹치면 혼동 보장) ③ 엄격한 입출력 스키마가 로직 자체만큼 중요하다. 단점은 확장성·중복(팀마다 재구현)·유지보수(변경마다 재배포).

§2API 기반 툴과 플러그인 툴

모델 재학습 없이 능력을 확장하는 두 가지 길.

API 기반 툴은 외부 서비스(날씨·주가·번역)로 실시간 데이터와 무거운 연산을 가져온다. 설계 초점은 신뢰성·보안·우아한 실패: HTTPS+강한 인증, 레이트 리밋 대비, 프라이버시(필요시 익명화), 프로바이더 이중화.

플러그인 툴은 플랫폼이 제공하는 기성 모듈이다 — 통합은 쉽지만 커스터마이징이 제한된다:

§4상태 유지(Stateful) 툴 — 최대 위험 지대

실화: 에이전트가 DB 성능을 "최적화"한다며 프로덕션 테이블의 행 절반을 삭제했다.

영속 상태를 바꿀 권한을 모델에 주는 순간, 파괴적 실수와 악용 가능성도 함께 준다. 완화책은 등록 계층에서 시작한다:

  • 좁게 스코프된 연산만 툴로 등록 — "임의 SQL 실행" 대신 get_user_profile(user_id)처럼 잘 검증된 단일 연산
  • 읽기만 필요한 에이전트에게 삭제·수정 권한 금지 — 등록 단계 제약이 공격 표면을 가장 크게 줄인다
  • 자유형 쿼리가 불가피하면: 프롬프트 인젝션(악성 지시를 입력에 숨겨 모델을 조종하는 공격)으로 DROP/ALTER가 끼어들 수 있으니 입력 검증 + prepared statement + 최소 DB 권한
  • 모든 툴 호출 로깅 + 이상 패턴(대량 삭제·스키마 변경) 실시간 알림
최소 권한 원칙(principle of least power): 모델에게 꼭 필요한 툴만, 정밀한 경계와 감독과 함께 줘라. 로컬이든 API든 MCP든 같은 원칙이 적용된다. — p.85, Stateful Tools

§5자동 툴 개발

모델은 이제 툴의 소비자가 아니라 제작자이기도 하다.

모델이 툴을 만든다

API 스펙을 먹이면 래퍼 초안 생성 → 샌드박스(격리된 안전 실행 환경)에서 실행 → 자기 비평("400이 왔네, 파라미터를 고치자") → 반복. 사람 리뷰 후 CI/CD 진입. API가 바뀌면 같은 루프 재실행 — 방대한 API 지형에서 특히 유효.

실시간 코드 생성

낯선 API·문제를 만나면 즉석에서 코드 작성·실행. 적응력은 최고지만 품질·보안 통제가 어렵고, 반복 가능성을 잃는다 — 매번 툴을 새로 만들면 이번 성공이 다음 성공을 보장하지 못해 디버깅·인증이 곤란해진다.

  2. MCP는 AI의 USB-C 포트 — M×N 맞춤 어댑터를 M+N 표준 인터페이스로 바꾼다 (보안은 아직 미완).

§0오케스트레이션의 본질 — 모델은 매 호출마다 기억상실 상태다

5장 전체를 꿰는 통찰 하나에서 시작하자.

LLM 호출은 상태가 없다. 이전 호출에서 무슨 일이 있었는지 모델은 전혀 모르고, 이번 호출의 컨텍스트 윈도우에 넣어준 것만 본다. 그런데 에이전트는 여러 스텝에 걸쳐 일관되게 일해야 한다 — 이 간극을 메우는 것이 오케스트레이션이다. 그래서 오케스트레이션은 매 스텝마다 세 가지를 결정한다:

  • 다음에 뭘 할까 — 툴 선택과 계획 (§1~2)
  • 어떻게 실행할까 — 파라미터 채우기, 실행 구조 (§3 토폴로지)
  • 모델에게 뭘 보여줄까 — 이전 결과·지식·상태 중 무엇을 컨텍스트에 넣을까 (§4 컨텍스트 엔지니어링)

세 번째가 "절반의 무게"인 이유가 여기서 나온다 — 앞의 둘을 아무리 잘해도, 기억상실 상태의 모델에게 잘못된 조각을 보여주면 잘못된 결정을 한다.

§1에이전트 유형

1장 Q&A("루프에 무엇을 꽂는가")에서 한 발 더 — 루프 자체를 어떻게 조직하는가. 본질적으로는 "계획을 언제, 얼마나 하느냐"의 스펙트럼이다.

같은 작업, 네 가지 처리 방식

작업: "지난주 결제 실패가 급증한 원인을 찾아줘"

  • Reflex: "결제 실패" 키워드 감지 → 무조건 결제_로그_조회 호출 → 결과 반환. 계획 자체가 없다. 빠르지만 "왜"까지는 못 간다.
  • ReAct: "일단 실패 로그를 보자" → 조회 → "타임아웃이 많네? PG사 응답시간을 보자" → 조회 → "특정 PG사만 느리네" → 결론. 한 발짝 걷고, 본 것에 따라 다음 발을 정하는 방식 — 어디로 갈지 미리 모르는 탐색에 강하다.
  • Planner-Executor: 먼저 계획을 완성("① 실패 로그 집계 ② 시간대 분포 ③ PG사별 분리 ④ 배포 이력 대조 ⑤ 종합") → 각 단계 실행. 계획이 명시적 산출물이라 검사·디버깅이 쉽고 실행은 싼 모델에 맡길 수 있다. 대신 예상 밖 발견에는 재계획 비용.
  • Reflection: ReAct처럼 걷되 매 걸음 후 "지금까지의 결론이 목표와 맞나? 방금 결과가 내 가설과 모순되지 않나?"를 되돌아보는 스텝이 끼어든다. 비가역 작업(환불 실행 같은) 전에 잘못을 잡는 안전장치 — 대신 호출 수가 는다.

유형은 골라 쓰는 완제품이 아니라 조합하는 재료다 — Deep Research가 Planner-Executor + Query-Decomposition + ReAct의 합성인 것처럼. 이 분류는 정답표가 아니라 출발점이다 — 하이브리드·메타추론 패턴이 계속 등장하는, 빠르게 진화 중인 지형.

§2툴 선택 — 세 가지 전략

툴이 몇 개냐에 따라 선택 메커니즘이 달라진다.

§3툴 토폴로지 — 단일 → 병렬 → 체인 → 그래프

제어 흐름의 역전 — 개발자는 구조를 정의하고, 구체적 조합은 모델이 상황을 보고 구성한다.

전통 소프트웨어는 개발자가 실행 순서를 코드로 못 박았다(if → then → loop). 에이전트에서는 역할이 나뉜다 — 개발자가 정하는 것: "이 툴들이 있고, 병렬로 돌 수 있고, 체인 최대 길이는 5고, 분기는 이 라우터가 한다". 모델이 정하는 것: "이번 질문엔 툴 A와 C만, 이 순서로". 이것이 5장의 조용한 혁명이다.

"체인에 최대 길이 상한 필수"인 이유는 오류 증폭의 산수다: 각 스텝 정확도가 95%여도 10스텝 체인의 전체 성공률은 0.95¹⁰ ≈ 60%로 떨어진다. 그래프의 "노드 하나가 오류 모드를 곱절로 늘린다"는 경고도 같은 산수다. 결국 토폴로지 선택은 확률 관리다 — 1장의 "필요한 최소 계층" 원칙이 여기서 다시 반복되는 것이 우연이 아니다.

§4컨텍스트 엔지니어링 ⭐

오케스트레이션의 잊히기 쉬운 절반 — 매 호출의 입력을 조립하는 기술.

정의: 프롬프트 엔지니어링이 "지시문을 잘 쓰는 것"이라면, 컨텍스트 엔지니어링은 매 모델 호출마다 모든 입력(사용자 메시지 · 검색된 지식 · 워크플로우 상태 · 시스템 프롬프트)을 구조적이고 토큰 효율적으로 동적 조립하는 것이다. 계획과 실행을 잇는 다리 — 계획이 "무엇을 할지"를 정하면, 컨텍스트 엔지니어링이 "각 단계가 제대로 실행될 정보"를 보장한다.

① 관련성 우선

큰 텍스트 덩어리를 통짜로 붙이지 말고, 메모리·지식 베이스에서 가장 유용한 것만 검색해 넣는다.

② 구조화된 포맷

MCP 같은 스키마로 상태·지식을 예측 가능하고 해석 가능한 형태로 전달한다.

③ 요약 압축

긴 이력을 핵심을 보존한 요약으로 압축해 토큰 낭비 없이 유지한다.

④ 동적 재조립

매 추론 단계마다 현재 목표·워크플로우 단계·입력에 맞게 컨텍스트를 다시 조립한다.

파운데이션 모델이 좋아질수록 프런티어는 모델 아키텍처에서 우리가 제공하는 컨텍스트의 품질로 이동한다. 잘 설계된 컨텍스트는 평범한 모델의 잠재력을 열고, 나쁜 컨텍스트는 최고의 모델도 무너뜨린다. — p.113, Context Engineering

  2. "체인으로 시작하고, 분기+합류가 둘 다 필요할 때만 그래프로." 토폴로지에도 최소주의가 적용된다 — 요구를 만족하는 가장 단순한 계획 접근을 선택하라.
  3. 프런티어는 컨텍스트 품질로 이동 중. 잘 조립된 컨텍스트가 평범한 모델을 살리고, 나쁜 컨텍스트가 최고 모델을 죽인다.

§1Knowledge vs Memory — 서로 다른 두 재료

둘 다 "모델 가중치 밖의 정보"지만 출처가 다르다.

Knowledge = 외부 사실. 기술 스펙, 정책 문서, 제품 카탈로그, 시스템 로그 — 대화와 무관하게 존재하는 검증 가능한 콘텐츠로, 주로 RAG로 생성 시점에 주입된다. Memory = 에이전트 자신의 역사. 과거 대화, 툴 출력, 상태 갱신 — 턴과 세션을 넘는 연속성의 재료다.

메모리는 지식이 저장되는 곳이고, 컨텍스트 엔지니어링(5장)은 그 지식을 지능적 행동으로 바꾸는 방법이다. — p.115, Knowledge and Memory

§2검색의 사다리 ⭐

기억·지식 접근에도 계층이 있다 — 1장 "최소 계층" 원칙의 세 번째 등장.

§3RAG와 경험 메모리

"모델도 사람처럼 긴 자료 전체가 아니라 작고 관련 있는 부분만 필요하다."

§4GraphRAG — 점을 잇는 검색

baseline RAG가 무너지는 곳에서 시작하는 상위 계층.

RAG가 약한 세 상황: ① 여러 문서에 흩어진 정보의 연결이 필요할 때("이 사람이 한 일을 종합하면?") ② 데이터셋 전반의 주제 요약 ③ 크고 서사적인 데이터. GraphRAG는 문서에서 RDF 트리플(주어-술어-목적어: "Jay-Z, 배우자, Beyoncé")을 추출해 지식 그래프(엔티티=노드, 관계=간선)를 만들고, 질의 시 관련 서브그래프를 검색해 멀티홉(몇 다리 건너) 추론을 가능하게 한다. 파운데이션 모델이 트리플 추출을 잘하게 되면서 대규모 구축이 현실화됐다 (Microsoft graphrag CLI, Neo4j graphrag).

구축 8단계(수집→전처리→엔티티 추출→관계 추출→온톨로지 설계→적재→통합·검증→유지보수) 중 실무 함정은 엔티티 중복 해소와 유지보수다 — "프로토타입은 쉽지만 프로덕션은 큰 작업"이라고 책이 직접 경고한다. 동적 지식 그래프(실시간 갱신)는 신선도·적응력을 주지만 유지보수 복잡성·자원·보안·과의존의 대가가 있다.

롱컨텍스트 반론과 하이브리드 컨센서스

1M 토큰 모델(Gemini 2.5, GPT-4.1)로 "검색 없이 통짜 로드"하는 retrieval-free 접근이 가능해졌다. 그러나 ① 수백만 토큰 처리의 비용·레이턴시가 검색 제거의 단순함을 상쇄하고 ② 거대 컨텍스트에서 모델이 관련 조각을 정확히 찾아낸다는 보장이 없다.

커뮤니티 컨센서스: 하이브리드 — 확장 컨텍스트 윈도우와 선택적 검색 노드의 결합이 성능·비용·사실 정확도의 균형점이다. RAG는 사실 탐색·신선도·정밀 랭킹에서 여전히 우위다. — p.131, Promise and Peril of Dynamic Knowledge Graphs

§5Q. 메모리의 한계는 뭔가?

6장이 기법마다 흘려 말한 한계를 세 층위로 모으면.

① 작업 기억(컨텍스트 윈도우)의 한계 — 유한하고, 롤링 윈도우는 중요도 무관하게 나이순으로 잃는다. 크다고 해결되지 않는다: 1M 토큰 모델도 비용·레이턴시가 토큰 수에 비례하고, 거대 컨텍스트에서 관련 조각을 찾아낸다는 보장이 없다 — "중요한 건 프롬프트 끝 가까이에"라는 위치 팁의 존재 자체가 한계의 증거다.

② 장기 기억(외부 저장+검색)의 한계 — 용량은 풀리지만 검색이 병목이 된다. BM25는 패러프레이즈를 놓치고, 벡터 RAG는 청크 경계에서 맥락이 잘리며 흩어진 정보를 못 잇고, top-k가 놓친 정보는 존재하지 않는 것과 같다(모델은 못 받은 걸 모른 채 자신 있게 답한다). GraphRAG는 구축·유지보수가 무겁다.

③ 구조적 한계 — 기법으로 완전히 못 없애는 것들:

  • 저장 ≠ 회상: 그 호출의 컨텍스트에 조립되지 않은 기억은 없는 기억이다 (5장 기억상실 프레임). 메모리 품질은 저장소가 아니라 회상 파이프라인이 결정한다
  • 저장 판단의 역설: 다 저장하면 노이즈·프라이버시 위험, 골라 저장하면 "나중에 중요할지"를 지금 알아야 한다 — 그래서 "망각"도 설계 대상이다
  • 신선도·모순: 기억은 낡는다. 갱신 메커니즘이 없으면 낡은 기억으로 자신 있게 틀린다
  • 검증 부재: 잘못 저장된 기억도 모델은 신뢰한다 — 출처(provenance) 추적이 필요한 이유

이 한계들은 인간 기억과 평행하다 — 작업 기억 용량, 회상 실패, 선택적 저장, 기억 왜곡. 실무 대응의 정석은 아무거나 저장하지 않고 판단 단계(회고·큐레이션)를 거쳐 일반화된 단위만 승격시키는 것이다.

Q. 에이전트의 지침 파일(CLAUDE.md류)과 메모리 파일은 Knowledge인가?

분류 기준은 파일 형식이 아니라 출처다: 코딩 에이전트의 세계에서 지침 파일(CLAUDE.md·AGENTS.md류)은 Knowledge도 Memory도 아닌 시스템 지시(정책) 계층 — 5장 컨텍스트 구성 요소 중 "역할을 정의하는 시스템 프롬프트"다. 메모리 파일(세션 간 유지되는 사용자 선호·피드백·진행 상태)은 정확히 경험 메모리의 파일 기반 구현이고, 참조 문서·코드베이스가 Knowledge다.

흥미로운 것은 경계가 흐려지는 지점이다: 지침 파일 속 변경 이력은 기록(Memory)이고, 규율 대부분은 경험에서 증류된 것이다. 성숙한 에이전트 시스템에는 승격 파이프라인이 있다 — 경험(Memory) → 회고·큐레이션 → 일반화된 교훈 → 정책(지침 파일). 이것이 "저장 판단의 역설"(위 ③)에 대한 실전 답이기도 하다: 아무거나 저장하지 않고 판단을 거쳐 승격시킨다.

§6노트테이킹 (Self-Notes)

책 여백에 메모하며 읽는 것을 모델에게 시키는 기법.

모델이 답하기 전에 컨텍스트 곳곳에 노트를 끼워 넣게 한다: 표준 방식(컨텍스트+질문→답), CoT(추론 후 답)와 달리, self-note는 컨텍스트의 부분마다 노트를 생성하고 질문에 대한 노트까지 만든 뒤에 최종 답을 낸다. 여러 추론·평가 태스크에서 좋은 결과 — 긴 컨텍스트에서 중간 정리가 최종 품질을 끌어올리는 사례다.

  3. 롱컨텍스트 시대에도 하이브리드가 이긴다. 통짜 로드는 "모델이 관련 조각을 찾아줄 것"이라는 보장 없는 베팅이다.

§1학습의 두 갈래

학습은 필수가 아니다 — 설계·평가·모니터링 투자가 따라오므로 ROI를 따져야 한다.

여기서 학습이란 환경과의 상호작용을 통한 성능 개선이다. 갈래는 둘: 비파라메트릭 학습은 모델 가중치를 건드리지 않고 개선하는 기법(예시 재사용·자기 비평·인사이트 증류)이고, 파라메트릭 학습은 가중치를 직접 조정(파인튜닝)한다. 순서는 명확하다 — 비파라메트릭 먼저: 더 단순하고, 빠르고, 재학습 비용이 0이다.

① 예시 학습 (Exemplar Learning)

③ 경험 학습 (ExpeL) — 인사이트의 증류

§4ADAS — 에이전트 설계의 자동화

손으로 설계하는 시대의 끝을 예고하는 연구 프런티어.

ADAS(Automated Design of Agentic Systems, Hu·Lu·Clune 2024)의 발상: 에이전트의 각 부품을 사람이 조립하는 대신, 메타 에이전트가 코드로 새 에이전트를 발명·평가·개선하게 한다 (Meta Agent Search).

튜링 완전(Turing complete) = 계산 가능한 것은 뭐든 표현할 수 있다는 뜻 — 조건 분기·무한 반복·기억, 세 재료가 있으면 대체로 해당한다 (Python 등 범용 언어 전부. 반례: JSON·순수 HTML은 데이터 표현만 가능). ADAS에서 이 말이 중요한 이유는 대비다: 설계를 설정 파일·템플릿 메뉴로 표현하면 선택지가 유한하지만, 코드로 표현하면 설계 공간에 상한이 없다 — 사람이 이름 붙인 적 없는 워크플로우·툴 조합·결정 구조까지 발명할 수 있다. 단, 튜링 완전은 표현 가능성의 이야기지 좋은 설계를 잘 찾는다는 보장이 아니다 — 그래서 나머지 절반이 검색 알고리즘과 평가 함수다.

사이클: 과거 성공작 아카이브를 조건으로 → 새 설계 생성 → Reflexion 2단계 정제(7장!) → 검증 데이터로 평가(에러 시 5회까지 디버깅) → 성공작을 성적표와 함께 아카이브 — 25~30세대 반복. "탐색(새 설계)과 활용(고성능 패턴)의 균형 — 진화 과정의 미러링." 결과: ARC 퍼즐에서 손설계 베이스라인(CoT·Self-Refine·LLM-Debate)을 능가했고, 도메인·모델을 바꿔도 성능이 유지됐다(ARC 에이전트가 MMLU에서도, GPT-3.5 설계가 GPT-4에서도). 남는 질문은 안전·정렬 — 자동 설계된 에이전트가 예측 밖 행동을 하지 않도록 "자율과 제약의 균형"이 필요하다.

§5통신 기법 — 멀티에이전트의 배관

단일 프로세스에선 함수 호출로 충분하지만, 분산되는 순간 통신은 명시적·비동기·장애 허용으로 진화해야 한다.

§1측정이 핵심이다

측정 없이는 "개선됐다"가 착각인지 진짜인지 알 수 없다 — 전문가 팀도 눈대중에는 속는다.

히어로 시나리오(대표 고빈도 유스케이스)를 정하고 거기서 지표를 도출한다 — 정량(정확도·응답시간·정밀도·재현율)과 정성(만족도)을 함께. 언어 에이전트는 정답이 여러 형태로 표현되므로 exact-match(글자 그대로 일치)가 자주 실패한다 — 그래서 시맨틱 유사도 계열 지표(임베딩 거리, BERTScore, BLEU, ROUGE: 표현이 달라도 의도 충족을 재는 방법들)를 병용한다. 그리고 평가를 개발 수명주기에 통합하라 — 코드 머지·모델 업데이트마다 자동 실행되게.

§2평가셋 만들기와 키우기 ⭐

정적 손수 큐레이션 스위트는 부족하다 — 과적합되고, 롱테일을 놓치고, 진화를 못 따라간다.

좋은 케이스는 입력 상태 + 대화 이력 + 기대 최종 상태(호출됐어야 할 툴과 파라미터, 응답에 포함될 문구)를 구조화한 것 — 케이스 하나가 추론·툴 선택·커뮤니케이션을 동시에 검증한다. 확장 경로는 셋: 손 추가 → 프로덕션 로그 채굴 → 모델 생성 변형(모호함 주입·희귀 관용구·엣지 변이) 후 사람 검수.

공격적 생성 기법도 있다: 적대적 프롬프팅("에이전트가 자기모순하게 만드는 입력을 찾아라") · 반사실 편집(한 단어만 바꿔 실패 여부 확인) · 분포 보간(두 의도를 섞어 의도적으로 모호한 요청 생성). 표준 벤치마크(MMLU·HELM)는 상대 위치 파악용일 뿐, 도메인 에이전트에는 커스텀 벤치마크가 필수다.

잘 구조화된 평가셋은 테스트 스위트를 넘어 살아있는 명세(living specification)가 된다 — 에이전트가 다뤄야 할 것의 명세이자, 회귀 감지와 지속 모니터링의 근거. — p.209, Creating and Scaling Evaluation Sets

§4종단 평가 — 전체가 함께 도는가

케이스 하나를 끝까지 실행해 지표 묶음을 산출한다: tool recall · precision · 파라미터 정확도 · 문구 재현 · 태스크 성공.

주의보 하나와 확장 셋: 지표 과적합(metric overfitting) — 좁은 지표 하나(BLEU·exact match)에 최적화하면 벤치마크만 잘하는 형식적 출력이 나온다. 지표를 다양화하고 정기적 인간 리뷰로 사각을 메워라. 일관성 — LLM은 확률적이므로 표현이 달라도 같은 절차(환불 전 사진 요청)를 지키는지, 멀티턴에서 이전 발언과 모순이 없는지를 LLM 기반 평가 + Actor-Critic(8장) + 인간 리뷰 조합으로 본다. 환각 — RAG 접지·데이터 품질·피드백 루프(자동 감지 + 도메인 전문가 HITL)로 완화하고, 최근엔 "환각 비용"(정확도 개선 vs 추론 비용)을 정량화한다. 예상 밖 입력 — 퍼징(무작위 기형 입력)과 과거 사고 기반 엣지케이스로, 크래시 대신 명확화·거절·에스컬레이션하는지 검증.

§5배포 준비 — 게이트 뒤에서만

프로덕션 준비 = 테스트 통과 그 이상.

배포 기준을 명시한다: 평가셋 정량 임계치(예: 환불 시나리오 tool recall ≥ 95%) + 스트레스·엣지 안정성 + 핵심 워크플로우 전수 체크리스트. 이를 강제하는 게 게이트(gating) — 최신 평가 스위트에서 회귀가 하나라도 나오면 승격 자동 차단, 모호하면 인간 리뷰로 에스컬레이션. 그리고 나간 뒤를 대비한다: 단계적 출시, 출시 후 회귀 모니터링, 신속한 롤백 경로.

§6핵심 3문장

  1. 평가셋은 살아있는 명세다. 기능이 늘 때마다 케이스도 늘어야 하고, 그 명세가 회귀 감지·배포 판단의 단일 근거가 된다.
  2. 지표는 다양하게, 과적합은 경계. tool recall/precision·파라미터 정확도·일관성·환각을 함께 보고, 정기적 인간 리뷰로 지표의 사각을 메워라.
  3. 배포는 게이트 뒤에. 회귀가 있으면 자동으로 막히고, 나가더라도 빠르게 되돌릴 수 있어야 한다.

섀도 모드

신버전을 트래픽 1~5%에만 — 버전 태그로 지표를 비교하고, 회귀가 보이면 최소 피해로 즉시 롤백.

자가치유 에이전트

에이전트가 자기 텔레메트리를 읽고 대응 — 툴 반복 실패 시 단순 폴백, 레이턴시 급등 시 선택적 추론 생략, 환각 점수 높으면 면책·인간 회부. 폴백 결정 자체도 로깅.

사용자 언어·신조어·API 응답·모델 업데이트로 환경의 통계적 성질이 변한다. 정량 감지 3종: KS 검정(두 데이터가 같은 분포에서 왔는지 — 쿼리 길이 같은 연속 특징, KS > 0.1 경보) · KL 발산(토큰 분포가 얼마나 벌어졌는지 — 개념 드리프트, > 0.5 경보) · PSI(범주 비율 변화 — 툴 사용 분포 등, 0.1~0.25 경미 / > 0.25 개입). 실용 신호로는 24시간 롤링 정확도 5~10% 하락, 포기율 > 15%, 재시도 > 세션 20%. 대응은 이원화: 일시적 변화 = 임계값·파싱 조정, 지속적 변화(PSI > 0.25가 48시간) = 재학습·API 적응 우선.

§3FM 방어 기법과 레드팀

완벽한 방어가 아니라 다층 방어 — 폭발 반경을 줄이는 게임.

모델 선택 자체가 보안 결정이다(범용 대형 = 강력하나 예측 어려움 / 소형 파인튜닝 = 감시 쉬움 / 민감 앱은 온프렘·에어갭). 방어는 층으로 쌓는다: 입력 새니타이즈(악성 프롬프트를 모델 도달 전 차단 — LLM Guard로 PII 익명화+금지 문구 밴, PINT·BIPIA 벤치마크로 측정) → 프롬프트 인젝션 방지(지시 앵커링: 주 지시를 프롬프트 전반에 강하게 반복 + 엄격한 템플릿) → 출력 필터링 → 접근 제어·레이트 리밋·전수 로깅 → 샌드박싱(폭발 반경 축소). 레드팀은 기능 검증이 아니라 오용·적대 견고성을 탐침하는 반복 사이클(구현→공격→평가→완화)이다 — DeepTeam·NVIDIA Garak(FM판 Nmap)·Microsoft PyRIT.

§4MAESTRO — 에이전트 AI 위협 모델링 ⭐

STRIDE·PASTA는 자율·동적 학습·다중 상호작용을 못 담는다 — CSA의 에이전트 전용 7계층 프레임워크.

§5데이터·에이전트 보호

최소 권한이 관통 원칙 — 4장의 재확인.

데이터 보호

저장 AES-256+RBAC / 전송 TLS·mTLS / 데이터 최소화(필요 최소만 처리) / 출처·무결성(SHA-256·서명·불변 로그) / 로그에 평문 민감정보 금지.

에이전트 세이프가드

RBAC로 좁은 권한 · 행동 제약(정책 강제 계층) · 샌드박스·컨테이너로 폭발 반경 제한 · 입출력 검증 · 이상 감지 · 불변 감사 로그 · 폴백/페일세이프.

외부 위협

DMZ 네트워크 격리 · mTLS·OAuth · 공급망(SCA·SBOM·서명 검증) · 허니토큰 · 엔드포인트 하드닝.

내부 실패

목표 오정렬·경쟁 조건·캐스케이드 → 상태 일관성(멱등·트랜잭션)·의존성 격리 + 카오스 엔지니어링(장애 주입·폭발 반경 통제)으로 선제 발견.

§6핵심 3문장

  1. 에이전트 보안은 전통 보안 + 고유 위협. 프롬프트 인젝션·탈옥·스웜 악용은 확률적 시스템 특유의 표면이고, 완벽 방어가 아니라 다층 방어로 폭발 반경을 줄이는 게임이다.
  2. 최소 권한이 관통 원칙. 등록 계층에서 좁게(4장 재확인), RBAC·샌드박스·데이터 최소화로 공격 표면 자체를 줄여라.
  3. MAESTRO로 계층별 위협 모델링. STRIDE로는 에이전트를 못 담는다 — 7계층 각각에 위협·완화를 매핑하고 레드팀으로 지속 검증하라.

역할의 진화 ⭐ 채택 = 변화 관리 규모별 설계 신뢰·거버넌스 책 전체 결론 핵심 3문장

§1인간 역할의 진화 ⭐

에이전트 자율성이 커질수록 인간은 실행에서 정책·감독으로 올라간다 — 능력이 아니라 책임의 층위가.

§2채택은 변화 관리다

가장 유능한 에이전트도 사람이 받아들이지 않으면 실패한다.

실패 패턴은 에이전트를 기술 업그레이드로만 소개하는 것 — 신기함·방해물로 인식되어 저조한 채택과 능동적 우회를 부른다. 성공 조건은 이해관계자를 테스터가 아니라 공동 창작자로 조기 참여시키고, 성공 지표가 기술 성능을 넘어서게 하는 것("빨리 하되 신뢰를 깎으면 채택 안 됨"). 대조 사례가 선명하다: ZoomInfo의 GitHub Copilot은 50명 파일럿 → 지표(수락률 33%·만족 72%)와 정성 피드백 확인 후 400+명으로 — 확장마다 신뢰 신호에 묶어 성공했다.

§3규모별 협업 설계

개인 → 팀 → 프로젝트 → 부서 → 전사 — 범위가 커지면 자율성·위험·거버넌스가 함께 오른다.

범위자율성위험거버넌스
Personal낮음~중간낮음사용자 관리 선호, 감독 최소
Team중간중간공유 메모리 경계, 동료 에스컬레이션
Project중간~높음중간~높음교차기능 가시성, 로깅, 충돌 해결
Functional높음(도메인 한정)높음RBAC, 감사 로그, 컴플라이언스
Organizational높음~제한매우 높음다층 승인, 거버넌스 위원회, 윤리 감사

규모의 핵심 리스크는 공유 메모리·컨텍스트 경계다 — 팀 에이전트가 1:1 비공개 대화를 회상하거나 부서 에이전트가 사업부 간 기밀을 노출하면 신뢰가 붕괴한다. 6장 메모리 한계의 조직 버전: 범위별 메모리 스코핑(개인=격리 기본)과 "무엇을 기억하는지 보고 끌 수 있는" 투명성. 사례: Bank of America Erica — 20억+ 요청, 확신도가 임계값 넘으면 라이브 상담원으로 명확히 핸드오프.

§4신뢰의 라이프사이클과 거버넌스

신뢰는 이분법이 아니라 진화한다 — 방울로 쌓고 양동이로 잃으며, 복구 경로가 필수다.

Klarna는 2024년 고객지원 700석을 AI 챗봇으로 대체했다가, 공감·판단 상실로 불만이 폭증하자 2025년 중반 인간 상담원을 재고용했다 — 견고한 인간 폴백 없는 과잉 자동화는 신뢰를 빠르게 무너뜨린다. — p.305, The Lifecycle of Trust

핵심 패턴은 점진적 위임(초기엔 승인 대기 → 신뢰 상승에 따라 자율 확대) + 신뢰 복구 메커니즘(실수 시 리셋·재학습·권한 제한 — 복구 경로 없으면 사소한 실수가 지속 손상). 거버넌스 도구: NIST AI RMF(govern·map·measure·manage), 로깅 3종(결정·상호작용·에러), 그리고 에스컬레이션 설계 — "언제·어떻게 인간이 개입하는가"의 정책 계층으로, 결정 유형·위험·확신 경계로 임계값을 정한다($1,000 미만 자동, 초과는 다자 서명). 에스컬레이션은 실패가 아니라 책임 있는 자율의 일부이고, 해결된 케이스는 피드백으로 환류된다. 컴플라이언스(EU AI Act·GDPR·HIPAA…)는 최종 게이트가 아니라 파이프라인에 내장한다(빌드마다 PII·공정성 스캔, policy-as-code, 살아있는 모델 카드).

§6핵심 3문장

  1. 인간 역할은 실행자에서 거버너로 진화한다. 에이전트 자율성이 커질수록 인간은 실행에서 정책·감독으로 올라가고, 인터페이스도 그에 맞춰 바뀐다.
  2. 채택은 소프트웨어 배포인 만큼 변화 관리다. 이해관계자를 공동 창작자로, 확장을 신뢰 신호에 묶어라 (Klarna 실패 vs ZoomInfo 성공).
  3. 신뢰는 라이프사이클이고 에스컬레이션은 실패가 아니다. 점진적 위임 + 복구 경로 + 파이프라인에 내장된 컴플라이언스가 지속 가능한 협업을 만든다.
